# EFE Compliance Package

EFE ships a per-tenant **compliance package** at every release. The
package is a **cosign-signed ZIP** containing all evidence a tenant or
their auditor needs to validate that their EFE deployment meets
SOC 2, GDPR, AI Act, and ISO 27001 expectations.

---

## Generation

The package is generated by `scripts/release/generate-compliance-pack.sh`.

### On-demand (CLI)

```bash
efe-admin compliance pack <tenant>
# → /tmp/<tenant>-compliance-pack.zip
```

This wraps the script and pulls live attestation data from the running
EFE control plane (audit chain integrity, attestation status JSON).

### Offline / CI

```bash
./scripts/release/generate-compliance-pack.sh acme /tmp/acme-pack
# → /tmp/acme-pack-compliance-pack.zip
# → /tmp/acme-pack-compliance-pack.zip.sig
# → /tmp/acme-pack-compliance-pack.zip.cert.pem
```

The CI variant emits **stub** values for the live attestation data,
clearly marked with `_action: "fetch from production"` keys.

### Cron

A nightly cron at 02:00 UTC regenerates packages for every active
tenant and uploads to the per-tenant S3 bucket :
`s3://efe-compliance-packs-<tenant>/<YYYY-MM-DD>.zip`.

## Contents

```
acme-pack-compliance-pack.zip
├── README.md                          ← describes the package
├── SOC2_EVIDENCE.md                   ← SOC 2 Type II readiness evidence
├── GDPR_ART30_REGISTER.md             ← GDPR Art. 30 register entry (tenant-personalized)
├── AI_ACT_ART11_TECHNICAL_DOC.md      ← EU AI Act Art. 11 technical doc
├── ISO_27001_READINESS.md             ← ISO 27001:2022 readiness self-assessment
├── audit-chain-report.md              ← HMAC chain integrity report
└── compliance-status.json             ← live attestation status (AI Act Art. 14, GDPR Art. 22)
```

### File-by-file

#### `SOC2_EVIDENCE.md`

Source : `docs/compliance/SOC2_EVIDENCE_TEMPLATE.md`

Maps EFE controls to **AICPA Trust Services Criteria** :

- CC1 — Control Environment
- CC2 — Communication and Information
- CC3 — Risk Assessment
- CC5 — Control Activities
- CC6 — Logical and Physical Access
- CC7 — System Operations
- CC8 — Change Management
- CC9 — Risk Mitigation
- A1 — Availability (audit logs, DR drills)
- C1 — Confidentiality (KMS-managed encryption at rest + in transit)
- PI1 — Processing Integrity (HMAC chain on `llm_call_audit`)

The audit window is documented as **2026-Q3 → 2027-Q1** with **Coalfire**
as the target Type II auditor.

#### `GDPR_ART30_REGISTER.md`

Source : `docs/compliance/GDPR_ART30_REGISTER.md` with placeholders
substituted (`{{tenant_name}}`, `{{generated_at}}`).

Per-tenant **Record of Processing Activities** (RoPA) entry, including
data categories, retention schedules, sub-processors, transfer
mechanisms (SCCs / adequacy decisions), and the data subject rights
implementation (Articles 15–22).

#### `AI_ACT_ART11_TECHNICAL_DOC.md`

Source : `docs/compliance/AI_ACT_ART11_TECHNICAL_DOC.md`

EU AI Act Article 11 technical documentation covering :

- General description (intended purpose, system architecture)
- Detailed description (model versions, training data lineage)
- Information about monitoring (drift detection, eval pipeline)
- Validation and testing procedures
- Risk management system
- Compliance with Article 13 transparency requirements

#### `ISO_27001_READINESS.md`

Source : `docs/compliance/ISO_27001_READINESS.md`

Self-assessment against the 93 controls of **ISO 27001:2022** Annex A,
grouped under :

- A.5 Organizational controls (37 controls)
- A.6 People controls (8)
- A.7 Physical controls (14)
- A.8 Technological controls (34)

For each control : status (implemented / in-progress / not-applicable),
evidence pointer, gap notes if any.

#### `audit-chain-report.md`

Stub in offline mode ; in production it is a PDF generated by
`efe-admin audit verify <tenant> --output-pdf`. The PDF validates :

1. The HMAC chain of `llm_call_audit` is unbroken from row 1 to row N.
2. Every chain link is verifiable against the **per-tenant master
   key** (KMS-managed, rotation history attached).
3. No row has been tombstoned without an audit override entry.
4. The chain endpoint matches the latest `audit_chain_head` record.

#### `README.md`

A 1-page index of the package contents and verification instructions :

```bash
cosign verify-blob \
  --certificate <pack>.cert.pem \
  --signature <pack>.sig \
  --certificate-identity-regexp "^https://github\.com/efe-ai/efe/.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  <pack>.zip
```

## Signing

Each pack is **cosign-signed** in the GitHub Actions workflow that
invokes the cron, with the same OIDC identity as the release pipeline.
Signatures land in **Rekor** (transparency log) for permanent audit.

**Why cosign?** Compliance evidence regenerated nightly cannot rely on
manual key rotation. Cosign keyless signing means no long-lived secrets
exist for compliance-pack signing — if the pack came from an EFE
GitHub Actions runner with the right OIDC identity, it is authentic.

## Security considerations

1. **No PII in the package.** The pack contains *attestations and
   metrics* about PII processing, not the PII itself. Audit chain
   reports include row counts and HMAC roots — never row contents.
2. **Tenant isolation.** Each pack is generated within a **per-tenant
   KMS context** ; cross-tenant data leakage is structurally
   impossible.
3. **Reproducibility.** The pack is **deterministic** given a fixed
   `--at-timestamp` flag, allowing auditors to recompute the same pack
   locally for tamper-evidence verification.
4. **Storage retention.** The signed packs live in the per-tenant S3
   bucket for **7 years** (SOC 2 Type II audit window), with **WORM
   policies** to prevent overwrites or deletes.

---

## Audit access

External auditors get **read-only** S3 IAM credentials scoped to a
single tenant's bucket, plus a public Rekor URL for signature
cross-reference. No EFE staff can override an auditor's read access
without a 2-of-3 break-glass flow.
