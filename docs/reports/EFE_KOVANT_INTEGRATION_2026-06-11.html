§1  Résumé exécutif : pourquoi EFE pour Kovant

Kovant et EFE partagent la même thèse : remplacer le gros modèle généraliste par des essaims de petits agents spécialisés (SLM) sous garde-fous, traçables. Kovant a construit le produit d'entreprise (Blueprints, équipes, Mission Control, Integration Hub). EFE a construit le moteur d'exécution vérifiable de ces essaims. Les deux s'emboîtent.

Ce que Kovant veut
des swarms de SLM, des garde-fous « accuracy, auditability, compliance », une piste auditable « ce que chaque worker a fait et pourquoi », du human-in-the-loop, du model-agnostic.
Ce qu'EFE apporte
un moteur d'essaim (4 topologies parallèles + 43 nano-agents), une provenance cryptographique re-prouvable, une gouvernance de budget infalsifiable, et un mode souverain (SLM local, zéro egress).
Le gain net
l'« audit trail » de Kovant devient un audit proof : un régulateur (ou un client industriel nordique) re-vérifie chaque décision d'agent hors-ligne, sans faire confiance à Kovant ni à un fournisseur de modèle.

§4  Architecture d'intégration

EFE s'insère comme une couche d'exécution & de preuve : la plateforme Kovant reste le cerveau (Blueprints, Mission Control, Integration Hub, UX) ; EFE est le muscle vérifiable qui exécute chaque opération d'essaim et en scelle la preuve, qui remonte ensuite au System of Record.

Figure 1 — EFE s'insère sous l'Agent Runtime (exécution d'essaim) et alimente le System of Record (preuve). Kovant conserve toute sa surface produit ; EFE est invisible pour l'utilisateur métier.

Le contrat d'intégration, en une ligne

Le runtime de Kovant envoie à EFE une tâche + une topologie + un budget + un mode ; EFE renvoie une sortie + une preuve (provenance_root, records, résumé N17). Kovant range la preuve dans son System of Record et peut, à tout moment, la re-vérifier (live ou hors-ligne). Aucun couplage de code : l'échange est du JSON sur HTTP (ou un appel SDK Rust in-process).

§5  Le cœur EFE (rappel technique, ancré dans le code)

Pour situer les surfaces d'intégration, voici les cinq mécaniques d'EFE — toutes implémentées et testées.

5.1 — Nano-agents (crate efe-swarm-topology)

43 agents Mode A déterministes (struct Rust mono-fonction, sans poids), répartis en 6 rôles (générateurs, vérificateurs, stages, décomposeurs, mergers, juges). Montables par nom via AgentFleet ; un agent custom Kovant s'enregistre en une ligne. En Mode C, le « nom » devient une instruction-prompt envoyée à un SLM — la topologie ne change pas.

5.2 — Substrat de communication (crate efe-blackboard)

Deux organes : un Blackboard (DashMap clé-JSON-pointer, versioning, CAS write_if, bornes mémoire) = la vérité ; un TopicRouter (broadcast par topic) = l'indice live. Les agents écrivent /cand/*, /ballot/* en parallèle (sharding → pas de lock global) ; deux seams non-couplés (WriteSink, EventSink) exposent tout à la provenance et au dashboard.

5.3 — Quatre topologies parallèles

PatternMécaniqueUsage Kovant typique
T1 Generate-VerifyK générateurs ∥ → vérificateur déterministe a-posterioriextraire un champ vérifiable d'un PDF/email (montant, n° de commande)
T-ConsensusK gén ∥ + J juges ∥ → Borda/Condorcet + confiance + escaladeclasser/router une demande (compliance, catégorie achat) quand il n'y a pas de vérité mécanique
T2 Pipelineétages chaînés en streaming (quiescence)normaliser → extraire → valider un input non-structuré
T3 Hierarchicaldécompose → résout ∥ (récursif) → agrègetraiter un dossier multi-pièces (facture + bon de livraison + contrat)

5.4 — Provenance vérifiable (crate efe-swarm-provenance)

Chaque pas → un AgentCallRecord (hash entrée/sortie blake3, rôle, parents DAG, lien N17). Les records forment une chaîne HMAC signée par une clé tenant (dérivée HKDF, jamais transmise). verify_swarm recalcule chaîne + contenu + DAG + root hors-ligne ; toute altération casse la preuve et est localisée.

5.5 — Les trois modes (model-agnostic)

Keyless (nano-agents déterministes, démo/ancre) ; Self-host (SLM local, souverain, 0 clé — le mode phare pour Kovant EU) ; Network (modèle frontière via routeur server-side qui détient les clés — pour les cas où un grand modèle est requis).

Si un composant Kovant est en Rust, il appelle directement le SDK (zéro HTTP) :

let outcome = swarm.run_traced(task, TopologySpec::Consensus {…}, Budget::cents(500)).await?;
// outcome.run.provenance.root  → System of Record ; outcome.records() → export/verify

Un « foundation agent » de Kovant peut être ajouté à la flotte EFE en implémentant un des 6 traits (ex. un Judge métier « conforme-au-contrat ») et en l'enregistrant : fleet.register_judge("contract_compliant", Arc::new(MyJudge)). §8  Le System of Record, rendu vérifiable

C'est l'apport le plus différenciant pour Kovant. Leur System of Record capture « ce que chaque digital worker a fait et pourquoi » sous forme de journal (auditable trail). EFE le fait passer d'un journal qu'il faut croire à une preuve qu'on peut re-vérifier — un « audit proof ».

Journal (avant)

« Voici nos logs : l'agent X a décidé Y. » → il faut faire confiance à l'intégrité des logs. Un log peut être édité après coup ; rien ne le prouve.

Preuve (avec EFE)

« Voici les records + un root. Recalcule-les avec la clé tenant : si un seul octet a bougé, ça casse, et on te dit où. » → aucune confiance requise, re-vérifiable par un tiers, hors-ligne, des mois plus tard.

Ce que Kovant stocke, et comment il re-prouve

  1. À chaque opération, Kovant range dans son System of Record : le run_id, le provenance_root (64 hex), et l'export records (JSON). C'est petit et durable.
  2. Pour un audit live : GET /v1/swarm/verify/:id → {verified, chain_intact, content_intact, dag_consistent, root}.
  3. Pour un audit hors-ligne / par un tiers : on fournit l'export records + la clé tenant ; verify_swarm tourne sur une machine déconnectée (aucun appel à Kovant ni à un provider). C'est le scénario « le régulateur ne nous croit pas » — et c'est exactement la promesse.

Le « why » à la granularité de l'appel (pont N17)

Kovant veut « what every digital worker did and why ». Le pont N17 d'EFE attache à chaque appel de SLM un LlmProvenanceRecord forensique : quel modèle, quel seed, quels paramètres, le hash du prompt et de la réponse, la latence, le nombre de re-tentatives. L'AgentCallRecord d'essaim le référence (llm_provenance_id). On peut donc, pour une décision contestée, remonter jusqu'à « le digital worker compliance-checker a appelé qwen3:30b avec ce prompt précis et a reçu cette réponse précise » — vérifiable.

Argument commercial pour Kovant : dans l'industrie/manufacturing nordique (le segment client de Kovant), les audits (ISO, fournisseurs, régulateurs sectoriels) exigent de la traçabilité démontrable. « Audit proof » au lieu d'« audit trail » est un argument de vente différenciant, et c'est du code déjà testé (Lot P5 : tamper_detected = 100 % sur 3 modèles).

§9  Souveraineté & résidence des données

Kovant est basé en Suède, vise des clients industriels EU, et traite des inputs sensibles (factures, contrats, emails). La résidence des données et le RGPD sont structurants. EFE offre nativement le mode qui répond à ça.

Le mode self-host : données qui ne quittent pas l'hôte

En Mode C self-host, le SLM tourne sur 127.0.0.1 (sidecar Ollama/vLLM dans le même pod). La tâche, les pièces (PDF/email) et les sorties restent sur l'hôte ; aucune donnée ne part vers un provider. C'est air-gappable : une NetworkPolicy egress=deny rend le pod incapable de sortir sur Internet (défense en profondeur, en plus du garde-fou applicatif). Seule la preuve (records + root) circule, et elle ne contient que des hashs.

Trois postures, au choix du client Kovant

PostureMode EFEPour quel client Kovant
Souverain on-prem / EUSelf-host (SLM local)industriel régulé, données sensibles, RGPD strict, air-gap
Cloud EU (Azure/AWS)Self-host en pod (Helm)tenant cloud du client, SLM dans sa VPC/région EU
Frontière (au besoin)Network (routeur server-side)tâches exigeant un grand modèle ; clés au routeur, jamais chez Kovant

Déploiement (Helm, compatible Azure/AWS — la stack de Kovant)

EFE fournit un chart Helm prêt : pod = passerelle + sidecar SLM, Secret HKDF (clé de signature de provenance, server-side), provision-job (modèles pré-téléchargés → air-gap), NetworkPolicy egress=deny, ServiceMonitor (Prometheus). Le binaire prod sélectionne EnvHkdf (signature réelle) dès que le master est présent. Kovant déploie EFE dans le même tenant cloud que son Agent Runtime, sans rip-and-replace.

Note model-agnostic : le mode Network réutilise un routeur OpenAI-compat (LiteLLM, ou un routeur maison). Kovant peut y brancher Azure OpenAI / Bedrock — cohérent avec leur stack — tout en gardant les clés hors de la couche d'essaim.

§10  PII, conformité & gouvernance

PII : caviardage local pour les inputs non-structurés

Les opérations de Kovant sont « filled with unstructured inputs like emails and PDFs » — qui contiennent souvent des données personnelles. EFE (feature pii) caviarde localement (regex : email/SSN/carte/IBAN/IP/téléphone) — aucun service réseau, compatible air-gap. Crucial : on caviarde la présentation (sortie renvoyée, previews, copie au repos), pas les records → la preuve re-vérifie l'original. Opt-in par tenant : un client RGPD-strict active Redact, un autre reste à Off, sans recompiler.

Gouvernance de budget = un garde-fou de plus

L'invariant I13 garantit qu'une opération ne dépasse jamais son plafond de coût (atomique, prouvé sous concurrence). Trois politiques mappent les besoins Kovant :

  • Error : refuse si l'estimation dépasse → garantie stricte (pas un centime de trop).
  • Degrade : réduit la taille de l'essaim (K, juges) pour tenir → opération complète, plus petite.
  • Stop : exécute et s'arrête proprement à l'épuisement → résultat partiel signalé.

Human-in-the-loop : des points d'arrêt nets

Kovant insiste sur le human-in-the-loop & les escalations. EFE fournit des signaux machine exploitables par Mission Control pour déclencher l'humain :

Signal EFEDéclenche
provenance.verified == falseblocage : la preuve ne tient pas → revue obligatoire
confiance consensus < seuil (escalade)désaccord des juges → escalade vers un humain
budget_stopped == truerésultat partiel → validation humaine
juge métier (custom) = fauxnon-conformité détectée → blocage + revue
n17.all_consistent == falseanomalie forensique → investigation

Ces signaux sont déjà dans la réponse SwarmRun — Kovant n'a qu'à les router vers ses règles d'escalade existantes.

§11  Sécurité & gestion des clés

EFE distingue rigoureusement deux « clés », ce qui simplifie la posture sécurité de Kovant.

« Clé »RôleOù elle vit
Clés provider (Azure OpenAI, Anthropic…)dépensent de l'argent chez un tiersUNIQUEMENT dans le routeur Network (server-side). Jamais dans la couche d'essaim ni dans Kovant. En self-host : aucune clé du tout.
Master HKDF (EFE_NANO_AUDIT_HMAC_MASTER)signe la provenance (ne dépense rien)lu server-side via l'environnement ; dérive une clé par tenant ; n'apparaît dans aucun record
OIDC (feature)authentifie les appelants (RBAC)clé publique server-side uniquement (jamais une clé privée)
  • Isolation par tenant. La clé de provenance est dérivée par tenant (HKDF + UUID) : les chaînes de deux clients Kovant sont incomparables. Un client re-prouve avec sa clé.
  • RBAC. Les routes exigent un rôle (operator/admin) ; en prod, JWT OIDC validé contre l'IdP de Kovant (clé publique).
  • Vérifié à la compilation. Un test CI asserte que la couche SDK n'embarque ni reqwest ni TLS et n'émet aucun en-tête d'auth — la souveraineté n'est pas qu'une promesse.
  • Persistance write-once. Le PgRunStore (feature postgres) stocke les records de façon durable et write-once (la preuve ne se ré-écrit pas).
Pour la due-diligence sécurité de Kovant : EFE peut tourner sans aucune clé (Keyless/Self-host). Le seul secret introduit en prod est le master HKDF de signature (pas d'accès, pas de dépense) — un Secret Kubernetes monté server-side, jamais transmis. C'est un profil de risque minimal.

Effort & risques

Pourquoi le risque est faible

  • découplage par HTTP/JSON (pas de réécriture Kovant)
  • EFE est déjà testé (~700 tests, runs réels 3 modèles)
  • self-host = zéro clé, zéro egress → due-diligence simple
  • adoption réversible (EFE est en aval, encapsulé)

Points d'attention (honnêtes)

  • la preuve porte sur l'intégrité/lignée, pas sur le rejeu d'un LLM (à communiquer clairement)
  • le mode Network exige un routeur déployé (LiteLLM/Azure OpenAI) — intégration ops
  • les agents custom métier sont à écrire (Rust) — ou pilotés en Mode C par instruction
  • mapping Blueprint→topologie à formaliser (un adaptateur côté Kovant)
Prochain pas concret : un atelier d'une journée pour choisir un Blueprint pilote (ex. triage de facture), le mapper en topologie EFE, et lancer P0 en self-host sur un SLM déjà utilisé par Kovant. Livrable : une opération réelle, re-prouvée devant l'équipe.
