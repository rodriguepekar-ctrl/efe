Architecture · sous gate (ADR-003 · ADR-005)

Les topologies itératives — Gossip & Debate

Des agents qui se lisent et s'adaptent — l'architecture complète, prête pour le jour du GO.
Les quatre topologies livrées d'EFE sont one-shot : générer, juger, agréger — personne ne révise sa copie à la lumière de celle du voisin. Ce document est l'architecture complète de la cinquième famille : l'influence mutuelle — le Gossip (raffinement stigmergique par tours) et le Debate (argumentation contradictoire devant jury). Son statut est singulier et assumé : ces topologies sont gatées à 0 LOC par deux ADR aux priors défavorables et chiffrés. L'architecture respecte cette discipline à la lettre — elle ne précède pas les gates, elle les prépare : chaque mécanisme est conçu jusqu'au pseudo-code sur les primitives existantes (vérifiées une à une), les harnais de gate sont spécifiés jusqu'aux critères, et le coût du build post-GO est borné. Le jour où S2-bis ou S3-bis rend un GO robuste, il ne restera qu'à écrire — tout le reste est ici.

§1 Le problème — « se lire et s'adapter »

Commençons par définir exactement ce que les topologies livrées ne font pas, pour cerner ce que l'itératif ajouterait — et pourquoi le projet a décidé, données à l'appui, de ne pas le construire avant preuve.

1.1 — Ce que one-shot veut dire, et sa limite théorique

Dans les quatre topologies livrées, l'information circule en avant seulement. T1 : K générateurs produisent indépendamment, un vérificateur tranche. Consensus : K candidats, J juges notent, l'agrégation conclut. T2/T3 : des étapes se passent le travail, sans retour. À aucun moment un agent ne voit la production d'un pair et n'en tient compte pour réviser la sienne. C'est un choix qui a une vertu mesurée (l'indépendance des erreurs est précisément ce qui fait fonctionner la sélection a-posteriori — le pari S1) et une limite théorique : certaines tâches semblent appeler la révision mutuelle. Deux archétypes : l'estimation continue bruitée (K estimateurs d'une grandeur — un score, un montant, un délai — dont la moyenne itérée pourrait converger mieux qu'une sélection sèche) ; et le jugement contradictoire (une décision subjective où des arguments POUR et CONTRE, confrontés, donneraient au jury une matière plus riche qu'une lecture isolée des candidats).

L'influence mutuelle a un nom dans chaque cas. Gossip : N agents partagent des estimations partielles par stigmergie — coordination indirecte par traces dans l'environnement partagé, le Blackboard — et convergent par tours, chacun lisant les pairs du tour précédent. Debate : des agents PRO et CONTRA argumentent sur r tours, chacun lisant les arguments adverses, puis un jury note les candidats à la lumière du dossier. Les deux sont des formes d'itération — et c'est exactement là que la prudence du projet s'enclenche.

1.2 — Les priors : pourquoi 0 LOC, chiffré

Le réflexe de l'industrie serait de construire — le débat multi-agents est photogénique. EFE a fait l'inverse, pour deux raisons mesurées, consignées dans les ADR. Première donnée (Lot 1, historique) : le consensus itératif sur ancres a été mesuré équivalent au one-shot — Δ = −0,4 % ± 3,1 % ; l'itération n'apportait rien, et l'ADR-P6-001 a déjà documenté le coût d'avoir construit avant de prouver (« binder efe-core pour un gain nul »). Seconde donnée (Lot S3) : le consensus one-shot crack déjà le non-vérifiable — Borda à 0,716 avec des juges moyens (v = 0,70), 0,871 à v = 0,85, contre un oracle à 0,896. La conclusion de l'ADR-005 est arithmétique : le levier est la qualité des juges (v), pas le nombre de tours — ajouter des rounds, c'est payer r× pour un gain probablement marginal. D'où les deux décisions jumelles : Gossip et Debate sont spécifiés mais non construits — 0 LOC, build conditionné à un gate dédié (S2-bis, S3-bis), et le prior est explicitement NO dans les deux cas.

Le rôle exact de ce document, dans cette discipline. Une architecture sous gate sert trois objectifs que la spec gelée d'un ADR ne couvre pas. Un : vérifier — primitive par primitive, avec les signatures du code d'aujourd'hui — que la promesse « aucune primitive nouvelle requise » tient réellement (§2). Deux : réduire le coût du jour-du-GO à sa plus simple expression, en concevant la pièce commune (le moteur de rounds, §3) et les deux topologies (§4, §5) jusqu'au pseudo-code, provenance et budget compris. Trois : rendre les gates exécutables demain matin — bras, critères, artefacts (§6) — car le vrai chemin critique n'est pas le build : c'est la preuve. Rien ici n'autorise à écrire une ligne de Gossip ou de Debate avant un GO ; tout ici fait que le GO, s'il vient, coûte des jours et non des semaines.

§3 Le moteur de rounds — la seule pièce neuve

Gossip et Debate partagent une mécanique identique : exécuter des vagues d'agents séparées par des barrières, sur un namespace par tour, jusqu'à convergence ou plafond. L'architecture en fait donc une pièce unique et interne — le RoundDriver — sur laquelle les deux topologies sont des couches minces. C'est le choix structurant du design : un seul composant à tester durement, deux usages.

3.1 — Le contrat

// efe-swarm-topology/src/iterative/round_driver.rs  (NOUVEAU — post-GO uniquement)
pub(crate) struct RoundDriver {
    ns: &'static str,          // "/gossip" | "/debate"  (namespace transient, purgé par new_epoch)
    topic: &'static str,       // "gossip"  | "debate"   (un topic par round : "{topic}.r{r}")
    max_rounds: usize,         // r_max — borne dure (I-IT2)
    max_concurrency: usize,    // fan-out borné par round (Semaphore, motif T1)
}

impl RoundDriver {
    /// Exécute des rounds jusqu'à `stop` vrai ou r == max_rounds.
    /// `wave(r, snapshot_du_round_précédent)` lance les agents du tour r (fan-out borné),
    ///   chacun écrivant SA cellule write-once sous `{ns}/{r}/…` ;
    /// la quiescence de round (compteur de crédits) ferme le tour ;
    /// `stop(r, snapshot_du_round_r)` décide l'arrêt (ε, accord, ou politique).
    pub async fn run<W, S>(&self, ctx: &SwarmContext, wave: W, stop: S) -> RoundsReport { … }
}

Trois décisions de conception, et leurs raisons. Barrière par quiescence, pas par compteur naïf : un tour est clos quand la quiescence de round l'établit (sources du tour épuisées et inflight = 0) — le schéma de crédits de WS2, instancié par tour. C'est plus robuste qu'« attendre K écritures » : un agent peut légitimement s'abstenir (sentinel budgétaire), et la quiescence le comptabilise correctement là où un compteur d'écritures bloquerait. Décision d'arrêt sur snapshot : le prédicat stop reçoit la vérité du tour (le snapshot du namespace {ns}/{r}/), jamais les notifications — c'est le keystone (P3 §1) appliqué à la convergence : perdre toutes les notifs d'un tour ne peut ni bloquer ni fausser l'arrêt, au pire le retarder d'un réveil. Le driver ignore la sémantique : il ne sait pas si la vague est un raffinement ou un argument, ni si stop mesure une variance ou un accord — Gossip et Debate injectent ces deux fermetures. Le driver ne connaît que : namespace, tours, barrières, bornes.

I-IT3 mérite un mot de plus, car c'est lui qui rend l'itératif prouvable. En figeant la lecture au snapshot pré-vague, chaque tour devient une fonction pure de l'état précédent — pas de course où un agent rapide du tour r lirait la moitié des écritures du tour r en cours. C'est ce qui permettra à la provenance (§4.5) d'enregistrer des reads à versions exactes, au DAG de les vérifier, et au rejeu déterministe (Mode A) de reproduire la convergence au bit près — l'itératif hérite de l'ancre ADR-007 sans aménagement.

3.3 — Ce que le moteur ne fait pas

Pas de tolérance aux retardataires entre tours (un agent qui n'a pas écrit avant la quiescence du tour a son mot perdu pour ce tour — c'est un choix de simplicité, documenté, cohérent avec le write-once) ; pas de topologie de voisinage (le gossip lit tous les pairs — un voisinage partiel type k-régulier serait une variante post-gate, inutile à K ≤ 20) ; pas de streaming inter-tours (les barrières sont assumées : la forme « par tours » de la spec ADR est plus simple, plus mesurable, et la Partie 14 montre que le coût de coordination est négligeable devant un appel SLM). Chaque renoncement réduit la surface à tester — et reste réversible si un gate ultérieur exige la variante.

§4 T4 Gossip — architecture détaillée

Le Gossip instancie le moteur de rounds avec une sémantique de raffinement : chaque agent porte une estimation, lit celles de ses pairs, et produit une estimation affinée — jusqu'à ce que la nuée s'accorde. Voici le cycle exact, la convergence, et la propriété qui rend ce design supérieur aux implémentations habituelles du genre : son graphe d'influence est cryptographiquement vérifiable.

4.1 — Le rôle Refiner et la surface de spec

// L'API pressentie par l'ADR-003, précisée :
#[async_trait] pub trait Refiner: Send + Sync + 'static {
    /// `own` = sa propre cellule du tour r−1 (None au tour 0 → c'est la génération initiale) ;
    /// `peers` = les cellules des AUTRES agents au tour r−1 (snapshot figé, I-IT3).
    async fn refine(&self, task: &Value, own: Option<&Value>, peers: &[Value]) -> Value;
}
// Spec produit :
TopologySpec::Gossip { refiner: String,   // nom → flotte (Mode A) ou instruction SLM (Mode C)
                       k: usize, max_rounds: usize, epsilon: f64,
                       metric: ConvergenceMetric /* Variance | Agreement */ }

Deux choix s'expliquent. Un trait dédié plutôt qu'un réemploi forcé de Stage : la signature porte la sémantique (« voici ton état, voici les pairs ») — et c'est elle qui, en Mode C, se sérialise naturellement en prompt (« votre estimation précédente : … ; les estimations des autres : … ; produisez une estimation révisée »). Le tour 0 est le cas own = None, peers = [] : le Refiner est aussi le générateur initial — un seul nom d'agent pour toute la topologie, fidèle au principe « le nom est la job description ». La métrique dans la spec, pas dans le code : Variance pour l'estimation numérique (la famille cible de l'ADR), Agreement — la fonction existante du sélecteur de consensus — pour le catégoriel/textuel. L'appelant déclare la nature de sa tâche ; le driver reste agnostique.

4.2 — Le cycle d'un tour, pas à pas

Figure 1 — Le tour de gossip : snapshot figé → vague bornée → écritures write-once + notifs → barrière de quiescence → arrêt sur vérité. Chaque flèche réutilise une mécanique des Parties 3–5.

Le déroulé appelle deux précisions. La sortie finale n'est pas « la dernière cellule d'un agent élu » mais un agrégat du dernier tour — moyenne pour le numérique, valeur majoritaire ou meilleur score pour le reste — calculé par le driver sur le snapshot final : la convergence rend cet agrégat trivial (c'est toute l'idée), et l'écart résiduel à ε est rendu dans le résultat comme signal de confiance, homogène à la confidence des agrégateurs existants. Le coût est exactement K × (tours effectués) appels de Refiner — borné a priori par K×(r_max) (le tour 0 compris dans r_max), facturé appel par appel par le Meter inchangé, dégradé par r_max d'abord (perdre un tour de raffinement coûte moins, en espérance, que perdre des voix — c'est l'enseignement S1 : la présence croît avec K).

4.3 — Le cadeau : le graphe d'influence est prouvable

Voici la propriété qui distingue ce design de tout framework de gossip ordinaire, et elle tombe gratuitement des Parties 7–8. Chaque appel de Refiner, enveloppé par le Meter, produit son AgentCallRecord — et ce record déclare dans son corps scellé : ses reads = les cellules des pairs effectivement lues, à version exacte (/gossip/r−1/b@v) ; ses causal_parents = les records de ces écritures-là, plus sa propre cellule du tour précédent ; son llm_provenance_id en Mode C. Conséquence : le « qui a influencé qui, à quel tour » — la question centrale de toute dynamique d'opinion — n'est pas un log d'application : c'est un DAG scellé dans la chaîne HMAC, que verify_swarm contrôle déjà (parents existants, pas de lecture fantôme — P7–8 §4.2). Un auditeur peut re-prouver, hors ligne, que l'estimation finale descend bien des estimations initiales par les lectures déclarées — et le rejeu Mode A peut reproduire la convergence entière au hash près. Aucun des frameworks multi-agents photogéniques n'offre cela ; chez EFE, c'est un sous-produit de l'architecture existante.

§5 Debate — architecture détaillée

Le Debate n'est pas une cinquième topologie — et c'est la décision d'architecture la plus importante de cette section. L'API pressentie de l'ADR-005 le dit déjà en creux (impl Aggregator for DebateConsensus) ; on l'assume ici complètement : le Debate est un enrichisseur de ballots à l'intérieur du consensus existant. Cette inversion de perspective change tout — le gate, le coût, et l'intégration.

5.1 — Le recadrage : un amplificateur de v, pas un pattern nouveau

Le Lot S3 a établi le levier du non-vérifiable : la compétence des juges, v. À v = 0,70 le Borda fait 0,716 ; à v = 0,85, il frôle l'oracle (0,871). La question honnête du Debate n'est donc pas « le débat est-il impressionnant ? » mais : donner aux juges un dossier contradictoire élève-t-il leur v effectif — assez pour battre le meilleur autre usage du même budget ? Architecturalement, cela place le Debate en amont du jury, dans le pipeline de consensus inchangé : générateurs → candidats → [débat : construction du dossier] → juges (qui lisent candidats + dossier) → ballots → Borda/Condorcet, tels quels. Rien ne change en aval : mêmes Ballot, même AggOutcome, mêmes tiebreaks — le débat fabrique de la matière à juger, il ne juge pas.

5.2 — Le thread : structure, rôles, cycle

// Namespace (transient, purgé par new_epoch) — la forme gelée de l'ADR-005 :
/debate/<r>/pro/<i>      l'argument POUR le candidat i au tour r
/debate/<r>/contra/<i>   l'argument CONTRE le candidat i au tour r
// Spec produit (le débat est une OPTION du consensus, pas une topologie) :
TopologySpec::Consensus { …, debate: Option<DebateCfg { rounds: usize }> }   // feature "debate"

Le cycle réutilise le RoundDriver à l'identique, avec une vague de 2×K agents par tour (un PRO et un CONTRA par candidat — des Generator Mode C dont le nom-instruction reçoit le candidat, la tâche, et les arguments adverses du tour précédent, lus du snapshot figé). Au tour 1, PRO_i plaide sur pièces (le candidat seul) ; au tour r, il répond au CONTRA_i du tour r−1 — c'est la contradiction qui, hypothèse du gate, fait émerger les faiblesses qu'une lecture isolée manque. Après le dernier tour, les juges existants (les mêmes — c'est essentiel pour le gate) reçoivent chaque candidat accompagné de son dossier (le thread complet, sérialisé du snapshot) et produisent leurs ballots comme aujourd'hui. L'arrêt anticipé a ici une métrique naturelle : la stabilité des arguments (accord entre le tour r et r−1 — agreement réutilisée sur les paires de tours) — un débat qui se répète a fini de dire ce qu'il savait.

5.3 — L'intégration : le troisième étage de l'escalade

Le consensus possède déjà une politique coût-consciente à deux étages (P4 §4.3) : Vote gratuit → Borda/Condorcet si la confiance est sous le seuil. Le Debate s'y insère comme troisième étage, et cette place résout d'avance son problème économique :

étagemécanismecoût marginaldéclencheur
1Vote (mode des valeurs)0toujours tenté
2Borda/Condorcet (J juges)J×K appelsconfiance(vote) < s₁

Le débat ne se paie donc que sur les instances où l'essaim, déjà escaladé, hésite encore — la fraction la plus dure du flux, là où son espérance de gain est maximale et son coût amorti par la rareté. C'est l'application directe du principe « payer selon l'hésitation » (P4), et c'est aussi ce qui rend la feature déployable sans risque budgétaire : I13 et la pré-estimation (qui compte le pire cas K×(1 + J + 2r + J)) restent souverains.

5.4 — Le transcript prouvable — l'argument produit

Comme pour le Gossip, la provenance transforme un gadget en pièce d'audit. Chaque argument est un record scellé : le PRO_i du tour r déclare en reads le candidat i et le CONTRA_i@r−1, en causal_parents les records correspondants ; chaque ballot de juge déclare ses lectures du dossier ; le tout entre dans la chaîne HMAC du run. Le « pourquoi cette décision » devient un transcript contradictoire re-prouvable hors ligne : qui a objecté quoi, à quel tour, ce que le jury a lu avant de noter — sans qu'une ligne du dossier puisse être éditée après coup sans casser la racine. Pour un produit dont les clients sont des fonctions conformité (la lecture Kovant en sait quelque chose), c'est la version du débat multi-agents qui a une valeur probatoire — pas une démo, un dossier d'instruction.

§6 Les harnais de gate — S2-bis & S3-bis, exécutables

Les gates sont le chemin critique — pas le build. Voici leur design exécutable, dans le moule des harnais existants (lot_s2.py, lot_s3, bootstrap ±σ, artefact JSON daté), avec le raffinement d'honnêteté que les ADR appellent : l'itératif ne doit pas seulement battre son baseline — il doit battre le meilleur autre usage du même budget.

Même logique : le témoin ④ encode la phrase-clé de l'ADR-005 (« le levier est v, pas les rounds ») en bras mesurable. Un GO qui n'aurait pas affronté « et si on payait juste deux juges de plus ? » ne convaincrait personne — à commencer par ce projet.

6.3 — Mécanique commune des deux harnais

Exécution dans le moule établi : simulation à compétences contrôlées d'abord (reproductible, rapide, c'est elle qui rend le verdict statistique), rejeu réel Ollama sur un sous-échantillon si GO (le motif LLAMA/ALLPHASES), artefact EFE_SWARM_S2BIS_<date>.json / S3BIS étiqueté selon la discipline P13 (_real ou caveat en tête), verdict calculé par le harnais avant écriture. Coût d'implémentation des harnais : ~un jour chacun — ils réutilisent les générateurs de tâches et le bootstrap des lots S2/S3 existants. C'est l'investissement total requis pour trancher ces deux questions une fois pour toutes.

§7 Risques & anti-patterns — la chambre d'écho

L'itératif a un mode de défaillance que le one-shot n'a pas, et il faut le nommer avant tout GO : l'influence mutuelle peut amplifier exactement ce que l'indépendance protégeait.

Le risque n° 1 : la chambre d'écho. Tout l'édifice S1 repose sur un fait : les erreurs des petits modèles sont corrélées, et c'est l'indépendance des K générations qui permet à la bonne réponse minoritaire d'exister — puis à la sélection de l'extraire. Le gossip détruit cette indépendance par construction : dès le tour 1, chaque agent a lu les autres. Si la majorité du tour 0 est fausse (le cas mesuré : vote7 = 0,396), le raffinement risque de tirer la minorité juste vers l'erreur commune — la convergence devient un consensus de groupe sur le faux, avec une variance superbement basse. Trois défenses architecturales : (a) l'ancre ADR-002 étendue — le vérificateur/jury déterministe reste a-posteriori et hors de la boucle : jamais un signal de vérification intra-tours qui guiderait la convergence (le juge juge la fin, pas le chemin) ; (b) la diversité initiale préservée — les variants du tour 0 restent distincts (le mécanisme existant de T1), et le prompt du Refiner Mode C demande la révision argumentée, pas l'alignement (« révisez si les pairs vous convainquent, maintenez sinon ») ; (c) le signal d'alerte est mesuré par le gate : le bras ④ de S2-bis (moyenne sans itération) détecte précisément le cas où l'itération ne fait que verrouiller le biais — c'est sa raison d'être.

Les risques secondaires, et leurs bornes. Oscillation / non-convergence (deux camps stables qui alternent) : bornée par r_max (I-IT2), rendue dans le résultat comme écart-à-ε — l'appelant sait que la nuée n'a pas convergé, au lieu d'un résultat faussement net. Volume de provenance ×r : un gossip K = 10, r = 3 produit ~30 records + le dossier — soit ~25 Kio aux 815 o/record mesurés ; sous le plafond G8 de 256 Kio, mais l'estimation pré-vol doit le compter (I-IT4) et la dégradation budgétaire mord r_max d'abord. Latence ×r en Mode C : trois tours de 12 B ≈ 3× la latence d'un one-shot — c'est l'affaire de l'étage 3 d'escalade (§5.3) : on ne la paie que sur les instances qui hésitent. Prompt-injection inter-agents (un argument CONTRA malveillant qui détourne les PRO du tour suivant) : surface réelle en Mode C ; mitigée par la canonicalisation PII/adversariale existante en présentation, et — surtout — rendue auditable par le transcript prouvable : l'argument injecté est scellé, attribuable, rejouable. Aucune de ces bornes n'est nouvelle : ce sont les garde-fous des Parties 3–9, qui couvrent l'itératif sans amendement.

A.1 — RoundDriver (cœur, pseudo-code complet)

pub async fn run<W, S>(&self, ctx, wave: W, stop: S) -> RoundsReport {
    ctx.blackboard().new_epoch(&[self.ns]);                  // purge transient (existant)
    let mut r = 0;
    loop {
        let prev = ctx.blackboard().snapshot_prefix(&ns_round(self.ns, r.wrapping_sub(1))); // figé (I-IT3)
        let q = QuiescenceTracker::new();                     // quiescence DE ROUND (WS2)
        wave(r, &prev, &q).await;                             // K (ou 2K) agents ∥, bornés ;
                                                              //   chacun : refine/argue → write_if(ns/r/…, 0) (I-IT1)
                                                              //   → publish "{topic}.r{r}" → q.on_done()
        q.wait_quiescent().await;                             // barrière du tour
        let cur = ctx.blackboard().snapshot_prefix(&ns_round(self.ns, r));
        if stop(r, &cur) || r + 1 == self.max_rounds {        // ε sur VÉRITÉ, pure (I-IT5) | borne (I-IT2)
            return RoundsReport { rounds: r + 1, final_cells: cur, residual: stop.residual() };
        }
        r += 1;
    }
}
