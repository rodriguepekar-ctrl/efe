P1 — Roadmap du Code

Le plan d'ingénierie concret du moteur d'évidence de conformité : les crates, le chemin critique, les sprints (~12 semaines), et les invariants d'honnêteté écrits comme tests.
Cette roadmap traduit l'architecture P1 en code buildable. Le principe d'ingénierie cardinal : tout ce qui porte la confiance est en Rust, audité et testé — le scellement, la re-preuve, le vérifieur, l'export ; la console n'est qu'une VUE, non un ancre de confiance (même compromise, l'export forensic et le vérifieur indépendant la rattrapent). On réutilise massivement EFE : la chaîne HMAC + manifest-root + reprove + HmacKeySource ∘ TenantId (R0/N17), le seam ClientMode::SelfHost + le garde is_local_endpoint (la passerelle souveraine), la grammaire SwarmObserver/AgentCall (le hook). Le chemin critique est court : le modèle de DAG scellé (nœuds typés : acte, arête, évidence, humain) + sa re-preuve → les taps (passerelle, hook, 3ᵉ tap d'évidence) + le store local → l'API d'audit → puis deux pistes parallèles, la console (surface opérationnelle) et l'export forensic + le vérifieur autonome (le composant-fossé, statique et sans dépendance). On termine par les nœuds humains (oversight EU AI Act) et les gabarits réglementaires. La discipline est celle d'EFE : les invariants d'honnêteté sont des tests — la falsification du sceau (toute mutation casse la re-preuve), « intègre ≠ correct » imposé au niveau API, la vérification trustless (le vérifieur tourne avec le seul DAG + clé, zéro dépendance), l'évidence figée (content_hash), l'air-gap, le déterminisme bit-à-bit — plus une revue adversariale par composant. La porte est l'usabilité + la conversion ; le code est conçu pour la passer.

Le geste, en une phrase

Bâtir, en Rust pour tout le trust-critique et une vue web par-dessus, le moteur d'évidence de P1 — modèle DAG scellé → taps → store → API → {console ∥ export+vérifieur} → humain → gabarits — en réutilisant les primitives re-prouvées d'EFE, avec chaque invariant d'honnêteté encodé en test et une revue adversariale par composant, sur ~12 semaines.

Le choix d'architecture logicielle qui dé-risque tout. La confiance ne vit jamais dans l'UI. Le scellement, la re-preuve et le vérifieur sont en Rust, audités, déterministes ; la console ne fait que lire et demander une re-preuve au cœur Rust. Conséquence : la console peut être bâtie vite et pragmatiquement (React/TS) sans être un risque de sécurité — car même une console compromise ne peut pas forger l'intégrité (la re-preuve tourne côté Rust, et l'export forensic est vérifiable indépendamment de toute console). Le fossé est dans le cœur Rust + le vérifieur autonome, pas dans l'écran.

§2 Le chemin critique & le graphe de dépendances

Chemin critique : provenance-dag → taps → dag-store → audit-api → {console ∥ export+verify}. Le vérifieur forensic ne dépend que du modèle scellé (pointillé) — c'est ce qui le rend trustless.

La règle de séquencement : rien ne se construit avant provenance-dag (le modèle + la re-preuve), car c'est le contrat que tout consomme. Les trois taps se parallélisent une fois le modèle figé. La console et l'export+vérifieur se parallélisent une fois l'API debout. Les nœuds humains et les gabarits réglementaires viennent en dernier (ils enrichissent, ne bloquent pas).

§4 Le composant-fossé : le vérifieur forensic autonome

verify est le seul composant dont la qualité fait ou défait le fossé. Sa spec est exigeante et contre-intuitive : il doit être le plus petit et le plus indépendant possible, pas le plus riche.

  • Zéro dépendance d'exécution. Un binaire statique (musl), ou à défaut un script auto-contenu, qui prend dag.sealed.jsonl + K_tenant et rend PASS/FAIL. Il ne contacte ni Kovant ni EFE, ni le réseau — c'est ce qui le rend trustless.
  • Re-implémente la re-preuve, minimalement. Il ne réutilise PAS la grosse crate EFE (sinon « faites confiance à notre crate ») — il re-dérive le manifeste depuis les records bruts avec la seule primitive HMAC standard. Quelques centaines de lignes, lisibles par un auditeur en une heure. La transparence du vérifieur EST l'argument.
  • Reproductible. Le binaire est buildé de façon reproductible (même source → même binaire), pour qu'un tiers puisse le re-compiler et vérifier qu'il fait ce qu'il dit.
  • Documenté pour le sceptique. Le README répond à « comment vérifier sans nous faire confiance » — l'inverse exact d'un produit fermé.

Pourquoi c'est le fossé, et pourquoi il est en code, pas en marketing. N'importe qui peut afficher « vérifié » dans une UI. Très peu livrent un vérifieur autonome, minuscule, re-compilable, qui prouve l'intégrité sans faire confiance au vendeur. C'est exactement ce qu'un régulateur, un auditeur Big-Four, ou un juge accepte — et ce qu'un concurrent ne peut pas imiter sans la même rigueur cryptographique. Tout le poids commercial de P1 repose sur la qualité de ce binaire.

§5 Les invariants d'honnêteté, écrits COMME TESTS

La signature EFE : un invariant qui n'est pas un test n'existe pas. Chaque propriété de confiance de P1 est un test qui casse le build s'il échoue.

InvariantLe test
Falsification du sceaumuter n'importe quel champ d'un nœud/arête/évidence/humain ⇒ reprove_dag rend FAIL (le tamper-evidence prouvé, pas affirmé)
Intègre ≠ correctl'API/console n'émet jamais le mot « correct/correcte » à propos d'une re-preuve (test de grep sur la sortie + sur la copy) ; la re-preuve ne porte que l'intégrité
Trustless verifyverify tourne dans un sandbox sans réseau et sans le code EFE/Kovant, avec seulement dag+clé, et rend le bon verdict
Évidence figéechanger la source après coup ne change PAS le content_hash scellé ; le DAG montre la version réellement utilisée
Air-gapgateway + store + api + verify fonctionnent réseau externe coupé (test d'intégration)
Déterminismemême DAG + même clé ⇒ même manifest-root, bit-à-bit, à chaque exécution (re-prouvabilité)
Oversight completun override humain non scellé est impossible : l'action console passe TOUJOURS par un nœud humain scellé (test de chemin)

§6 La discipline d'ingénierie (le rythme EFE)

  • CI dure. cargo test vert, clippy sans avertissement, les invariants-tests (§5) bloquants — exactement le standard du monorepo EFE.
  • Revue adversariale par composant trust-critique (S0 le modèle, S1 les taps, S4 le vérifieur) : le pattern qui a attrapé un vrai bug à chaque frontière du programme EFE (panic NaN, fuite de format, puissance inversée…). On l'applique au cœur de confiance — là où un bug serait une responsabilité.
  • Pré-enregistrement re-prouvable (hérité de P0) : le contrat de mesure (et les critères d'usabilité) sont scellés avant les tests d'usabilité — on ne déplace pas les poteaux.
  • Souveraineté par défaut : tout build/test tourne local ; le garde is_local_endpoint reste actif ; aucun secret/donnée client ne quitte la frontière.
  • Frontière de confiance versionnée : seul le cœur Rust trust-critique exige la revue lourde ; la console évolue vite (elle n'est qu'une vue) — la vélocité va où le risque est faible.

§7 Hors-périmètre & alignement portes/arrêt

Explicitement HORS de P1 (c'est P2/P4). Aucun petit-spécialiste, aucun fine-tuning, aucun routeur coût/qualité, aucune mesure de non-infériorité par sous-tâche, aucune mesure GPU-secondes (B2), aucun fabric de communication mesuré, aucun templating multi-workflow. P1 code = la provenance vendable, un workflow. Confondre les périmètres est la première façon de rater la porte.

Alignement avec la porte/arrêt de P1 :

  • Porte (S7). Le code DOIT rendre la conversion possible : la console assez claire pour qu'un agent de conformité l'adopte, l'export assez crédible pour son auditeur. Les sprints S3 (usabilité) et S4 (vérifieur trustless) sont les livrables de porte.
  • Arrêt (usabilité). Si le test d'usabilité S3 échoue (le non-cryptographe ne sait pas lire la re-preuve), on gèle les features et on simplifie l'UX (le « cadenas vert », le récit) avant tout le reste — le code est priorisé pour l'usabilité, pas la richesse.

§8 Registre réutilisé, & ce que la roadmap code décide

Ce qu'EFE donne déjà (la vitesse)

Le cœur de confiance est, pour l'essentiel, déjà écrit et re-prouvé dans EFE : la chaîne HMAC + manifest-root, reprove, HmacKeySource∘TenantId (R0/N17) ; le seam SelfHost + is_local_endpoint (la passerelle) ; SwarmObserver/AgentCall (le hook). P1 compose ces briques en un produit ; il n'invente pas la cryptographie ni la souveraineté — il les orchestre et y ajoute les surfaces (console, export, vérifieur, gabarits). C'est ce qui rend ~12 semaines crédibles pour un produit de confiance d'entreprise.

EffortComposants
Quasi-réutilisé (assemblage)le scellement, reprove, la passerelle/garde d'egress, le hook
Extension modéréeprovenance-dag (liste→graphe typé), dag-store (index), audit-api
Neuf intégralle 3ᵉ tap d'évidence, les nœuds humains, la console, verify autonome, les gabarits réglementaires

Ce que la roadmap code décide. Elle rend P1 exécutable : un chemin critique court (le cœur Rust de confiance existe déjà), des surfaces neuves bien isolées (la console n'est qu'une vue, le vérifieur est le fossé), et chaque propriété de confiance encodée en test qui casse le build. Si l'équipe livre les sprints S0–S4 avec leurs tests verts et la revue adversariale passée, P1 a son produit défendable — et la conversion (S7) devient une question commerciale, plus technique. C'est la phase où la provenance d'EFE cesse d'être un instrument de recherche pour devenir un logiciel d'entreprise vendable.

Note d'honnêteté. Roadmap d'ingénierie de proposition, fondée sur les crates réelles et testées d'EFE et l'architecture P1. Le découpage en sprints suppose le runtime Kovant et le beachhead fixés en P0 ; les estimations (~12 semaines) sont indicatives et dépendent de l'effectif et de la propreté du point de tap d'orchestration côté Kovant.
