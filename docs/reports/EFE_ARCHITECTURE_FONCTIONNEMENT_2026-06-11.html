§1  Carte du système

EFE est un monorepo Rust organisé en couches strictes : chaque couche ne dépend que des couches inférieures (aucun cycle). C'est ce qui permet de garder le SDK léger et la passerelle de dev sans dépendance prod.

§2  Le modèle conceptuel & le cycle d'un run

Cinq idées suffisent à tout comprendre. (1) Nano-agents : beaucoup de petits agents déterministes, mono-fonction, sans poids. (2) Substrat : un Blackboard (vérité) + un bus (indice) où ils s'échangent l'information. (3) Topologies : 4 façons de les orchestrer en parallèle. (4) Modes : la même topologie peut faire tourner des agents déterministes (Mode A) ou de vrais LLM (Mode C/Network). (5) Provenance : chaque pas est scellé → un tiers re-prouve le run hors-ligne.

Le cycle complet d'un run (ce qui se passe, dans l'ordre)

Figure 2 — Le cycle de bout en bout (routes/run.rs → sdk.rs::run_traced → topology → provenance → store). C'est la colonne vertébrale ; les sections suivantes zooment sur chaque étage.

À retenir : l'orchestration (qui décide quoi exécuter) est séparée de l'exécution (les agents sur le substrat), elle-même séparée de la preuve (le scellement). Ces trois plans ne se connaissent que par des interfaces minces (un trait Topology, un trait WriteSink), ce qui rend chaque étage remplaçable sans toucher aux autres.

Un exemple concret, du début à la fin

Pour ancrer les idées, suivons une vraie requête. On envoie à la passerelle :

{ "task": { "text": "The court ruled the clause unenforceable.", "expected": "legal" },
  "topology": { "kind": "consensus", "generator": "echo_generator",
                "judges": ["consistency","length_band","j_non_empty"], "k": 5, "pattern": "borda" },
  "budget": { "max_cents": 1000 }, "mode": "keyless" }

Voici ce qui se déroule, dans l'ordre, avec les valeurs réelles :

  1. La passerelle vérifie le rôle (RBAC), puis resolve_mode("keyless") → mode inchangé, allow_remote = false, pas de surcharge de tarif. Le prix par appel sera 1 ¢ (tarif Keyless).
  2. Swarm::run_traced démarre. Budget pré-vol : 5 générateurs + 3 juges = 8 appels × 1 ¢ = 8 ¢, bien sous le plafond de 1000 → on exécute.
  3. Mode Keyless → pas de backend, AgentKind::ModeA. Le Resolver récupère echo_generator et les 3 juges depuis la flotte (nano-agents). Chacun est enveloppé par le Meter.
  4. La topologie consensus s'exécute : 5 candidats générés en parallèle → écrits en /cand/0…4 ; les 3 juges lisent et écrivent /ballot/0…2 ; Borda agrège. 8 écritures au Blackboard → 8 AgentCallRecord capturés, 8 ¢ facturés.
  5. Scellement : la chaîne HMAC produit un provenance_root de 64 hex ; verify_swarm le re-prouve immédiatement (verified = true).
  6. La passerelle persiste les 8 records et renvoie { run_id, run } avec budget.spent_cents = 8, provenance.records = 8, le root, et le résultat.

Ce run est exactement celui qu'on voit dans le dashboard live (panneau Provenance : « records 8, traced_pct 100 %, VERIFIED » ; panneau Budget : « 8 / 1000 »). Chaque cent dépensé correspond à un record tracé — c'est la cohérence vérifiable de bout en bout, en un seul exemple.

§3  Le substrat de communication (crate efe-blackboard)

Le substrat est la réponse à « comment des dizaines d'agents se passent l'information en parallèle sans se corrompre ». Il a deux organes complémentaires (Keystone WS1) : un Blackboard (la vérité durable, exhaustive) et un TopicRouter (l'indice live, pub/sub).

Figure 3 — Le substrat. blackboard.rs (Blackboard), topic_router.rs (bus), sink.rs (seams), metrics.rs (compteurs).

Le Blackboard : un magasin clé-valeur versionné, conçu pour le parallélisme

Structure réelle (blackboard.rs) : fields: DashMap<String, BlackboardValue> où la clé est un JSON-pointer (/cand/0, /ballot/2) et la valeur porte { value, version, written_by, written_at }. Deux propriétés rendent le parallélisme massif viable :

  • Sharding (DashMap). La map est découpée en shards verrouillés indépendamment. Quand 7 générateurs écrivent /cand/0…6, leurs clés tombent dans des shards différents → aucune attente mutuelle. Un Mutex global aurait sérialisé tout le monde — le sharding est la raison technique pour laquelle « beaucoup d'agents en parallèle » fonctionne.
  • CAS (write_if(pointer, value, expected_version)). Quand deux agents visent la même clé, l'écriture n'est acceptée que si la version stockée est encore celle qu'on a lue. Exemple concret : A et B lisent /x v3 ; A écrit → v4 ; B tente « si v3 » → refusé, bb_conflicts_total++. Pas de perte silencieuse : on gagne, ou on est explicitement recalé.

Bornes (garde-fou G8). L'historique détaillé est un ring borné (DEFAULT_RECENT_HISTORY = 8192) ; les compteurs exacts (writes_total, par agent) sont des atomiques O(1) ; un cap d'octets global (MAX_BLACKBOARD_BYTES) + des caps par namespace empêchent un essaim de saturer la mémoire (écritures en excès → rejections_total).

Le bus, et la règle d'or « bus = indice, Blackboard = vérité »

Le TopicRouter (topic_router.rs) est un broadcast::channel par topic. Pourquoi ne pas tout faire au bus ? Parce qu'un canal broadcast peut perdre des messages (si un abonné est lent, l'événement est dropped → ev_dropped_total). Or l'agrégateur de consensus doit voir TOUS les ballots (S1). Solution : le bus sert d'indice (« un ballot vient d'arriver »), mais la décision lit la vérité au Blackboard via snapshot(), exhaustif. Le live peut être imparfait sans jamais fausser le verdict.

Les deux seams : observer sans coupler

Tout passe par deux callbacks (sink.rs) : WriteSink::on_write(&BlackboardWrite) à chaque écriture committée, et EventSink::on_event(&SwarmEvent) à chaque publish. La couche provenance branche son sink sur le premier (elle ancre 100 % des écritures pour la preuve) ; le dashboard branche le sien sur le second. La topologie ignore complètement ces consommateurs — elle ne dépend que du type efe_blackboard::WriteSink (pas de cycle, pas de couplage). Règle d'or : ces callbacks doivent être rapides et non-bloquants (variantes lossy via try_send), car ils s'exécutent sur le chemin chaud des agents.

Pourquoi des clés JSON-pointer (et pas un simple HashMap<String,String>)

Les clés sont des chemins (/cand/0, /ballot/2) pour deux raisons. D'abord, elles donnent une structure : on peut adresser un namespace entier (/cand/*) — utile pour les caps par namespace (« les candidats peuvent peser jusqu'à X, les contrôles jusqu'à Y ») et pour la réconciliation (« relis tous les /ballot/* »). Ensuite, les valeurs sont des serde_json::Value arbitraires, donc un agent peut écrire un objet riche ({judge, scores[]}) et un autre n'en lire qu'un champ. C'est un petit « système de fichiers en mémoire » par run, pas un cache plat.

Le snapshot() : pourquoi c'est lui qui décide

À la fin de la phase de jugement, l'agrégateur n'écoute pas le bus pour décider — il appelle bb.snapshot(), qui renvoie une vue cohérente de tous les champs présents. Il reconstruit alors les ballots en lisant /ballot/0…J. Pourquoi ce détour ? Parce que c'est la seule façon d'être certain de n'en rater aucun : un juge a peut-être fini avant que son message bus ne soit consommé, ou son message a pu être dropped ; mais son écriture, elle, est dans le Blackboard. Le snapshot transforme « ce que j'ai entendu passer » (faillible) en « ce qui est réellement là » (exact).

Lire les métriques de substrat (ce qu'elles racontent)

Le SubstrateMetrics (exposé en /metrics) est un tableau de bord de santé de l'essaim :

  • bb_writes_total — volume d'information échangée (devrait ≈ K + J par run consensus).
  • bb_cas_attempts_total / bb_conflicts_total — pression de concurrence : si les conflits montent, deux agents se disputent souvent la même cellule (signal de contention).
  • bb_rejections_total — écritures refusées pour dépassement de cap (un essaim qui pousse trop de données ; garde-fou G8 actif).
  • ev_published_total / ev_dropped_total — trafic bus et pertes d'observation (rappel : une perte ici n'affecte que le live, jamais l'audit).

Un histogramme de latence (buckets + quantiles) complète le tableau : on voit la distribution des durées d'écriture, pas seulement une moyenne trompeuse.

§4  Les nano-agents (crate efe-swarm-topology)

Un nano-agent est une struct Rust mono-fonction, déterministe, sans poids. Il implémente l'un des 6 traits ci-dessous. Leur petitesse est ce qui autorise à en lancer beaucoup, en parallèle, pour presque rien.

Les 6 contrats (traits, traits.rs + consensus/)

trait Generator { async fn generate(&self, task, variant: usize) -> Value; }  // variant = DIVERSITÉ
trait Verifier  { fn score(&self, task, candidate) -> f64;  fn passes(...) -> bool; } // a-posteriori
trait Stage     { async fn process(&self, input) -> Vec<Value>; }   // 1→1, 1→N (fan-out), 1→0 (filtre)
trait Decomposer{ async fn decompose(&self, task) -> Vec<Value>; }  // T3 : tâche → sous-tâches
trait Solver    { async fn solve(&self, subtask) -> Value; }         // T3 : RÉCURSIF (peut être un essaim)
trait Merger    { async fn merge(&self, task, results) -> Value; }   // T3 : agrège
trait Judge     { async fn assess(&self, task, candidates) -> Vec<f64>; } // consensus : note K candidats

À quel point c'est « nano » : un agent réel, en entier

Voici Uppercase, tel qu'il est dans catalog.rs — l'agent complet tient en une ligne de logique :

pub struct Uppercase;
impl Stage for Uppercase {
    async fn process(&self, input: &Value) -> Vec<Value> {
        vec![json!({ "text": text_of(input).to_uppercase(), "idx": idx_of(input) })]
    }
}

Pas de modèle, pas de poids, pas d'état : du Rust pur. EchoGenerator renvoie l'entrée, WordSplit découpe en mots, NonEmptyText score 1.0 si non-vide. C'est cette trivialité individuelle qui rend l'essaim bon marché — la valeur naît du nombre, de la diversité et de la sélection, pas d'un agent isolé.

La flotte : un registre interrogeable par nom (fleet.rs)

AgentFleet est un registre (BTreeMap<String, Arc<dyn Trait>> par rôle). AgentFleet::standard() enregistre les 43 agents intégrés. On les monte par nom, répétitions comprises : judge_panel(&["j_equals_expected"; 5]) donne un panel de 5 juges identiques — une topologie consensus peut donc être assemblée entièrement depuis la flotte sans construire un seul agent à la main.

Rôle#Exemples (noms réels)
Décomposeurs7word_split · sentence_split · char_chunk · json_array_split
Transformations (Stage)10trim · lowercase · uppercase · normalize_whitespace · word_count
Vérificateurs8non_empty_text · is_object · equals_expected · length_bounded
Agrégateurs (Merger)7join_lines · majority_value · sum_values · max_by_score_field

Pourquoi « nano » et « déterministe » sont des choix, pas des limites

On pourrait penser que des agents si simples sont un pis-aller. C'est l'inverse : ce sont des propriétés recherchées.

  • Petit → nombreux → bon marché. Un agent qui coûte presque rien peut être lancé par dizaines en parallèle. La puissance vient de l'essaim (diversité + sélection), pas d'un cerveau unique.
  • Déterministe → reproductible → preuve solide. Un nano-agent Mode A redonne exactement la même sortie pour la même entrée. C'est ce qui fait du Mode A l'ancre : le provenance_root d'un run keyless est rejouable bit-à-bit (ADR-007). Un LLM, lui, ne l'est pas — d'où la nuance « on prouve l'intégrité, pas le rejeu ».
  • Sans poids → sans réseau → souverain. Pas de modèle à charger, pas d'API à appeler : ça tourne air-gap par construction, et c'est aussi le squelette de test/CI (rapide, gratuit, hermétique).
  • Composable. Les 6 traits sont volontairement minuscules (une méthode chacun), donc un agent écrit une fois sert dans T1, T2, T3 ou Consensus sans adaptation.

Vérificateur vs Juge : deux façons de « noter », pour deux familles de tâches

La distinction est au cœur du pari produit (ADR-001/002).

Verifier (T1) — tâches vérifiables

score + passes sur un candidat. Pour une tâche dont on peut checker la réponse (un calcul, un format, une égalité), le vérificateur est déterministe et atteint le « OR » : il sait dire vrai/faux. C'est lui qui extrait le bon candidat même minoritaire.

Juge (Consensus) — tâches non vérifiables

assess(task, candidates) → un score par candidat. Quand il n'y a pas de vérité mécanique (qualité d'un résumé, pertinence d'un label), on s'appuie sur un panel de juges et on agrège leurs classements (Borda/Condorcet) — la précision n'est plus 1, mais le consensus discrimine.

Détail important : même en self-host (Mode C), le vérificateur de T1 reste déterministe (pris dans la flotte), jamais un LLM — c'est l'ancre a-posteriori qui garde la sélection honnête.

§5  Les quatre topologies parallèles

Les 43 nano-agents se recombinent en 4 patterns, tous derrière une interface unique (trait Topology { async fn run(task, ctx) -> TopologyOutput }, object-safe — donc un Vec<Box<dyn Topology>> exécute n'importe lequel uniformément). Le SwarmContext leur injecte la flotte + 3 seams (provenance, métriques, dashboard).

Figure 4 — Les 4 patterns. Fichiers : generate_verify.rs, consensus_topology.rs, pipeline.rs, hierarchical.rs.

Comment le parallélisme est réellement obtenu

  • T1 (generate_verify.rs) : un JoinSet lance K tâches générateur, chacune prenant un permis d'un Semaphore(max_concurrency) (backpressure si les agents sont des SLM lents). On collecte les candidats dans l'ordre d'arrivée, puis le vérificateur sélectionne a-posteriori le passant de meilleur score (sinon le meilleur score en fallback).
  • T-Consensus (consensus_topology.rs) : génération via JoinSet, puis jugement via tokio::spawn (bornés). Voir le déroulé ci-dessous.
  • T2 (pipeline.rs) : étages exécutés en streaming sur efe_blackboard::StreamingSwarm — pas de barrière entre couches, terminaison par quiescence (plus rien à faire). Un étage peut faire du fan-out 1→N.
  • T3 (hierarchical.rs) : décompose, puis résout les sous-tâches en parallèle via un T2 mono-étage (Pipeline.run_batch), puis agrège. Récursif : le Solver peut être un T1/T2/T3 → profondeur arbitraire (ramène une tâche dure dans l'enveloppe de capacité en la découpant).

Déroulé d'un consensus (K=7, J=2), pas à pas

  1. Génération ∥. 7 tâches générateur (JoinSet + Semaphore), chacune avec un variant 0…6 (le levier de diversité). Les candidats sont écrits en /cand/0…6 au Blackboard.
  2. Vote gratuit d'abord (escalade). On tente un MajorityVote sans juge ; si la confiance ≥ seuil → terminé (juges économisés, coût = 7). Sinon on escalade.
  3. Jugement ∥. 2 juges en spawn ; chacun lit les 7 candidats, écrit /ballot/j (vérité) et publie sur ballot.j (indice → dashboard).
  4. Réconciliation. On draine le bus pour le tempo, puis on relit le Blackboard (snapshot()) pour reconstruire exhaustivement les 2 ballots.
  5. Agrégation. Borda combine 2 ballots × 7 candidats → gagnant + confiance ; publie consensus.decided.

L'agrégation (le « vote intelligent ») — exemple Borda chiffré

Borda donne à chaque candidat des points = Σjuges ((K−1) − rang). Avec 3 candidats (K=3) : 1ᵉʳ→2 pts, 2ᵉ→1, 3ᵉ→0.

CandidatJuge 1Juge 2Total
A1ᵉʳ → 21ᵉʳ → 24 ← gagnant
B2ᵉ → 13ᵉ → 01
C3ᵉ → 02ᵉ → 11

L'intérêt : si 7 candidats contiennent 3 corrects (variés) et 4 fois le même leurre, un vote majoritaire choisit le leurre ; Borda, en intégrant tout le classement de juges qui savent reconnaître la qualité, fait remonter un correct. Condorcet (vainqueur pairwise, fallback Copeland sur cycle) est l'alternative. La confiance = marge (1ᵉʳ−2ᵉ) ÷ gain max : 0 en cas d'égalité (candidats identiques → « CONF 0 % » du démo keyless), élevée si un candidat domine.

Le mode Auto du SDK choisit pour vous : si la tâche porte un expected (vérifiable), il oriente vers T1/Consensus. C'est « conscient du mode » : en self-host, Auto monte un consensus N-juges local.

T2 : « streaming » et « quiescence », expliqués

Un pipeline classique a des barrières : l'étape 2 attend que TOUTE l'étape 1 soit finie. T2 n'en a pas : dès qu'un item sort de l'étape 1, il coule vers l'étape 2 (streaming sur StreamingSwarm). Comment savoir qu'on a fini, sans barrière ? Par quiescence : le système se déclare terminé quand plus aucun item n'est en vol et qu'aucune étape n'a de travail en attente — « le silence retombe ». C'est plus efficace (pas d'attente inutile) et naturel pour des étages de vitesses différentes.

T3 : la récursion, sur un exemple

Tâche trop grosse pour un petit modèle : « résume ce document de 40 pages ». T3 la décompose (page-split → 40 sous-tâches), résout chaque sous-tâche en parallèle — et voici l'astuce : chaque Solver peut lui-même être un T1 (générer 5 résumés de page, garder le meilleur) ou un autre T3. Un Merger (ex. join_lines) recombine. On a ramené une tâche hors-enveloppe dans l'enveloppe de capacité des nano-modèles en empilant des essaims (« superviseur de superviseurs »). La profondeur est arbitraire car Solver est juste un trait que toutes les topologies satisfont.

§6  Le SDK : orchestration d'un run (crate efe-swarm-sdk)

Le SDK est le chef d'orchestre. Swarm::run_traced(task, topology, budget) assemble tout : il choisit le backend selon le mode, monte la topologie via le Resolver, exécute, puis scelle la provenance. Voici sa séquence réelle (sdk.rs).

  1. Pré-vol budget. On calcule le prix par appel (du mode, ou du budget). En politique Error, si l'estimation dépasse le plafond → on refuse avant d'exécuter. En Degrade, on réduit K (et on rogne les juges) pour tenir.
  2. Mode → backend + nature. Keyless → pas de backend, AgentKind::ModeA. SelfHost → build_local_backend (avec le garde-fou souveraineté), AgentKind::ModeC. Network est écarté ici (le SDK le refuse in-process ; c'est la passerelle qui l'a déjà traduit en SelfHost-vers-routeur).
  3. Health-check. En self-host, on sonde le backend (échec rapide si injoignable).
  4. Provenance + budget + N17. On crée un ProvenanceRecorder, un BudgetGuard, et (en Mode C) un LlmProvenanceCollector. Le tout est porté par un Meter.
  5. Substrat + observateur. On construit le SwarmContext en branchant le ProvenanceSink (et, si dashboard, un TeeSink qui duplique vers l'observateur) sur le write_sink, plus les métriques et le tap d'événements.
  6. Résolution + exécution. La topologie est concrétisée puis résolue par le Resolver (voir ci-dessous), et exécutée : topo.run(&task, &ctx).await.
  7. Scellement + re-preuve. recorder.seal_with_key(clé) produit la SealedProvenance ; verify_swarm la re-prouve immédiatement (et alimente les métriques) ; on assemble le résumé N17.
  8. Retour. Un RunOutcome { run, sealed, llm_records } : la passerelle persiste sealed.records (la preuve) et renvoie run.

Le Resolver : le même nom, deux réalités (resolver.rs)

C'est le point de bascule Mode A / Mode C. Pour chaque rôle, le Resolver regarde s'il y a un backend :

fn generator(name, id):
    g = match backend {
      Some(b) => llm_gen(b, name)          // Mode C : le NOM est une INSTRUCTION (prompt)
      None    => fleet.generator(name)?    // Mode A : le NOM est une CLÉ de flotte (nano-agent)
    }
    meter_gen(g, meter, id)                // ENVELOPPE : budget + provenance + N17 + observateur

Conséquence remarquable : la topologie ne change pas d'une ligne entre Mode A et Mode C. En keyless, "echo_generator" désigne un nano-agent ; en self-host, "Classe le sujet en un mot…" devient l'instruction envoyée au LLM. Le vérificateur reste toujours déterministe (depuis la flotte) — c'est l'ancre a-posteriori d'ADR-002.

Le Meter : la couche qui rend chaque pas gouverné et prouvé (agents.rs)

Chaque agent résolu est décoré par le Meter. Autour de chaque appel, dans l'ordre :

  • charge (I13) : BudgetGuard.charge facture l'appel (atomique, jamais de dépassement) ; si épuisé → sentinel neutre.
  • scope N17 : run_agent pose un puits task-local, exécute l'appel, draine le puits → un LlmProvenanceRecord (Mode C).
  • capture : un AgentCallRecord (input/output hash, rôle, variant, lien N17) est remis au ProvenanceRecorder.
  • observe : notification au dashboard (sortie + coût + budget courant), coût nul si aucun observateur.

C'est ici que « beaucoup de petits agents » devient « beaucoup de petits agents gouvernés et prouvés » — sans que les agents ni les topologies aient à le savoir.

Les trois politiques de budget, et quand les choisir

  • Error — refuse avant d'exécuter si l'estimation dépasse le plafond (et échoue si épuisé en cours). À choisir quand on veut une garantie stricte « jamais un centime de trop, quitte à ne rien faire ».
  • Stop — exécute et s'arrête proprement à l'épuisement (résultat partiel). Le défaut raisonnable : on prend ce qu'on peut dans le budget.
  • Degrade — réduit K et rogne les juges avant d'exécuter pour tenir dans le budget, puis exécute normalement. À choisir quand on préfère un essaim plus petit mais complet à un essaim tronqué.

Dans tous les cas l'invariant I13 tient : le compteur ne dépasse jamais le plafond (ajout atomique → test → revert). Le test i13_holds_under_concurrency le vérifie sous 8 threads.

Deux détails d'orchestration qui comptent

concretize. Avant l'exécution, la topologie est « concrétisée » selon la tâche et le mode (ex. Auto devient un T1 ou un consensus). C'est ce qui permet à l'utilisateur de dire Auto sans connaître les internals.

TeeSink. Quand un observateur (dashboard) est branché, le SDK ne remplace pas le sink de provenance : il duplique (un TeeSink écrit vers les deux). Conséquence cruciale : la provenance reste byte-identique qu'on regarde ou non le dashboard — l'observation ne peut pas altérer la preuve. C'est le principe « live ≠ audit » poussé jusqu'à l'octet.

§7  La provenance — le moat (crate efe-swarm-provenance)

L'argument différenciant : chaque pas de chaque nano-agent laisse un AgentCallRecord scellé, et un tiers re-prouve tout le run à partir des seuls records + une clé tenant — hors-ligne, sans nous croire ni croire un provider (ADR-SWARM-006/009).

Figure 5 — La chaîne HMAC + DAG + sa re-preuve.

Ce que « sceller » veut dire, concrètement

Un AgentCallRecord capture un pas : qui (rôle, agent_id), entrée (input_hash = blake3 du JSON), sortie (output_hash), parents (DAG), et — pour un agent LLM — un llm_provenance_id vers le forensique N17. À la fermeture, on chaîne un HMAC :

hmac₀ = HMAC(clé_tenant, genesis ‖ record₀)
hmacᵢ = HMAC(clé_tenant, hmacᵢ₋₁ ‖ recordᵢ)     // chaque maillon scelle le précédent
provenance_root = f(hmac…) → 64 hex

La clé tenant est dérivée par HKDF-SHA256 (master + UUID tenant, efe-audit-core) : elle signe, n'est jamais transmise ni stockée dans un record. Deux tenants → deux clés → deux chaînes incomparables (isolation).

Les trois contrôles de verify_swarm, et ce que chacun attrape

  • chain_intact : recalcule toute la chaîne HMAC → détecte insertion / suppression / réordonnancement (la structure).
  • content_intact : recalcule les blake3 entrée/sortie → détecte la mutation d'un seul octet (le contenu).
  • dag_consistent : vérifie que les arêtes de causalité pointent vers des records cohérents (le graphe).

Les trois passent ⇒ verified = true et root recalculé == root d'origine. Le calcul n'exige rien d'autre que les records (exportables via GET …/records) et la clé tenant → un régulateur le fait sur une machine déconnectée. Quand ça casse, first_break localise le record fautif.

La nuance honnête : ceci prouve l'intégrité et la lignée (tamper-evidence), pas que le LLM redonnerait le même texte. On ne re-exécute pas le modèle ; on prouve que ce qui a été produit n'a pas bougé, et par qui / dans quel ordre.

Une falsification, pas à pas (ce que voit l'attaquant et ce que voit verify)

Imaginons qu'après coup, quelqu'un veuille faire croire que l'essaim a répondu « finance » au lieu de « legal ». Il a accès aux records stockés. Il modifie la sortie du record gagnant : output: "legal" → "finance". Que se passe-t-il au prochain verify ?

  1. verify recalcule output_hash = blake3("finance") et le compare au hash scellé (blake3("legal")) → différent → content_intact = false.
  2. Pour « réparer », l'attaquant devrait aussi changer le output_hash scellé. Mais ce hash entre dans le HMAC du record, donc hmacᵢ change → chain_intact = false à partir de ce maillon.
  3. Pour « réparer » la chaîne, il faudrait recalculer tous les HMAC suivants — ce qui exige la clé tenant, qu'il n'a pas (elle n'est nulle part dans les records ; elle vit côté serveur).

Résultat : verified = false, et first_break pointe le record gagnant. La falsification est détectée et localisée. C'est précisément ce que vérifie le test verify_detects_tampering de la passerelle, et ce qu'on a mesuré en réel (Lot P5 : tamper_detected = 100 %). Sans la clé, on ne peut pas forger une chaîne valide — d'où l'importance du binaire prod qui signe avec EnvHkdf et non la clé de test publique.

§8  Le pont N17 — forensique par-appel (sdk/n17.rs)

L'AgentCallRecord dit « quel agent, quelle entrée/sortie ». Le pont N17 ajoute la granularité par appel LLM : un LlmProvenanceRecord capte modèle, seed, paramètres, hash prompt/réponse, latence, re-tentatives. L'AgentCallRecord le référence via llm_provenance_id. Une seule lignée, deux granularités.

Le fossé d'information, et l'astuce du task-local

Le backend connaît le modèle/prompt/réponse mais ignore le contexte d'essaim (quel agent, quel tenant). Le Meter connaît le contexte mais ne voit pas l'appel LLM brut. On les relie par un task-local (variable propre à la tâche async) :

  1. Avant l'appel d'agent, le Meter pose un puits dans le task-local (scoped).
  2. Le backend, à chaque complete(), dépose sa forensique (push_pending) dans le puits courant — sans savoir à qui il appartient (no-op hors scope).
  3. L'appel terminé, le Meter draine le puits, ajoute le contexte, assemble le LlmProvenanceRecord et lie l'AgentCallRecord au ProvenanceId.

C'est concurrence-safe par construction : chaque appel d'agent a son puits (task-local scopé), donc même avec 7 générateurs en parallèle, aucune confusion — chaque forensique retombe dans le bon panier.

Le piège des re-tentatives (et sa correction)

Si le Retrier rappelait le backend 3 fois, il pousserait 3 forensiques pour un seul appel logique → le pont compterait des appels fantômes et risquerait de lier le record à une tentative échouée. La correction : le Retrier exécute chaque tentative dans un puits imbriqué qu'il vide, et ne ré-émet qu'un record final (l'issue retenue) avec retry_count (0 = réussi du 1ᵉʳ coup, >0 = N re-tentatives → retry_outcome RetriedSucceeded/RetriedExhausted). Le lien pointe donc toujours vers ce qui a compté. Sur le run Claude réel : consistent: 4, unlinked: 0, broken: 0.

§9  Les backends locaux & la résilience (sdk/backend/)

En Mode C, les agents appellent un LLM via un LocalBackend. Tout est keyless et local par défaut : on « shell-out » curl vers 127.0.0.1, sans en-tête d'auth, sans dépendance réseau crate (G10).

Un trait, deux moteurs

trait LocalBackend {
    async fn complete(&self, prompt, params) -> Option<String>;  // None = échec → sentinel
    fn descriptor(&self) -> BackendDescriptor;                    // moteur+modèle+endpoint (N17)
    async fn health(&self) -> bool;                              // sonde rapide
}
  • OllamaBackend (ollama.rs) : POST /api/generate (protocole natif Ollama).
  • OpenAiLocalBackend (openai_local.rs) : POST /v1/chat/completions — couvre llama.cpp-server, vLLM, TGI, LM Studio (et, en mode Network, le routeur frontière).

Le garde-fou souveraineté (G2) et les deux enveloppes

build_local_backend(endpoint, model, allow_remote) :

  1. Refuse l'egress par défaut : si l'endpoint n'est pas local (127.*/localhost/::1) et allow_remote == false → RemoteBackendDenied. Seul le mode Network (egress assumé) passe allow_remote = true.
  2. Choisit le moteur : modèle préfixé openai: ou endpoint contenant /v1 → OpenAI-compat ; sinon Ollama.
  3. Empile la résilience : Breaker(Retrier(moteur)) sur le chemin Network ; Breaker(moteur) en self-host local.

Breaker (circuit-breaker, G3)

Après N échecs consécutifs, ouvre le circuit pour un cooldown : les appels suivants renvoient un sentinel sans toucher au backend (protège l'hôte ; la topologie dégrade au lieu d'empiler les timeouts). Un succès réarme.

Retrier (Network seulement)

Re-tentatives à back-off exponentiel + jitter sur hoquet transitoire d'un appel frontière (réseau). En self-host local, pas de Retrier : un échec sur boucle locale est franc, le Breaker suffit. N17-correct (un seul record final).

La machine d'états du circuit-breaker, en clair

Le but du breaker : ne pas s'acharner sur un backend mort. Il a trois états (comme un disjoncteur) :

  • Fermé (normal) : les appels passent. On compte les échecs consécutifs.
  • Ouvert : après N échecs d'affilée, on « disjoncte ». Pendant un cooldown, les appels suivants renvoient immédiatement un sentinel sans toucher au backend — on arrête d'empiler des timeouts qui satureraient l'hôte. La topologie dégrade proprement (résultat partiel).
  • Réarmement : passé le cooldown, on laisse repasser un appel ; un succès réarme (retour à Fermé), un échec ré-ouvre.

Concrètement : avec un seuil de 5, si un Ollama tombe, les 5 premiers appels échouent (timeout), puis le 6ᵉ et les suivants échouent instantanément (circuit ouvert) au lieu d'attendre 5 timeouts de plus × K agents. C'est ce qui empêche un essaim de geler tout l'hôte quand son modèle est indisponible.

Pourquoi Breaker(Retrier(...)) et pas l'inverse ? Le Retrier épuise ses re-tentatives à l'intérieur d'un appel logique ; le Breaker ne voit donc qu'une défaillance par appel (après épuisement), et ne compte pas chaque petite re-tentative comme un échec distinct. L'ordre des enveloppes est délibéré.

Un test CI (keyless_guardrails) asserte que le SDK n'embarque ni reqwest ni TLS, et ne lit aucune clé / n'envoie aucun en-tête d'auth — la souveraineté vérifiée par la compilation, pas seulement par la doctrine.

§10  La passerelle HTTP & le mode Network (crate efe-swarm-gateway)

La passerelle est mince : elle authentifie (RBAC), résout le mode, délègue au SDK, persiste la preuve, expose la re-preuve. Les routes (lib.rs) :

Le mode Network, concrètement (Inc.4.b)

Le SDK refuse Network in-process (il n'a pas les clés). La passerelle le rend possible en l'interposant un routeur : resolve_mode (state.rs) traduit Network{provider} en SelfHost{endpoint=routeur/v1, model=résolu} avec allow_remote = true — et renvoie le tarif Network à préserver.

Figure 6 — Le mode Network. La passerelle parle OpenAI-compat sans auth applicative ; le routeur injecte la clé. Un nom de modèle n'est pas un secret, donc le mapping vit côté passerelle.

Le mode Network réutilise donc tout le chemin self-host (le OpenAiLocalBackend + le Retrier) — l'égalité d'implémentation est volontaire : un seul code à éprouver. La seule différence est allow_remote = true (egress assumé) et le tarif (5¢ vs 0¢), préservé à travers la traduction.

§11  Déploiement souverain

Le binaire de production (src/main.rs) sélectionne la source de clé de provenance selon l'environnement : EnvHkdf (master lu server-side) si présent, sinon repli test_key() avec avertissement bruyant (le master de test est public → la provenance serait forgeable). Bind 0.0.0.0, arrêt gracieux SIGTERM. Câble store/oidc/pii/routeur depuis l'env.

Figure 7 — Tâche, données et modèle restent sur l'hôte ; seule la preuve sort, re-vérifiable sans clé ni réseau. Défense en profondeur : garde-fou applicatif (egress refusé) + NetworkPolicy cluster.

Deux « clés », deux natures. Les clés provider (qui dépensent de l'argent chez un tiers) ne sont jamais touchées par EFE — en Network, elles vivent au routeur. Le master HKDF (qui prouve, ne dépense pas) est lu server-side et dérive une clé par tenant ; il n'apparaît dans aucun record. La PII (feature, détection locale) caviarde la présentation sans toucher aux records → verify reste exact.
