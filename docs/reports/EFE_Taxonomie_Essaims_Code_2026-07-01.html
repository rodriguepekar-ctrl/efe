« Y a-t-il plusieurs types d'essaim ? » — oui, et pas sur un seul axe : quatre moteurs distincts, plus trois axes de variantes, à des maturités très différentes.
Question simple, réponse qui compte : ce qu'on appelle « l'essaim » n'est pas une implémentation avec des réglages — c'est quatre architectures réellement différentes, développées en pistes parallèles (les numérotations de phases se contredisent dans le code, preuve de tracks distincts). A est stigmergique : des nano-robots se coordonnent par un blackboard à phéromones et pré-mâchent pour de gros LLM. B est topologique : swarm.run(task, topology, budget), des agents qui se passent des artefacts typés — c'est celui que le bench P2 a mesuré. C est un runtime à catalogue : des agents Mode A/B/C (code pur / petit modèle local / LLM), c'est le productisé qu'enveloppe la provenance. D est un méta-essaim : plusieurs essaims convergent sur un consensus latent sans se connaître — mathématique, expérimental. Par-dessus, trois axes de variantes : 7 topologies, 3 modes d'exécution, 5 patterns multi-LLM. Cette multiplicité est de la R&D visible — et un signal de dispersion : la bonne question n'est pas « quel est le meilleur essaim » mais « lequel garde-t-on, mesuré et provenancé ». Ce document fixe la carte pour décider.

§1 La carte : 4 moteurs, 3 axes de variantes

« Type d'essaim » se décline sur deux niveaux qu'il faut distinguer : les moteurs (des architectures d'essaim vraiment différentes — des codebases distinctes) et, à l'intérieur d'un moteur, les axes de variantes (topologie, mode d'exécution, pattern de coordination — des réglages d'un même moteur).

La distinction clé : ne pas confondre un moteur (architecture) avec une topologie (réglage). Il y a 4 moteurs, et l'un d'eux (B) porte à lui seul 7 topologies.

§2 Les 4 moteurs — les vrais « types »

A · L'essaim stigmergique (« nano-robots »)

Crates : efe-nano-app-coordinator (6 nano-robots : analyzer, reformulator, compressor, verifier, filter, router) → efe-coordinator → efe-multi-llm. Principe : les nano-robots ne s'appellent pas — ils se coordonnent en déposant des traces sur un blackboard à phéromones (PheromoneBlackboard, stigmergie bornée 256 Ko, « SwarmSys-inspired »), et leur rôle est de pré-mâcher pour de gros LLM (mission A) ou de servir de substrat d'info entre N gros LLM (mission B, vote pondéré « Symphony »). Ce qui le distingue : le petit sert le gros ; la coordination est indirecte (phéromones), pas par messages typés.

B · L'essaim topologique (« swarm-SDK »)

Crates : efe-swarm-sdk · efe-swarm-topology · efe-blackboard · efe-swarm-memory. Principe : swarm.run(task, topology, budget) lance un essaim vérifiable, plafonné en coût, re-prouvable — des agents qui se passent des artefacts typés selon une topologie choisie, avec une provenance auto-câblée (un provenance_root re-vérifiable par un tiers). Ce qui le distingue : c'est le mesuré — mon bench P2 (portes ①/②) l'a piloté directement (GenerateVerify, Consensus). C'est l'essaim que le programme sait chiffrer et re-prouver.

C · Le runtime à catalogue (« Nano Agent » M50)

Crates : efe-nano · efe-swarm-orchestrator · efe-nano-preanalysis · efe-nano-swarm-adapter. Principe : un catalogue d'agents typés + un dispatcher, exécutés en trois modes (A/B/C, §3), orchestrés par un DAG déclaratif de pré-analyse (scheduling par couches, timeouts par-agent). Ce qui le distingue : c'est le productisé — l'adaptateur pose les gardes de politique (signature, gold, idempotence) et c'est ce runtime que la provenance P1 enveloppe (chaque dispatch = un événement d'audit).

D · Le méta-essaim (« essaim d'essaims »)

Crates : efe-meta-swarm (+ -proto / -server). Principe : plusieurs essaims indépendants convergent sur un consensus latent partagé — un espace de méta-consensus (espace de Hilbert), avec des opérateurs Lift (espace agent → méta) et Pull (méta → agent), un MetaOperator, une projection de sûreté, et une itération couplée jusqu'à convergence — sans qu'aucun essaim connaisse l'état interne de l'autre. Ce qui le distingue : ce n'est pas « des agents qui se parlent », c'est une géométrie de consensus. Statut : expérimental (MockParticipant ; l'adaptateur réel LocalParticipant est différé).

La distinction qui compte. A, B, C, D ne sont pas quatre réglages — ce sont quatre façons différentes de faire coopérer des agents : par phéromones (A), par messages typés + topologie (B), par catalogue + DAG (C), par consensus latent (D). Confondre « on a un essaim » avec « on a quatre essaims » est précisément l'erreur que cette carte évite.

Attention au recouvrement. Les topologies (axe 1, moteur B) et les patterns (axe 3, moteur A) se ressemblent (Vote≈Consensus, Relay≈Pipeline, Debate≈Debate, Specialist≈Hierarchical, Cascade≈Speculative). Ce n'est pas une redondance de conception — ce sont deux moteurs différents qui ont chacun ré-implémenté un vocabulaire proche. C'est exactement le symptôme de pistes parallèles (§4).

La preuve de pistes parallèles. Deux indices, tous deux dans le code : (1) les numérotations de phases se contredisent — le « Phase 2 » de efe-coordinator (DAG nano-robots) n'est pas le « Phase 2 » de efe-swarm-topology (topologies) ; (2) le vocabulaire est ré-implémenté (Vote/Debate/Specialist existent des deux côtés). Ce ne sont pas des bugs — c'est la trace d'une idée explorée en plusieurs architectures, ce qui est sain en R&D mais coûteux à maintenir en produit.

Le risque : la dispersion. Quatre moteurs d'essaim, c'est le même signal que les huit produits du portefeuille : de la profondeur réelle, mais un coût de maintenance et une lisibilité qui se dégradent. Pour un produit — et pour un board — porter quatre essaims qu'on ne peut pas tous mesurer/provenancer est un passif, pas un actif.

§5 La recommandation de consolidation

Garder deux, archiver deux. La question n'est pas « quel est le meilleur essaim » — c'est « lequel garde-t-on, mesuré et provenancé ». La réponse suit la maturité :

✅ Garder B (topologique) — le seul mesuré (bench P2), re-prouvable, à provenance auto-câblée. C'est l'essaim que le programme sait chiffrer.

✅ Garder C (runtime à catalogue) — le productisé, celui que la provenance P1 enveloppe, avec les gardes de politique.

📦 Archiver A (stigmergique) et D (méta-essaim) comme R&D — déjà figés/expérimentaux ; les ressortir seulement si un besoin précis les tire (le stigmergique pour un cas où la coordination indirecte paie ; le méta-essaim si l'on prouve un jour la valeur du consensus latent).

Le lien avec la leçon P2 / MoE — décisif

La mesure de P2 a montré qu'un MoE bon marché peut battre un essaim de petits modèles + routeur sur le coût brut. Cette leçon s'applique identiquement aux quatre moteurs : quelle que soit l'architecture d'essaim, elle n'est justifiée — face à un MoE — que par ce qu'un modèle unique ne peut pas offrir : la provenance et la souveraineté par-agent, l'hétérogénéité multi-fournisseur, la spécialisation extrême. Autrement dit : le moteur d'essaim qu'on garde doit être celui qui maximise ces propriétés, pas celui qui promet le coût le plus bas — et c'est exactement B (mesuré + provenancé) et C (productisé + provenancé).

La conclusion, en une ligne. Il y a bien plusieurs essaims dans le code — quatre moteurs, trois axes de variantes. Ce n'est pas un problème tant qu'on choisit : consolider sur les deux mesurés/provenancés (B + C), archiver les deux expérimentaux/anciens (A + D), et se rappeler que la valeur d'un essaim n'est jamais le coût brut (un MoE le bat) mais la confiance par-agent qu'aucun modèle unique ne donne.
