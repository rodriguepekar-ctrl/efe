TL;DR ingénieur — dix affirmations, chacune falsifiable en salle

Chaque claim est formulé pour être attaqué. « Falsifier » indique le geste concret qui le réfuterait — c'est aussi le protocole de la démo. Si l'un de ces gestes échoue, le claim tombe, et nous préférons le savoir devant vous.

Toute étape d'orchestration — sur les trois tiers — se re-prouve hors-ligne, sans nous. Chaîne HMAC-SHA256 par étape, bundle auto-porteur, vérification par recalcul intégral.

Falsifier : prenez un bundle, flippez un octet arbitraire, relancez verify_meta_mini air-gap → doit sortir exit 1 avec l'étape fautive localisée. Sinon, le claim est mort.

Le vérifieur a un arbre de dépendances d'exactement une ligne. std-only, zéro crate externe — la surface d'audit est le fichier que vous lisez.

Falsifier : cargo tree sur verify-mini. Plus d'une ligne → mort.

La clé de scellement n'est jamais sérialisée dans un bundle. Clé par tenant (dérivation HKDF), signature côté serveur ; le bundle contient les records scellés + la source du vérifieur, jamais le secret.

Falsifier : inspectez un bundle produit par forensic-export — cherchez le matériau de clé. Présent → mort.

Même les agents silencieux sont dans la preuve. Les workers Rust purs (Mode A) qui n'émettent aucun texte sont hachés dans des chaînes par agent, agrégées en un provenance_root par run.

Falsifier : inspectez les chaînes per-agent d'un run contenant des agents Mode A muets ; absence → mort.

La provenance n'altère pas le calcul. L'observateur est hors du chemin de calcul (« crypto-free observer ») ; la non-interférence est testée : résultats byte-identiques avec et sans capture.

Falsifier : exécutez la suite de non-interférence ; le moindre octet de divergence → mort.

Le consensus méta converge même depuis une graine hostile. Projection non-expansive sur un ensemble admissible déclaré (boîte/polyèdre) ; l'écart de correction safety_delta = ‖z − z̃‖ est scellé à chaque pas.

Falsifier : lancez la démo safety_violation_attempt — l'état adversarial doit être ramené dans les bornes, écart scellé. Divergence → mort.

Tout run passé se rejoue octet-identique. Les appels LLM sont scellés puis rejoués depuis le record (pas re-générés) ; les pas déterministes se ré-exécutent.

Falsifier : rejouez un run archivé, comparez les sorties octet par octet.

La conformité est sur le chemin de requête, fail-closed. Un flag (experimental_fast → tier1_strict) exige les contrôles N17/N18/N19 par requête ; contrôle manquant = requête refusée, pas loggée-quand-même.

Falsifier : flippez le flag, soumettez une requête sans contrôle — si elle passe, mort.

L'effacement RGPD ne casse pas la chaîne. Tombstone haché à la place de la donnée ; verify_chain / verify_subchain re-prouvent autour du trou.

Falsifier : tombstonez un record d'une chaîne archivée, re-prouvez. Échec de vérification → mort.

Nos chiffres de science se re-calculent chez vous. ~1 200 runs re-jouables (harnais livré) — y compris le résultat qui réfute notre propre thèse de routage.

Falsifier : re-exécutez le harnais sur vos machines/modèles ; si les effets ne se retrouvent pas sur nos données, mort.

Ce que ce document n'est pas

Ce n'est ni une spec complète ni la doc d'API — c'est l'argumentaire du deck, densifié au niveau ingénieur, avec le vocabulaire exact du code (noms de crates, d'endpoints, d'invariants testés) pour que votre due diligence puisse commencer pendant la lecture. Les limites et chantiers sont en §8 — avant la conclusion, pas en note de bas de page.

1 · La thèse, formulée en frontière de confiance

Monter un graphe d'agents est résolu — LangChain, CrewAI, AutoGPT et consorts l'ont commoditisé, et la chute continue du prix des tokens fait le reste. La conséquence structurelle intéresse davantage : quand l'orchestration ne différencie plus, la question migre vers la vérifiabilité de ce qu'elle a produit. Et là, l'état de l'art a un angle mort précis, qui se décrit proprement en termes de trusted computing base (TCB).

Les plateformes d'observabilité LLM existantes (traces, evals, dashboards) sont utiles, mais elles partagent toutes la même frontière : la vérification s'exécute dans le périmètre de confiance du vendeur. Vous regardez leur UI, interrogez leur API, faites confiance à leur stockage — la TCB inclut le vendeur, son stack, et le canal réseau. Pour un usage interne, c'est acceptable. Pour un artefact opposable — celui qu'un régulateur ou une contrepartie doit accepter — c'est une pétition de principe : « croyez le dashboard ».

La boucle de re-preuve — mécanique exacte

(1) Capture. Chaque action d'agent produit un record structuré — l'atome est l'AgentCallRecord : qui, quoi, quand, à partir de quels inputs — empreinté (BLAKE3 + SHA-256) puis scellé dans une chaîne HMAC-SHA256 où chaque maillon couvre le digest du précédent. Les clés de scellement sont par tenant, dérivées via HKDF ; elles signent côté serveur et ne quittent jamais ce périmètre. (2) Export. forensic-export produit un bundle auto-porteur : records scellés + la source du vérifieur vendorée. La clé n'y figure jamais — le destinataire peut tout vérifier, rien contrefaire. (3) Recompilation. Le destinataire audite la source (elle est volontairement minuscule), la recompile (verify-mini : std-only, arbre de dépendances = une ligne) et coupe le réseau. (4) Recalcul. Le vérifieur recompute chaque maillon : exit 0 = intact ; exit 1 = altéré, étape localisée. Les primitives sont écrites à la main — précisément pour tenir la propriété zéro-dépendance — et prouvées contre les vecteurs officiels : SHA-256 sur FIPS 180-4, HMAC sur RFC 2104.

Modèle de menace — ce qui est couvert, ce qui ne l'est pas

Couvert. Altération a posteriori d'un résultat stocké (détectée + localisée) ; insertion/suppression de maillons (la chaîne casse) ; falsification par un tiers ne détenant pas la clé (HMAC infalsifiable) ; vendeur malhonnête au moment de l'audit (il n'est plus dans la TCB : le vérifieur est recompilé, le réseau coupé) ; vérifieur truqué (vous le recompilez depuis une source lisible — ou en réécrivez un depuis le format documenté).

Non couvert, dit franchement. (a) Le détenteur de la clé peut sceller une histoire falsifiée au moment de l'écriture — le scellement prouve l'intégrité depuis le scellement, pas la véracité de l'observation initiale ; mitigations : bundles déjà remis (la copie du régulateur est chez le régulateur — irrévocable), rotation par tenant, identités d'éditeur signées (N18). (b) La correction des décisions : le système atteste ce qui s'est passé, jamais qu'une décision était bonne ou conforme — les couches de qualité (gold-gates N19, juges-oracles) s'empilent au-dessus, et la conclusion « conforme » appartient au juriste (reg-evidence n'a volontairement pas de champ compliant). (c) Les canaux d'attribution : exit 1 dit quoi et où, pas qui ni pourquoi — l'attribution vient de vos logs d'accès, la chaîne fournit l'ancre.

Pourquoi de la crypto écrite à la main — la réponse complète

Réflexe légitime : « ne réécrivez jamais vos primitives ». La contrainte produit ici est inhabituelle : un vérifieur qu'un tiers hostile à votre convenance peut auditer intégralement et recompiler sans rien tirer du réseau. Chaque dépendance (OpenSSL, ring…) rajoute un tiers de confiance et des milliers de lignes non-auditables dans la TCB du vérifieur. Le choix : primitives réimplémentées, prouvées sur les vecteurs officiels (FIPS 180-4, RFC 2104), assez petites pour être lues en entier — 8 crates, 224 tests sur le socle. La revue adversariale interne du chemin de provenance a trouvé et corrigé 21 bugs — dont un « dishonest green » (un chemin de vérification qui répondait succès à tort) et une fuite de PII dans l'API d'audit ; un audit externe est un livrable de pilote que nous demandons, pas que nous subissons. La vérification formelle des primitives est l'étape de durcissement naturelle — bienvenue dans le partenariat.

2 · Tier 1 — efe-nano, le runtime B2A

Le tier d'exécution. Le pari architectural : plutôt qu'un modèle frontière monolithique appelé cent fois, décomposer en workers spécialisés à déterminisme fort, isolés selon le risque, et scellés par construction. Le crate pèse ~51 000 lignes / 1 175 tests — c'est le composant le plus ancien et le plus couvert du système. Ce qui suit est ce qu'un ingénieur doit savoir pour l'attaquer correctement.

2.1 Trois modes d'exécution, par frontière d'isolation

ModeExécutionLatence typiqueDéterminismeScellement
ARust pur, in-process~1–10 mspar construction (même entrée → même sortie)chaîne per-agent, y compris sans aucune sortie texte

La ligne à retenir sur le Mode C, parce que c'est là qu'on nous attend : on ne prétend pas rendre un LLM déterministe. On contraint sa sortie (schéma strict — le parsing défensif disparaît en aval), on scelle l'appel complet (prompt, réponse, coût, horodatage) dans un record N17, et le replay rejoue depuis le record — il ne re-génère pas. Le non-déterminisme du modèle est encapsulé dans une frontière prouvable, pas nié.

2.2 Scheduling et coût

L'orchestration intra-run est un dispatcher DAG (tri topologique de Kahn) : les étapes indépendantes s'exécutent en parallèle, les étapes Mode A restant dans la milliseconde — le coût wall-clock d'un pipeline est dominé par ses appels modèle, jamais par la plomberie. Cache Redis à deux niveaux : réponses LLM et embeddings. C'est l'implémentation concrète de l'argument « faster, cheaper » du deck ; le chiffrage honnête de « combien moins cher » est renvoyé à la couche mesure (§7), pas affirmé ici.

2.3 La chaîne d'audit — sémantique exacte

L'atome est l'AgentCallRecord (qui / quoi / quand / à-partir-de-quoi), digest BLAKE3 + SHA-256, scellé HMAC en chaîne. Trois propriétés utiles en contexte réglementaire, chacune testée : (i) notarisation par époques Merkle — les records sont agrégés en arbres par lots, ce qui borne le coût de notarisation et permet d'ancrer des archives ; (ii) tombstones RGPD — l'effacement remplace la donnée par son empreinte, et verify_chain re-prouve la chaîne autour du trou : suppression ≠ rupture, le conflit RGPD-vs-audit est résolu structurellement, pas par une dérogation ; (iii) verify_subchain — on peut extraire et remettre une tranche re-prouvable à un tiers, sans exposer le reste de l'historique. La granularité de divulgation est un objet de première classe.

2.4 Gouvernance des capacités — le plan de contrôle

Une capacité n'est pas un prompt : c'est une entrée de catalogue signée, versionnée, gold-testée. Le cycle de vie est porté par trois primitives : N18 — identité d'éditeur Ed25519, KYC à 4 niveaux, révocation en cascade (les dépendants d'une capacité révoquée sont déschedulés, l'historique reste dans la chaîne) ; N19 — gold-gate à 3 stratégies d'évaluation, dont le contournement n'existe que signé ; N24 — le câblage qui met tout cela sur le chemin de requête, fail-closed (§9). Conséquence opérationnelle : « quelle version exacte a tourné en mars ? » est une requête, et « rien ne change sans une modification signée » est un invariant, pas une politique RH.

3 · Tier 2 — le SDK d'essaim et son gateway

Le tier de composition. Surface d'API volontairement minimale : swarm.run(task, topology, budget) — une tâche, une forme de collaboration, un plafond dur. Le budget est un cap coût/tokens par run, appliqué comme invariant d'exécution : c'est de la gouvernance (l'agent emballé s'arrête), pas de la facturation.

Implémentation : les topologies sont génériques sur des traits — donc composables (un lead hiérarchique peut exécuter du generate-verify dans chaque branche) et extensibles sans toucher au cœur. Le choix de forme est une donnée d'entrée, pas une architecture à re-livrer.

3.2 La provenance exposée sur le fil

Le différenciateur du tier : chaque agent — y compris les workers Mode A qui n'émettent aucun texte — alimente une chaîne de hachage per-agent ; les N contributions d'un run s'agrègent en un provenance_root unique. Et le moat est exposé comme un endpoint : GET /verify/:id re-prouve n'importe quel run stocké côté serveur — la clé de signature ne quitte jamais le serveur — et rend un verdict binaire avec, en cas d'altération, l'étape fautive. L'intégration audit d'un client se résume à ce GET ; la version « sans accès du tout » passe par l'export de bundle (§1). Les appels Mode C rejoignent la même preuve via le pont N17.

3.3 Le stack — et la posture souveraineté par défaut

Gateway axum ; persistance Postgres write-once (les runs stockés ne se réécrivent pas, ils s'ajoutent) ; authentification OIDC ; rédaction PII sur le chemin d'ingestion. Et le choix de posture qui compte pour vos clients régulés : keyless / self-host par défaut — aucun compte cloud requis, air-gap possible — avec une garde de souveraineté qui refuse par défaut tout egress non-loopback ; les backends externes (Mode C) sont un opt-in explicite par allow-list. Cette garde a été durcie contre les contournements de classe SSRF lors de la revue adversariale interne. La donnée ne sort pas par accident ; elle sort par décision.

3.4 Blackboard, observabilité, replay

Le substrat de coordination est un blackboard stigmergique durable — les agents coordonnent par l'environnement partagé plutôt que par messages point-à-point, et cet environnement est l'enregistrement : c'est ce qui rend le rejeu structurellement possible, pas un feature bolt-on. Au-dessus : un dashboard temps réel en SSE, implémenté comme observateur sur les seams — hors du chemin de calcul, donc sans effet sur les résultats (même invariant de non-interférence que la provenance méta, §4) ; vos propres outils peuvent s'abonner au même flux. La mémoire partagée est elle-même scellée (memory_root). Le rejeu est octet-identique : pas déterministes ré-exécutés, appels LLM rejoués depuis leurs records — un litige fournisseur se re-tranche à l'identique, deux ans plus tard, avec les versions épinglées par le catalogue (§2.4).

Ce qu'un ingénieur devrait challenger ici

Les bonnes questions à nous poser en séance : la sémantique exacte du write-once sous migration de schéma ; le comportement du budget-cap en vol (arrêt propre vs abandon) ; la granularité de la rédaction PII ; le coût de stockage des chaînes per-agent sur de gros runs (réponse courte : digests et références, pas de copies — et notarisation par époques). Nous préférons ces questions à huis clos technique qu'en comité — c'est exactement l'objet du pilote.

4 · Tier 3 — le méta-essaim : consensus latent sous enveloppe prouvée

Le tier rare — celui qui n'a pas d'équivalent direct sur le marché. Problème posé : N essaims indépendants (équipes, filiales, contreparties) doivent produire une réponse commune sans mutualiser leurs données ni leurs modèles, et sans qu'aucun participant ne puisse pousser la décision hors d'un cadre déclaré. Le moteur pèse ~213 tests ; les structures sont petites, la valeur est dans les invariants.

4.1 Le consensus latent — lift / pull

Chaque essaim « lift » son état interne dans un méta-espace partagé de dimension 256 — une contribution latente compacte, pas ses records. L'opérateur de consensus qui agit dans cet espace est non-divergent ; le résultat est « pull » — redescendu chez chaque participant. Ce qui transite entre les parties : des vecteurs latents scellés. Ce qui ne transite jamais : données brutes, poids de modèles. La dimension 256 est un choix d'ingénierie (assez pour porter de la structure, assez peu pour rester rapide) — un paramètre, pas un dogme.

Posture de confidentialité — sans sur-vente

Ce n'est ni du MPC ni du chiffrement homomorphe — plus simple et moins cher : la confidentialité est architecturale (ce qui voyage est un résumé compact, et chaque échange est scellé et borné par l'enveloppe). Question légitime d'un pro : « que peut-on inverser depuis le vecteur latent ? » Réponse honnête : c'est un résumé 256-dim, pas des records ; la résistance à l'inversion est un objectif de conception, et son red-teaming est un excellent exercice de pilote — nous le proposons plutôt que de l'esquiver.

4.2 L'enveloppe de sûreté — la garantie mathématique

Les bornes de la décision collective sont déclarées comme politique : un ensemble admissible (boîte ou polyèdre) dans le méta-espace. À chaque pas, l'état consensuel est projeté sur cet ensemble par une projection non-expansive — d'où deux propriétés démontrables plutôt qu'espérées : la projection ne peut pas amplifier un écart, et la convergence est garantie y compris depuis une graine hostile (essaim empoisonné, contribution adversariale). L'écart de correction safety_delta = ‖z − z̃‖ est scellé à chaque pas — un clamp n'est jamais silencieux : une bande de politique trop serrée se lit dans les données, au lieu de biaiser en douce. Démo adversariale dédiée : safety_violation_attempt. Traduction contractuelle, telle que le deck la vend : « aucun fournisseur ne sera jamais auto-scoré hors de votre bande de politique » — c'est une clause, pas un vœu.

NiveauCe qui est scelléCe que ça permet de prouver

Trois invariants d'implémentation. (i) L'observateur de provenance est crypto-free et hors du chemin de calcul ; la non-interférence est testée : résultats byte-identiques avec et sans capture — l'instrumentation ne change pas les nombres. (ii) Le niveau se choisit par run : on dose la preuve selon l'enjeu, v1 pour l'exploratoire, v3 pour le contesté. (iii) Deux vérifieurs indépendants — verify_meta (pratique) et verify_meta_mini (zéro-dépendance, recompilable) — croisés octet par octet : le vérifieur de confort et le vérifieur de confiance se contrôlent mutuellement.

Démo phare, nommée pour l'audience : three_swarms_kovant — trois essaims procurement (scoring fournisseur, risque contractuel, catégorisation de dépenses) convergent sous enveloppe, provenance native, re-preuve offline en sortie. Statut honnête du tier : c'est la frontière du système — tournant, testé, démontrable aujourd'hui ; où il gagne sa place en production est précisément une question de pilote, pas un fait accompli.

5 · Le sidecar Scout & Synthesize — la preuve par les modèles frontière

Rôle dans l'argumentaire : démontrer que le socle de confiance tient aussi quand les modèles sont Claude, GPT et Gemini — pas seulement des composants locaux. C'est une application réelle qui coordonne les trois via le tier nano, derrière des adaptateurs provider-agnostiques.

Le point techniquement intéressant : la conformité de sortie par construction. Pour les modèles locaux, la sortie est contrainte par une grammaire GBNF appliquée au décodage — le JSON conforme n'est pas « très probable », il est le seul émissible ; pour les appels frontière (où l'on ne contrôle pas le décodeur), validation stricte de schéma + record scellé par appel. La différence avec le function calling, formulée pour un pro : le function calling est une convention que le modèle honore presque toujours ; une grammaire au décodage est une contrainte, pas une convention — et en aval, le parseur défensif disparaît.

Cinq workflows de collaboration — Vote (Borda / Condorcet), Relay, Debate, Specialist, Cascade — sur trois types de mission ; piste d'audit HMAC/BLAKE3 au format figé v1.0.0 ; et un invariant testé qui répond d'avance à la question lock-in : anti-monoculture — aucun fournisseur unique ne peut dominer une mission, le swap de provider est une configuration.

6 · Grounding et plateforme — les fondations qu'on ne pitche pas

6.1 Le plan de connaissance (~250 tests / 5 crates)

Les agents raisonnent sur vos corpus, pas sur la mémoire du modèle : retrieval hybride BM25 + dense fusionné par RRF ; index vectoriel HNSW ; graphe de connaissances (entités, relations, traversées) ; GraphRAG avec planificateur multi-hop ; ingestion multimodale (documents scannés). Embeddings enfichables, local-first — cohérent avec la posture keyless/self-host. L'exemple qui parle à un ingénieur ET à un acheteur : « quels fournisseurs partagent un bénéficiaire effectif ultime ? » est une requête de traversée de graphe — invisible pour du plein-texte, naturelle ici, et le résultat entre dans la même chaîne de preuve que le reste.

7 · La couche mesure — résultats, y compris ceux qui nous coûtent

Un système qui vend de la preuve doit s'appliquer sa propre discipline. Tout ce qui suit sort d'un harnais de mesure rejouable (~1 200 runs, modèles locaux via Ollama) qui est livré avec le produit — l'argument n'est pas « croyez ces chiffres », il est « re-calculez-les sur votre tâche ».

7.1 Les trois résultats principaux

(i) La spécialisation paie plus que la taille. Instruire correctement un petit modèle sur une tâche étroite l'a fait passer de 40 % à 75,3 % — un levier supérieur, sur cette tâche, au passage à un modèle plus gros. (ii) Un petit mixture-of-experts a battu notre propre routeur d'essaim sur le coût. Résultat publié tel quel — il réfute notre thèse de départ, et c'est précisément pour ça qu'il est crédible. (iii) Une loi de bascule dit quand l'essaim vaut le coup : C > K/(1−f), où C est le ratio de coût gros/petit modèle, K le nombre d'échantillons de diagnostic, f la fraction d'escalade vers le gros modèle. Grand C, petit f → l'essaim gagne ; sinon, il perd, et la loi le dit aussi.

Le mot interdit

À aucun moment nous ne prétendons « small beats big » — c'est faux en général, et c'est réfutable en une slide. La position est : la couche de mesure et de preuve qui vous dit quelle architecture gagne sur votre tâche. Face à une équipe qui a parié sur les SLM-swarms, c'est un cadeau, pas un désaccord : la loi de bascule transforme leur pari en décision instrumentée.

7.2 Les résultats négatifs — l'arc « aggregation ne suffit pas »

Deux campagnes internes (série HB), menées sur une cellule difficile modèle×tâche (petit modèle × math), pour tester une hypothèse tentante : « un bon agrégateur rattrape un modèle bruité ». Verdict : non — et le détail vaut la peine pour un pro. HB.3 : un vérifieur déployable par ré-exécution arithmétique atterrit sous la simple self-consistency à n=50 — 92 % contre 94 % : l'écart résiduel est un problème de modélisation, pas de calcul. HB.4 : les agrégateurs de synthèse (médiane, moyenne tronquée, médiane pondérée par audit) plafonnent ≤ 85 % (la fusion tombe à 70 %), parce que les erreurs sont systématiquement biaisées (skew mesuré +8,72) — elles ne s'annulent pas, elles tirent d'un côté. Conclusion assumée : sur cette cellule, aucune agrégation déployable ne comble l'écart — c'est un écart de modèle. La leçon vendue à Kovant : mesurer d'abord, architecturer ensuite ; c'est exactement ce que le harnais outille.

7.3 La limite du consensus — et son option de correction

Limite structurelle, dite en face : un consensus mesure l'accord, pas l'exactitude — dix agents peuvent se tromper unanimement, et un apprentissage qui crédite l'accord peut renforcer l'erreur unanime. Deux réponses dans le système : quand une vérité terrain existe, un juge-oracle de correction peut siéger dans le panel (opt-in) et casse ce biais ; et la provenance, par construction, ne certifie jamais « right » — seulement « what happened, provably ». Nous poursuivons par ailleurs des campagnes de caractérisation (harnais « Terrain », 118 tests) pour cartographier où les architectures d'essaim récupèrent réellement de la valeur — premiers sondages exploratoires inclus quand ils sont négatifs. Un fournisseur qui documente les conditions d'échec de sa propre approche est un fournisseur dont les conditions de succès signifient quelque chose.

10 · Le protocole de pilote — et l'échelle absorbée

10.1 Deux semaines, protocole d'acceptation falsifiable

Entrée : une tâche procurement réelle, choisie par vous (candidates immédiates : scoring fournisseur · approbation de clause · onboarding vendeur). Sortie : le workflow livré en bundle re-prouvable + le vérifieur zéro-dépendance. Acceptation — le protocole tient en quatre gestes : vos ingénieurs auditent la source du vérifieur (une après-midi), cargo tree (une ligne), recompilent, coupent le réseau ; re-preuve du run livré (exit 0) ; puis flip d'un octet arbitraire dans le bundle et re-preuve (exit 1, étape localisée). Si l'un de ces gestes échoue, le pilote a échoué — prouvablement, et vous gardez l'évidence. Zéro intégration côté Kovant pour ce premier tour ; votre clavier, nos instructions, si vous préférez conduire.

Catalogue exécutable (tout tourne sur un laptop, air-gap) : three_swarms_kovant · meta_provenance → verify_meta_mini (le flip-byte) · gateway /verify · efe-claude-smoke (N17 sur appel frontière réel) · missions du coordinator · preview-server · publisher/gold verify.

10.2 L'échelle — et pourquoi l'absorption est le bon modèle

Le périmètre agentique : ~31 crates · ~5 200 tests · ~258 000 lignes de Rust, au sein d'un workspace de 65 crates — le reste étant la plateforme (§6.2). Techniquement, c'est un workspace de crates composables : l'absorption se découpe proprement — les trois tiers deviennent votre IP, le substrat de confiance voyage dessous comme garantie, la plomberie suit là où elle sert votre stack. Et l'argument de sûreté de l'absorption est le produit lui-même : vous re-vérifiez ce que vous absorbez — chaque affirmation de ce document a un test, une démo ou un chiffre re-calculable derrière elle, et la suite de tests est le contrat de vérité du système, pas une métrique de couverture.

La phrase de fin — la même qu'en salle

Proof, not promise : une tâche, deux semaines, un bundle — et vous n'avez à nous croire sur rien, parce que le système est construit pour que vous n'ayez pas à le faire.
