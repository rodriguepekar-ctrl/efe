Architecture · avant code · borner les runs sur trois axes

Admission & Deadline

Trois plafonds, un principe : concurrence, temps, coût — borner visiblement, sceller le partiel.
Un run EFE est borné en coût (le BudgetGuard atomique, I13 — OnExceed::Stop) et en concurrence (l'admission process d'ADR-014 CP-2 : un sémaphore global FIFO, 429 + Retry-After quand la passerelle est pleine). Mais il manque le troisième plafond — le temps : rien ne borne la durée wall-clock d'un run, et un agent lent ou un backend qui traîne peut produire un run zombie qui tient un permis d'admission indéfiniment. Et l'admission, aujourd'hui globale, laisse un seul tenant monopoliser tous les permits (ADR-014 a explicitement laissé la fairness par-tenant ouverte). Ce document complète la gouvernance des runs : ① admission équitable (aucun tenant n'affame les autres) sur tous les chemins de run ; ② un deadline par run — le jumeau temporel du budget : une sonde coopérative (comme BudgetProbe) qui arrête l'essaim entre vagues et scelle la provenance partielle (toujours vérifiable), doublée d'un backstop tokio::timeout dur contre les hangs. Et — honnêteté héritée d'ADR-017 — un run tronqué par deadline est re-prouvable (R0) mais non reproductible (R1) : le point de troncature est wall-clock, donc hors du moat.

§1 Le problème — un run non borné est une ardoise ouverte

Un run d'essaim consomme trois ressources : du CPU/concurrence (les agents en parallèle), du temps wall-clock (la durée jusqu'au verdict), et de l'argent (les appels LLM payants en Mode C). Le système borne déjà deux des trois — le coût (BudgetGuard) et la concurrence (l'admission process). Le temps reste une ardoise ouverte, et l'admission, globale, a un angle mort de fairness.

1.1 — Le temps n'est borné nulle part — le run zombie

Rien ne plafonne la durée d'un run. Un agent Mode A peut entrer dans une boucle pathologique ; un backend self-host (Ollama) ou le routeur Network peut traîner, se bloquer, ou répondre au goutte-à-goutte. Le run continue alors d'occuper un permit d'admission (ADR-014) sans limite de temps — un run zombie qui ne rend jamais son permit. Quelques zombies suffisent à saturer le cap d'admission : la passerelle commence à répondre 429 à des requêtes parfaitement légitimes, non par charge réelle, mais parce que des runs morts-vivants tiennent les places. Le budget ne sauve pas : un run peut être lent sans être cher (Mode A keyless = 0¢, mais potentiellement long), ou cher-mais-bloqué (un appel LLM qui pend avant de facturer). Le temps est une dimension orthogonale au coût, et elle n'a pas de garde.

1.2 — L'admission est globale — la monopolisation par tenant

L'admission process (state.rs : admission: Arc<Semaphore>) est un sémaphore global FIFO : un seul compteur de permits pour toute la passerelle, tous tenants confondus. ADR-014 l'a posé comme une borne process honnête — mais a explicitement laissé ouverte la fairness par-tenant (« les tiers/files par tenant restent ouverts »). Conséquence : un tenant qui lance une rafale de runs peut consommer tous les permits et faire passer tous les autres tenants en 429. Le backpressure est visible (bien), mais il n'est pas équitable : la famine d'un tenant par un autre est possible. Pour une passerelle multi-tenant, c'est un trou de gouvernance.

1.3 — Pourquoi un tokio::timeout naïf détruit la preuve

La tentation, pour le deadline, est d'envelopper run_traced dans un tokio::time::timeout et de laisser tomber le futur à l'échéance. C'est faux pour EFE. run_traced (sdk.rs) exécute la topologie, PUIS scelle la provenance (recorder.seal_with_key) — le scellement est la dernière étape. Si l'on drop le futur au milieu, on perd le recorder, les AgentCallRecord capturés, et donc toute trace du run : pas de provenance_root, rien à vérifier, rien à rejouer. Un timeout dur naïf transforme un run lent en trou noir — l'opposé du moat. Le deadline doit donc être coopératif : l'essaim doit cesser d'émettre du travail à l'échéance, finaliser ce qu'il a, et laisser run_traced sceller la provenance partielle — qui reste un run vérifiable, juste tronqué.

Le gap en une phrase. Le temps n'est borné nulle part (run zombie), et l'admission globale laisse un tenant en affamer d'autres. Il faut un deadline coopératif (qui scelle le partiel, pas un timeout qui détruit la preuve) et une admission équitable — les deux plafonds manquants de la gouvernance des runs.

§2 État des lieux — ce qui borne déjà, ce qui manque

2.1 — Le coût : Budget/OnExceed + la sonde coopérative

Le coût est borné par un BudgetGuard atomique (invariant I13) avec trois politiques (budget.rs) : Error (pré-vol : refuse si le coût estimé dépasse le plafond), Degrade (pré-vol : réduit K et rogne les juges pour tenir), et Stop (en vol : facture chaque appel, et à l'épuisement les agents cessent). Le mécanisme de Stop est exactement le patron que le deadline réutilisera : une sonde coopérative. La taille adaptative (ADR-014) consulte une BudgetProbe = Arc<dyn Fn(usize) -> bool> (sizing.rs) entre les vagues — run_waves_pure n'émet une vague que si la sonde dit « tu peux la payer ». Quand le budget est épuisé, la boucle s'arrête, k_used < k_max, et le run finalise proprement sur ce qu'il a généré. C'est un arrêt propre et scellé, pas un crash.

2.2 — La concurrence : l'admission process (ADR-014 CP-2)

L'admission (state.rs) est un Arc<Semaphore> de admission_max permits. Chaque handler de run fait s.admission.clone().try_acquire_owned() en tête ; un échec renvoie 429 + Retry-After et incrémente admission_rejected. Le permit (FIFO, owned) suit le run jusqu'à sa fin (tenu dans la tâche du job pour les runs asynchrones). Les jauges /metrics exposent inflight = max − disponibles, inflight_max, et admission_rejected_total. C'est du backpressure visible — la doctrine ADR-014 : « refuser vite plutôt qu'une file invisible qui finit en timeouts ». Déjà gardés : POST /run (sync ET job), et POST /replay/:id R1 (ajouté en ADR-017 — la re-exécution est un run en vol). Manque : la fairness par-tenant (le sémaphore est global).

2.3 — Le temps : seulement des timeouts par-batch (T2/T3), pas de deadline run

Le seul mécanisme temporel existant est un timeout: Duration au niveau des batches de sous-tâches des topologies T2 (pipeline) et T3 (hierarchical) — pipeline.rs : run_batch(inputs, timeout), hierarchical.rs : défaut 30 s. Il borne le temps d'une vague de sous-tâches, pas le run entier. Il n'y a aucun plafond wall-clock au niveau du run, ni de champ deadline sur la requête, ni de statut « tronqué par le temps ». C'est précisément la pièce neuve.

§3 La thèse — trois plafonds, un principe

3.1 — Le deadline est le jumeau temporel du budget

La thèse centrale : le temps se borne exactement comme le coût. Le budget a un BudgetGuard (état atomique : dépensé / plafond) et une BudgetProbe (« puis-je payer la prochaine vague ? ») consultée entre les vagues. Le deadline aura un DeadlineGuard (état : instant de départ / durée max) et une DeadlineProbe (« reste-t-il du temps pour la prochaine vague ? ») consultée au même point de la boucle run_waves_pure. Les deux sondes composent trivialement : une vague n'est émise que si budget ET deadline l'autorisent. Quand l'une dit non, l'essaim s'arrête, scelle, et le statut dit laquelle a mordu. Aucune nouvelle machinerie de contrôle de flux : on greffe une seconde sonde sur le chemin coopératif déjà prouvé d'ADR-014.

Coût et temps bornent la DURÉE (sondes coopératives entre vagues) ; la concurrence borne l'ENTRÉE (admission, avant le run). Trois axes, un principe.

3.2 — Borner visiblement, sceller le partiel

Deux règles non négociables, héritées de la doctrine du projet. (1) Visibilité : un refus est un 429 explicite avec Retry-After (admission), un arrêt est un statut nommé dans le SwarmRun (budget_stopped / deadline_exceeded), jamais une file silencieuse ni un timeout opaque. (2) Scellement du partiel : un run tronqué — par budget OU par deadline — n'est pas un échec qui perd tout ; c'est un run plus court dont les AgentCallRecord produits sont scellés normalement et restent pleinement vérifiables (verify/:id passe sur le partiel). La preuve survit à la troncature. C'est ce qui distingue un deadline coopératif (qui scelle) d'un tokio::timeout dur (qui détruit, §1.3) — ce dernier n'est gardé que comme backstop de dernier recours contre un hang.

3.3 — Re-prouvable, pas reproductible (l'écho d'ADR-017)

Le deadline introduit une dépendance au wall-clock — et ADR-017 a établi que le wall-clock est hors du moat. Conséquence honnête, gravée d'emblée : un run tronqué par deadline est re-prouvable (R0 : re-sceller ses records partiels reproduit son provenance_root) mais non reproductible (R1 : re-exécuté sur une machine plus rapide, il atteindrait peut-être k+1 vagues avant l'échéance ; plus lente, k−1 — le point de troncature dépend du temps, comme wall_at). Le statut deadline_exceeded signale cette frontière : le rejeu R1 d'un run deadliné peut diverger au point de troncature sans que ce soit une faute. C'est exactement la leçon d'ADR-017 (« la computation se reproduit, l'empreinte non »), appliquée au temps.

§4 Architecture A — admission équitable, tous les chemins

4.1 — Fairness par-tenant : un tenant n'affame pas les autres

On conserve le sémaphore global (le plafond process dur, contre l'écroulement mémoire/CPU) et on lui superpose une borne par-tenant. Le design retenu — minimal et sans file invisible : un cap par-tenant (per_tenant_max, configurable, défaut = une fraction du global, ex. ⌈admission_max / 2⌉) plus un compteur d'inflight par-tenant (HashMap<TenantId, AtomicUsize> sous le verrou d'état, ou un Semaphore par-tenant créé à la demande). L'admission devient un double permit : le run doit acquérir (a) un permit global ET (b) rester sous son cap tenant ; sinon 429. Ainsi un tenant ne peut prendre plus de per_tenant_max places, garantissant que les autres gardent admission_max − per_tenant_max places toujours disponibles. Le 429 distingue les deux causes ("reason": "gateway_full" vs "tenant_quota") pour un diagnostic honnête. La fairness reste du rejet visible, pas une file — fidèle à ADR-014.

4.2 — Tous les chemins de run sont gardés

Un plafond troué ne vaut rien. L'invariant I-AD7 exige que tout chemin qui exécute un essaim acquière un permit : POST /run sync, POST /run?stream=true (job détaché — le permit suit la tâche), et POST /replay/:id R1 (la re-exécution, gardée en ADR-017). Les endpoints de lecture/re-preuve qui n'exécutent rien — GET /verify/:id, GET /replay/:id (R0), GET /runs/:id/* — ne prennent pas de permit (ils ne sont pas des runs). La fairness par-tenant s'applique uniformément à tous les chemins gardés. Un test de couverture énumère les routes et vérifie que chaque exécution d'essaim passe par la garde.

§5 Architecture B — le deadline run

5.1 — La sonde coopérative DeadlineProbe (dans la boucle de vagues)

Le cœur du deadline est une sonde, jumelle de BudgetProbe. Un DeadlineGuard capture un start: Instant et une budget: Duration ; remaining() et expired() sont des lectures atomiques bon marché. Une DeadlineProbe = Arc<dyn Fn() -> bool> (« reste-t-il du temps ? ») est passée au sizer à côté de la BudgetProbe ; dans run_waves_pure, une vague n'est émise que si budget_probe(n) && deadline_probe(). Quand le temps est écoulé, la boucle s'arrête (comme pour le budget), k_used reflète les vagues faites, le run finalise et scelle le partiel. La granularité est la vague : pour le Mode A (vagues en µs), le deadline est quasi-exact ; pour le Mode C (vagues en secondes), il est approché à la vague près — acceptable, et le backstop (§5.2) couvre une vague qui déraille. Pour les topologies sans vagues (T2 pipeline, T3 hierarchical), on réutilise leur timeout par-batch existant, dérivé du deadline restant.

5.2 — Le backstop dur tokio::timeout (contre les hangs)

La sonde coopérative ne se déclenche qu'entre les vagues ; une vague (ou un appel LLM) qui pend ne la consulterait jamais. D'où un backstop : la passerelle enveloppe run_traced dans tokio::time::timeout(deadline + grâce, …). En fonctionnement normal, la sonde coopérative mord avant le backstop (la grâce, ex. +5 s, garantit l'ordre) → provenance partielle scellée. Le backstop n'est atteint que par un hang pathologique ; là, le futur est abandonné, la provenance partielle est perdue (§1.3, assumé), et le run échoue proprement en deadline_hard_abort — un échec net, jamais un zombie. Le permit d'admission est libéré dans tous les cas (le drop du futur libère le permit owned).

5.3 — Sceller le partiel · le statut du run · la composition des plafonds

La requête gagne un champ deadline_ms: Option<u64>, plafonné serveur (clamp à deadline_max_ms, parité avec la largeur d'I-CP1 : le client peut demander plus strict, jamais plus large ; défaut = le max serveur). Le SwarmRun gagne un statut de terminaison — Completed / BudgetStopped / DeadlineExceeded / DeadlineHardAbort — exposé sur le fil et en métrique. Composition : les deux sondes coopératives s'évaluent au même point ; le run s'arrête au premier plafond atteint, et le statut dit lequel. Un run DeadlineExceeded reste vérifiable (I-AD3) et porte le caveat de reproductibilité (I-AD6, §3.3). Métriques neuves : deadline_exceeded_total, deadline_hard_abort_total, histogramme de durée de run.

Le chemin coopératif (normal) scelle le partiel et reste vérifiable ; le backstop dur (pathologique) abandonne proprement. Dans les deux cas, le permit d'admission est libéré.

Ce que les plafonds n'attrapent PAS (honnêteté). Le deadline coopératif a une granularité de vague : une vague unique très longue dépasse l'échéance jusqu'à son terme (ou jusqu'au backstop) — il n'interrompt pas un appel LLM en cours. Le backstop dur, lui, perd la provenance partielle (le futur est abandonné) — assumé pour le seul cas pathologique. La fairness par-tenant est statique (un cap), pas une part équitable pondérée dynamique (un ordonnanceur fair-share serait un autre chantier). Et un run deadliné n'est pas reproductible au point de troncature (I-AD6) — c'est une borne physique du wall-clock, pas un bug.

§8 Le harnais — Lot ADMIT-DEADLINE

Gate mixte : correction (admission équitable, le prior est favorable — le sémaphore existe) + capacité neuve mesurée (deadline). Artefact daté scripts/swarm/EFE_SWARM_ADMITDL_2026-06-17.json.

8.1 — Les volets éprouvés

① Admission & fairness. Saturer le cap global → les runs suivants reçoivent 429 + Retry-After, admission_rejected monte (I-AD1). Saturer le cap d'un tenant A → A reçoit 429 alors qu'un tenant B obtient encore un permit (I-AD2, pas de famine). Critère GO : cap respecté, 429 visible, B non affamé.

② Deadline coopératif + scellement. Un run keyless avec une charge volontairement large (K élevé, agents ralentis par un sink de test) et un deadline_ms court → le run s'arrête à k_used < K, statut DeadlineExceeded, et verify/:id sur le partiel passe (I-AD3). Un run dont une vague pend au-delà de deadline + grâce → DeadlineHardAbort, permit re-disponible (I-AD4). Critère GO : partiel scellé+vérifié ; backstop ferme net ; permit toujours libéré.

③ Composition + honnêteté de rejeu. Budget court + deadline long → BudgetStopped ; l'inverse → DeadlineExceeded (I-AD5, le premier plafond nommé). Un run DeadlineExceeded : R0 reproduit son root partiel ; R1 porte le caveat (I-AD6). deadline_ms au-delà du max serveur est clampé (I-AD8). Critère GO : le bon statut, R0 tient, le clamp mord.

8.2 — Le volet Mode C réel (ignoré sans Ollama)

Un run Mode C self-host avec un deadline_ms plus court que la latence d'un tour de juges → le run s'arrête coopérativement entre vagues, scelle les appels LLM déjà faits (forensique N17 intacte), et verify_run_offline passe sur le partiel. Preuve honnête que le deadline tient en conditions réelles — y compris que la troncature N'EST PAS reproductible (le statut le dit).

9.2 — ADR-SWARM-018, le squelette

Titre : « Gouvernance des runs — admission équitable par-tenant + deadline coopératif (scelle le partiel, backstop dur), trois plafonds composables ». Contexte : le coût (Budget) et la concurrence (admission CP-2) sont bornés ; le temps ne l'est pas (run zombie) et l'admission globale autorise la famine par tenant. Décision : ① fairness par-tenant (cap + double permit, 429 distinct) ; ② deadline = jumeau temporel du budget (sonde coopérative dans la boucle de vagues) ; ③ scellement du partiel (le run tronqué reste vérifiable) ; ④ backstop tokio::timeout contre les hangs (échec net, partiel perdu assumé) ; ⑤ statut de terminaison nommé + composition au premier plafond ; ⑥ deadline_ms clampé serveur (parité width I-CP1) ; ⑦ admission sur tous les chemins de run. Hors-périmètre versionné : ordonnanceur fair-share pondéré dynamique ; interruption intra-vague d'un appel LLM en cours ; persistance d'une file (la doctrine est le rejet visible). Verdict : Lot ADMIT-DEADLINE — GO sur admission équitable (correction) + deadline (partiel scellé+vérifié, backstop, composition). Related : ADR-014 (admission CP-2, budget I13), ADR-006/016 (moat, partiel vérifiable), ADR-017 (wall-clock hors moat → caveat de rejeu). Conséquences : plus de run zombie, plus de famine par tenant ; les trois plafonds (coût/temps/concurrence) composent ; le partiel reste prouvable, et le rejeu reste honnête.

§10 Risques honnêtes & hors-périmètre

Risque / limiteRéalité, sans fardTenue
Granularité de vague du deadlineune vague unique longue (ou un appel LLM en cours) dépasse l'échéance jusqu'à son terme — la sonde ne mord qu'entre vaguesbackstop dur en filet (deadline+grâce) ; granularité fine pour le Mode A (vagues µs) ; l'interruption intra-appel est un chantier futur, scopé dehors
Le backstop dur perd le partielun tokio::timeout abandonne le futur → recorder perdu, pas de provenancepar conception : c'est le dernier recours (hang pathologique) ; le chemin NORMAL est coopératif et scelle (la grâce garantit qu'il mord d'abord)

Doctrine du rejet (pas de file)à saturation, on renvoie 429 — on ne met pas en filechoix assumé d'ADR-014 (backpressure visible > file invisible qui finit en timeouts) ; Retry-After guide le client

Synthèse de décision. ≈ 650 LoC, zéro nouvelle machinerie de contrôle de flux (on greffe une seconde sonde sur la boucle de vagues d'ADR-014, et un cap par-tenant sur le sémaphore existant). En face : plus de run zombie, plus de famine par tenant, et les trois plafonds — coût, temps, concurrence — composent sous un seul principe : borner visiblement, sceller le partiel, dire ce qui reste reproductible. Le deadline est le jumeau temporel du budget ; l'admission équitable ferme l'angle mort qu'ADR-014 avait nommé.
