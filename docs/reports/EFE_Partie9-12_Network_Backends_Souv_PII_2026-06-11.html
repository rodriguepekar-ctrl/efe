§1 Le mode Network — la frontière sans les clés

Le mode SelfHost est le phare souverain d'EFE, mais certains clients veulent la qualité d'un modèle frontière (Claude, GPT-4o…). Le problème : ces modèles exigent des clés d'API, et la règle absolue du projet interdit qu'une clé touche le client ou la passerelle. Le mode Network résout cette équation — et la manière dont il la résout (l'incrément 4.b) est un petit modèle de décision d'architecture.

1.1 — La décision : le routeur reste un endpoint OpenAI-compatible

Quand il a fallu câbler le protocole concret du routeur, deux options se présentaient. La première : inventer un protocole propriétaire entre la passerelle et le routeur (gRPC dédié, schéma maison) — le crate efe-llm-router avait d'ailleurs une ébauche gRPC, restée à l'état de squelette. La seconde, retenue : le routeur est, vu de la passerelle, un simple serveur OpenAI-compatible. Cette décision a une conséquence élégante : la passerelle n'a aucun code Network spécifique à maintenir. Elle réutilise tel quel le backend OpenAI-local du SDK (§2) — le même qui parle à un llama.cpp sur la boucle locale parle au routeur frontière. Le routeur (un LiteLLM, un vLLM gateway, ou l'efe-llm-router à terme) reçoit l'appel au format OpenAI, détient les clés des fournisseurs server-side (environnement ou coffre), et traduit vers le fournisseur réel. La frontière des secrets est nette : tout ce qui est en amont du routeur est keyless ; tout ce qui exige une clé vit dans le routeur.

Restait une question de vocabulaire : l'appelant demande Network { provider: "anthropic" } — une famille — mais un routeur OpenAI-compatible attend un identifiant de modèle concret ("anthropic/claude-3-5-sonnet-latest"). Qui traduit ? La réponse tient dans une observation de sécurité : un nom de modèle n'est pas un secret — c'est une politique de routage. Il peut donc vivre côté passerelle, configurable au déploiement, sans rien compromettre. C'est la RouterMap.

1.2 — La RouterMap : trois règles déterministes

La table de résolution applique trois règles, dans cet ordre, et chacune a sa justification. Règle 1 — le passthrough explicite : si la demande contient déjà un identifiant qualifié (famille/modèle ou famille:modèle), on ne touche à rien — l'appelant a tranché, la passerelle ne réinterprète pas une décision explicite. Règle 2 — la famille connue : si la demande est une famille nue présente dans la table, on la traduit par l'identifiant par défaut. Règle 3 — la famille inconnue : passthrough encore — on laisse le routeur trancher (ou renvoyer une erreur claire), plutôt que d'inventer une traduction hasardeuse côté passerelle.

Et la forme retenue est provider/model (la convention des routeurs OpenAI-compatibles type LiteLLM) — surtout pas le préfixe openai:, et ce n'est pas un caprice : on verra en §2 que ce préfixe est précisément le sélecteur de moteur du SDK ; l'utiliser ici forcerait une interprétation parasite au mauvais étage. Enfin, la table entière est surchargeable au déploiement par la variable EFE_SWARM_ROUTER_MODELS — la politique de routage appartient à l'exploitant, pas au code.

1.3 — resolve_mode : la traduction, et le tarif préservé

Côté passerelle, tout converge dans une fonction : resolve_mode. Pour les modes souverains (Keyless, SelfHost), elle est transparente. Pour Network { provider }, elle opère la traduction complète : si un routeur est configuré (EFE_SWARM_ROUTER_ENDPOINT), le mode devient SelfHost { endpoint: routeur, model: router_map.resolve(provider) } avec allow_remote = true (l'egress vers le routeur est assumé — c'est le seul cas) ; s'il n'y en a pas, la réponse est un 501 net avec un message qui dit exactement quoi faire (« définissez EFE_SWARM_ROUTER_ENDPOINT côté serveur »). Pas de demi-mesure : le Network non câblé n'est pas simulé, il est refusé.

La fonction renvoie un troisième élément, et son histoire vaut d'être racontée parce que c'est un bug réel trouvé par les tests de bout en bout. La traduction Network → SelfHost héritait du modèle de prix du véhicule : SelfHost = 0 ¢. Résultat observé lors du premier test réel : un run Network entier affichait spent_cents: 0 — la gouvernance de budget était muette précisément sur le seul mode qui coûte de l'argent réel. Le correctif : resolve_mode renvoie un tarif à forcer (Some(5 ¢), le prix nominal Network) que le chemin d'exécution injecte dans le budget (price_per_call_cents.get_or_insert(...)). Le run est exécuté par le véhicule SelfHost, mais facturé au tarif du mode demandé. Trois tests verrouillent désormais ce comportement (souverains inchangés, 501 sans routeur, traduction avec tarif).

1.4 — Les preuves : in-process et bout en bout réel

Le chemin Network est prouvé à deux niveaux. In-process (CI, sans réseau ni clé) : un test monte un faux routeur OpenAI-compatible (un serveur axum sur un port éphémère de la boucle locale), configure la passerelle dessus, et soumet un run Network. Les assertions couvrent toute la promesse : le run est verified, le moteur forensique est openai_local (le descripteur traverse les enveloppes), le modèle est bien l'identifiant traduit par la RouterMap, la dépense est non nulle (le tarif a survécu à la traduction), et le pont N17 est intégralement cohérent. Un second test vérifie le 501 sans routeur. Bout en bout réel : la même passerelle, pointée sur un proxy LiteLLM local détenant une vraie clé Anthropic (server-side, jamais vue par EFE), a produit un run réel — vérifié, modèle anthropic/claude-3-5-sonnet-latest, pont N17 4/4 cohérent. La chaîne complète — famille → RouterMap → routeur → fournisseur frontière → réponse → provenance scellée — fonctionne avec exactement zéro clé côté EFE.

Ce qu'il faut retenir du Network. Le mode frontière n'a pas affaibli la posture : il l'a déplacée. La passerelle ne connaît que des noms de modèles (publics) et un endpoint de routeur ; les clés vivent dans le routeur, server-side, remplaçables sans toucher EFE. Et la gouvernance (tarif, budget, provenance, N17) traverse la traduction intacte — parce qu'un test l'a exigé.

§2 Les backends locaux — keyless par construction

Sous le mode SelfHost (et, on vient de le voir, sous le Network traduit), il y a une pièce unique : le LocalBackend. Sa conception illustre une discipline rare — le keyless n'y est pas une configuration, c'est une propriété structurelle : il n'existe aucun champ, aucun en-tête, aucune dépendance où une clé pourrait se glisser.

2.1 — Un seul trait, deux moteurs

Le trait LocalBackend expose trois méthodes : complete(prompt, params) qui rend Option<String> (l'échec est un None franc, jamais une exception — la couche appelante le transforme en sentinel neutre), descriptor() qui rend le triplet forensique (moteur, modèle, endpoint — jamais une clé, le commentaire le précise), et health(), la sonde de démarrage. Derrière ce trait, deux moteurs : Ollama natif (son API /api/generate) et OpenAI-compatible local (llama.cpp-server, vLLM, TGI, LM Studio — et le routeur Network, §1). La sélection du moteur est déterministe et documentée : un modèle préfixé openai: ou un endpoint contenant /v1 désignent l'OpenAI-compatible (le préfixe est retiré du nom de modèle au passage) ; tout le reste va à Ollama. C'est ce sélecteur que la RouterMap évite soigneusement de déclencher (§1.2) : le openai: est un mot-clé du SDK, pas un préfixe décoratif.

2.2 — Le transport : un shell-out curl, et c'est voulu (G10)

Le choix le plus surprenant — et le plus délibéré — est le transport. Le SDK ne dépend d'aucune bibliothèque HTTP, d'aucune pile TLS : il invoque curl en sous-processus. La fonction curl_json tient en vingt lignes : un POST avec content-type: application/json, un --max-time strict, et — détail de sécurité — le corps passé par stdin (-d @-), jamais par argument : aucun échappement shell, aucun prompt qui fuite dans la liste des processus. Aucun en-tête Authorization n'est construit nulle part : le grep le plus paranoïaque du crate ne trouvera pas un point d'injection de clé, parce qu'il n'y en a pas.

Pourquoi cette austérité ? C'est le garde-fou G10 : aucune dépendance réseau dans le crate SDK. Les bénéfices sont en cascade. L'audit de sécurité du SDK se réduit à « il appelle curl vers un endpoint que G2 contraint » — pas de pile TLS à auditer, pas de CVE de bibliothèque HTTP à suivre, pas de négociation de certificats dans le périmètre du code. Le binaire reste petit. Et la frontière de confiance est limpide : ce qui sort de la machine est exactement ce que curl envoie, observable par n'importe quel outil système. Le coût assumé : un spawn_blocking par appel (le sous-processus est bloquant) et une granularité d'erreur grossière — on y reviendra en §3.4, car cette limite est documentée honnêtement dans le code.

2.3 — La sonde de santé et le garde-fou d'egress

Deux compléments ferment le dispositif. La sonde de santé (health_probe) : un curl --max-time 3 de joignabilité, sans secret transmis — c'est elle que le SDK appelle au démarrage d'un run quand require_healthy_backend est actif (la passerelle l'active toujours), pour échouer en une requête plutôt qu'en K timeouts. Et le garde-fou G2 : la fabrique build_local_backend refuse tout endpoint non local (RemoteBackendDenied) sauf opt-in explicite. Le test de localité (is_local_endpoint) ne se contente pas d'un contains("localhost") naïf : il parse l'autorité de l'URL — schéma, userinfo éventuel (ignoré, pour qu'un http://localhost@evil.com ne trompe pas le test), littéraux IPv6 [::1], port — et n'accepte que localhost, ::1 et 127.*. Les tests énumèrent les deux côtés : quatre formes locales reconnues, quatre formes distantes refusées (dont les adresses privées 10.x et 192.168.x — « privé » n'est pas « local »).

La hiérarchie des refus. Notons la cohérence d'ensemble : le SDK refuse l'egress par défaut (G2), la passerelle n'autorise l'egress que pour le routeur Network qu'elle a elle-même configuré (allow_remote = true sur ce seul chemin), et le Network sans routeur est un 501. À chaque étage, la voie par défaut est la plus souveraine, et chaque ouverture est un acte explicite et localisé.

§3 La résilience — Breaker & Retrier (et la correction N17)

Un backend peut tomber, hoqueter, ou ramer. La pile de résilience d'EFE répond avec deux enveloppes composables — un circuit-breaker et un module de re-tentatives — dont l'empilement n'est pas le même selon le chemin. Et elle contient un bijou d'ingénierie discret : la correction qui empêche les re-tentatives de polluer la preuve.

3.1 — L'empilement différencié : Breaker(Retrier(moteur)), mais pas partout

La fabrique assemble la pile selon le chemin. Self-host souverain (boucle locale) : Breaker(moteur) seul. La justification est physique : sur la loopback, un échec est franc et rapide — le serveur local répond ou ne répond pas, il n'y a ni congestion réseau ni hoquet transitoire qui justifierait de réessayer ; re-tenter ne ferait que marteler un service déjà en difficulté. Chemin routeur Network (egress assumé) : Breaker(Retrier(moteur)). Là, le réseau étendu introduit des défaillances transitoires — un paquet perdu, un load-balancer qui bascule, un 503 momentané — pour lesquelles la re-tentative est la réponse correcte.

L'ordre d'empilement est lui-même un choix raisonné : le Breaker enveloppe le Retrier, pas l'inverse. Conséquence : le breaker compte une défaillance par appel logique — après épuisement des re-tentatives — et non une par tentative. Si c'était l'inverse, trois tentatives échouées d'un même appel consommeraient trois « points » du seuil du breaker, et deux appels malchanceux suffiraient à ouvrir un circuit calibré pour cinq défaillances réelles. L'empilement choisi préserve la sémantique du seuil.

3.2 — Le Breaker : protéger l'hôte, pas masquer la panne

Le circuit-breaker est volontairement simple : un compteur d'échecs consécutifs (seuil par défaut : 5), une fenêtre d'ouverture (15 secondes). Tant que le circuit est fermé, les appels passent ; chaque succès réarme le compteur à zéro ; au cinquième échec consécutif, le circuit s'ouvre : pendant la fenêtre, les appels renvoient None sans toucher au backend. Le test le vérifie au compteur près : après ouverture, le moteur interne n'est plus appelé du tout. L'objectif n'est pas de cacher la panne — les sentinels remontent et la topologie dégrade (Partie 5–6, §5.1) — mais de protéger l'hôte et le backend : pas de tempête de requêtes sur un service à terre, pas de file de timeouts qui s'accumule. Après la fenêtre, le prochain appel re-sonde naturellement le backend ; s'il répond, le succès referme tout.

3.3 — Le Retrier : back-off exponentiel plafonné, jitter sans dépendance

Le Retrier exécute jusqu'à 3 tentatives au total (l'essai initial plus deux re-tentatives), avec un délai croissant entre elles : base 200 ms, doublée à chaque tentative, plafonnée à 5 s. Au délai s'ajoute un jitter de type equal-jitter — la moitié du délai est fixe, l'autre moitié tirée au hasard — pour éviter qu'une flotte d'appels échoués au même instant ne re-frappe le routeur en vague synchronisée. Détail d'implémentation fidèle à la sobriété du crate : l'aléa vient des nanosecondes de l'horloge système (« entropie bon marché », dit le code), pas d'une dépendance rand — pour du jitter, c'est exactement suffisant. Et l'arithmétique est blindée aux extrêmes : le décalage exponentiel est plafonné à 2¹⁶, les multiplications saturent au lieu de déborder.

3.4 — La correction N17 : les tentatives ne polluent pas la preuve

Voici le point le plus délicat du module, et le code le qualifie lui-même de tel. Rappel du pont N17 (Parties 7–8, §6) : le backend feuille pousse, à chaque complete(), une fiche forensique dans le puits task-local posé par le Meter ; le Meter assemble et lie l'enregistrement d'agent à la première fiche. Maintenant, introduisons naïvement le Retrier : trois tentatives = trois complete() du moteur feuille = trois fiches dans le puits du Meter. Double dégât : le pont compterait des appels fantômes (des tentatives, pas des appels logiques), et — pire — l'enregistrement d'agent se lierait à la première fiche, c'est-à-dire à une tentative échouée, alors que la réponse réellement utilisée vient de la troisième. La preuve raconterait une histoire fausse.

La correction : le Retrier exécute chaque tentative dans un puits imbriqué — un scope task-local à lui, posé par-dessus celui du Meter. La fiche de la tentative tombe dans ce puits privé, où le Retrier la draine. À l'issue de l'appel logique, il ne ré-émet vers le puits parent qu'une seule fiche : celle de l'issue retenue (la réponse en cas de succès, la dernière tentative en cas d'épuisement), en y inscrivant le retry_count. Trois tests verrouillent les trois cas : succès après deux échecs → une fiche, retry_count = 2, réponse présente ; épuisement → une fiche, retry_count = 2, réponse absente ; succès immédiat → une fiche, retry_count = 0. Le pont N17 voit des appels logiques, jamais des tentatives — et le compteur de re-tentatives, loin d'être perdu, devient une donnée forensique de la fiche.

La limite, documentée dans le code. La couche curl keyless ne distingue pas un 4xx (erreur définitive : mauvaise requête, modèle inconnu) d'un 5xx ou d'un timeout (transitoire) — elle rend None dans tous les cas. Les re-tentatives sont donc transitoires-par-défaut : on réessaie aussi ce qui ne méritait pas de l'être. Le commentaire assume cette imperfection et trace l'évolution possible (faire remonter le code HTTP via curl %{http_code}). C'est un compromis typique du projet : une limite réelle, bornée (au pire deux re-tentatives inutiles), dite à voix haute plutôt que masquée.

§4 Souveraineté & déploiement — le binaire qui ferme le trou

« Souverain » est un mot facile à mettre sur une plaquette. Cette section le rend vérifiable : l'inventaire exhaustif des secrets du système, les garde-fous qui tiennent la frontière, le binaire de production — qui a fermé un vrai trou de sécurité — et l'image Docker qui porte le tout.

4.1 — L'inventaire des secrets, exhaustif

Faisons l'exercice que tout audit devrait faire : lister tout ce qui, dans le système, relève du secret. La liste est remarquablement courte. Un : le master de signature HKDF (EFE_NANO_AUDIT_HMAC_MASTER), qui signe la provenance — server-side, jamais saisi, jamais loggé (Parties 7–8, §5). Deux : les clés des fournisseurs frontière — qui vivent dans le routeur Network, pas dans EFE (§1.1). Et c'est tout. L'authentification OIDC de la passerelle ne détient que des clés publiques de vérification de signature (ES256) ; le mode SelfHost ne demande rien ; le mode Keyless, par définition, rien non plus. Un déploiement souverain pur (keyless + self-host, sans Network) embarque donc exactement un secret — et ce secret ne protège pas des données : il rend la preuve infalsifiable.

4.2 — Les garde-fous, en système

Les sections précédentes ont égrené des garde-fous numérotés ; voici comment ils se composent en une défense en profondeur. G2 (egress) : aucun backend non local sans opt-in explicite — et l'unique opt-in du système est le routeur Network configuré par l'exploitant (§2.3). G3 (robustesse) : le circuit-breaker protège l'hôte d'un backend à terre (§3.2). G8 (mémoire) : le Blackboard est borné par construction (Partie 3, §2.5) — pas d'épuisement de ressources par un run emballé. G9 (PII) : le caviardage par tenant, qu'on verra en §5. G10 (surface) : aucune dépendance réseau dans le crate SDK (§2.2). À quoi s'ajoutent les disciplines transverses : #![deny(unsafe_code)] sur les sept crates de bibliothèque, zéro panic! en production, zéro avertissement clippy — la souveraineté commence par un binaire dont on peut lire chaque ligne.

4.3 — Le binaire de production : l'histoire d'un trou fermé

Le binaire efe-swarm-gateway mérite qu'on raconte pourquoi il existe. Pendant le développement, le serveur de référence était un exemple (serve_standalone) qui, par commodité, signait la provenance avec la clé de test — un master public, écrit en clair dans la source. Parfaitement acceptable en développement. Mais le chart Helm de déploiement, lui, montait consciencieusement un Secret Kubernetes contenant le master HKDF de production… que l'exemple n'utilisait pas. Conséquence silencieuse : un déploiement « production » aurait signé toute sa provenance avec une clé publique — c'est-à-dire forgeable par quiconque lit le dépôt. Le moat, vidé de sa substance, sans qu'aucun voyant ne s'allume.

Le binaire de production ferme ce trou par une logique de sélection explicite : si EFE_NANO_AUDIT_HMAC_MASTER est présent et non vide dans l'environnement, la source de clé est EnvHkdf (le master réel, dérivé par tenant au moment de signer) ; sinon, repli sur la clé de test avec un avertissement bruyant sur la sortie d'erreur : « la provenance serait FORGEABLE (verify non fiable). NE JAMAIS utiliser en production. » Notons la discipline dans le détail : le binaire ne teste que la présence du master — sa valeur n'est jamais lue à cet endroit, jamais loggée ; c'est EnvHkdf::derive qui la lira, server-side, à l'instant de la signature. Même pour décider, on ne manipule pas le secret.

Le reste du binaire est l'outillage d'un service qui doit vivre dans un cluster : bind par défaut 0.0.0.0:8080 (joignable dans le pod, surchargeable par EFE_SWARM_GATEWAY_ADDR), arrêt gracieux sur SIGTERM et Ctrl-C (les rollouts Kubernetes drainent les connexions au lieu de les couper), et le câblage depuis l'environnement de tous les modules optionnels : le store Postgres (DATABASE_URL, feature postgres), l'authentification OIDC (clé publique, issuer, audience — feature oidc), la politique PII par défaut (EFE_PII_DEFAULT_POLICY, feature pii), et le routeur Network (EFE_SWARM_ROUTER_ENDPOINT + EFE_SWARM_ROUTER_MODELS, §1).

4.4 — L'image Docker : rien dedans, tout au runtime

L'image de production suit la même philosophie. Construction multi-étages : un étage rust:1-bookworm compile en release avec les features de production (postgres oidc pii) ; l'étage final, un debian:bookworm-slim, ne reçoit que le binaire et deux paquets — curl (le transport des backends et du routeur, §2.2 : le shell-out est une dépendance système, pas crate) et ca-certificates (le TLS vers un routeur frontière distant, le cas échéant). L'exécution est non-root (un utilisateur dédié, uid 10001 — défense en profondeur : une compromission du processus n'offre pas la machine), un HEALTHCHECK sonde /metrics toutes les 15 secondes (la passerelle est vivante dès qu'elle répond — c'est la même sonde que le chart Helm utilise en liveness/readiness). Et le commentaire final de l'image est la règle du déploiement entier : « AUCUNE clé dans l'image » — le master HKDF, l'URL de base, les paramètres OIDC arrivent de l'environnement et des Secrets Kubernetes au runtime, jamais des couches de l'image. Une image compromise ou redistribuée ne contient rien à voler.

La souveraineté, en pratique. Un déploiement EFE souverain se décrit en une phrase auditable : un binaire Rust sans unsafe, sans dépendance réseau crate, qui refuse l'egress par défaut, dont l'image ne contient aucun secret, et dont l'unique secret runtime — un master de signature — n'est jamais ni saisi, ni affiché, ni embarqué. Chaque mot de cette phrase correspond à un mécanisme vérifié de ce document ou des précédents.

§5 PII — caviarder sans casser la preuve

Un essaim qui traite du texte client traite, tôt ou tard, des données personnelles — adresses électroniques, numéros de sécurité sociale, cartes bancaires. La couche PII d'EFE répond à deux exigences qui semblent se contredire : caviarder ce qui sort du système, et ne rien altérer de ce qui a été prouvé. La résolution de cette tension est le point le plus intéressant de la section.

5.1 — Le crate efe-pii : trois couches et un disjoncteur

Le crate historique (M29) organise la détection en trois couches successives. Première couche, la canonicalisation — et elle est pensée contre un adversaire, pas contre la maladresse. Avant toute analyse, le texte subit une normalisation Unicode NFKC (le « А » cyrillique, homoglyphe parfait du « A » latin, redevient un A — les confusables ne cachent plus rien), un retrait des caractères de contrôle (les zero-width joiners qui découperaient un numéro en fragments invisibles sont éliminés), et un plafond de longueur (4 096 caractères — pour borner le temps de calcul de l'analyseur, donc fermer un vecteur de déni de service). Le crate documente aussi, honnêtement, ce qu'il ne fait pas : la PII encodée en base64 n'est pas auto-décodée — un client qui a ce besoin met un pré-processeur en amont, plutôt que de laisser croire à une protection qui n'existerait qu'à moitié.

Deuxième couche, l'analyse : un trait PiiAnalyzer dont l'implémentation de référence appelle l'API HTTP d'un sidecar Presidio (l'analyseur PII open-source de Microsoft) et rend des spans détectés, typés. Troisième couche, la politique : quatre niveaux par tenant — Off (rien), Detect (détecter et signaler, sans modifier), Redact (caviarder les spans), Strict (caviarder, et rejeter si l'analyse est indisponible). Ce dernier point est articulé au mode de défaillance : si le sidecar Presidio ne répond plus, un disjoncteur s'ouvre après trois échecs consécutifs et les appels suivants rendent immédiatement « indisponible ». La décision appartient alors à la politique : les niveaux Off/Detect/Redact sont fail-open (le service continue, sans garantie PII), le niveau Strict est fail-closed (mieux vaut refuser de répondre que laisser fuir). Le compromis disponibilité/conformité n'est pas tranché par le code — il est rendu au client, par tenant.

5.2 — Le tour de la passerelle (G9) : détection locale, présentation caviardée, preuve intacte

La passerelle réutilise ce crate, mais avec deux inflexions qui changent tout. Première inflexion : la détection est locale. Appeler un sidecar Presidio, c'est une dépendance réseau — incompatible avec un déploiement egress = deny. Le module pii.rs de la passerelle n'utilise donc pas le client Presidio : il embarque ses propres détecteurs regex compilés une fois (adresse électronique, numéro de sécurité sociale américain, carte bancaire de 13 à 19 chiffres avec séparateurs…) et ne réutilise du crate que le redactor pur (la fonction qui remplace des spans dans un texte) et la taxonomie de politiques. Les détecteurs sont volontairement conservateurs — le commentaire le dit : « sur-caviarder est sûr » ; un faux positif coûte un peu de lisibilité, un faux négatif coûte une fuite. La politique se règle par tenant, avec Off par défaut et une valeur d'amorçage par l'environnement (EFE_PII_DEFAULT_POLICY).

Seconde inflexion — la plus importante : on caviarde la présentation, jamais la preuve. Posons le dilemme qu'elle résout. La provenance (Parties 7–8) scelle le hash de la sortie de chaque agent ; la racine engage ces hashs. Si la passerelle caviardait la sortie avant scellement, la preuve porterait sur un texte expurgé — et le caviardage, qui peut évoluer (nouvelles regex, nouvelle politique), rendrait les runs anciens non reproductibles. Si elle caviardait les enregistrements après coup, elle détruirait littéralement la preuve — verify_swarm échouerait, par construction. La solution : le caviardage s'applique aux surfaces de présentation — la sortie renvoyée à l'appelant, les aperçus du dashboard, la copie au repos destinée à l'affichage — tandis que les AgentCallRecord et leurs hashs restent byte-intacts. Le commentaire du module le résume : « verify_swarm re-prouve l'original ».

Pourquoi c'est la bonne décomposition. La conformité PII et l'intégrité de preuve protègent contre des risques différents : la première contre l'exposition d'une donnée personnelle, la seconde contre la falsification de l'historique. Les confondre — caviarder dans la preuve — sacrifierait la seconde sans renforcer la première (la donnée a déjà été traitée ; c'est sa diffusion qu'on contrôle). La séparation présentation/preuve donne les deux : ce que les humains voient est expurgé selon la politique du tenant ; ce que l'auditeur re-prouve est l'original exact. L'accès aux enregistrements bruts relève alors du contrôle d'accès (OIDC, rôles), c'est-à-dire du bon outil pour ce risque-là.

§6 Le dashboard — voir l'essaim sans le toucher

Dernière pièce : rendre visible ce que les onze parties précédentes décrivent — les petits agents qui se passent l'information en parallèle. Le crate efe-swarm-dashboard le fait avec une discipline qui tient en une phrase de sa documentation : « le dashboard est un observateur, pas un acteur ».

6.1 — Le branchement : les seams existants, et rien d'autre

Le cœur est un DashboardBus auquel on attache un DashboardObserver — une implémentation du hook générique SwarmObserver du SDK (Partie 5–6, §5.1, quatrième temps du Meter). Le branchement tient en une ligne de builder (with_observer(...)), et c'est tout : le dashboard se nourrit exclusivement des seams déjà existants — le WriteSink des écritures (en tee avec la provenance, qui reste byte-identique), l'EventSink du trafic de bus, et les événements de cycle de vie du Meter (départ, appel facturé, scellement, fin). Pas un agent réécrit, pas une topologie modifiée, pas un chemin d'exécution conditionné par « est-on observé ? ». Si l'observateur est absent, le coût est un test d'option ; s'il est présent, l'essaim se comporte à l'identique — c'est vérifiable puisque la provenance scellée est la même dans les deux cas.

6.2 — Ce qu'on voit : quatre familles de panneaux

Le bus diffuse chaque micro-événement (DashboardEvent) vers quatre familles de panneaux, qui correspondent exactement aux quatre récits des parties précédentes : le trafic inter-agents (qui écrit quoi, qui lit quoi — le substrat de la Partie 3 rendu visible), le consensus (les candidats, les ballots des juges, le verdict — la Partie 4 en direct), la provenance (les enregistrements qui s'accumulent, le scellement, la racine — les Parties 7–8), et le budget (la dépense appel par appel, l'instantané vivant — la Partie 5–6). Un tampon de rejeu (8 192 événements) permet de revoir un run qui vient de s'achever : la méthode replay() rend la séquence complète des événements captés.

6.3 — La hiérarchie des vérités, une dernière fois

Le flux du dashboard est best-effort et avec perte — assumé, documenté. Sous charge, des événements d'affichage peuvent être abandonnés plutôt que de ralentir l'essaim (les variantes lossy des sinks, Partie 3 §6.2). Est-ce un problème ? Non, et c'est le keystone du projet qui répond, appliqué une dernière fois : le dashboard est un indice — il montre, il oriente, il rassure — mais la vérité durable est ailleurs : dans la chaîne de provenance, scellée et re-prouvable. Perdre un événement d'affichage ne fait perdre ni une donnée (le Blackboard l'a), ni une preuve (la chaîne l'a). Le tableau de bord peut mentir par omission sous charge extrême ; l'audit, jamais. C'est la même séparation indice/vérité qui structure le substrat, la lane fiable, et maintenant l'observabilité — un seul principe, décliné à tous les étages.

Le démonstrateur. Au-dessus de ce cœur sans HTTP, un exemple de serveur expose les panneaux en direct dans un navigateur — c'est la démo « on voit les nano-agents se passer l'info ». Mais la valeur architecturale est dans le cœur : n'importe quel front (web, TUI, export métriques) peut se brancher sur le même bus, parce que l'observation est découplée de la présentation.

Jamais une convention, jamais un « il suffit de ne pas » : un type, un garde-fou, un test. C'est ce qui permet d'affirmer, à la fin de cette série de douze parties, que les promesses du projet — keyless côté client, souverain par défaut, prouvable par un tiers — ne sont pas des intentions : ce sont des propriétés du code, chacune adossée à la mécanique qui l'impose.
