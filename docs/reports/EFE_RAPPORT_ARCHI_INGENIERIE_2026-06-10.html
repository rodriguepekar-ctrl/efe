§1  Thèse & vision : pourquoi « beaucoup de petits »

EFE prend un parti à contre-courant. Là où l'industrie construit des agents gros et intelligents (mémoire, outils, boucles de raisonnement), EFE construit beaucoup d'agents minuscules et bêtes — chacun fait une chose, en quelques lignes, sans état — et les fait communiquer en parallèle. L'intelligence est dans la topologie (le câblage) et la circulation de l'information (les substrats), pas dans l'agent.

Les quatre piliers de la proposition

🔒 Souverain. Mode phare self-host keyless : les modèles tournent sur 127.0.0.1, air-gappable, zéro egress. Aucune clé dans le binaire ; le seul secret est le master HKDF qui signe la provenance, lu server-side.
✅ Vérifiable. Chaque run renvoie un provenance_root (64 hex). Un tiers re-prouve la chaîne + le contenu + le DAG à partir des seuls records et d'une clé tenant — hors-ligne, sans nous croire.
💧 Fluide & parallèle. K générateurs et J juges tournent en parallèle borné ; l'information circule en continu via deux substrats. Pas de barrière globale rigide.
💸 Gouverné. Budget atomique (invariant I13) : le plafond n'est jamais dépassé, même en concurrence. Dégradation gracieuse plutôt qu'effondrement.

Pourquoi ce choix gagne (et n'est pas un compromis)

  • Vérifiabilité. Un pas minuscule et déterministe se re-prouve trivialement ; un gros modèle opaque non. La petitesse achète l'auditabilité.
  • Robustesse. Un nano-agent qui rate renvoie un sentinel neutre — la topologie dégrade, elle ne s'effondre pas. Pas de point de défaillance unique « intelligent ».
  • Souveraineté. Des fonctions Rust locales n'ont besoin ni de clé ni de réseau. Air-gappable par construction.
  • Gouvernance. Chaque appel est une unité atomique facturable (I13). Le coût est borné et prévisible — l'opposé d'un agent monolithique au coût opaque.
La nuance honnête. On ne promet jamais la reproductibilité bit-à-bit d'un LLM. On promet la re-preuve forensique : les sorties LLM sont captées (hash prompt/réponse, modèle, params, seed) et tamper-evident, mais pas rejouables à l'identique. Le Mode A déterministe et l'agrégation, eux, sont reproductibles (ADR-SWARM-007). Le provenance_root est stable pour un même ensemble de records.

§2  Architecture en couches (la stack)

EFE est un monorepo Rust. La stack essaim s'empile en couches strictes : le haut dépend du bas, sans cycle. Le SDK reste léger (aucune dépendance réseau/TLS dans son cœur, asserté en CI) ; les préoccupations prod (Postgres, OIDC, PII) sont des features optionnelles.

Figure 1 — Les couches et leurs dépendances (flèches : le haut dépend du bas). Le routeur frontière est server-side, hors du binaire souverain.

Principe d'isolation : le SDK « shell-out » curl vers 127.0.0.1 pour les modèles locaux — il n'importe ni reqwest ni TLS. Un test CI (keyless_guardrails) asserte l'absence de dépendance réseau/clé dans le SDK : la souveraineté est vérifiée mécaniquement, pas seulement promise.

§3  Le modèle d'agent (5 traits, 43 agents)

Un agent est une fonction async sans état, à signature minimale. Toute la « surface agent » du système tient en cinq contrats (traits) :

trait Generator  { async fn generate(&self, task:&Value, variant:usize) -> Value; }     // propose 1 candidat
trait Verifier   { fn score(&self, task:&Value, cand:&Value) -> f64; }            // note ∈ [0,1]
trait Stage      { async fn process(&self, input:&Value) -> Vec<Value>; }        // 1 → 0..N
trait Decomposer { async fn decompose(&self, task:&Value) -> Vec<Value>; }     // tâche → sous-tâches
trait Merger     { async fn merge(&self, task:&Value, parts:Vec<Value>) -> Value; } // N → 1

La flotte standard : 43 agents

La flotte enregistre exactement 43 agents (assert vérifié dans fleet.rs) : 34 du catalogue Mode A + 9 juges. Répartition :

Quatre propriétés obtenues « gratuitement »

L'agent le plus simple, en entier. 
struct Uppercase;                                  // 0 champ de config
impl Stage for Uppercase {
  async fn process(&self, x:&Value) -> Vec<Value> {
    vec![json!({ "text": text_of(x).to_uppercase() })]    // 1 ligne utile
  }
}
Le plus « gros » du dépôt a deux champs (ex. LengthBounded{min, max}). Aucun agent ne dépasse cette taille — la complexité vit dans la composition, jamais dans l'agent.

§4  Les deux substrats d'échange (vérité / indice)

Si les agents ne gardent rien, l'information du run vit dans le substrat. EFE en utilise deux, complémentaires — c'est le keystone WS1 de l'architecture.

Blackboard — la VÉRITÉ durable

  • store adressé par contenu : DashMap<String, BlackboardValue> (verrou par shard, µs).
  • chaque pointeur a une version monotone (v1, v2…) — horloge logique locale.
  • CAS : write_if(ptr, version_attendue, …) atomique (réservation, accord).
  • write-sink : chaque écriture devient un maillon de provenance.
  • bornes : cap global d'octets + caps par namespace + ring de 8192 (mémoire O(1)).

Garantit la complétude : l'agrégateur reconstruit TOUS les ballots depuis /ballot/* — aucun vote perdu.

TopicRouter — l'INDICE éphémère

  • pub/sub partitionné : DashMap<topic, broadcast::Sender> — un canal par sujet.
  • publish(ev) → diffuse aux abonnés du seul topic concerné.
  • subscribe_prefix("ballot.") → fusionne plusieurs topics (un forwarder par topic).
  • capacité bornée → backpressure ; les drops sont comptés (jamais silencieux).

Corrige le goulot F1 : un bus global diffusait chaque événement à N agents → O(N²). Par topic ⇒ fan-out O(abonnés intéressés).

Pourquoi deux substrats — le compromis indice/vérité

Aucun seul ne suffit. Le bus seul est rapide mais peut perdre un message sous pression (canal borné) — inacceptable pour un vote (un vote incomplet est faux). Le tableau seul ne perd rien mais obligerait à scruter (polling, lent). Combinés : le bus réveille le consommateur (latence basse), le tableau lui garantit l'exhaustivité (correction). On résume : « le bus est l'indice, le Blackboard est la vérité ». Concrètement, un juge fait les deux : bb.write("/ballot/j", …) (vérité) ET router.publish("ballot.j", …) (indice).

§5  Les quatre topologies de câblage

La même flotte de nano-agents, câblée de quatre façons. C'est ici qu'est l'intelligence du système.

TopologieCâblageOù est le parallélismeQuand
T1 · Generate-VerifyK candidats → 1 vérificateur sélectionne le meilleurK générateurs en //tâche vérifiable (oracle)
T2 · Pipelineétages en chaîne, données en flux (streaming)items en vol simultanés / étagetransformation séquentielle
T3 · Hierarchicaldécompose → résout → fusionne (récursif)sous-tâches résolues en //problème décomposable
ConsensusK candidats + J juges + vote (Borda/Condorcet)générateurs ET juges en //non-vérifiable mais jugeable

Détails fonctionnels notables

  • Composition. Un Solver de T3 peut être lui-même un T1, un T2 ou un autre T3 → profondeur arbitraire. Un test démontre un « superviseur de superviseurs » (T3 dont le solveur est un T3).
  • Streaming (T2). Chaque étage est un agent asynchrone qui consomme un topic, traite, et émet vers le topic de l'étage suivant — ou écrit dans /out/* s'il est le dernier. Le pipeline s'arrête par quiescence (tous les topics drainés), pas par un compteur.
  • Fan-out/in. Un étage peut renvoyer 0, 1 ou N sorties — un filtre (0/1), un transformateur (1), un démultiplicateur (N). Le flux se réorganise dynamiquement.
  • Auto, conscient du mode. Auto regarde la tâche ET le mode : tâche vérifiable → T1 ; mode self-host (vrai LLM) → consensus N-juges (la délibération réduit l'erreur). Testé (auto_is_mode_aware).

Le mode self-host est le phare : le client lance l'essaim sur son modèle, sans clé, sans egress ; son régulateur re-prouve hors-ligne. §7  Le moat : la provenance vérifiable

Chaque appel d'agent produit un AgentCallRecord scellé. Les records forment une chaîne HMAC (chaque maillon couvre le précédent → détecte insertion/suppression/réordonnancement) et un DAG de causalité ; le contenu de chaque record est haché en blake3. Une racine unique (provenance_root, 64 hex) résume l'ensemble. verify_swarm recalcule tout à partir des seuls records + une clé tenant — hors-ligne.

Figure 2 — La chaîne de provenance et sa re-preuve. Muter un octet d'une sortie casse content_intact ; réordonner casse chain_intact ; les deux changent le root. La faute est localisée.
ADR-SWARM-009 : « le endpoint verify EST le produit ». La preuve ne dépend ni d'EFE ni d'un provider. Le client exporte GET /records et re-prouve avec sa propre clé tenant, sur une machine déconnectée. C'est le différenciateur qu'aucun fournisseur hébergé ne peut offrir sans renoncer à son lock-in.

§8  Le pont N17 (forensique par-appel)

Au niveau essaim, un AgentCallRecord dit quel agent, quelle entrée, quelle sortie. Le pont N17 ajoute une granularité par appel LLM : pour chaque agent Mode C (self-host / network), un LlmProvenanceRecord forensique capte le modèle, les paramètres, le seed, les hashs prompt/réponse, la latence, le retry_count. L'AgentCallRecord le référence via llm_provenance_id. Une seule lignée, deux granularités.

Le seam (sans réécrire les agents)

Le backend ne connaît pas le contexte d'essaim ; le Meter ne voit pas l'appel LLM brut. On les relie par un task-local (un « puits » par appel d'agent) : le Meter pose le puits, le backend y pousse sa fiche à chaque complete(), le Meter draine et assemble. Concurrence-safe : un puits par appel ⇒ pas de course même à K générateurs parallèles. Correct sous re-tentative : le Retrier (mode réseau) exécute chaque tentative dans un puits imbriqué et ne ré-émet qu'un record final (l'issue retenue, avec son retry_count), jamais un appel fantôme.

Le résumé du run (N17Summary) expose : calls (records LLM), mode_c_records, consistent, unlinked, broken, all_consistent. Prouvé en réel : sur Claude 3.5 Sonnet via routeur → consistent 4, unlinked 0, broken 0, all_consistent true ; et sur gemma3:12b en self-host local.

La conséquence profonde. Chaque pas de l'essaim — chaque écriture, chaque appel de modèle — est forensiquement lié à la chaîne de provenance. La circulation d'information n'accompagne pas la preuve : elle est la preuve. C'est ce qui permet de re-prouver, hors-ligne, « quel nano-agent a produit quoi, avec quel modèle, et pourquoi tel gagnant ».

§9  Le cycle de vie d'un run (ordre exact)

Voici la séquence réelle de run_traced — l'unique fonction qui exécute un run et expose sa provenance scellée. L'ordre est strict ; chaque étape a une raison.

  1. Rejet précoce de Network in-process. Si le mode est Network, on échoue immédiatement avec NetworkRequiresGateway : le réseau exige la passerelle serveur (clés). En pratique, la passerelle a déjà traduit Network → SelfHost (§2 du fonctionnement) avant d'arriver ici.
  2. Calcul du tarif. price = budget.price_per_call_cents.unwrap_or(mode.price_per_call_cents()) — le tarif explicite du client gagne, sinon celui du mode.
  3. Concrétisation + politique de pré-vol. Auto devient concret (selon tâche + mode). Puis : Degrade → on réduit la topologie pour tenir (degraded_to_fit) ; Error → si le coût estimé dépasse le plafond, BudgetTooLow (rien n'est exécuté) ; Stop → on laisse tel quel.
  4. Construction du backend + nature. Keyless → (None, ModeA) ; SelfHost → on construit le backend local (build_local_backend, qui applique le garde-fou egress) → (Some, ModeC).
  5. Health-check. Si require_healthy_backend, on sonde le backend ; injoignable ⇒ BackendUnavailable (échec rapide, pas N timeouts).
  6. Capture du descripteur backend (moteur + modèle + endpoint) pour la forensique — avant que le backend ne soit déplacé dans le résolveur.
  7. Câblage. SwarmId neuf ; ProvenanceRecorder ; BudgetGuard(plafond, tarif) ; collecteur N17 (seulement si ModeC) ; le Meter qui réunit tout ça + l'observateur.
  8. Substrat. Un puits de provenance (ProvenanceSink) ; si un observateur fournit un exutoire, on tee provenance + dashboard (la provenance reste byte-identique) ; on branche le tap d'événements (trafic inter-agent → dashboard) et les métriques de substrat.
  9. Résolution de la topologie. Chaque agent nommé est cherché dans la flotte et enveloppé du Meter (sinon UnknownAgent{role, name}). On obtient une topologie exécutable.
  10. Notification de démarrage (on_run_start) à l'observateur.
  11. Exécution : topo.run(&task, &ctx).await — le cœur (§14).
  12. Post-vol budget : politique Error + budget épuisé ⇒ BudgetExceeded.
  13. Collecte des records N17 (ModeC).
  14. Scellement + verify : on scelle la chaîne (seal_with_key), on appelle verify_swarm, on alimente les métriques partagées, on construit le résumé N17, on notifie on_seal.
  15. Assemblage du SwarmRun (les 9 champs, §13), notification on_finish, et retour du RunOutcome (run + sealed + llm_records).
Notre fil rouge. Keyless → étape 1 sautée, tarif 1¢ (étape 2), pas de dégradation (étape 3), pas de backend (étape 4-6), câblage sans collecteur N17 (étape 7), exécution du consensus (étape 11), scellement (étape 14), réponse (étape 15).

§10  Le micro-cycle d'un appel d'agent

La pièce la plus importante du fonctionnement. Aucun agent n'est appelé « nu » : il est enveloppé par le Meter dans un décorateur qui exécute toujours la même séquence de trois actes — facturer, exécuter (dans le scope forensique), capturer. Voici le code réel du générateur (les autres rôles sont identiques) :

impl Generator for MeteredGen {
  async fn generate(&self, task:&Value, variant:usize) -> Value {
    if !self.meter.charge(&self.id) {                 // ① FACTURE
      return Value::Null;                              //    budget épuisé → SENTINEL, on s'arrête
    }
    let (out, llm) = self.meter
        .run_agent(&self.id, Generator, self.inner.generate(task, variant)).await; // ② EXÉCUTE (scope N17)
    self.meter.capture(&self.id, Generator, Some(variant), task, &out, llm); // ③ CAPTURE
    out
  }
}

Acte ① — charge : payer avant de travailler

Le Meter facture le tarif (1¢ keyless / 0¢ self-host / 5¢ network) au BudgetGuard. Si le plafond serait dépassé, charge renvoie false : l'agent ne s'exécute pas, renvoie son sentinel, et rien n'est tracé (pas de provenance pour un appel qui n'a pas eu lieu). C'est exactement ainsi que la politique Stop dégrade : à court de budget, les agents deviennent des passe-plats neutres et la topologie continue avec ce qu'elle a.

Acte ② — run_agent : exécuter dans le scope forensique

On lance l'agent réel à l'intérieur d'un scope task-local (le puits N17). En Mode A (keyless), ce scope est vide — aucun appel LLM à capter — et run_agent renvoie simplement (sortie, None). En Mode C, le backend pousse sa fiche forensique dans le puits ; run_agent la draine, assemble un LlmProvenanceRecord, et renvoie (sortie, Some(ProvenanceId)) — le lien forensique. Détail concurrence : si plusieurs appels LLM sont poussés dans un même scope, run_agent les assemble tous et lie l'AgentCallRecord au premier ProvenanceId.

Acte ③ — capture : graver la preuve ET prévenir le dashboard

L'acte double. capture fabrique un AgentCallRecord (§11) — hash de l'entrée, hash de la sortie, rôle, variante, et (s'il existe) le lien llm_provenance_id — et le remet au ProvenanceRecorder (la preuve grandit d'un maillon). Puis, s'il y a un observateur, il notifie on_agent_call avec la sortie, le coût et l'état du budget — ce qui fait apparaître le candidat dans le panneau « consensus » et met à jour le panneau « budget » en direct.

Le sentinel, exhaustivement par rôle

Quand le budget est épuisé, chaque rôle renvoie un sentinel choisi pour préserver le flux, jamais une exception :

RôleSentinelEffet sur la topologie
GeneratorValue::Nullcandidat vide (les juges le noteront bas)
Stagevec![input.clone()]pass-through — le pipeline ne se rompt pas
Decomposervec![task.clone()]pas de découpe — la tâche entière passe
SolverValue::Nullsous-tâche non résolue
MergerValue::Nullfusion vide

Dans tous les cas : aucune exécution, aucune provenance, aucun coût. La topologie dégrade au lieu de planter — c'est le comportement « résultat partiel » de la politique Stop.

§11  L'anatomie d'un AgentCallRecord (15 champs)

C'est l'unité atomique de la preuve. Chaque appel d'agent (qui s'exécute réellement) en produit un. Sa structure est divisée en quatre zones, et la distinction entre ce qui est haché et ce qui est advisory (hors hash) est le secret de la reproductibilité déterministe.

Zone 1 — le contenu (engagé dans payload_hash)

agent_kindAgentKindModeA (déterministe) ou ModeC (LLM)

Zone 2 — advisory (HORS payload_hash — ADR-SWARM-007)

Le détail qui rend la reproductibilité possible. wall_at est advisory : on le conserve (utile pour le débogage et l'observabilité) mais il n'entre pas dans payload_hash. Conséquence directe : deux exécutions du même run, à deux instants différents, produisent le même provenance_root. Si l'horloge était hachée, aucune re-preuve déterministe ne serait possible. C'est l'application concrète d'ADR-SWARM-007 (« le rejeu déterministe se base sur la version, pas l'horloge »).

Ainsi, altérer n'importe quel champ de la zone 1 change payload_hash, donc hmac, donc tous les HMAC suivants, donc le root — et verify_swarm le détecte et localise le premier record en faute (first_break). On ne stocke jamais les données brutes, seulement leurs empreintes : la preuve est compacte et ne fuit pas le contenu.

§12  La concurrence bornée (en détail)

« En parallèle » ne signifie pas « sans limite ». EFE borne partout la concurrence par un sémaphore (un distributeur de P jetons) : pour s'exécuter, une tâche prend un jeton, le rend à la fin ; plus de jeton ⇒ on attend. C'est ce qui protège l'hôte (garde-fou G8, anti-déni-de-service).

Le schéma des générateurs / juges (JoinSet + Semaphore)

let sem = Arc::new(Semaphore::new(max_concurrency));   // P jetons
let mut set = JoinSet::new();
for variant in 0..k {
  set.spawn(async move {
    let _permit = sem.acquire_owned().await;     // borne : attend si P déjà pris
    (variant, gen.generate(&task, variant).await) // le micro-cycle complet (§10)
  });
}
while let Some(r) = set.join_next().await { /* collecte à mesure que ça finit */ }

On lance K tâches d'un coup, mais au plus P tournent en même temps. join_next collecte les résultats à mesure qu'ils finissent — on ne bloque pas sur le plus lent. Pour les juges, le même schéma avec tokio::spawn + le sémaphore.

Le schéma du pipeline (async_agent)

En T2, chaque étage est un agent asynchrone : une boucle while let Some(ev) = sub.recv() qui, pour chaque message, prend un permis, spawn le handler, signale on_done() à la fin, et rend le permis. Backpressure : si un modèle est lent, les P permis restent pris, la boucle cesse de consommer, et les messages s'accumulent dans le canal borné du bus (qui finira par dropper) plutôt que dans une file mémoire illimitée. La pression se propage proprement de l'aval vers l'amont.

Détail subtil — l'ordre « émettre puis créditer ». Le crédit de quiescence (on_done()) est signalé après que le handler ait émis ses sorties. Si on créditait avant, le compteur « en vol » pourrait atteindre zéro alors qu'une chaîne d'étages n'est pas finie → on terminerait trop tôt. L'ordre garantit qu'on ne déclare jamais la fin prématurément.

§13  Le write path, le CAS & la quiescence

Le chemin d'écriture (7 étapes)

Chaque write(pointer, value, agent) traverse : (1) validation du pointeur ; (2) mesure d'octets (ancien vs nouveau) ; (3) cap global — si ça déborde le budget mémoire total, refus SizeLimitExceeded + compteur de rejets ; (4) cap par namespace (le préfixe le plus spécifique l'emporte) ; (5) version++ (ancienne + 1) ; (6) insertion dans le shard DashMap (seul verrou, µs) ; (7) triple exutoire : write-sink (provenance), metrics (Prometheus), ring 8192 (rejeu). Le rejet est typé pour l'agent (il dégrade) et compté pour la télémétrie (jamais silencieux).

Le compare-and-swap (CAS)

write_if(ptr, version_attendue, value, agent) écrit seulement si la version courante vaut exactement version_attendue. La comparaison ET l'échange se font sous le même verrou de shard (correctif d'audit B-CAS) → deux écrivains concurrents sur le même pointeur sérialisent ; le perdant voit une version inattendue et réessaie. Aucune mise à jour perdue — prouvé par swarm_cas_invariant (somme exacte de N writers). C'est la primitive des réservations et accords.

La terminaison par quiescence à crédit

Comment savoir qu'un essaim a fini sans coordinateur ? Par un bilan : produced (émis) vs consumed (traités), avec in_flight = produced − consumed. Quand in_flight == 0 ET que les sources sont taries, l'essaim est quiescent. L'arrêt est élégant : les agents ne tiennent qu'un pointeur faible (Weak<TopicRouter>) ; le coordinateur drop l'unique pointeur fort → tous les canaux se ferment → chaque recv() renvoie None → les boucles sortent d'elles-mêmes et rendent leur rapport. Un timeout borne l'attente (anti-blocage) ; le rapport expose quiesced, produced, consumed, elapsed.

Le sharding déterministe (pour distribuer sans chef)

N items sur R workers, sans file partagée contendue : l'item i est possédé par shard_owner(i) = i mod R. Tous les workers calculent la même formule → accord sans communication. La notif d'un item est routée vers {base}.shard.{owner}, et seul le propriétaire y est abonné. Chaque item traité exactement une fois, partition stable (donc reproductible). Testé par work_queue_sharding.

§14  La génération, le jugement, le vote

Le cœur d'un consensus, phase par phase, en suivant notre fil rouge (K=3, 1 juge).

Phase 1 — la génération parallèle

Trois tâches sont lancées (variants 0, 1, 2), bornées par un sémaphore. Chaque générateur traverse son micro-cycle : charge 1¢ → exécute (un agent déterministe qui classe le texte) → capture un record. Le résultat est écrit sur le Blackboard en /cand/0, /cand/1, /cand/2 (la vérité durable). En keyless déterministe, les 3 candidats valent « legal ». Bilan : 3 appels = 3¢, 3 records, 3 valeurs sur le tableau. En self-host, les 3 candidats différeraient — c'est cette diversité que les juges départagent.

Phase 2 — le choix du motif, puis le jugement parallèle

Avant de juger, le système choisit le motif : en mode adaptatif, si les candidats sont en fort accord, un simple vote majoritaire suffit (et on peut sauter les juges, économisant des appels) ; sinon Borda ou Condorcet. Puis les J juges notent en parallèle (chacun son micro-cycle). Chaque juge produit un ballot (un score par candidat) et fait les deux écritures : bb.write("/ballot/j", scores) (vérité) ET router.publish("ballot.j", scores) (indice). Bilan pour notre fil rouge : 1 juge → 1 ballot, 1¢, 1 record.

Phase 3 — la réconciliation & le vote

L'agrégateur, abonné au préfixe ballot., est réveillé par le bus. Mais il ne compte pas depuis le bus : il relit le Blackboard (/ballot/0..J) — garanti exhaustif. Avec la matrice complète J×K, il applique le motif. Borda : chaque juge classe les candidats (rangs), un candidat marque (K−1) − rang points par juge, on additionne, le plus haut total gagne. La confiance = margin(points) / (|juges| × (K−1)) ∈ [0,1]. Les ex-æquo sont départagés déterministiquement (somme → premières places → index), jamais par l'ordre d'arrivée.

Calcul Borda, déroulé (exemple à 2 juges, 4 candidats). 
candidats : ["hello", "hi", "hello world", "h"]
juge 0 scores [0.998, 0.002, 0.5, 0.0001] → rangs [0,2,1,3] → points [3,1,2,0]
juge 1 scores [1.0, 0.5, 0.75, 0.0]       → rangs [0,2,1,3] → points [3,1,2,0]
Borda total = [6, 2, 4, 0]  →  gagnant = index 0 ("hello")
confiance = (6 − 4) / (2 × 3) ≈ 0,33
Notre fil rouge (keyless) : les 3 candidats valent « legal », notés identiquement → égalité parfaite → gagnant « legal », confiance 0 (aveu honnête : aucun vrai désaccord à trancher). En self-host, une confiance sous un seuil déclencherait une escalade humaine.

Condorcet (alternative) : un vainqueur bat tous les autres en duels (prefers) ; un cycle (A>B>C>A) est détecté (cycle_detected) → repli Borda. C'est « le consensus craque le non-vérifiable si on a des juges » (ADR-SWARM-004). Le candidat gagnant devient la sortie du run.

§15  Le scellement & la re-preuve (champ par champ)

Le scellement

À la fin du run, le ProvenanceRecorder a accumulé tous les AgentCallRecord. On les scelle (seal_with_key(clé_tenant)) : pour chaque record, on calcule payload_hash (blake3 du contenu), puis hmac = HMAC(clé, chain_parent_hmac ‖ payload_hash), en chaînant du premier au dernier. Le HMAC du dernier maillon, combiné, donne le provenance_root (64 hex). La clé tenant est dérivée par HKDF-SHA256 du master, salée par l'UUID du tenant — server-side, jamais exposée.

L'auto-vérification immédiate

Juste après le scellement, on appelle verify_swarm(records, clé) sur nos propres records — la même fonction qu'un tiers exécutera. Elle reçoit les records (dans un ordre quelconque) et la clé, et ne consulte aucun provider. Elle renvoie un SwarmProvenanceReport :

Champ du rapportTypeSens
recordsusizenombre d'enregistrements vérifiés
traced_pctf64fraction ancrée à une cellule durable (cible 100 %)
chain_intactbooltous les HMAC se recalculent (chaîne non altérée)
content_intactbooltous les payload_hash se recalculent (contenu non altéré)
dag_consistentboolDAG causal cohérent (parents existants, pas de lecture de version fantôme)
first_breakOption<Uuid>le premier record en faute (forensique), si rupture
rootOption<[u8;32]>le provenance_root reconstruit, si la chaîne est intacte

Le run est intégralement re-prouvé ssi chain_intact && content_intact && dag_consistent (méthode ok()). Ce booléen alimente provenance.verified du SwarmRun. On lance déjà cette vérification ici pour garantir qu'on ne renvoie jamais un run non re-prouvable.

Les trois dimensions d'altération. chain_intact tombe si on réordonne / insère / supprime un record (le chaînage HMAC casse). content_intact tombe si on mute une sortie (le payload_hash ne se recalcule plus). dag_consistent tombe si un record prétend lire une version qui n'a jamais existé, ou référence un parent absent. Les trois ensemble couvrent intégrité, ordre, et causalité. La faute est localisée par first_break (le record_id du premier maillon brisé).

§16  Le budget I13 & la gouvernance

Le BudgetGuard facture chaque appel d'agent. Son invariant I13 est absolu : le compteur ne dépasse JAMAIS le plafond, même sous concurrence.

Le mécanisme : ajout atomique puis revert

fn charge(&self, who:&str) -> bool {
  if self.price_cents == 0 { self.note(who, 0); return true; } // local/gratuit : compté, jamais plafonné
  let prev = self.spent.fetch_add(cents, SeqCst);        // ajoute d'abord (atomique)
  if prev + cents > self.max_cents {
    self.spent.fetch_sub(cents, SeqCst);            // REVERT : on annule le dépassement
    self.exhausted.store(true); false             // l'agent renverra un sentinel
  } else { self.note(who, cents); true }
}

L'astuce : on ajoute d'abord (opération atomique), puis si le total dépasse, on annule (fetch_sub). Comme l'ajout est atomique, deux threads ne peuvent pas tous les deux « passer » un appel qui ferait déborder : l'un voit le total au-dessus du plafond et reverte. La somme finale est toujours ≤ plafond. Prouvé par i13_holds_under_concurrency (8 threads × 1000 charges → spent ≤ 100).

Le snapshot exposé

À la fin, BudgetSnapshot expose spent_cents, max_cost_cents, remaining, et per_llm (la ventilation par agent, ordre déterministe). C'est ce qui alimente le panneau « budget » du dashboard et le champ budget du SwarmRun.

Le tarif zéro est spécial. En self-host (0¢/appel), charge compte l'appel (pour la ventilation) mais ne plafonne pas — un run local « gratuit » ne s'arrête jamais pour cause de budget. C'est cohérent : le coût d'un modèle local est en compute, pas en cents. En network (5¢), le tarif est préservé à travers la traduction (§2) pour que la gouvernance garde du mordant.

§17  Souveraineté, clés & déploiement

La règle absolue des clés

  • Aucune clé provider n'est jamais saisie, lue ou stockée par la passerelle. En network, elles vivent dans le routeur, server-side.
  • Le seul secret côté EFE est le master HKDF (EFE_NANO_AUDIT_HMAC_MASTER) qui signe la provenance — lu server-side via l'environnement, jamais transmis. Le binaire prod sélectionne EnvHkdf dès qu'il est présent ; sinon repli test_key() dev avec avertissement bruyant (le master de test est public → provenance forgeable).
  • OIDC : clé publique server-side uniquement.

Le déploiement souverain

EFE se déploie via un chart Helm dans le tenant Azure/AWS du client : la passerelle + un sidecar Ollama (modèles pré-provisionnés sur un PVC, OLLAMA_NOPRUNE, aucun pull réseau), une NetworkPolicy egress=deny (le pod ne peut pas sortir sur Internet), un Secret HKDF, et (features) PgRunStore + OIDC + PII. La donnée, le run et le modèle restent sur l'hôte ; seule la preuve (records + root) circule, et se re-vérifie sans clé ni réseau. C'est l'air-gap par construction.
