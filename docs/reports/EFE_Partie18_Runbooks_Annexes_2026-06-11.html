§1 La philosophie : des runbooks exécutables

Un runbook classique est une page de wiki : des étapes rédigées un jour, divergentes du code le lendemain. EFE prend l'autre voie, cohérente avec tout ce que cette série a montré : les runbooks sont des fichiers du dépôt — des exemples Rust et des scripts shell, versionnés avec le code qu'ils pilotent, compilés par la CI (un exemple qui ne compile plus casse le build), et dont l'en-tête documente la commande exacte.

L'inventaire de ces artefacts opérationnels, vérifié ce jour : côté SDK, cinq exemples — quickstart.rs (le premier contact), selfhost_flagship.rs et selfhost_ollama.rs (le mode phare), lot_p5.rs (rejouer le gate multi-modèles), bench_scale.rs (rejouer le benchmark de la Partie 14). Côté passerelle, un serveur de démonstration (serve_standalone.rs) et deux scripts de bout en bout (curl_e2e.sh, curl_network_e2e.sh) avec la configuration du routeur (litellm-config.yaml). Côté déploiement, trois charts Helm (efe-swarm-gateway, efe-agent-runner, efe-stack) et le Dockerfile de production. Chaque runbook ci-dessous cite son fichier — le texte explique, le dépôt exécute.

La conséquence pratique. « Documentation à jour » cesse d'être une discipline pour devenir une propriété : la dérive entre la doc opérationnelle et le code est détectée par le compilateur (exemples Rust) ou par l'échec du script (les E2E shell sortent en erreur au premier écart, set -euo pipefail). C'est le même principe que les tests-gardiens de la Partie 15 — la promesse transformée en vérification mécanique.

§2 Runbooks I — faire tourner les trois modes

2.1 — Keyless : la première minute

Le contact le plus court avec le produit : un seul terminal, aucune dépendance, aucun réseau.

cargo run --example quickstart -p efe-swarm-sdk

Ce qui se passe : un essaim Mode A (la flotte déterministe) exécute une tâche via swarm.run(task, TopologySpec::Auto, Budget::cents(…)) — Auto choisit un Generate-Verify à K = 3 (Partie 17, §3.2) — et le résultat affiche la sortie, la comptabilité, et le résumé de provenance. Ce qu'on doit voir : verified: true et une racine de 64 caractères hexadécimaux — la preuve, dès la première minute. La variante serveur du même contact : cargo run -p efe-swarm-gateway --example serve_standalone dans un terminal, puis ./crates/efe-swarm-gateway/examples/curl_e2e.sh dans un autre — le script enchaîne run → verify → records → metrics sur l'API HTTP (il exige curl et jq, rien d'autre).

2.2 — Self-host souverain : le mode phare

Prérequis : un Ollama local servant un modèle (ollama pull gemma3:12b puis ollama serve, ou le service déjà actif sur 127.0.0.1:11434).

cargo run --release --example selfhost_flagship -p efe-swarm-sdk

Ce qui se passe : le même SDK bascule en ClientMode::SelfHost — les noms d'agents deviennent des instructions au SLM local (Partie 4, §2.3), le garde-fou G2 vérifie que l'endpoint est bien une boucle locale, la sonde de santé échoue net si Ollama ne répond pas (« échec rapide plutôt que N timeouts »), et chaque appel LLM produit sa fiche N17 liée. Ce qu'on doit voir : des réponses réelles du modèle (donc des secondes de latence par appel — c'est normal, cf. Partie 13 §3), puis verified: true, un pont N17 cohérent, et aucune clé demandée à aucun moment. Pour rejouer le gate complet de la Partie 13 (les quatre critères à 1.0) : cargo run --release --example lot_p5 -p efe-swarm-sdk — long (plusieurs modèles × plusieurs runs), mais c'est la campagne GO elle-même, pas une simulation.

2.3 — Network réel : trois terminaux, la clé chez le routeur seul

Le runbook chorégraphié de la Partie 13 §6.3 — sa structure en trois terminaux est la démonstration de l'architecture des clés :

# T1 — le ROUTEUR (le seul endroit où une clé existe) :
export ANTHROPIC_API_KEY=…   # dans CE terminal uniquement
litellm --config crates/efe-swarm-gateway/examples/litellm-config.yaml --port 4000

# T2 — la PASSERELLE (pointée sur le routeur, zéro clé) :
EFE_SWARM_ROUTER_ENDPOINT=http://127.0.0.1:4000/v1 \
  cargo run -p efe-swarm-gateway --example serve_standalone

# T3 — le CLIENT :
./crates/efe-swarm-gateway/examples/curl_network_e2e.sh        # provider par défaut : anthropic

Ce qu'on doit voir : un run de consensus Borda dont le résumé affiche le modèle résolu par la RouterMap (anthropic/claude-3-5-sonnet-latest), verified: true, un spent_cents non nul (le tarif Network a survécu à la traduction — Partie 9–12 §1.3), et le pont N17 cohérent. Les pièges, documentés dans le script lui-même : un 501 signifie EFE_SWARM_ROUTER_ENDPOINT absent ; une erreur backend signifie routeur éteint, URL sans /v1, ou model_name non mappé dans la config LiteLLM. Le YAML du routeur ne contient aucun secret — il lit les clés par os.environ/… dans l'environnement de son propre processus.

§3 Runbooks II — la preuve, les tests, la production

3.1 — Re-prouver un run : l'opération du moat

La re-preuve a deux visages, selon qu'on est client de l'API ou auditeur hors ligne. Par l'API — le geste d'une ligne, sur n'importe quel run persisté :

curl -s http://127.0.0.1:8080/v1/swarm/verify/<run_id> | jq .

La passerelle recharge les enregistrements scellés (tenant-scopés), dérive la clé du tenant, exécute verify_swarm et rend le rapport — chaîne, contenu, DAG, racine reconstruite (l'ADR-009 : cet endpoint est le produit). Hors ligne — le scénario d'audit fort : exporter les enregistrements (GET /runs/:id/records, ou la colonne JSONB du store), puis, dans un programme Rust indépendant, appeler verify_swarm(&records, &clé_tenant) — aucune connexion au système d'origine, des années plus tard si besoin (Parties 7–8, §4.3). La clé du tenant se dérive du master via HmacKeySource::EnvHkdf — ou est remise au client selon sa politique de custody. Ce qu'on doit voir : ok() == true et une racine identique à celle annoncée à l'exécution ; toute divergence désigne l'enregistrement fautif et la raison (les cinq BreakReason, annexe A.2).

3.2 — Rejouer les vérités : tests, gates, benchmark

3.3 — La production : binaire, image, chart

Le binaire (Partie 9–12, §4.3) — la forme la plus directe :

EFE_NANO_AUDIT_HMAC_MASTER=…  DATABASE_URL=…  EFE_OIDC_PUBLIC_KEY_PEM=… \
  cargo run --release -p efe-swarm-gateway --features "postgres oidc pii" --bin efe-swarm-gateway

Ce qu'on doit voir au démarrage : la sélection de la source de clé (EnvHkdf si le master est présent) — et si le master manque, l'avertissement bruyant « la provenance serait FORGEABLE » : ce message en production est un incident, pas un détail. L'image : docker build -f crates/efe-swarm-gateway/Dockerfile -t <registre>/efe-swarm-gateway:<tag> . (le contexte est la racine du workspace) — multi-étages, non-root, healthcheck /metrics, aucune clé en couche. Le chart : charts/efe-swarm-gateway déploie la configuration souveraine par défaut — sidecar Ollama dans le pod, NetworkPolicy egress=deny, le master HKDF monté en Secret ; pour le mode Network, deux valeurs ouvrent l'egress vers le seul routeur (egressToNamespace, egressPorts) — le deny-all reste la règle, le routeur l'exception nommée. Les sondes liveness/readiness pointent /metrics, l'arrêt SIGTERM est gracieux : un rollout Kubernetes draine au lieu de couper.

La checklist de mise en production, en cinq vérités. (1) Le master HKDF est présent et le démarrage n'affiche pas l'avertissement de clé de test. (2) egress=deny est actif et la seule exception est le namespace du routeur, s'il y en a un. (3) /metrics répond — c'est la sonde de tout le reste. (4) Un curl_e2e.sh pointé sur l'instance rend verified: true. (5) L'admission-control n'existant pas encore (Partie 17, §6), l'exposition multi-tenant réelle attend sa garde — ou un contrôle d'amont (API gateway) en attendant.

A.5 Le glossaire

Les termes porteurs du projet — ceux qu'un nouveau lecteur doit posséder pour lire le code, les ADR ou cette série. Chaque entrée renvoie à la partie qui la développe.

Keystonele principe fondateur du substrat : le bus est un indice (peut tout perdre), le Blackboard est la vérité (durable) ; la perte d'indice est récupérable par réconciliation. (P3 §1)
Moatl'avantage défensif : chaque run re-prouvable par un tiers — « quel agent a dit quoi, quand, à partir de quoi » — sans coopération du fournisseur. (P7–8)
Nano-agentune fonction pure Rust implémentant un des 6 rôles — sans poids, sans état, sans réseau. (P4 §2)
Mode A / Mode Cnature d'un agent : déterministe (flotte) / LLM (backend local). Le même nom d'agent désigne l'un ou l'autre selon le mode. (P4 §2.3)
Keyless · SelfHost · Networkles 3 modes d'exécution : en-process / SLM local souverain (le phare) / routeur frontière server-side. (P5–6 §2)
Gate · Lotune campagne de mesure avec critères a priori et verdict (GO / NO-GO / INCONCLUS) ; rien ne se construit sans gate. (P13, P16)
ADRArchitecture Decision Record — une décision datée, motivée, citant son gate. (P16 §4)
CAS / write-onceécriture conditionnelle write_if(ptr, version) ; expected = 0 = « attendu absent » — la base des réclamations uniques. (P3 §2.3)
Lost updatel'écrasement silencieux entre écrivains concurrents — le bug que le CAS sous garde de shard rend impossible. (P3 §2.3)
Quiescencel'état « plus rien en vol ni en attente », détecté par compteur de crédits (emit-avant-done). (P3 §4)
Stigmergiecoordination indirecte par traces dans l'environnement partagé (le Blackboard) — la forme spécifiée du Gossip gaté. (ADR-003)
Seampoint d'extension par interface (WriteSink, EventSink, SwarmObserver) : observer sans coupler. (P3 §6.2)
Sentinella non-valeur neutre rendue quand budget/backend refusent — l'essaim dégrade sans paniquer. (P5–6 §5.1)
Enveloppe de capacitéla difficulté qu'un petit modèle gère en un coup ; T2/T3 ramènent les tâches dures dedans. (P4 §6)
Oracle ORborne haute de toute sélection : « juste si au moins un candidat est juste » — prouve le gisement, n'est pas un sélecteur. (P13 §2.1)
Borda · Condorcet/Copelandagrégations ordinales : somme des rangs / duels pairwise (+ bilan de victoires sur cycle). (P4 §5)
Escaladepayer le jugement fin seulement si la confiance du vote gratuit est insuffisante. (P4 §4.3)
payload_hash · provenance_rootSHA-256 du corps canonique d'un atome / le tip de la chaîne HMAC — l'engagement unique du run. (P7–8 §2–3)
N17 · LlmProvenanceRecordla fiche forensique d'un appel LLM (modèle, hashs de prompts, sampling, jetons, retries), liée à l'atome par llm_provenance_id. (P7–8 §6)
traced_pctfraction d'enregistrements ancrés à une écriture durable — qualité de capture, pas intégrité. (P7–8 §4.2)
Tenantl'unité d'isolation : clé HKDF dédiée, stockage scopé, politiques (PII) par tenant. (P7–8 §5)
I13 · I17invariants : budget jamais dépassé (débit atomique + revert) / aucune garde de shard tenue à travers une suspension. (P5–6 §6, P3 §2.3)
G2 · G3 · G8 · G9 · G10garde-fous : egress refusé par défaut · circuit-breaker · bornes mémoire · PII par tenant · zéro dépendance réseau dans le SDK. (P9–12)
Breaker · Retrierla pile de résilience : couper après 5 échecs/15 s · re-tenter 3× (egress seulement), un seul record N17 final. (P9–12 §3)
Egresstout trafic sortant de la machine/du pod — refusé par défaut (G2, NetworkPolicy deny), ouvert nommément vers le seul routeur. (P9–12)

S'il fallait résumer la série en un paragraphe, ce serait celui-ci. EFE est une machine à transformer du calcul bon marché en réponses sélectionnées — beaucoup de très petits agents en parallèle sur un substrat qui sépare la vitesse de la vérité — et chaque pas de cette machine laisse une preuve qu'un tiers re-vérifie seul, hors ligne, des années plus tard. Le client n'y manipule jamais une clé ; le déploiement phare tient sur une machine coupée du réseau ; le coût de la preuve se mesure en microsecondes ; et la culture qui a produit le système — gates avant le code, verdicts négatifs conservés, absences démontrées — est la même que celle qu'il vend. Tout ce qui précède est dans le dépôt : le code, les mesures, l'histoire, et les commandes pour tout refaire.
