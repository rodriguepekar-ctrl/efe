§4  Integration architecture

EFE inserts as an execution & proof layer. Your platform stays the brain (Blueprints, Mission Control, Integration Hub, UX); EFE is the verifiable muscle that runs each swarm operation and seals its proof, which then flows back into your System of Record.

Figure 1 — EFE inserts beneath your Agent Runtime (swarm execution) and feeds your System of Record (proof). You keep your entire product surface; EFE is invisible to the business user.

The integration contract, in one line

Your runtime sends EFE a task + topology + budget + mode; EFE returns an output + a proof (provenance_root, records, N17 summary). You store the proof in your System of Record and can re-verify it at any time — live or offline. No code coupling: the exchange is JSON over HTTP, or an in-process Rust call.

The request lifecycle, end to end

When your Agent Runtime delegates an operation, here is the exact sequence on EFE's side:

  1. Auth & mode resolution. The gateway checks the caller's role (RBAC / OIDC) and resolves the requested mode into an executable backend (sovereign self-host, or — if a router is wired — Network).
  2. Budget pre-flight. It estimates the cost (agents × per-call price) and either proceeds, degrades the swarm to fit, or refuses up front — per your on_exceed policy.
  3. Parallel execution. The topology runs the nano-agents on the substrate (K generators ∥, J judges ∥), each call metered, traced, and N17-linked.
  4. Seal & self-check. The records are sealed into an HMAC chain producing a provenance_root, and verify_swarm re-proves the run immediately (so a corrupt run never returns “verified”).
  5. Persist & return. Records are stored (write-once); the response carries the output + proof + governance signals.

Steps 3–4 are where the value concentrates: the operation is executed and proven in the same pass, so there is never a gap between “what ran” and “what we can prove ran.”

§5  What EFE is (technical core)

To position the integration surfaces, here are EFE's five mechanics — all implemented and tested.

5.1 — Nano-agents

EFE ships 43 deterministic Mode-A agents: tiny, single-purpose Rust structs with no weights. They cover six roles (generators, verifiers, stages, decomposers, mergers, judges) and are assembled by name through an AgentFleet. To make this concrete, here is a complete agent — the entire logic is one line:

struct Uppercase;
impl Stage for Uppercase {
    async fn process(&self, input) -> Vec<Value> { vec![json!({ "text": text_of(input).to_uppercase() })] }
}

In Mode C (self-host), that same “name” becomes an instruction prompt sent to a local SLM — the topology code does not change. This is how you can take a Kovant “digital colleague” and run it either as a deterministic agent or as an SLM, behind one interface.

5.2 — Communication substrate

Two organs. A Blackboard (a DashMap keyed by JSON-pointer, per-field versioning, compare-and-set writes, memory bounds) is the durable truth; a TopicRouter (per-topic broadcast) is the live index. Agents write /cand/* and /ballot/* in parallel — sharding means no global lock, so many agents really do run at once. Two decoupled seams (WriteSink, EventSink) expose every write and event to provenance and to your Mission Control feed, with zero coupling to the topology.

The golden rule (which matters for correctness): the bus is the index, the Blackboard is the truth. The aggregator never trusts the bus to decide — it reads a snapshot() of the Blackboard, so it is guaranteed to see every ballot even if a live message was dropped.

How dozens of agents write at once without corrupting each other

This is the question every parallel-agent system must answer, so it is worth being concrete. EFE solves it at two levels. First, sharding. The Blackboard is a DashMap — internally split into many independently-locked shards. When generator A writes /cand/0 and generator B writes /cand/1, their keys land in different shards, so neither waits for the other. A single global lock would serialise every agent and kill the parallelism; sharding is the technical reason “many agents at once” is actually viable. Second, compare-and-set. When two agents target the same key, EFE uses write_if(pointer, value, expected_version): the write only lands if the stored version is still the one you read. Example: A and B both read /x at version 3; A writes → it becomes v4; B tries “write if v3” → rejected, and a conflict counter increments. No silent loss — you either win, or you are explicitly told you were working on stale data and can re-read.

5.3 — Four parallel topologies

PatternMechanicsTypical Kovant use
T1 Generate-VerifyK generators in parallel → deterministic a-posteriori verifierextract a verifiable field from a PDF/email (amount, PO number)
T-ConsensusK gens ∥ + J judges ∥ → Borda/Condorcet + confidence + escalationclassify/route a request (compliance, spend category) where there is no mechanical truth

The selection principle (S1): on a verifiable task the correct answer is often present but a minority among K cheap candidates; a majority vote would miss it, an a-posteriori verifier (or a judge panel) extracts it. That is precisely how small models are made reliable — by the swarm, not by any single agent.

A consensus run, step by step (K=7 generators, J=2 judges)

  1. Parallel generation. Seven generator tasks run concurrently (bounded by a semaphore so a slow SLM can't overwhelm the host). Each gets a variant index 0–6 — the diversity lever (different temperature/persona/seed). The seven candidates are written to /cand/0…6 on the Blackboard.
  2. Free vote first (cost-aware escalation). A plain majority vote is tried without judges; if its confidence ≥ threshold, the run stops there — judges are saved (cost = 7). Otherwise it escalates.
  3. Parallel judging. Two judges run concurrently; each reads all seven candidates, writes its ballot to /ballot/0…1 (truth) and publishes on the bus (live index for your Mission Control).
  4. Reconciliation. The collector drains the bus for timing, then re-reads the Blackboard (snapshot()) to reconstruct all ballots exhaustively.
  5. Aggregation. Borda combines 2 ballots × 7 candidates into a winner + a confidence score, then publishes the decision event.

Why a judge panel beats a vote — a worked example

Borda awards each candidate points = Σjudges ((K−1) − rank). With three candidates (K=3): 1st → 2 pts, 2nd → 1, 3rd → 0.

CandidateJudge 1Judge 2Borda total
A1st → 21st → 24 ← winner
B2nd → 13rd → 01
C3rd → 02nd → 11

Now imagine 7 candidates where 3 are correct (but varied) and 4 are the same wrong answer: a majority vote picks the wrong one (it has the plurality), while Borda — using the judges' full ranking — surfaces a correct one. The returned confidence = margin (1st − 2nd) ÷ max possible gain: it is 0 when everything ties (e.g. identical candidates) and high when one clearly dominates. Your Mission Control can use that single number as an escalation trigger.

5.4 — Verifiable provenance

Every step produces an AgentCallRecord (blake3 input/output hashes, role, DAG parents, N17 link). Records form an HMAC chain signed by a per-tenant key (HKDF-derived, never transmitted). verify_swarm recomputes chain + content + DAG + root offline; any tampering breaks the proof and is localised to the offending record.

What “signing” actually means here

At the end of a run, EFE chains an HMAC across the records:

hmac₀ = HMAC(tenant_key, genesis ‖ record₀)
hmacᵢ = HMAC(tenant_key, hmacᵢ₋₁ ‖ recordᵢ)     // each link seals the previous one
provenance_root = f(hmac…) → 64 hex

The tenant key is derived via HKDF-SHA256 from a master + the tenant UUID; it signs and is never transmitted or stored in a record. Two tenants get two keys → two incomparable chains (isolation).

The three checks of verify, and what each catches

  • chain_intact — recomputes the whole HMAC chain → catches any insertion, deletion, or reordering of records (the structure).
  • content_intact — recomputes the blake3 input/output hashes → catches a single mutated byte in any output (the content).
  • dag_consistent — checks that the causality edges (parents) point to coherent records (the graph of who-fed-whom).

All three pass ⇒ verified = true and the recomputed root equals the original. The computation needs nothing but the records and the tenant key — so a regulator runs it on a disconnected machine.

5.5 — Three model modes

Keyless (deterministic nano-agents — demo/anchor), Self-host (local SLM, sovereign, zero keys — the flagship for your EU customers), and Network (frontier model via a server-side router that holds the keys — for the cases that need a large model). Resolution is automatic and the default is sovereign: Network only activates if an operator explicitly wires a router URL.

5.6 — The per-call “why” (N17 bridge)

Your System of Record wants “what every digital worker did and why.” There is an information gap to bridge: the backend knows the model/prompt/response but not the swarm context (which agent, which tenant); the orchestration layer knows the context but not the raw LLM call. EFE links them with a task-local sink: before an agent call, the orchestrator installs a sink; the backend, on each completion, deposits its forensic record into the current sink (a no-op outside a scope); when the call returns, the orchestrator drains the sink, adds the swarm context, and produces an LlmProvenanceRecord — model, seed, parameters, prompt/response hashes, latency, retry count — which the AgentCallRecord references. It is concurrency-safe by construction (one sink per agent call), so even with seven generators in flight nothing gets mixed up. Retries emit exactly one final record (with a retry count), so the link always points to the outcome that mattered, never to a failed attempt.

§8  The verifiable System of Record

This is the most differentiating piece for Kovant. Your System of Record captures “what every digital worker did and why” as a journal (an auditable trail). EFE upgrades it from a journal you have to trust to a proof you can re-verify — an audit proof.

Journal (today)

“Here are our logs: agent X decided Y.” → you must trust the integrity of the logs. A log can be edited after the fact; nothing proves it wasn't.

Proof (with EFE)

“Here are the records + a root. Recompute them with the tenant key: if a single byte moved, it breaks, and we tell you where.” → no trust required, re-verifiable by a third party, offline, months later.

What you store, and how you re-prove

  1. For each operation, store in your System of Record: the run_id, the provenance_root (64 hex), and the records export (JSON). Small and durable.
  2. Live audit: GET /v1/swarm/verify/:id → {verified, chain_intact, content_intact, dag_consistent, root}. Wire a “re-prove” button into Mission Control.
  3. Offline / third-party audit: hand over the records export + the tenant key; verify_swarm runs on a disconnected machine, with no call to Kovant or a provider. This is the “the regulator doesn't trust us” scenario — and it is exactly the promise.

The per-call “why” (the N17 bridge)

You want “what every digital worker did and why.” EFE's N17 bridge attaches to each SLM call an LlmProvenanceRecord: which model, seed, sampling parameters, the hashes of the prompt and response, latency, and retry count. The swarm-level AgentCallRecord references it. So for a contested decision you can trace down to “the compliance-checker digital worker called qwen3:30b with this exact prompt and got this exact response” — and verify it.

A tampering attempt, step by step

Suppose someone with access to the stored records wants to make it look like the swarm classified an invoice as “opex” instead of “capex.” They edit the winning record's output. What happens at the next verify?

  1. verify recomputes output_hash = blake3("opex") and compares it to the sealed hash (blake3("capex")) → mismatch → content_intact = false.
  2. To “fix” that, they would have to change the sealed hash too. But that hash feeds the record's HMAC, so hmacᵢ changes → chain_intact = false from that link onward.
  3. To “fix” the chain, they would need to recompute every subsequent HMAC — which requires the tenant key, which they do not have (it is nowhere in the records; it lives server-side).

Result: verified = false, and first_break points at the offending record. The forgery is detected and localised. Without the key, no valid chain can be forged — which is why the production binary signs with the real EnvHkdf master rather than a default test key. This is the scenario behind the measured “tamper detected 100%.”

Commercial angle for Kovant: in Nordic industry & manufacturing (your customer segment), audits (ISO, supplier, sector regulators) demand demonstrable traceability. “Audit proof” instead of “audit trail” is a differentiating sales argument — and it is already-tested code (Lot P5: tamper detected 100% across three models).

§10  PII, compliance & governance

PII: local redaction for unstructured inputs

Your operations are “filled with unstructured inputs like emails and PDFs” — which often carry personal data. EFE (the pii feature) redacts locally (regex for email/SSN/card/IBAN/IP/phone) — no network service, air-gap-compatible. Crucially, it redacts the presentation (returned output, previews, at-rest copy), not the records → the proof still re-verifies the original. It is opt-in per tenant: a strict-GDPR customer enables Redact, another stays Off, with no recompilation.

Budget governance is one more guardrail

The I13 invariant guarantees an operation never exceeds its cost cap (atomic, proven under concurrency). Three policies map your needs:

  • Error: refuse if the estimate exceeds the cap → strict guarantee (not a cent over).
  • Degrade: shrink the swarm (K, judges) to fit → complete but smaller operation.
  • Stop: execute and stop cleanly at exhaustion → partial result, flagged.

Human-in-the-loop: crisp machine signals

You emphasise human-in-the-loop & escalations. EFE provides machine signals (already in the SwarmRun response) that your Mission Control can route to its existing escalation rules:

§11  Security & key management

EFE rigorously distinguishes two things both called “keys” — which simplifies your security posture.

“Key”RoleWhere it lives
Provider keys (Azure OpenAI, Anthropic…)spend money at a third partyONLY in the Network router (server-side). Never in the swarm layer or in Kovant. In self-host: no key at all.
HKDF master (EFE_NANO_AUDIT_HMAC_MASTER)signs provenance (spends nothing)read server-side from the environment; derives a per-tenant key; appears in no record
OIDC (feature)authenticates callers (RBAC)a server-side public key only (never a private key)
  • Tenant isolation. The provenance key is derived per tenant (HKDF + UUID): two customers' chains are incomparable. A customer re-proves with their key.
  • RBAC. Routes require a role (operator/admin); in production a JWT is validated against your IdP (public key).
  • Verified at compile time. A CI test asserts the SDK pulls neither reqwest nor TLS and emits no auth header — sovereignty isn't just a claim.
  • Write-once persistence. The PgRunStore (postgres feature) stores records durably and write-once (the proof cannot be rewritten).
For your security due-diligence: EFE can run with no keys at all (Keyless/Self-host). The only secret introduced in production is the HKDF signing master (no access, no spend) — a Kubernetes Secret mounted server-side, never transmitted. This is a minimal risk profile.

§14  Anticipated questions

Does EFE replace our Agent Runtime or Blueprints?

No. EFE sits beneath the runtime as an execution engine and behind the System of Record as a proof source. Your Blueprints, Mission Control, Integration Hub and UX are untouched.

You say “verifiable” — does that mean the LLM is reproducible?

No, and we are deliberate about this. We never promise bit-for-bit LLM reproducibility. We promise forensic re-provability: we prove that what was produced has not been altered, and by which agent / in which order. Deterministic Mode-A agents are reproducible (they are the anchor); LLM outputs are captured and tamper-evident.

We're model-agnostic and use Azure OpenAI/Bedrock. Compatible?

Yes. Self-host covers any local SLM (Ollama/vLLM/llama.cpp). Network covers frontier models via an OpenAI-compatible router you point at Azure OpenAI/Bedrock — with provider keys held at the router, never in the swarm layer. The swarm code is identical across modes.

Our stack is TypeScript/Python, not Rust. Is that a problem?

No. The primary surface is the HTTP API — language-agnostic JSON. The Rust SDK is an option for in-process components. Only custom deterministic agents are written in Rust; business logic can also be expressed as instructions to an SLM (Mode C) with no Rust at all.

How heavy is the proof to store?

Light: a run_id, a 64-hex root, and a compact JSON records export per operation. It is write-once and durable (Postgres in prod).

What does it take to operate?

A Helm release in your Azure/AWS tenancy (gateway + SLM sidecar), one Kubernetes Secret (the HKDF signing master), and a Prometheus scrape. No external dependency in self-host mode.

Can a customer verify without us?

Yes — that's the point. Give them the records export and their tenant key; verify_swarm runs offline on a disconnected machine. Neither Kovant nor a provider is in the loop.

What's the licensing / commercial model?

To be discussed. EFE is the source's project; engagement options range from a source/embed license to a co-development arrangement around the integration above.
