Thèse du document. Le Mode C ne demande aucune nouvelle structure de preuve : la chaîne d'essaim, le pont N17, la souveraineté locale et l'injection few-shot existent et tournent (harnais Ollama #[ignore]). Ce qu'il demande, c'est une compréhension exacte de la bascule du moat (reproduction → attestation) et une seule mesure manquante : l'influence du few-shot sur un vrai modèle. Les quatre autres lectures-retour (taille, pattern, réputation-agrégation, réputation-sizing) sont agnostiques au mode — elles opèrent sur des candidats opaques, déjà chiffrées en Mode A, et un run Mode C les confirme actives sans rien à re-mesurer. Le harnais #[ignore] n'est pas un aveu de faiblesse : c'est la réponse honnête à « on ne simule pas un LLM ».

§1 Le principe : reproduire → attester

Tout le moat d'EFE repose sur une idée : la sortie d'un essaim doit être re-prouvable hors-ligne par un tiers qui ne fait pas confiance à l'opérateur. En Mode A, cette re-preuve a une forme forte et rare — la reproduction. Les agents de la flotte sont des fonctions pures de (tâche, variant) ; un vérificateur qui connaît le code peut, depuis l'instantané scellé, rejouer chaque agent et retrouver l'octet exact (ADR-017, mode R1 ; c'est ce que mesure replay_outputs). La preuve ne demande pas de confiance : elle re-calcule.

Le Mode C casse cette possibilité, et il faut le dire sans détour. Un vrai modèle de langage est stochastique : deux appels au même prompt, même à température basse, peuvent diverger (échantillonnage, non-déterminisme matériel, versions de modèle). On ne peut donc pas « rejouer le LLM et retrouver l'octet ». La reproduction (R1) n'est pas disponible en Mode C — et prétendre le contraire serait malhonnête.

Mais le moat ne s'effondre pas : il bascule. Là où le Mode A reproduit la sortie, le Mode C l'atteste. Chaque appel LLM produit un record forensique signé — un LlmProvenanceRecord (le « N17 ») — qui fige le prompt, la sortie, le modèle et les paramètres, chaîné et lié au record d'essaim correspondant. Le vérificateur ne re-calcule pas la sortie ; il constate, preuve cryptographique à l'appui, exactement ce que le modèle a produit, lié à exactement ce run, pour exactement ce tenant. La non-confiance est préservée par une voie différente : non « je refais », mais « je tiens une attestation infalsifiable de ce qui fut fait ».

R0 (re-prouver la chaîne) vaut pour les deux modes. La reproduction exacte (R1) est le privilège du déterminisme Mode A ; le Mode C la remplace par l'attestation forensique N17.

Le mot juste. En Mode C, le run reste auditable et infalsifiable ; il n'est pas rejouable. La distinction n'est pas une concession — c'est la nature de la chose. Un régulateur ne demande pas « refaites tourner le modèle » ; il demande « prouvez-moi ce que le modèle a produit, et que vous n'avez pas falsifié après coup ». Le N17 répond exactement à cette question.

La mesure qui manque. Aucun de ces harnais ne mesure l'influence du few-shot : injecter des exemplaires change-t-il, de façon mesurable et bornée, ce que le modèle produit ? C'est l'unique lecture-retour d'ADR-019 qui touche le prompt du LLM — donc la seule dont l'effet ne peut PAS être chiffré en Mode A (où il n'y a pas de prompt, I-MEM8). C'est précisément l'objet du gate Mode C proposé au §11.

§3 La structure : entrée re-prouvable → [LLM] → sortie attestée

La clé pour raisonner sur le Mode C est de voir où, exactement, le non-déterminisme entre — et de constater qu'il est encerclé des deux côtés par du re-prouvable. Un appel de générateur Mode C se décompose en trois temps :

Le « sandwich » Mode C : un prompt re-prouvable, un LLM stochastique encerclé, une sortie attestée. La preuve mord aux deux extrémités du maillon non-déterministe.

Le prompt (①) est re-prouvable. Il est une fonction déterministe de l'instantané pinné : gen_prompt(instruction, task, exemplars) où les exemplaires viennent de la cellule mémoire épinglée (R1 ré-épingle le même instantané → mêmes exemplaires → même prompt octet, llm.rs), et où la température et la graine sont 0,2 + 0,3·variant et 42 + variant — pures fonctions du variant. Un tiers reconstruit le prompt exact sans toucher au modèle.

La sortie (③) est attestée. Le record N17 fige le prompt_hash et l' output_hash ; le record d'essaim le référence par llm_provenance_id. Le vérificateur lie l'entrée re-prouvée (①) à la sortie attestée (③) et constate la cohérence : ce prompt-ci a produit cette sortie-là, signée, à cet instant, dans ce run.

Le LLM (②) est le seul maillon non rejouable — et il est encerclé. C'est la structure élégante du Mode C : on n'élimine pas le non-déterminisme (impossible), on le confine à un segment unique, borné des deux côtés par du re-prouvable et du signé. La chaîne entière (R0) re-prouve ; seule la flèche du milieu échappe à R1, et le N17 est précisément ce qui la rend néanmoins infalsifiable après coup.

§4 Le pont N17 : l'attestation forensique par-appel

Le pont (bridge.rs) lie chaque record d'essaim à son record LLM. Sa fonction-pivot, classify_link, est un oracle de cohérence qui ne laisse passer aucune ambiguïté entre les modes. Sa logique mérite d'être lue telle quelle, car c'est elle qui définit ce que « N17 cohérent » veut dire :

match record.agent_kind {
    ModeA => if record.llm_provenance_id.is_some() { UnexpectedLinkOnModeA } // un agent déterministe NE DOIT PAS avoir de N17
             else { ModeA },
    ModeC => match record.llm_provenance_id {
        None        => Unlinked,            // lacune : l'agent LLM n'a pas exposé son id N17
        Some(id)    => match resolver.resolve(id) {
            None        => Missing,          // pointeur PENDANT : id présent, record introuvable
            Some(view)  => if view.tenant_id != record.tenant_id        { TenantMismatch }   // fuite inter-tenant
                           else if view.swarm_request_id != record.swarm_id { SwarmMismatch }  // record d'un AUTRE run
                           else                                            { Consistent },
        },
    },
}

Sept statuts, dont un seul — Consistent — est acceptable pour un appel Mode C. Les six autres sont des défauts nommés : un Mode A qui porte un lien (contamination), un Mode C sans lien (lacune d'instrumentation), un pointeur pendant (record perdu ou falsifié), une fuite inter-tenant, un record emprunté à un autre run. Le résumé du run agrège ces verdicts : N17Summary{calls, mode_c_records, unlinked, broken, all_consistent} (result.rs). Le contrat est binaire et dur : all_consistent exige unlinked == 0 ∧ broken == 0 et chaque Mode C lié, tenant et run vérifiés.

Pourquoi c'est le moat de Mode C. Le N17 ne reproduit rien — il atteste. Mais il atteste sous une triple contrainte cryptographique : le record est signé (HKDF tenant-scopé), chaîné (chaque N17 lie le précédent), et lié au bon run et au bon tenant (les vérifications TenantMismatch / SwarmMismatch). Falsifier ce qu'un modèle a produit demanderait de re-signer toute la chaîne N17 ET la chaîne d'essaim ET de faire coïncider tenant et run — exactement l'effort que le moat rend infaisable sans le secret maître. Le non-déterminisme du LLM ne donne donc aucune marge à la falsification.

La parité avec Mode A est exacte sur le seul point qui compte : R0 ne change pas. verify_swarm re-hash la chaîne d'essaim de la même façon, que les records soient Mode A ou Mode C — il ne connaît que des hash d'entrée/sortie et un ordre canonique (ADR-007). Le N17 est une seconde chaîne, forensique, que verify_n17_chain vérifie en plus. Mode C = Mode A pour R0, + l'attestation N17 là où R1 ne peut plus mordre.

§5 La stratification des lectures-retour par mode

Voici l'observation qui rend le Mode C bien plus simple qu'il n'en a l'air. Les cinq lectures-retour de la mémoire d'ADR-019 n'ont pas le même rapport au mode. Quatre opèrent sur la couche consensus/sizer, qui traite les candidats comme des valeurs opaques — elle ne sait pas, ne veut pas savoir, si un candidat vient d'une fonction Mode A ou d'un LLM. Une seule, le few-shot, touche le prompt — donc le LLM lui-même.

La conséquence est libératrice. Les quatre lectures agnostiques sont déjà chiffrées (gates Mode A : PATBIAS, REPUTATION, SIZER_REPUTATION, le warm-start) et un run Mode C les exerce sans rien de neuf à mesurer — la couche consensus/sizer ne distingue pas l'émetteur des candidats, donc une preuve faite sur des candidats Mode A vaut sur des candidats Mode C (mêmes types, mêmes fonctions, même véto). Un harnais Mode C les confirme actives (elles tournent vraiment dans le pipeline LLM), mais ne re-démontre pas leur logique.

Reste le few-shot, seul cas à mesurer, précisément parce qu'il est le seul dont l'effet n'existe pas en Mode A : sans prompt, injecter des exemplaires ne fait rien (I-MEM8, vérifié). Son influence — change-t-elle, et de combien, la sortie d'un vrai modèle ? — ne peut se chiffrer que sur un vrai modèle. D'où le harnais #[ignore].

Ce n'est pas un hasard, c'est une conception. Si quatre des cinq lectures « marchent déjà » en Mode C, c'est parce qu'elles ont été conçues agnostiques dès le départ — elles vivent dans la couche topologie, qui manipule des Value opaques. Cette discipline (la mémoire amorce le consensus, pas l'agent) est ce qui rend le passage en Mode C presque gratuit. Le few-shot est l'exception assumée : il amorce l'agent, donc il dépend de la nature de l'agent.

§6 Le few-shot vivant : la seule lecture qui touche le prompt

Le few-shot est, en Mode C, là où la mémoire parle au modèle. Sa mécanique est volontairement minimale et testable sans backend (gen_prompt est pure) :

fn gen_prompt(instruction, task, exemplars) -> String {
    if exemplars.is_empty() {
        // I-MEM8 : forme HISTORIQUE exacte — byte-identique au chemin sans mémoire.
        format!("{instruction} Text: \"{task}\". Answer with only the result, no preamble.")
    } else {
        // bloc few-shot : les aperçus de gagnants passés, recall-és de l'instantané pinné.
        format!("{instruction} Examples of good past answers:\n{- e1\n- e2 …}\n\nText: \"{task}\". …")
    }
}

Trois propriétés en font une lecture bornée et re-prouvable, fidèle à la colonne vertébrale d'ADR-019 (« amorcer sans gouverner ») :

  • Re-prouvable (l'entrée) — les exemplaires viennent de l'instantané pinné ; R1 ré-épingle le même instantané → mêmes exemplaires → même prompt octet. L'influence du few-shot est donc une fonction déterministe de la mémoire passée, anchorée dans le record MemoryRead (I-MEM2 : la version et le content_hash de l'instantané lu entrent dans la racine). Un prompt influencé par un recall non tracé serait invalide — il ne peut pas exister.
  • Bornée — au plus FEWSHOT_N exemplaires ; ce sont des aperçus de gagnants passés, pas la réponse. Le modèle reste libre de répondre à la tâche ; les exemplaires orientent, ils n'imposent pas.
  • Dormante sans donnée — exemplaires vides ⇒ prompt strictement historique (I-MEM8). En Mode A, il n'y a jamais de prompt : le few-shot y est un no-op honnête (l'extraction se fait, sans effet). La lecture ne « s'éveille » qu'en Mode C, et seulement quand la mémoire a des gagnants à montrer.

La sortie, elle, est attestée (N17) — comme toute sortie Mode C. Donc le few-shot hérite exactement de la structure du §3 : un prompt re-prouvable (incluant les exemplaires anchorés) → un LLM stochastique → une sortie attestée. La seule chose neuve qu'un harnais doit établir est empirique : sur un vrai modèle, ce bloc d'exemplaires déplace-t-il la sortie dans le bon sens, et de façon bornée ? C'est une question de mesure, pas de structure — et c'est pourquoi elle exige un vrai modèle (§10–11).

§7 R-b/R-c en Mode C : le profil EST la (température, graine)

Une subtilité mérite un développement, car elle renforce la valeur de l'ouverture R-b/R-c qu'on vient de livrer. En Mode A, le « profil » variant = i désigne une variante de flotte — une fonction déterministe distincte. En Mode C, le variant pilote l'échantillonnage : la température et la graine sont 0,2 + 0,3·variant et 42 + variant (llm.rs). Le profil generator_{i:03} est donc, en Mode C, une configuration d'échantillonnage — une façon particulière de tirer le modèle (plus ou moins créative, avec telle graine).

Cela donne à R-b/R-c un sens plus riche en Mode C qu'en Mode A. La réputation par-profil y apprend « quelle température, quelle graine tend à produire le candidat gagnant pour cette famille de tâches » — une connaissance authentiquement utile (les tâches factuelles aiment les basses températures ; les tâches créatives, les hautes). L'ordonnancement réputationnel fait alors tourner d'abord les configurations d'échantillonnage qui ont historiquement gagné, et l'arrêt adaptatif en récolte l'économie. C'est la même structure qu'en Mode A — mais ce qu'elle exploite n'est plus un artefact synthétique, c'est une vraie diversité de sampling.

Le moat tient à l'identique, et pour la même raison (I-REP8). Le variant — donc la (température, graine) — est enregistré : en Mode C, il l'est dans le record d'essaim et dans le record N17 (les paramètres SamplingParams font partie de l'attestation). L'auteur d'écriture reste l'unique "generator". Donc R0 re-prouve la chaîne inchangé, et l'attestation N17 fige quel sampling a produit quelle sortie à quelle position. La permutation des profils est transparente au moat en Mode C exactement comme en Mode A — sauf qu'ici, le « variant enregistré » qui sert de pivot porte une information physique réelle (les paramètres de tirage), ce qui rend l'audit encore plus parlant.

Conséquence. L'ouverture R-b/R-c, déjà chiffrée et re-prouvée en Mode A (gate REP-4), se transpose en Mode C sans changement de structure — c'est une lecture agnostique (§5). Un harnais Mode C la confirmerait active sur de vrais samplings (et l'attestation N17 montrerait la (température, graine) gagnante remontée en tête), mais sa correction est déjà acquise. Le Mode C n'ouvre pas une nouvelle dette de preuve pour R-b/R-c ; il en révèle la pertinence physique.

§8 Le déterminisme borné : sizing auditable, non re-dérivable

Une honnêteté de plus, sur le sizer adaptatif (ADR-014). En Mode A, la trajectoire du sizer — « après k candidats, l'accord valait x ; on s'arrête / on continue » — est une fonction pure des candidats, eux-mêmes reproductibles ; donc un tiers la re-dérive entièrement hors-ligne (c'est le test sizing_trace_matches_offline_rederivation : on reconstruit les candidats, on recalcule l'accord par préfixe de vague, on exige l'égalité). En Mode C, les candidats ne sont pas reproductibles — l'accord observé dépend des sorties réelles du modèle. La trajectoire n'est donc plus re-dérivable de zéro.

Mais elle reste auditable, et c'est suffisant. Les candidats réels sont figés dans les records N17 ; un vérificateur lit ce que le modèle a produit à chaque vague, recalcule l'observable (l'accord) sur ces candidats attestés, et confirme que la décision d'arrêt était correcte étant donné ce que le modèle a produit. La différence est précise : en Mode A, on re-dérive la trajectoire sans les records (on refait tout) ; en Mode C, on la vérifie avec les records (on constate la cohérence). C'est exactement la formule du commentaire de n17_consistent_under_adaptive_k : « la trajectoire adaptative reste auditable même non rejouable ».

La règle générale, énoncée une fois. En Mode C, tout ce qui en Mode A se re-dérive (R1, trace de sizing, sorties d'agents) se vérifie-étant-donné-les-records (N17). La preuve passe de « je refais et je compare » à « je tiens l'attesté et je vérifie sa cohérence interne ». Le moat ne perd pas en force — il change de nature de garantie, du reproductible à l'infalsifiable.

§9 La souveraineté : Ollama local, zéro clé, G2/G3

Le Mode C d'EFE est souverain par défaut : il parle à un modèle local, jamais à une API tierce, et ne manipule aucune clé. C'est une propriété de sécurité, pas un détail de déploiement, et elle est gardée par deux gardes-fous (backend/mod.rs).

G2 — le garde d'egress. build_local_backend consulte is_local_endpoint (vrai pour localhost, ::1, 127.*). Un endpoint non-local avec allow_remote == false est refusé net — SwarmError::RemoteBackendDenied. Par défaut, le Mode C ne peut donc pas sortir de la machine : aucune donnée de tâche, aucun prompt, aucune sortie ne traverse le réseau. Le self-host est, au sens fort, sur site.

G3 — le disjoncteur. Le seul chemin qui assume l'egress (le routeur Network, allow_remote == true) enveloppe les appels d'un Breaker (circuit-breaker) + re-tentatives à jitter — pour la résilience, jamais pour la souveraineté. Le self-host souverain (loopback), lui, reste sans re-tentative : un appel local qui échoue échoue franchement (pas de masquage). La santé du backend est sondée avant le run (échec net plutôt que N timeouts).

Et surtout : zéro clé. Là où la plupart des piles LLM exigent une clé d'API (un secret à protéger, à faire tourner, à ne jamais logger), le Mode C souverain d'EFE n'en a aucune. Le seul secret de tout le système reste le maître de provenance (HKDF, qui scelle les chaînes) — signé côté serveur, jamais exposé à l'agent ni au prompt. Le modèle local ne s'authentifie pas ; il est sur la machine. Cette absence de clé n'est pas une lacune : c'est la conséquence directe du choix souverain, et elle élimine d'un coup toute une classe de risques (fuite de clé, exfiltration par prompt, dépendance à un tiers).

Le lien avec le moat. Souveraineté et re-preuve se renforcent. Parce que le modèle est local, le prompt re-prouvable (§3①) et la sortie attestée (§3③) ne quittent jamais le périmètre ; l'attestation N17 est produite sur la machine qui a fait l'inférence, sans intermédiaire de confiance. Un Mode C qui appellerait une API distante introduirait un tiers entre le prompt et la sortie — exactement le maillon que la souveraineté supprime.

§10 Le harnais #[ignore] : honnête parce que gated

Vient la question de méthode : comment prouver en chiffres une lecture qui n'existe que sur un vrai modèle, dans un dépôt dont la CI n'a pas de modèle ? La réponse d'EFE est le harnais #[ignore] — et il faut défendre ce choix, car il a l'air d'une dérobade et n'en est pas une.

On ne simule pas un LLM. Un gate Mode A est synthétique par honnêteté : les agents sont des fonctions étiquetées, déterministes, et la preuve porte sur la logique de production (les vraies fonctions du consensus, du sizer, de la mémoire). On ne peut pas faire l'équivalent pour le few-shot : « simuler » la réponse d'un modèle à un prompt enrichi reviendrait à inventer le résultat qu'on prétend mesurer — la pire des malhonnêtetés. La seule mesure honnête de l'influence du few-shot passe par un vrai modèle.

Donc : le harnais est réel, mais gardé. Il porte #[ignore = "nécessite un Ollama local"] — il ne tourne pas en CI (qui n'a pas de modèle, et où un LLM serait lent et instable), mais se lance à la demande (cargo test -- --ignored) sur un Ollama local. C'est le pendant exact de la discipline Mode A : là, des agents synthétiques mais honnêtes en CI ; ici, un vrai modèle mais gardé hors CI. Les deux refusent de fabriquer le résultat ; ils diffèrent seulement sur ce qui est simulable honnêtement.

Le dépôt suit déjà ce patron pour les axes structurels : adaptive_keyless::n17_consistent_under_adaptive_k, replay_real.rs, n17_persist_real.rs, et les tests Mode C de la passerelle, tous #[ignore] sur gemma3:12b local. Le harnais few-shot proposé (§11) rejoint cette famille : même garde, même modèle, même posture — réel, gated, lancé quand on veut la preuve empirique.

La limite à nommer. Un harnais #[ignore] ne garde PAS contre la régression en CI (il ne tourne pas). C'est assumé : il prouve une propriété empirique (l'influence d'un modèle), pas une invariance de code. Les invariants de structure du few-shot (prompt re-prouvable, borné, dormant sans donnée, I-MEM8) sont, eux, gardés en CI par des tests purs sur gen_prompt (sans backend) — déjà présents. La division est nette : la structure se garde en CI (pur) ; l'effet empirique se mesure à la demande (Ollama).

§11 Le gate Mode C des lectures-retour (M-§A…F)

Le harnais proposé — lot_fewshot_modec (#[ignore], Ollama local) — est le pendant Mode C des gates de mémoire. Sa cible unique et neuve est l'influence mesurée du few-shot ; il exerce au passage la cohérence N17 et la re-preuve R0 d'un vrai run LLM. Six sections.

SectionCe qui est prouvé, sur un VRAI modèle
M-§A
prompt re-prouvable		 le prompt froid (sans mémoire) est byte-identique à la forme historique (I-MEM8) ; le prompt chaud re-pinne l'instantané → mêmes exemplaires → même prompt (R1 de l'entrée). Vérifiable sans backend (test pur) — la moitié « structure » du gate, gardée en CI.
M-§B
influence mesurée		 le cœur. Sur une famille de tâches où des gagnants passés aident (p. ex. un format de réponse stable, un vocabulaire de domaine), le run chaud (exemplaires injectés) produit une sortie mieux conforme que le run froid — un delta mesuré (taux de bonne forme, exactitude, ou distance à l'attendu). Honnête : exige Ollama.
M-§C
influence bornée		 au plus FEWSHOT_N exemplaires ; le modèle répond toujours à la tâche (il ne recopie pas un exemplaire ni n'ignore l'entrée) — la mémoire oriente, ne gouverne pas.
M-§D
N17 cohérent		 chaque appel Mode C attesté et lié : all_consistent, unlinked==0, broken==0, tenant et run vérifiés (§4).
M-§E
R0 re-prouve		 la chaîne d'essaim du vrai run LLM re-prouve (verify_swarm) — auditable, même non rejouable (§8).
M-§F
souveraineté		 le backend est local (loopback) ; aucun egress ; aucune clé (§9) — le run souverain est la condition du gate.

M-§B est la seule section qui n'a aucun équivalent ailleurs, et c'est elle qui justifie le harnais. Sa construction honnête : choisir une famille où les exemplaires devraient aider (un signal mesurable — format, domaine, contrainte de sortie), exécuter froid puis chaud sur le même modèle local, et exiger un delta dans le bon sens, reproductible statistiquement (sur quelques répétitions, pour absorber la stochasticité — on ne mesure pas un octet, on mesure une tendance). Le gate ne prétend pas que le few-shot aide toujours (ce serait faux) ; il prouve qu'il peut aider, de façon bornée et re-prouvable-en-entrée, sur une famille où c'est attendu — exactement la promesse d'ADR-019, ni plus ni moins.

Les quatre autres lectures, au passage. Le même run Mode C peut confirmer actives les lectures agnostiques (§5) : le warm-start de k_min, le biais de pattern, le routage R-a et l'ordonnancement R-b/R-c tournent dans le pipeline LLM et leur trace apparaît (k_min amorcé, pattern décidé, poids appliqués, profils réordonnés). Mais leur correction est déjà acquise (gates Mode A) ; le harnais Mode C les montre vivantes, il ne les re-démontre pas. Une seule dette de mesure — M-§B — et elle est nommée.

§12 Séquence + ce qui reste fermé

La séquence de livraison est courte, parce que l'essentiel existe. Elle se réduit à combler la mesure manquante et à verrouiller la structure en CI.

ÉtapeGesteGarde
1Tests purs sur gen_prompt : froid=historique (I-MEM8), chaud=bloc few-shot borné, déterminisme du promptCI (sans backend) — la structure M-§A/C
2Harnais lot_fewshot_modec #[ignore] : froid vs chaud sur Ollama, delta mesuré + N17 + R0 + souverainetéà la demande — l'effet M-§B/D/E/F
3(option) confirmation des lectures agnostiques actives dans un run Mode C à la demande — illustratif, non load-bearing

Restent honnêtement fermées — chacune un acte distinct, nommée pour ne pas planer :

  • Le routeur Network (egress assumé) reste hors souveraineté par défaut : G2 le refuse sauf allow_remote explicite, sous disjoncteur. L'architecture d'un Mode C distant re-prouvable (où l'attestation N17 viendrait d'une machine tierce) est une question ouverte, distincte, plus délicate pour la chaîne de confiance.
  • La reproduction approchée (R1 « à ε près » : re-tirer le modèle et mesurer une distance plutôt qu'une égalité) n'est pas l'objet — le Mode C s'en tient à l'attestation exacte (N17), pas à une reproduction floue dont la sémantique de preuve serait fragile.
  • Le few-shot multi-tour / la sélection adaptative d'exemplaires (choisir quels gagnants montrer selon la tâche courante) est une extension de la cellule Exemplaires, pas du Mode C — à mesurer séparément le jour venu.

En une phrase. Le Mode C réel ne réclame aucune nouvelle structure de preuve : il bascule la re-preuve de la reproduction (R1, Mode A) vers l'attestation (N17, Mode C), en confinant le non-déterminisme du LLM à un maillon encerclé de re-prouvable. Quatre des cinq lectures-retour, agnostiques au mode, y tournent déjà chiffrées ; la seule à mesurer est le few-shot, et la seule mesure honnête de son influence passe par un vrai modèle — d'où le harnais #[ignore], réel et gardé. La structure se verrouille en CI ; l'effet se mesure à la demande. Souverain, sans clé, infalsifiable.
