Ce rapport décrit l'architecture, les garanties cryptographiques, les résultats de tests réels (Ollama local + Claude 3.5 Sonnet via routeur), l'état d'avancement face à la définition de « fait » de la Phase 5, et la marche à suivre opérationnelle. §1  Thèse & positionnement

EFE productise le moat : non pas « un essaim d'agents de plus », mais un essaim dont chaque pas laisse une preuve cryptographique qu'un tiers re-vérifie seul, hors-ligne, sans faire confiance ni à nous ni à un fournisseur.

Le problème

Les orchestrateurs d'agents produisent des sorties dont on ne peut pas prouver l'intégrité : ni qui a produit quoi, ni que la sortie n'a pas été altérée, ni que le run respecte un budget. En environnement régulé (santé, finance, juridique), c'est rédhibitoire — et les API frontières imposent en plus l'egress des données et la détention de clés.

La proposition de valeur (3 piliers)

🔒 Souverain
Aucune clé dans le binaire. Le seul secret est le master HKDF qui signe la provenance, lu server-side via l'environnement. Les clés provider (mode Network) vivent dans le routeur, jamais dans la passerelle.
🏠 Local
Mode phare self-host keyless : le modèle tourne sur 127.0.0.1 (Ollama / llama.cpp / vLLM). Air-gappable, zéro egress, les données ne quittent pas l'hôte.
✅ Vérifiable
Chaque run renvoie un provenance_root (64 hex). Un régulateur re-prouve la chaîne HMAC + le contenu (blake3) + le DAG à partir des seuls records et d'une clé tenant — hors-ligne.
💸 Gouverné
Budget atomique (invariant I13) : le plafond n'est jamais dépassé, même en concurrence. Dégradation gracieuse de la topologie pour tenir le budget.

La nuance honnête sur « vérifiable »

On ne promet jamais la reproductibilité bit-à-bit d'un LLM. On promet la re-preuve forensique : les ballots LLM ne sont pas rejouables à l'identique, mais ils sont captés (hash prompt/réponse, modèle, paramètres, seed) et tamper-evident. Le Mode A déterministe (flotte d'ancres) et l'agrégation, eux, sont reproductibles (ADR-SWARM-007). Le provenance_root est stable pour un même ensemble de records.

§2  Vue d'ensemble du système

EFE est un monorepo Rust. La stack essaim s'empile en couches strictes (pas de cycle : le haut dépend du bas). Le SDK reste léger (aucune dépendance réseau/TLS) ; les préoccupations prod (Postgres, OIDC, PII) sont des features optionnelles compilées à la demande.

Figure 1 — Architecture en couches. Les flèches indiquent les dépendances (le haut dépend du bas ; aucun cycle). Le routeur frontière est server-side, hors du binaire souverain.

Le SDK n'importe ni reqwest ni TLS : les backends locaux « shell-out » curl vers 127.0.0.1. Un test CI (keyless_guardrails) asserte l'absence de dépendance réseau/clé dans le SDK.

§4  Le moat — provenance vérifiable

Chaque appel d'agent produit un AgentCallRecord scellé. Les records forment une chaîne HMAC (chaque maillon couvre le précédent → détecte toute insertion/suppression/réordonnancement) et un DAG de causalité ; le contenu de chaque record est haché en blake3. La racine (provenance_root) résume l'ensemble. verify_swarm recalcule tout à partir des seuls records + une clé tenant dérivée par HKDF — hors-ligne.

Figure 3 — La chaîne de provenance et sa re-preuve. Muter un seul octet d'une sortie casse content_intact ; réordonner un record casse chain_intact ; les deux changent la racine. La faute est localisée (first_break).
Pourquoi c'est un moat : la preuve ne dépend ni d'EFE ni d'un provider. Le client exporte GET /v1/swarm/runs/:id/records et re-prouve avec sa propre clé tenant, sur une machine déconnectée. C'est ADR-SWARM-009 : « le endpoint verify EST le produit ».

§5  Pont N17 — forensique par-appel

Au niveau essaim, un AgentCallRecord dit quel agent, quelle entrée, quelle sortie. Le pont N17 ajoute une granularité par appel LLM : pour chaque agent Mode C (self-host / Network), un LlmProvenanceRecord forensique capte modèle, paramètres, seed, hash prompt/réponse, latence, re-tentatives. L'AgentCallRecord le référence via llm_provenance_id. Une seule lignée, deux granularités.

Le seam (sans réécrire les agents)

Le backend ne connaît pas le contexte d'essaim ; le Meter ne voit pas l'appel LLM brut. On les relie par un task-local : concurrence-safe (un puits par appel d'agent, même quand K générateurs tournent en parallèle).

Figure 4 — Le pont N17. Une re-tentative (Retrier) n'émet qu'un record final (avec retry_count) — le lien pointe vers l'issue retenue, jamais vers une tentative échouée.

Prouvé en réel (§11) : sur Claude 3.5 Sonnet via routeur — n17: consistent 4 · unlinked 0 · broken 0 · all_consistent true ; et sur gemma3:12b en self-host local.

§6  Inc.4.b — protocole Network réel

Le mode Network parle OpenAI-compat (POST /v1/chat/completions) à un routeur server-side qui détient les clés et les injecte vers les providers. La passerelle ne porte jamais de clé applicative — l'auth passerelle↔routeur est infra (mTLS / NetworkPolicy).

Figure 5 — Protocole Network. La traduction Network{provider} → SelfHost{routeur, modèle résolu} réutilise le backend OpenAI-compat local ; le Retrier ajoute la résilience aux hoquets transitoires.
Limite assumée (honnête) : la couche curl keyless ne distingue pas un 4xx (non-retryable) d'un 5xx/timeout (transitoire) — elle renvoie une erreur uniforme. Les re-tentatives sont donc transitoires-par-défaut. Évolution notée : surfacer %{http_code}.

§7  Gouvernance de budget (invariant I13)

Un BudgetGuard atomique facture chaque appel d'agent. I13 : le compteur ne dépasse JAMAIS le plafond, même sous concurrence (ajout atomique puis revert si dépassement). Trois politiques : Error (refus pré-vol), Stop (arrêt propre, résultat partiel), Degrade (réduit K et rogne les juges pour tenir).

Prouvé sous concurrence

8 threads × 1000 charges, plafond 100¢ → spent ≤ 100 garanti (i13_holds_under_concurrency). Aucun dépassement possible.

Correctif cost-governance Network

La traduction Network → SelfHost faisait tomber le tarif à 0¢ (spent_cents: 0). resolve_mode renvoie désormais le tarif à préserver ; routes::run l'injecte au budget (en respectant un tarif client explicite). Prouvé en réel contre Ollama : spent_cents > 0, multiple du tarif Network.

// resolve_mode (state.rs) — la traduction préserve le tarif
Network → (SelfHost{endpoint, modèle_résolu}, allow_remote=true, Some(5))
souverains → (mode, false, None)

// routes/run.rs — injection respectueuse d'un tarif client
if let Some(price) = price_override {
    budget.price_per_call_cents.get_or_insert(price);   // ne JAMAIS écraser un choix explicite
}

Le coût réel en mode Network reste facturé chez le provider (via le routeur) ; la passerelle ne le voit pas (par conception : zéro clé). Le tarif est l'unité de gouvernance nominale.

§8  Souveraineté, clés & déploiement

Gestion des clés — la règle absolue

  • Aucune clé provider n'est jamais saisie, lue ou stockée par la passerelle. Mode Network : les clés vivent dans le routeur, server-side.
  • Le seul secret côté EFE est le master HKDF (EFE_NANO_AUDIT_HMAC_MASTER) qui signe la provenance — lu server-side via l'environnement, jamais transmis. Le binaire prod sélectionne EnvHkdf dès qu'il est présent ; sinon repli test_key() dev avec avertissement bruyant (le master de test est public → provenance forgeable).
  • OIDC : clé publique server-side uniquement (jamais une clé privée).
Trou fermé cette session : il n'existait aucun binaire prod — seul l'exemple dev (forçant test_key()) était runnable, alors que le chart Helm monte un Secret HKDF. Un déploiement « prod » aurait signé avec la clé de test publique → moat forgeable. Le binaire [[bin]] efe-swarm-gateway (sélection EnvHkdf, arrêt gracieux SIGTERM, bind 0.0.0.0) comble ce trou.
Figure 6 — Déploiement souverain. Le run, les données et le modèle restent sur l'hôte ; seule la preuve (records + root) circule, et se re-vérifie sans clé ni réseau.

§9  PII opt-in (G9)

Caviardage opt-in par tenant (défaut Off), feature pii. La détection est LOCALE (regex : email, SSN, carte, IBAN, IP, téléphone) → compatible egress=deny, le détecteur réseau Presidio n'est jamais appelé. On réutilise seulement le redactor pur d'efe-pii.

Ce qui est caviardé

La présentation : la sortie renvoyée, la copie au repos, et les previews live du dashboard. Politiques Off · Detect · Redact · Strict.

Ce qui reste intact

Les AgentCallRecord et leurs hashs → verify_swarm re-prouve l'original. Le moat n'est pas affecté par le caviardage.

Architecture : le dashboard expose un trait léger PreviewRedactor (sans dépendance efe-pii) ; la passerelle fournit GatewayRedactor (efe-pii, détection locale). La passerelle de dev par défaut est inchangée (feature non compilée).

Note UX observée : à la fin d'un run, le serveur ferme le flux SSE (plus rien à streamer) → le navigateur affiche « interrompu » après un bref « terminé ». Ce n'est pas un échec (provenance VERIFIED, 4 panneaux remplis) — c'est l'onerror de l'EventSource sur la fermeture propre. Correctif cosmétique 1 ligne identifié (fermer le flux côté client sur run_finished).
