§1 Le problème — verify prouve l'intégrité, pas la reproductibilité

1.1 — Ce que /verify établit (et ce qu'il NE dit pas)

GET /v1/swarm/verify/:id (ADR-SWARM-009) est le cœur du moat : il appelle verify_run_offline(records, llm_records, n17_leaves, n17_root, key) (routes/verify.rs:31-37) et recompose, depuis les seuls éléments persistés plus la clé tenant, quatre faits — chain_intact (la chaîne HMAC se rejoue sans rupture), content_intact (chaque payload_hash se recalcule depuis le corps du record), dag_consistent (les parents causaux existent, aucune lecture fantôme — verify.rs:118-149) et traced_pct (la couverture d'ancrage). À cela s'ajoute, depuis ADR-016, la chaîne forensique N17 et le pont Mode A↔Mode C. C'est une machine de preuve remarquable : un tiers, sans process vivant, sans provider, sans réseau, établit que rien n'a bougé depuis le scellement.

Mais observons exactement ce que verify tient pour acquis. Le contrôle content_intact recalcule le payload_hash du record à partir des champs du record lui-même — y compris son output_hash stocké. Il prouve que le record est auto-cohérent : la signature scelle bien ce corps-ci. Il ne prouve pas que l'output_hash scellé est celui que l'agent aurait réellement produit à partir de son input_hash. Autrement dit : verify atteste l'intégrité de l'évidence, jamais sa fidélité à une exécution. Un opérateur de mauvaise foi — ou un bug — qui scelle un record syntaxiquement parfait mais dont la sortie ne correspond à aucune exécution réelle de l'agent passe verify sans broncher. La signature HMAC garantit « personne n'a touché ce record après coup » ; elle ne garantit pas « ce record est le produit honnête de la computation annoncée ».

1.2 — La question sans réponse : « si je relance, j'obtiens la même chose ? »

C'est la question d'un régulateur, d'un auditeur tiers, d'un client qui conteste une décision automatisée. Elle est d'une autre nature que celle de verify : non pas « cet enregistrement a-t-il été falsifié ? » mais « cette computation est-elle reproductible — re-exécutée dans les mêmes conditions, redonne-t-elle exactement ce verdict ? ». C'est la définition opérationnelle de l'auditabilité d'un système automatisé : pouvoir rejouer le calcul et retrouver la même réponse, bit pour bit, est ce qui distingue une décision déterministe et défendable d'une boîte noire dont la sortie n'engage personne.

Le système porte déjà, en germe, la réponse — mais elle n'est pas exposée comme produit. crates/efe-swarm-provenance/src/replay.rs offre trois fonctions : replay_root(records, key) (l.88-100) re-scelle l'ensemble des records en ordre canonique et retourne la racine recomposée ; replay(records, key) (l.128-155) y ajoute la vérification de chaque payload_hash et localise la première rupture de contenu ; replay_outputs(records, reproduce) (l.182-200) re-exécute chaque agent via une closure et compare l'output_hash fraîchement calculé à celui scellé. La troisième est la vraie « re-dérivation » — mais elle vit comme bibliothèque (tests, examples/replay.rs), invisible sur le fil HTTP. Ce document propose de l'élever au rang d'endpoint, avec la rigueur de scope qu'exige une promesse aussi forte que « reproductible ».

1.3 — Le déterminisme est asymétrique — et c'est honnête de le dire

La difficulté centrale, qui modèle toute l'architecture, est que la reproductibilité d'un run EFE n'est pas uniforme. Elle dépend du mode de chaque agent. Un agent Mode A (essaim keyless : générateurs et juges Rust purs — EchoGenerator, ConstGenerator, catalog.rs:501-521 ; les cinq juges de consensus/judges.rs:27-130) est une fonction pure de son entrée : generate(task, variant) redonne mot pour mot le même Value, sans état, sans RNG, sans réseau. Un agent Mode C (appel LLM via self-host ou routeur) est stochastique : même prompt, même graine (sampling.seed), le provider n'offre aucune garantie documentée de déterminisme bit-à-bit. Entre les deux, un Mode B « graine épinglée » est best-effort. Cette asymétrie n'est pas un défaut à cacher : c'est une propriété physique du système qu'il faut graver dans le contrat de l'endpoint. Un /replay honnête ne ment pas en promettant « identique » là où il ne peut qu'observer « plausiblement proche » ; il classe chaque record et localise chaque divergence.

Le gap en une phrase. /verify prouve qu'un run n'a pas été altéré ; il ne dit rien de sa reproductibilité. /replay répond à « si je relance, j'obtiens la même chose ? » — bit-à-bit pour le Mode A, et honnêtement classé pour le Mode C — en re-dérivant la computation, pas en se contentant de re-signer l'évidence.

§2 État des lieux — ce qui existe déjà

Le rejeu déterministe n'est pas une invention à partir de rien : c'est l'exposition d'un socle déjà bâti, déjà testé, déjà gravé en ADR. Le travail d'architecture consiste surtout à assembler des pièces vérifiées et à trancher les tensions de scope — pas à inventer de la cryptographie.

2.1 — Le socle ADR-007 : OrderKey, deterministic_order, replay_root

ADR-SWARM-007 (« deterministic replay keys on version ») établit le fait fondateur : l'ordre dans lequel les records scellent la chaîne HMAC est une fonction pure de l'ensemble des records, indépendante de l'ordre d'exécution concurrente et de l'horloge murale. La clé d'ordre (replay.rs:37-74) est le 4-uplet OrderKey(has_write: bool, version: u64, pointer: String, payload_hash: [u8;32]) : on trie sur les coordonnées du Blackboard (version, pointeur de la cellule écrite minimale), avec le payload_hash de contenu comme départage. deterministic_order(records) (l.80-86) est commutative au sens mathématique — les tests (l.242-261) prouvent que toute permutation, tout reverse, tout shuffle de l'entrée produit le même vecteur de sortie.

Sur ce tri, replay_root(records, key) crée une SwarmChain vierge et ré-enfile chaque record réordonné — recalculant son payload_hash, le liant au HMAC parent — pour retrouver le tip. Le test replay_matches_live_recorder_root (replay.rs) verrouille la propriété cardinale : le scellement vivant (ProvenanceRecorder::seal_with_key, recorder.rs:195-262, qui appelle SwarmChain::append_all_canonical, chain.rs:111-131) et le rejeu partagent exactement la même fonction de tri (key_of) : impossible que le provider scelle l'ordre A mais que le vérificateur reconstruise l'ordre B. La conséquence, c'est le moat : un tiers reçoit les records en désordre, appelle replay_root, et retrouve le provenance_root du scellement vivant — la preuve qu'il a reçu exactement les mêmes records, rien d'altéré, rien de manquant.

Point décisif pour l'honnêteté du design : wall_at (l'horloge de capture) est exclu du payload_hash (record.rs:137-168 énumère les 11 champs du corps canonique ; wall_at n'en fait pas partie ; test payload_hash_excludes_wall_at, l.586-590). Deux agents qui finissent à des instants différents, mêmes entrées/sorties, produisent un payload_hash identique. Le rejeu peut donc ignorer le temps : la racine est clavée sur la sémantique du substrat, pas sur le timing.

2.2 — La taxonomie DeterminismLevel (déjà codée, nano)

La couche nano (le runtime mono-agent sous l'essaim) possède déjà une taxonomie de reproductibilité : efe-nano/src/replay/determinism.rs définit DeterminismLevel avec cinq niveaux — FullDeterministic (Rust pur, Mode A : reproductible bit-à-bit), Seeded (modèle local à graine épinglée : best-effort), LlmReplayable (rejouable tant que le cache est chaud), LlmEphemeral (appel LLM sans cache ni graine : jamais rejouable) et SideEffect (effet de bord : jamais rejouable). Côté nano-SDK, types/replay.rs porte déjà un ReplayRequest (acteur, ticket, raison, mode, tolérance) et un MatchOutcome (Match / Tolerated / Mismatch / SkippedNonDeterministic). L'endpoint d'essaim réutilise cette taxonomie : il ne réinvente pas la notion de « jusqu'où ce record est-il rejouable » — il la projette sur les records d'essaim et la publie sur le fil.

Deux couches de rejeu, à ne pas confondre. Le rejeu mono-agent (N16, nano : re-jouer un appel LLM individuel avec attribution de coût, acteur, politique de tolérance) est un système distinct. Cette architecture porte sur le rejeu d'essaim — /v1/swarm/replay/:id, sœur de /verify/:id — qui rejoue un run complet. Il emprunte la taxonomie DeterminismLevel et délègue le rejeu mono-appel au moteur nano là où il faut (Mode C). Le moteur de rejeu multi-région nano reste hors-périmètre (§10).

2.3 — Ce qui est persisté — et ce qui manque (la task, la spec)

C'est la contrainte qui sculpte tout le reste. StoredRun (store.rs:24-40) persiste : records (les AgentCallRecord bruts), root, llm_records + n17_leaves + n17_root (la forensique N17, ADR-016), output (le résultat final), topology (le nom seul, ex. "T1:generate-verify" — store.rs:55), created_at, tenant. Sont absents : la task d'entrée (le JSON de la requête POST /run est désérialisé puis jeté — run.rs:66 ; jamais persisté), la TopologySpec complète (K, noms des juges, prompts, pattern, escalade — seul le nom survit), et le Budget d'origine (seul un snapshot de dépense est gardé). Enfin, chaque AgentCallRecord stocke des hash d'entrée/sortie (input_hash, output_hash) et des pointeurs de cellules (reads, writes) — pas les valeurs elles-mêmes (record.rs:364-390).

Conséquence chirurgicale, qu'on assume au lieu de la masquer : on ne peut pas re-exécuter un run « à partir de rien » depuis le seul store — il manque la task et les valeurs d'entrée. Cette contrainte n'est pas un obstacle à contourner par une migration lourde ; c'est un fait de conception qui dicte la forme de l'endpoint (§5.1) : R0 (re-sceller depuis les records) ne demande rien ; R1 (re-exécuter) demande au caller de re-fournir la task qu'il détient déjà.

§3 La thèse — re-dériver ≠ re-prouver

3.1 — Deux endpoints, deux questions

La thèse tient en une distinction nette, qu'on refuse de brouiller : /verify re-prouve, /replay re-dérive. /verify/:id répond « l'évidence est-elle intègre ? » en recalculant des hash et des HMAC depuis les champs stockés — il fait confiance à l'output_hash scellé comme vérité de terrain. /replay/:id répond « la computation est-elle reproductible ? » en re-faisant le calcul et en comparant le résultat fraîchement obtenu au scellé. La différence est exactement celle entre « ce reçu n'a pas été raturé » et « si je refais l'addition, je retrouve le total ». Le second attrape une classe de fautes que le premier ne peut pas voir (§7.1) : le record auto-cohérent mais non-reproductible.

Parce que la promesse de /replay est plus forte, son architecture offre deux tiers de fidélité, explicitement nommés, jamais confondus :

  • R0 — re-sceller depuis les records scellés (GET /v1/swarm/replay/:id, zéro-input, gratuit, ∞-reproductible). On charge les records persistés, on les ré-ordonne (deterministic_order) et on re-scelle (replay) : la racine recomposée doit égaler la racine stockée, le contenu se recalculer, la première divergence être localisée. On classe en outre chaque record par DeterminismLevel (quels records pourraient être re-exécutés). C'est l'exposition directe de la propriété ADR-007 « désordre/transmission → même racine » — sans task, sans provider, sans réseau.
  • R1 — re-exécuter le squelette déterministe (POST /v1/swarm/replay/:id avec { task, [topology] }). Le caller re-fournit la task (qu'il détient — elle n'est pas stockée, §2.3). L'endpoint ré-instancie la topologie sur un Blackboard vierge, re-exécute les agents purs, et compare les sorties (output_hash + flux de données) à celles scellées — pas la racine, qui lie l'identité par-run (§5.2). Mode A : sorties re-dérivées bit-à-bit. Mode C : par appel, cache_hit/replay_of (déterministe) ou MatchOutcome honnête.

3.2 — Le déterminisme asymétrique, gravé

L'architecture refuse de prétendre à un déterminisme uniforme. Elle publie l'asymétrie comme une donnée de sortie. Chaque opération rejouée porte un DeterminismLevel et un MatchOutcome : un Mode A qui doit matcher (et casse le gate s'il ne matche pas) ; un Mode C qui matche si et seulement si il fut un cache_hit ou pointe un replay_of relisible, et qui est sinon marqué SkippedNonDeterministic — jamais faussement « Match ». C'est l'honnêteté coûteuse en UX dont parle la doctrine EFE : il est plus simple de mentir « tout est identique » ; il est plus juste de dire « ces 7 agents Rust reproduisent à l'octet, ces 3 appels LLM sont hors de portée du déterminisme bit-à-bit, voici lesquels et pourquoi ».

Le rejeu ne promet pas un déterminisme uniforme : il classe chaque opération et n'exige le bit-exact que là où il est physiquement garanti (Mode A).

3.3 — Le prior est favorable — le genre du gate

Comme pour la persistance N17, le prior est favorable : le socle déterministe (ADR-007) est déjà prouvé en réel (Lot P4, 2026-06-09 : provenance_root reproductible), replay.rs est testé (permutations, wall_at advisory, falsification détectée, live/replay matching), et la taxonomie DeterminismLevel existe. Le gate de /replay n'est donc pas un gate de découverte (« le levier existe-t-il ? ») mais un gate de correction : assembler les pièces sans régression, prouver que R1 reproduit le Mode A bit-à-bit, que toute divergence est détectée et localisée, que R0 tient hors-ligne, et que le coût est borné. GO si ces quatre tiennent ; sinon, c'est un bug, pas un NO-GO de thèse.

§4 Architecture A — R0 : rejeu hors-ligne depuis les records scellés

R0 est le tier gratuit, sans entrée, infiniment reproductible. Il répond à la forme la plus pure de la question : « l'ensemble des records scellés se recompose-t-il, à lui seul, en la racine annoncée — et que pourrait-on re-exécuter ? ». Il n'exécute aucun agent ; il re-scelle.

4.1 — Re-sceller en ordre canonique → la racine se reproduit

Le handler charge le StoredRun (tenant-scopé), dérive la clé tenant (HKDF, server-side), puis appelle replay(&stored.records, &key) — la fonction existante de replay.rs:128-155. Celle-ci ré-ordonne par deterministic_order, re-chaîne, vérifie chaque payload_hash au passage, et retourne un ReplayReport { replayed, content_intact, first_content_break, root }. La garde cardinale (I-RP3) : la racine recomposée doit égaler la racine stockée (stored.root). Si oui, l'ensemble des records — dans n'importe quel ordre de transmission — commet bien la racine annoncée. C'est la propriété ADR-007 (« shuffle → same root ») élevée au rang de réponse HTTP.

R0 est délibérément plus exigeant que la simple lecture : il exerce le chemin de scellement complet (deterministic_order + append + HMAC), pas seulement le chemin de vérification. Là où verify_swarm recompose la chaîne pour la juger, R0 la reconstruit ex nihilo et exige l'égalité avec la racine de référence — c'est le geste qu'un tiers pose quand il refuse de croire le serveur.

4.2 — Classifier chaque record par DeterminismLevel

R0 attache à chaque record un DeterminismLevel : FullDeterministic pour un Mode A (aucun llm_provenance_id) ; pour un Mode C, LlmReplayable si le LlmProvenanceRecord lié porte un cache_hit ou un replay_of résolvable, Seeded si une sampling.seed est posée, sinon LlmEphemeral. Cette classification est l'inventaire de rejouabilité du run : avant même de payer une re-exécution (R1), l'auditeur sait quelle fraction du run est reproductible bit-à-bit, quelle fraction l'est sous condition de cache, et quelle fraction est hors de portée. C'est une réponse honnête et instantanée à « jusqu'où ce run est-il rejouable ? ».

4.3 — Pourquoi R0 est plus fort que /verify

/verify et R0 partagent la couche de re-preuve, mais R0 ajoute deux faits que /verify n'exprime pas : (1) il reconstruit la racine par re-scellement (et pas seulement « la chaîne stockée se re-vérifie »), confirmant que l'ensemble des records — indépendamment de l'ordre — est exactement celui qui produit cette racine ; (2) il publie l'inventaire de déterminisme. R0 ne remplace pas /verify (qui reste le contrôle d'intégrité de référence) ; il en est la face « reproductibilité », à coût nul. Pour un run Mode A, R0 est déjà une réponse quasi-complète à « est-ce reproductible ? » — il ne reste qu'à confirmer que les agents purs re-dérivent les mêmes sorties, ce que fait R1.

Frontière R0. R0 re-dérive l'ordre et la chaîne (la racine se reproduit, le contenu est intègre, la divergence est localisée), et inventorie la rejouabilité. Il ne re-dérive pas les sorties d'agents — c'est l'objet de R1. R0 ne touche jamais le store en écriture (I-RP4) et ne sort jamais du tenant (I-RP5).

§5 Architecture B — R1 : re-exécuter le squelette déterministe

R1 est la vraie re-dérivation : on refait le calcul et on compare. C'est là que « si je relance, j'obtiens la même chose ? » reçoit sa réponse la plus forte — pour le Mode A, un oui bit-à-bit opposable.

5.1 — Le contrat : la task n'est pas persistée → le caller la re-fournit

Puisque la task d'entrée n'est pas stockée (§2.3), R1 ne peut pas la deviner — et l'architecture refuse la parade coûteuse (persister chaque task + spec complète, +Ko par run, migration de schéma). Le contrat est explicite et assumé : POST /v1/swarm/replay/:id prend un corps { task: Value, topology?: TopologyDto, budget?: Budget }. Le caller re-fournit la task qu'il détient déjà (c'est sa requête d'origine). L'endpoint reconstruit la topologie depuis le topology nommé du StoredRun (et/ou la spec re-fournie), l'instancie sur un Blackboard vierge, et re-exécute. La garde anti-confusion : R1 compare les input_hash des générateurs (dont l'entrée dérive de la task) entre le run scellé et la re-exécution — si le caller a re-fourni une autre task, ces input_hash divergent, et R1 signale task_mismatch: true avec outputs_reproduced: null (erreur d'opérateur) plutôt que un faux outputs_reproduced: false qui laisserait croire le run non reproductible. (Affinement du build : un drapeau diagnostique dans le rapport, retenu sur un 400 opaque — le verdict de (non-)reproductibilité n'est jamais émis à tort.)

5.2 — Re-exécuter les agents purs (Mode A) → comparer

Pour un run Mode A, R1 re-dérive les sorties à l'octet. Les générateurs (EchoGenerator, ConstGenerator, et les 34 agents purs du catalogue) sont des fonctions pures : generate(task, variant) redonne le même Value. Les juges (VerifierJudge, LengthBandJudge, ConsistencyJudge, …) notent par évaluation déterministe. L'agrégation (Vote / Borda / Condorcet) est une fonction pure des bulletins. R1 implémente la closure reproduce de replay_outputs (replay.rs:182-200) : pour chaque record, re-jouer l'agent, re-hasher la sortie (BLAKE3 canonique), comparer à l'output_hash scellé.

Correction post-build : R1 compare les SORTIES, PAS la racine. Le build a établi empiriquement (deux POST /run identiques → deux racines différentes) que la provenance_root lie l'identité par-run : body_value (record.rs:137-168) hashe record_id (UUID v4 par record), swarm_id (frais par run) et causal_parents. La racine est donc de même nature que n17_root — re-provable par R0 (re-sceller les mêmes records → même racine) mais non reproductible par re-exécution. R1 ne compare donc jamais fresh_root == stored.root ; il compare l'empreinte de calcul identité-libre de chaque record (agent, rôle, mode, variant, input_hash, output_hash, lectures, écritures) — tout sauf l'identité par-run. Verdict R1 = outputs_reproduced.

La largeur d'exécution est sans effet (I-RP8, héritée d'I-CP1, ADR-014) — R1 peut rejouer à w=1 ce qui fut exécuté à w=32 et re-dériver les mêmes sorties.

5.3 — Mode C : cache_hit/replay_of, sinon MatchOutcome honnête

Pour un run Mode C, R1 ne tente jamais de garantir un bit-à-bit qu'il ne peut pas tenir. Par appel LLM, trois chemins, dans l'ordre de préférence : (1) si le LlmProvenanceRecord porte un cache_hit (llm_provenance.rs:698, CacheProvenance), R1 relit le cache (clé déterministe = sha256 du prompt + modèle + params canoniques) → Match déterministe ; (2) si l'appel pointe un replay_of (l.696) ou si l'on relit simplement le record persisté, R1 prend la sortie scellée comme dérivation par identité → Match ; (3) sinon (appel éphémère, pas de cache, pas de graine garantie), R1 marque SkippedNonDeterministic — et ne casse pas le verdict global pour autant : un Mode C non-rejouable n'est pas une faute, c'est une limite physique honnêtement publiée. Le re-appel du provider (option « Full », payante et non garantie même à graine épinglée) est hors-périmètre du MVP (§10) : on ne propose pas une reproductibilité qu'on ne peut pas honorer.

5.4 — N17 : re-prouvée, pas re-produite

Tension cruciale, tranchée nettement. La feuille N17 est sha256(canonical_bytes(record)) sur le record complet (ADR-016), lequel contient recorded_at: SystemTime et trace_id (UUID v4) — deux champs par-run. Donc n17_root diverge à chaque rejeu (timestamps neufs) : ADR-016 le dit déjà, « n17_root est par-run, une empreinte re-prouvable, pas une racine déterministe ». R1 ne doit donc jamais recalculer n17_root ni le comparer. À la place, il relit les feuilles N17 originales du store et appelle verify_run_offline (ADR-016) pour re-vérifier la chaîne N17 scellée et le pont (I-RP7). Autrement dit : la chaîne d'essaim est reproductible (clavée sur le substrat) ; la forensique N17 est re-prouvable mais non reproductible (clavée sur le temps). L'endpoint expose les deux faits sans les confondre.

R0 répond gratuitement « les records commettent-ils la racine ? » ; R1 répond, task en main, « la re-exécution reproduit-elle les sorties ? ».

§7 Le modèle de menace — ce que le rejeu attrape que verify n'attrape pas

Une architecture de preuve se juge à son modèle de menace explicite. Le point clé : /replay couvre une classe d'attaque orthogonale à /verify.

Forger un record auto-cohérent : sortie jamais produite par l'agent, mais output_hash et HMAC parfaitement scellésR1 (Mode A) — la re-exécution donne un output_hash ≠ scellé → NEUF, c'est le gain

7.1 — Le record auto-cohérent mais non-reproductible (le gain)

C'est la faille que verify ne peut pas voir et que /replay ferme. Un opérateur scelle un record dont la sortie est fabriquée — disons un juge qui « approuve » un candidat qu'il aurait en réalité rejeté. Le record est syntaxiquement parfait : son payload_hash recouvre son output_hash fabriqué, son HMAC est valide, le DAG est cohérent. verify dit « intègre ». Mais R1 re-exécute le juge sur les mêmes candidats et obtient un output_hash différent : le verdict réel du juge n'est pas celui scellé. R1 localise le record fautif et déclare le run non-reproductible. C'est la différence entre « ce reçu n'a pas été raturé » et « les chiffres du reçu sont faux ». Pour le Mode A, cette garde est totale : aucune sortie fabriquée ne survit à une re-exécution pure.

7.2 — Ce que le rejeu n'attrape PAS (scopé dehors, sans fard)

La deuxième colonne du modèle de menace est aussi importante que la première. Le rejeu ne prouve pas la reproductibilité bit-à-bit d'un appel Mode C éphémère : un LLM hébergé, sans cache et sans garantie de graine, peut produire une sortie différente à chaque appel — c'est une limite physique, pas un bug. R1 ne « rattrape » pas un Mode C fabriqué par re-appel du provider (le re-appel est hors-périmètre, et de toute façon non concluant). Il le signale (SkippedNonDeterministic) au lieu de prétendre. De même, le rejeu n'atteste pas l'identité du modèle à la source (un backend menteur déclarant gemma3:12b tout en appelant autre chose) — c'est la limite déjà assumée d'ADR-016 (model_hash_verified: false), héritée ici. Enfin, le rejeu ne reproduit pas le timing (latences, ordre d'achèvement Tokio, wall_at) : par conception ADR-007, le timing est hors du moat, donc hors du rejeu déterministe.

§8 Le harnais — Lot REPLAY

Le gate est de catégorie correction (le prior est favorable, §3.3). Trois volets éprouvés, exécutés le jour du build, artefact daté scripts/swarm/EFE_SWARM_REPLAY_2026-06-17.json.

8.1 — Les trois volets éprouvés

① Reproductibilité Mode A (le cœur). Assembler un run keyless réel (générateurs echo/const + consensus + juges purs, K et largeur variés), le sceller → root₀. R0 : re-sceller les records → root₀ reproduit hors-ligne (I-RP3). R1 : re-exécuter sur la même task et comparer les empreintes de calcul (mêmes output_hash + flux de données) pour w ∈ {1, 4, 32}. Critère GO : R0 reproduit root₀ ∧ R1 re-dérive toutes les sorties (outputs_reproduced). Note honnête : la racine fraîche de R1 diffère forcément de root₀ (elle lie swarm_id/record_id par-run) — on ne compare donc jamais les racines en R1, on compare les sorties (I-RP1, I-RP8).

② Divergence toujours attrapée et localisée. Pour chaque vecteur — (a) muter un output d'un record relu, (b) substituer un agent pur par une version impure, (c) injecter/retirer un record — re-jouer et exiger : rejeu cassé, premier record divergent identifié, raison renseignée (MatchOutcome). Critère GO : chaque mutation est détectée ET localisée ; aucun faux négatif (I-RP2).

③ Mode C honnête + N17 re-prouvée + coût borné. Sur des records Mode C synthétiques : un appel avec cache_hit rejoue en Match ; un appel éphémère (sans cache, sans graine) est SkippedNonDeterministic et ne casse pas le verdict ; la chaîne N17 est re-vérifiée par verify_run_offline sans recomputer n17_root (I-RP6, I-RP7). Coût : R0 ≈ coût de verify (re-scellement, µs–dizaines de µs/record) ; R1 Mode A ≈ coût d'un run keyless (pas d'appel provider). Critère GO : classification correcte, N17 intacte, coût mesuré et borné.

8.2 — Le volet Mode C réel (ignoré sans Ollama)

Un test ignoré-sans-modèle (#[ignore], parité ADR-016) exécute un vrai run Mode C self-host (Ollama, graine déterministe posée par le SDK : llm.rs:73), le persiste, puis le rejoue par R1. Il n'exige pas un bit-à-bit des sorties LLM (impossible à garantir) : il exige que (a) le squelette Mode A intercalé reproduise, (b) les appels Mode C avec cache rejouent en Match, (c) les appels éphémères soient honnêtement Skipped, (d) la chaîne N17 et le pont se re-vérifient. C'est la preuve honnête que le rejeu fonctionne en conditions réelles — y compris quand le déterminisme s'arrête.

9.2 — ADR-SWARM-017, le squelette

Titre : « Rejeu déterministe — re-dériver vs re-prouver, Mode A bit-exact, Mode C honnêtement classé ». Contexte : /verify prouve l'intégrité, pas la reproductibilité ; la question « si je relance, j'obtiens la même chose ? » reste sans réponse ; le socle (ADR-007, replay.rs, DeterminismLevel) existe mais n'est pas exposé. Décision : ① réutiliser l'ordre canonique ADR-007 (OrderKey), sans nouvelle coordonnée ; ② R0 GET /replay/:id re-scelle les records scellés (hors-ligne, gratuit) ; ③ R1 POST /replay/:id { task } re-exécute le squelette (Mode A bit-exact) — la task est re-fournie (non persistée, contrat assumé) ; ④ Mode C : cache_hit/replay_of ou MatchOutcome honnête ; ⑤ N17 re-prouvée (verify_run_offline), jamais re-produite ; ⑥ format de record GELÉ, largeur neutre (I-CP1). Hors-périmètre versionné : re-appel provider en Mode C (non garanti même à graine) ; persistance automatique de la task/spec ; rejeu de sous-ensemble ; UI opérateur. Verdict : Lot REPLAY — GO sur correction (Mode A bit-exact + divergence localisée) + coût chiffré. Related : ADR-006, ADR-007, ADR-009, ADR-014, ADR-016. Conséquences : le moat répond enfin à « est-ce reproductible ? », pas seulement « est-ce intègre ? » ; 8 invariants I-RP gardés ; l'auditabilité — relancer et retrouver — devient un endpoint.
