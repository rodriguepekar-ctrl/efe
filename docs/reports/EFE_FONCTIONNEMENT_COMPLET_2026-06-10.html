§0  Vue d'ensemble — le run en 14 étapes

Tout run, quel que soit le mode ou la topologie, suit ces 14 étapes dans cet ordre exact. Le reste du document détaille chacune jusqu'au champ près, avec le même exemple déroulé.

  1. Réception & auth — le corps (task, topology, budget, mode) est désérialisé et validé ; l'appelant est identifié et son rôle vérifié.
  2. Résolution du mode — resolve_mode décide le backend, le tarif par appel, et la posture d'egress.
  3. Concrétisation de la topologie — Auto devient une forme concrète, selon la tâche et le mode.
  4. Pré-vol budget — selon la politique (Error / Stop / Degrade), on refuse, on dégrade, ou on laisse tel quel.
  5. Construction du backend — Mode A (flotte) ou Mode C (modèle local) ; garde-fous egress & health.
  6. Câblage — on instancie ProvenanceRecorder, BudgetGuard, collecteur N17, Meter, et le substrat (Blackboard + TeeSink + EventTap).
  7. Résolution de la topologie en agents — chaque agent nommé est cherché dans la flotte et enveloppé du Meter (sinon UnknownAgent).
  8. Notification de démarrage — l'observateur (dashboard) reçoit on_run_start.
  9. Exécution de la topologie — le cœur : pour le consensus, génération // → jugement // → vote. Chaque appel d'agent passe par le micro-cycle (charge → exécute → capture).
  10. Post-vol budget — politique Error : échec si le budget a été épuisé en cours (BudgetExceeded).
  11. Scellement — les AgentCallRecord sont chaînés (HMAC) et hachés (blake3) → provenance_root.
  12. Auto-vérification — verify_swarm re-prouve immédiatement (chaîne + contenu + DAG) ; alimente les métriques partagées.
  13. Assemblage de la réponse — l'objet SwarmRun (9 champs) est construit ; l'observateur reçoit on_finish.
  14. Persistance & service — la passerelle range le run (records bruts) ; /verify/:id et /records permettront la re-preuve indépendante, hors-ligne.

§1  L'arrivée de la requête

Le corps : exactement quatre champs

L'API publique est délibérément minuscule. Un POST /v1/swarm/run porte un JSON à quatre clés, et rien d'autre. Détaillons chacune et ses sous-champs réels.

task — la donnée à traiter

Un JSON libre. Aucune forme imposée. Conventionnellement on y met un champ text ; si on fournit expected, certains juges l'utilisent comme oracle (le juge j_equals_expected enveloppe l'oracle equals_expected). expected est facultatif ; sans lui, le consensus s'appuie sur des juges non-oracle (consistance, longueur, recouvrement de mots).

topology — la forme du câblage

Discriminée par kind : generate_verify (T1), pipeline (T2), hierarchical (T3), consensus, ou auto. Champs par forme : T1 = {generator, verifier, k} ; T2 = {stages:[...]} ; T3 = {decomposer, solver, merger} ; Consensus = {generator, judges:[...], k, pattern} où pattern ∈ {vote, borda, condorcet}. Les noms référencent des agents de la flotte par identifiant snake_case.

budget — le plafond & la politique

Trois sous-champs : max_cents (u32, le plafond), on_exceed ∈ {stop, error, degrade} (défaut stop), et l'optionnel price_per_call_cents (u32) qui force le tarif par appel ; absent, c'est le tarif du mode qui s'applique (§2).

mode — avec quoi exécuter

Soit la chaîne "keyless", soit { "self_host": { "endpoint":"…", "model":"…" } } ou { "network": { "provider":"…" } }. C'est le seul champ qui détermine la souveraineté et le coût réel.

La validation : on échoue tôt

Le DTO est validé à la désérialisation. Une topologie incohérente est rejetée avant tout calcul : un pipeline à zéro étage lève EmptySpec → 400 Bad Request. Un nom d'agent inconnu provoquera UnknownAgent à la résolution (§7). Aucune ressource n'est consommée pour une requête malformée.

Le contrôle d'accès

L'extracteur Caller fournit tenant (chaîne) et roles (liste). En dev, il lit x-efe-tenant (défaut : tenant système) et x-efe-roles (CSV) ; si aucun rôle n'est fourni, l'appel est autorisé (démo keyless). En prod (feature oidc), il valide un JWT ES256 (clé publique server-side). Le run exige require_any_role(["operator","admin"]). Le tenant n'est jamais une clé : il sert à dériver la clé de provenance (HKDF, server-side).

Détail souveraineté. Aucune clé applicative ne transite par la requête. Le seul secret est le master HKDF (lu côté serveur via l'environnement) qui signe la chaîne de provenance — jamais transmis. En mode network, les clés provider vivent dans le routeur, pas dans la passerelle.

§2  Résolution du mode

resolve_mode transforme le mode demandé en mode exécutable et renvoie un triplet : (mode_exécutable, allow_remote, tarif_à_préserver). Les quatre cas, exhaustivement :

Mode demandéMode exécutableallow_remotetarif préservétarif/appel
Keylessinchangé (flotte Mode A)falseNone1 ¢
SelfHost{endpoint,model}inchangéfalseNone0 ¢ (local)
Network{provider} (routeur câblé)SelfHost{endpoint=routeur, model=résolu}trueSome(5)5 ¢
Network{provider} (pas de routeur)— refus ———501

Détail 1 — le mapping provider→modèle (Inc.4.b)

En network, provider est une famille (« anthropic »). La table RouterMap la traduit en identifiant de modèle concret attendu par le routeur (« anthropic » → « anthropic/claude-3-5-sonnet-latest », « openai » → « openai/gpt-4o »…). Règles : si provider contient déjà : ou / (déjà qualifié) → passthrough ; sinon consultation de la table (insensible à la casse) ; famille inconnue → passthrough (le routeur tranche). Surchargeable via EFE_SWARM_ROUTER_MODELS. Un identifiant de modèle n'est pas un secret.

Détail 2 — la préservation du tarif (cost-governance)

La traduction Network → SelfHost ferait tomber le tarif à 0¢, vidant la gouvernance de son sens en network. resolve_mode renvoie donc le tarif Network à préserver (5¢) ; le handler l'injecte au budget via get_or_insert, qui respecte un price_per_call_cents explicite du client et ne l'applique que s'il est absent. Le coût réel reste chez le provider via le routeur ; ce tarif est l'unité de gouvernance.

Détail 3 — pourquoi 501 plutôt qu'une exécution

Network demandé sans routeur câblé (EFE_SWARM_ROUTER_ENDPOINT absente) → 501, un refus net. Le déploiement par défaut est souverain ; on n'invente pas un egress non autorisé.

Notre fil rouge. Mode = keyless → exécutable inchangé, allow_remote=false, tarif = 1¢/appel, egress = 0. Run entièrement déterministe.
