L'Essaim — nano-agents parallèles

Beaucoup de petits agents à très peu de paramètres, en parallèle, qui se passent l'information.
Le nom le dit : Essaim Fluide Éphémère. Des dizaines d'agents minuscules (3–8 lignes, ≤ 2 paramètres, déterministes) s'exécutent en parallèle borné et échangent leurs résultats par deux substrats — un tableau noir vérité et un bus indice. De cette circulation d'information émergent des comportements (générer, vérifier, débattre, voter) — et chaque échange est tracé.

Idée-force. On ne construit pas un « gros agent » intelligent. On construit beaucoup de petits agents bêtes — chacun fait une chose, en quelques lignes, sans état — et on les fait communiquer en parallèle. L'intelligence est dans la topologie (comment ils sont câblés) et dans la circulation de l'information (les deux substrats), pas dans l'agent. C'est plus vérifiable (chaque pas minuscule est traçable), plus robuste (un agent qui rate ≠ tout rate), et plus souverain (tout tourne en local, déterministe).

§1  La vision : un essaim de nano-agents

Une tâche entre. Elle se diffuse à K générateurs qui produisent des variantes en parallèle. Chacun écrit son résultat dans un substrat partagé. Des juges lisent en parallèle et notent. Un agrégateur déterministe vote. Un gagnant ressort — et toute la circulation a laissé une trace cryptographique.

Figure 1 — L'essaim au travail. Vert = écritures vers la vérité (Blackboard) ; violet = indices (TopicRouter, pub/sub). Les K générateurs et J juges tournent en parallèle ; l'agrégateur lit la vérité (exhaustive) pour voter.

§2  Anatomie d'un nano-agent

Un agent = une implémentation de l'un de cinq traits. Pas d'état, pas d'I/O, pas de hasard (la diversité vient d'un paramètre variant: usize). Tous sont des structs immuables enveloppés d'Arc<dyn Trait> et enregistrés par nom dans AgentFleet.

Figure 2 — Les 5 familles de traits. La flotte standard enregistre 43 agents (34 du catalogue Mode A + 9 juges) — assert vérifié dans fleet.rs.

« Tiny » au sens littéral

// Un agent typique : 3 lignes, 0 paramètre.
pub struct Uppercase;
impl Stage for Uppercase {
  async fn process(&self, x:&Value)->Vec<Value> {
    vec![json!({"text": text_of(x).to_uppercase()})]
  }
}

Le plus « gros » : 2 champs

// Le maximum observé : 2 paramètres.
pub struct LengthBounded { min:usize, max:usize }
impl Verifier for LengthBounded {
  fn score(&self,_t:&Value,c:&Value)->f64 {
    let n = text_of(c).len();
    if n>=self.min && n<=self.max {1.0} else {0.0}
  }
}

Conséquence directe : un agent est auditable d'un coup d'œil, déterministe (donc reproductible — ADR-SWARM-007), et composable. La complexité vit dans la topologie, pas dans l'agent.

§3  Les deux substrats d'échange d'information

Comment la sortie d'un agent devient l'entrée d'un autre ? Par deux mécanismes complémentaires — le keystone WS1 de l'architecture : Blackboard = vérité  TopicRouter = indice.

Figure 3 — Les deux substrats. Le bus route vite l'information (indice), le tableau noir la garantit (vérité). Un juge fait les deux : bb.write("/ballot/j", …) + router.publish("ballot.j", …).
Pourquoi deux substrats ? Le bus seul peut perdre des messages (capacity bornée, abonné lent) — inacceptable pour un vote. Le tableau noir seul oblige à scruter (polling) — lent. Combinés : le bus réveille l'agrégateur (latence basse), le tableau noir lui garantit l'exhaustivité (correction). C'est le compromis indice/vérité.

§4  Le parallélisme (borné)

Le parallélisme est explicite (pas de pool caché) et borné (un Semaphore limite le nombre d'agents en vol → protège l'hôte). Deux idiomes Tokio :

Générateurs — JoinSet + Semaphore

let sem = Arc::new(Semaphore::new(max_concurrency));
let mut set = JoinSet::new();
for variant in 0..k {
  let (g, task, sem) = (g.clone(), task.clone(), sem.clone());
  set.spawn(async move {
    let _p = sem.acquire_owned().await; // borne
    (variant, g.generate(&task, variant).await)
  });
}
// collecte à mesure que ça finit
while let Some(r)=set.join_next().await { … }

Juges — tokio::spawn + Semaphore

for (j, judge) in judges.iter().enumerate() {
  handles.push(tokio::spawn(async move {
    let _p = sem.acquire_owned().await;
    let scores = judge.assess(&task, &cands).await;
    bb.write(&format!("/ballot/{j}"), …);   // vérité
    router.publish(SwarmEvent{ topic:
        format!("ballot.{j}"), … });        // indice
  }));
}
for h in handles { let _ = h.await; }
Figure 4 — Parallélisme borné. Le sémaphore plafonne les agents simultanés (DoS-safe, garde-fou G8). Tous les sites concurrents (générateurs, juges, étages de pipeline, solveurs) suivent ce schéma.

§5  Les 4 topologies de câblage

La même flotte de nano-agents, câblée de 4 façons. C'est ici qu'est l'intelligence.

Figure 5 — Les quatre topologies. T1 sélectionne, T2 transforme en flux, T3 récursif (« superviseur de superviseurs »), Consensus vote. Un Solver de T3 peut être lui-même un T1/T2/T3 → composition arbitraire.

confiance = marge / max = (6−4) / (2 juges × 3) ≈ 0.33
Le lien avec le moat. Chaque écriture au Blackboard passe par un write-sink → AgentCallRecord scellé. La circulation d'information de l'essaim EST la trace de provenance. Un régulateur re-prouve, hors-ligne, quel nano-agent a produit quel candidat, quel juge a voté quoi, et pourquoi tel gagnant — sans nous croire. (cf. le rapport « moat » pour la cryptographie.)

§7  Concurrence & garanties

Faire tourner des dizaines d'agents en parallèle exige des garanties dures. Le substrat les fournit et les teste.

CAS atomique (write_if)

Le verrou de shard est tenu pendant tout le compare-and-swap → deux écrivains concurrents sérialisent, aucune mise à jour perdue (invariant testé : swarm_cas_invariant).

Sharding du work-queue

Les pointeurs sont répartis sur des shards DashMap → verrous fins (µs), contention minimale même à K élevé (work_queue_sharding).

Livraison fiable & quiescence

Le pipeline streaming détecte la quiescence (tous les topics drainés) pour terminer proprement ; livraison fiable testée (reliable_delivery, streaming_quiescence).

Bornes & backpressure (G8)

Cap global d'octets + caps par namespace + ring de 8192 écritures + capacity bornée des canaux → mémoire O(1), drops comptés. L'essaim ne peut pas saturer l'hôte.

Idempotence & N17 sous re-tentative

Un appel d'agent Mode C peut être re-tenté (Retrier). Le pont N17 garantit qu'un seul record forensique final est émis (avec retry_count) — le lien pointe vers l'issue retenue, jamais vers une tentative échouée. La concurrence (K générateurs en //) est gérée par un puits task-local par appel : aucune course, même à fort parallélisme.

§8  Émergence · fluidité · éphémérité

🌀 Émergence

Aucun agent ne « sait » résoudre la tâche. La solution émerge de la mise en concurrence (générer K fois) et de la délibération (juger, voter). C'est le pari ADR-SWARM-001 : l'agrégateur est le pari.

💧 Fluide

L'information circule en continu : les résultats arrivent au fil de l'eau (join_next), les étages se déversent l'un dans l'autre (streaming), le bus réveille les consommateurs. Pas de barrière globale rigide.

⏳ Éphémère

Un essaim naît pour une tâche puis disparaît : SwarmId neuf, Blackboard neuf, bus neuf. Rien ne persiste sauf la preuve (records + root). Zéro état résiduel, zéro fuite entre runs.

Pourquoi « beaucoup de petits » bat « un gros ». (1) Vérifiabilité : un pas minuscule et déterministe se re-prouve trivialement ; un gros modèle opaque non. (2) Robustesse : un nano-agent qui rate renvoie un sentinel neutre — la topologie dégrade, elle ne s'effondre pas. (3) Souveraineté : des fonctions Rust locales n'ont besoin ni de clé ni de réseau. (4) Coût/gouvernance : chaque appel est une unité atomique facturable (I13). La quantité et la petitesse sont des features, pas un compromis.
