§0 Plan & méthode — la double exécution

La discipline de mesure du projet (Partie 13 : réel vs simulé-étiqueté, verdicts conservés) reçoit ici une couche supplémentaire : la contre-exécution par le propriétaire. Toutes les commandes ont été rejouées dans un terminal indépendant de la session de build ; ce document confronte systématiquement les deux jeux de sorties. Quand ils coïncident au millième, c'est une propriété démontrée (le déterminisme) ; quand le réel diverge de l'attendu (le Mode C, par nature non déterministe), l'écart est analysé — jamais lissé.

§1 L'objet testé — la verticale itérative

La campagne porte sur la cinquième famille de topologies — l'influence mutuelle (T4 Gossip, Debate) — construite sur décision propriétaire en levée des gates ADR-003/005, et actée par l'ADR-SWARM-013. Rappel du périmètre exact, pour que les chiffres qui suivent aient leur dénominateur.

Le code. Un module neuf (iterative/ : RoundDriver et ses cinq invariants I-IT1…5, GossipTopology, DebateTopology avec escalade à trois étages), la verticale SDK complète (spec, resolver, Meter, Mode C), le DTO de fil, les verdicts structurés au dashboard, et la pièce la plus profonde : le graphe d'influence scellé — chaque agent d'un tour ≥ 1 déclare ses lectures (pointer@version exacts, convention _reads liftée par le Meter), scellées dans le corps hashé des records et contrôlées par le check DAG anti-version-fantôme de verify_swarm. Commit 167f81f (+2 684 lignes), complété par la passe ADR-013 (tests de chemins résiduels : LlmRefiner, repli StageRefiner, erreurs typées, unités d'estimation/dégradation).

La politique de livraison. Opt-in strict — Auto ne sélectionne jamais l'itératif — parce que les gates exécutés avec le build (S2-bis, S3-bis) ont rendu des verdicts défavorables sur les familles mesurées : la notice d'emploi est versionnée avec le code. La campagne de ce document vérifie donc deux choses à la fois : que la machinerie tient (tests, preuve, API), et que les verdicts qui encadrent son usage se reproduisent.

§2 La suite de tests : 20 + 8 + 2, puis la pile entière

Première étape de la campagne propriétaire : les trois suites itératives ciblées, puis la pile complète des dix crates. Sorties verbatim du terminal.

2.1 — Les suites itératives : 30 tests, 0 échec

La suite topologie a rendu 20 passed; 0 failed — et la liste nominative affichée dans le terminal couvre exactement le contrat : les invariants du RoundDriver (write-once avec conflit compté, borne r_max, purge new_epoch entre runs, arrêt Stability), la convergence du gossip (mean_pull vers la moyenne, hold qui avoue sa non-convergence, majority_adopt catégoriel, seams observés), et le débat complet (Borda extrait le correct après débat, rounds = 0 = consensus pur, arrêt anticipé sur arguments répétés, le jury reçoit le dossier intégral, et les trois étages d'escalade chacun par son test). La suite d'intégration SDK a rendu 8 passed — dont les deux tests de preuve qui font la valeur de la verticale : gossip_run_is_sealed_and_reproven (scellé, 100 % tracé, comptabilité au centime) et influence_graph_is_sealed_as_reads_and_dag_checked (les lectures scellées à version exacte, validées par le DAG). La suite HTTP passerelle a rendu 2 passed : le contrat de fil, de la requête JSON à la re-preuve.

2.2 — La pile entière : 817 · 0 · 5, vérifié par addition

La commande pleine pile a affiché 36 lignes test result: ok. — pas une seule n'indiquant d'échec. L'addition des « passed » de ces lignes (faite indépendamment des compteurs de la session de build) donne 817 passés · 0 échec · 5 ignorés — la correspondance est exacte. Les cinq ignorés sont les attendus : les tests d'intégration à ressources externes (Postgres réel via DATABASE_URL, Ollama vivant pour les suites dédiées), marqués #[ignore] avec leur commande de lancement. Deux lignes de la sortie méritent une lecture particulière : le 80 passed de la suite topologie (77 historiques + 3 tests d'escalade — la croissance est traçable), et les 2 passed de keyless_guardrails — les tests-gardiens qui scannent la source du SDK et garantissent que toute cette extension n'a introduit ni dépendance réseau, ni lecture de clé.

Ce que cette étape établit. La verticale itérative ne vit pas dans un bac à sable : elle est insérée dans la pile complète, et la pile complète — substrat, provenance, SDK, passerelle, dashboard, PII, clés — reste intégralement verte avec elle dedans. Le coût d'intégration mesuré sur l'existant : zéro régression, sur 817 points de contrôle, constaté sur deux machines d'exécution.

§3 Les gates rejoués — le déterminisme entre machines

L'étape la plus instructive de la campagne n'est pas un test qui passe : c'est une coïncidence parfaite. Les deux harnais de gate, relancés dans le terminal propriétaire, ont reproduit les résultats de la session de build au millième près — chaque bras, chaque écart-type.

3.1 — Lot S2-bis (Gossip) : les deux exécutions, côte à côte

Brassession de buildterminal propriétairecoût
single3,490 ± 0,1373,490 ± 0,1371
mean@12 (le témoin)0,942 ± 0,0360,942 ± 0,03612
gossip 6×21,294 ± 0,0461,294 ± 0,04612
gossip 4×31,641 ± 0,0521,641 ± 0,05212

Verdict affiché dans les deux terminaux : NO-GO — « le prior ADR-003 confirmé : à budget égal, l'itération n'apporte rien que la moyenne n'ait déjà ». Le Lot S3-bis a fait de même : baseline 0,914, témoins 0,999 / 1,000, les quatre bras δ (0,888 · 0,934 · 0,959 · 0,979) identiques, verdict CONDITIONNEL, δ* ≈ ∞ — même à +0,15 de compétence créditée au débat, « payer plus de juges » domine au même budget. Les artefacts ont été réécrits dans scripts/swarm/ à contenu identique.

3.2 — Pourquoi cette coïncidence est une démonstration, pas une chance

Deux processus distincts, lancés à des moments différents, par des personnes différentes, sur des états de terminal différents — et 16 nombres à virgule flottante identiques au dernier chiffre affiché. Ce n'est possible que parce que les harnais tirent tout leur aléa de splitmix64 ensemencé (graines composées des indices de tâche, d'agent et de bootstrap) et rien de l'horloge ou de l'OS. C'est l'ancre de reproductibilité Mode A (ADR-007), exhibée non plus par un test unitaire mais par l'expérience la plus convaincante qui soit : le client refait le calcul chez lui et obtient le même résultat. La promesse commerciale du projet — « re-vérifiez vous-même » — vient d'être exécutée littéralement sur ses propres verdicts de gate.

Et le fond reste le fond. La reproduction ne change pas les verdicts : sur la famille « estimation bruitée », l'itération perd contre la moyenne à budget égal ; sur la famille S3, le levier reste la compétence des juges. Les topologies itératives demeurent ce que l'ADR-013 a acté — des instruments opt-in, livrés avec la preuve chiffrée de quand ne pas s'en servir.

§4 Le Mode C réel — gemma3, l'escalade traversée, le pont N17

L'étape 5 a fait tourner la verticale sur un vrai SLM local (Ollama, gemma3:12b, zéro clé) — le domaine où le non-déterminisme est la règle, et où l'analyse remplace la coïncidence.

4.1 — Gossip : convergence éclair, et l'honnêteté du « 0 lectures »

estimation : 36.0
tours : 1 · résiduel : 0.0 · convergé : true
preuve : verified=true · 4 records · 0 lectures scellées (graphe d'influence)
N17 : 4 appels LLM, cohérent=true

Les quatre refiners — interrogés sur le temps de lecture d'un rapport de 12 pages, à des températures distinctes (0,2 à 0,5) — ont répondu la même valeur : 36 minutes (3 min/page : l'estimation est raisonnable). Variance nulle dès le tour 0 → convergence au tour 1, résiduel 0. La ligne la plus précieuse est « 0 lectures scellées » : ce n'est pas un manque, c'est la véracité du graphe d'influence. Les _reads ne se déclarent qu'aux tours ≥ 1 (au tour 0, il n'y a pas de pairs) ; convergé en un tour = aucune influence n'a eu lieu = aucune lecture scellée. Le système refuse d'inventer de l'influence — exactement l'assertion du test d'intégration (3×(tours−1) lectures), vérifiée ici en conditions réelles. Et le pont N17 : 4 appels, cohérent — chaque record d'agent lié à sa fiche forensique LLM, sur de vraies réponses.

4.2 — Debate escaladé : 13 appels, la décomposition exacte

verdict : {"value":"Bias amplification"}
appels : 13 (l'escalade dit si le débat a été payé) · verified=true

Le nombre 13 raconte toute la traversée : 13 = 3 + 2 + 6 + 2. Trois candidats générés (températures 0,2/0,5/0,8 → des formulations distinctes) ; le Vote gratuit n'est pas confiant → étage ② ; le jury sans dossier (2 appels) rend une marge Borda sous le seuil → étage ③ ; le débat est payé (2K×1 = 6 arguments PRO/CONTRA) puis le re-jury sur dossier (2 appels) tranche. L'escalade est allée au bout parce que l'essaim hésitait réellement — « payer selon l'hésitation », observé en réel sur une question subjective. Et le verdict rendu — « Bias amplification » comme premier risque opérationnel d'un procurement agentique — est une réponse de qualité, issue d'un dossier contradictoire intégralement scellé.

4.3 — L'observation honnête de l'étape

Les seuils d'escalade câblés par escalate: true (0,9 / 0,9 — parité avec l'escalade du consensus) sont stricts en Mode C : avec K = 3 et J = 2, une confiance Borda ≥ 0,9 exige une quasi-unanimité — sur les questions subjectives, le débat sera donc souvent payé. C'est un comportement défendable (l'étage 3 existe précisément pour ces instances), ajustable en code (with_escalation(s1, s2)) ; l'exposition de seuils réglables au niveau de la spec est notée comme extension possible, à la demande.

§5 Le bout-en-bout HTTP — run, re-preuve, influence

La clôture de la campagne : un run gossip soumis par curl au contrat de fil, puis re-prouvé par l'endpoint du moat. Les deux réponses JSON, verbatim du terminal propriétaire.

5.1 — Le run (POST /v1/swarm/run, kind: gossip, keyless)

{
  "value": 100.0,
  "gossip": { "converged": true, "residual": 0.08573388203018059,
              "rounds": 4, "write_conflicts": 0 },
  "verified": true,
  "run_id": "6fe90cfa-53a1-403d-b42f-5815b2a0662b"
}

Quatre initiales [90, 110, 95, 105] → la nuée converge sur 100.0 exactement (la moyenne), en 4 tours — et la trajectoire est celle que l'arithmétique du mean_pull prédit : variance 62,5 → ~6,9 → ~0,77 → 0,0857 ≤ ε (0,1). Zéro conflit d'écriture (I-IT1 sous HTTP), et le run revient déjà verified: true — la re-preuve interne du scellement (Partie 5–6, phase 4) a eu lieu avant même que la réponse parte.

5.2 — La re-preuve par l'API (GET /v1/swarm/verify/:id)

{
  "verified": true,
  "dag_consistent": true,
  "traced_pct": 1.0,
  "root": "9686590317557e019101a11241a76e5cbca7d54811c5d8b9a3111aa45ef4b717"
}

C'est la pièce maîtresse de la campagne, et chaque champ porte. verified: true : la passerelle a rechargé les 16 records scellés (4 agents × 4 tours) depuis son store, re-déroulé la chaîne HMAC, recalculé chaque hash — l'intégrité complète, indépendamment de l'exécution. dag_consistent: true : le contrôle qui n'existait pour aucune topologie itérative au monde — ce run de 4 tours contient 12 déclarations de lecture (chaque refine des tours 1–3 déclare sa cellule et ses trois pairs, pointer@version exacts), toutes confrontées aux écritures ancrées : aucun parent pendant, aucune version fantôme. Le « qui a lu qui, à quel tour » de ce run précis est prouvé. traced_pct: 1.0 : les 16 appels ancrés à leur cellule. Et la racine 9686…b717 : l'engagement de 32 octets de ce run — exportable avec les records (GET /runs/:id/records) et re-dérivable hors ligne, sans la passerelle, pour toujours.

La phrase que cette étape autorise. « Un client a soumis un essaim à influence mutuelle par une requête HTTP, et a obtenu — par une seconde requête — la preuve cryptographique que la convergence observée résulte exactement des lectures déclarées, sans falsification possible a posteriori. » Aucun mot de cette phrase n'est de l'extrapolation : chaque clause correspond à un champ des deux JSON ci-dessus.
