§1 Le pari fondateur & les six rôles

Avant de décrire les agents et les topologies, il faut comprendre l'intuition qui les justifie tous. EFE ne mise pas sur un gros agent intelligent que l'on rendrait toujours plus puissant ; il mise sur une nuée de petits agents bon marché et sur la manière de les coordonner. C'est un pari, et il a un nom dans le code : le pari S1.

1.1 — L'intuition : la bonne réponse est souvent présente, mais minoritaire

Considérons une tâche dont on peut vérifier la réponse — par exemple « extrais les entiers de ce texte », « cette sortie est-elle un JSON valide contenant le champ x ? », « ce résumé est-il ancré dans la source ? ». Pour ce genre de tâche, vérifier une réponse est facile et fiable ; produire la bonne réponse du premier coup l'est beaucoup moins. Le pari S1 (formalisé dans l'ADR-SWARM-002) part de ce constat empirique : si l'on génère K candidats bon marché, la bonne réponse est très souvent présente parmi eux — mais elle peut être minoritaire.

C'est ce dernier point qui change tout. Le réflexe naturel, quand on a K candidats, est de les faire voter : on garde la réponse majoritaire. Mais le vote échoue précisément dans le cas qui nous intéresse. Si les générateurs partagent un biais — et de petits modèles partagent souvent les mêmes biais —, ils se trompent de la même façon. Leurs erreurs sont corrélées. Le vote élit alors l'erreur commune, et écrase la bonne réponse minoritaire qui, elle, était correcte mais isolée. Voter, c'est faire confiance à la fréquence ; or la fréquence est exactement ce qui ment quand les erreurs sont corrélées.

La conclusion du pari S1 est donc : il ne faut pas voter la réponse, il faut la sélectionner. Et pour sélectionner, on a deux instruments. Soit un vérificateur déterministe qui regarde la qualité intrinsèque de chaque candidat et garde le meilleur, indépendamment de sa popularité (c'est la topologie T1). Soit, quand aucun vérificateur unique n'est assez fiable, un panel de juges dont on agrège les classements de façon fine (c'est T-Consensus, et le Borda de la section 5). Dans les deux cas, on remplace la démocratie naïve du vote par un jugement sur le fond.

Le pari fondateur, en une phrase : sur une tâche vérifiable, générer est bon marché, vérifier est sûr — donc on génère beaucoup et on sélectionne finement, plutôt que de chercher à avoir raison du premier coup ou de voter. Toutes les topologies d'EFE sont des déclinaisons de cette idée.

1.2 — Le vocabulaire : les six rôles d'agents

Pour exprimer ces patterns, le code définit six traits Rust — six « formes » qu'un agent peut prendre. Un trait, ici, n'est rien d'autre qu'un contrat : une fonction (asynchrone, le plus souvent) avec une signature précise. C'est le vocabulaire minimal qui permet de décrire n'importe quelle topologie sans rien savoir de l'implémentation des agents — ce qui, on le verra en §2, permet de basculer entre agents déterministes et agents LLM sans toucher aux topologies.

Rôle (trait)Signature réelleCe qu'il fait dans l'essaim
Generatorasync generate(task, variant) → Valueproduit un candidat. Le paramètre variant sert à diversifier : le générateur n° 3 ne produit pas la même chose que le n° 0.
Verifierscore(task, candidat) → f64 · passes()note un candidat (et dit s'il « passe »). Déterministe, synchrone, sans appel externe — c'est l'ancre de confiance de T1.
Stageasync process(input) → Vec<Value>une étape de transformation, maillon d'un pipeline (T2). Peut produire plusieurs sorties.
Decomposerasync decompose(task) → Vec<Value>découpe une tâche trop dure en sous-tâches plus simples (T3).
Solverasync solve(subtask) → Valuerésout une sous-tâche. Récursif : un Solver peut lui-même être un T1, un T2 ou un T3 (§6).
Mergerasync merge(task, results) → Valuerecombine les sous-résultats en une réponse finale (T3).

On notera que le Verifier est le seul rôle synchrone et déterministe du lot. Ce n'est pas un hasard : c'est lui qui sert d'« ancre » objective. Même quand les générateurs sont des modèles de langage (donc non déterministes), le vérificateur, lui, reste une fonction pure et reproductible. On reviendra sur ce point en §3 — c'est ce qui empêche un essaim de se juger lui-même avec ses propres biais.

1.3 — Les quatre topologies, vue d'ensemble

À partir de ces six rôles, EFE compose quatre patterns de collaboration. Tous se cachent derrière un même trait Topology (object-safe, donc manipulable de façon uniforme). Voici la carte ; les sections suivantes les détaillent une par une.

TopologieFormePour quel genre de tâche
T1 · Generate-VerifyK générateurs en ∥ → un vérificateur a-posterioritâche vérifiable où la bonne réponse peut être minoritaire — le gagnant du gate S2 (§3)
T-ConsensusK générateurs + J juges en ∥ → Vote / Borda / Condorcetquand aucun vérificateur unique n'est fiable : on agrège plusieurs avis ordinaux (§4-5)
T2 · Pipelineétapes chaînées, en flux (streaming, sans barrière)décomposer une tâche en transformations successives bon marché (§6)
T3 · Hiérarchiquedécompose → résout en ∥ → fusionne (récursif)ramener une tâche trop dure dans l'enveloppe de capacité d'un petit modèle (§6)

§2 Les nano-agents — 43 fonctions pures

Le mot « nano » est à prendre au sérieux. Un nano-agent n'est pas un mini-modèle de langage, ni un acteur avec un état interne : c'est une fonction pure, une struct Rust qui implémente l'un des six rôles et ne fait rien d'autre. Pas de poids, pas de réseau, pas de mémoire entre les appels. Cette austérité est un choix, et elle a des conséquences profondes.

2.1 — Ce qu'est (et n'est pas) un nano-agent

Voici un agent complet, tel qu'il apparaît dans le code. Quatre lignes utiles :

struct Uppercase;
impl Stage for Uppercase {
  async fn process(&self, input: &Value) -> Vec<Value> {
    vec![ json!({ "text": text_of(input).to_uppercase() }) ]
  }
}

Cet agent met un texte en majuscules. Il n'a pas de modèle, pas de paramètres entraînés, pas d'état qui survivrait d'un appel au suivant. Donné la même entrée, il produit toujours exactement la même sortie. Cette propriété — le déterminisme — n'est pas un détail : elle rend l'agent testable (on peut écrire une assertion exacte sur sa sortie), reproductible (un run keyless rejoué donne le même résultat au bit près), et instantané (pas de latence réseau, pas de GPU). C'est ce qui permet à EFE d'avoir un mode entièrement gratuit et déterministe (Mode A) qui sert à la fois de démo, de banc de test et d'ancre de confiance.

La force, évidemment, ne vient pas d'un agent isolé — un agent qui met en majuscules ne « résout » rien. Elle vient de la composition : on assemble des dizaines de ces briques via une topologie, et c'est l'agencement qui produit un comportement utile. C'est l'analogue, dans le logiciel, de la division du travail : chaque ouvrier fait une chose simple, l'organisation produit l'objet complexe.

2.2 — Le catalogue des 43, par rôle

La flotte standard (AgentFleet) embarque 43 nano-agents, montables par leur nom. Les voici regroupés par rôle ; les noms sont suffisamment parlants pour que le catalogue se lise comme un inventaire de petites capacités composables.

Décomposeurs (7)sentence_split · line_split · word_split · paragraph_split · char_chunk · json_array_split · fixed_count_split — découper une entrée selon différentes granularités
Transformations (10)trim · lowercase · uppercase · normalize_whitespace · filter_nonempty · extract_field · rename_field · extract_integers · word_count · prefix_text — nettoyer, projeter, reformater
Vérificateurs (8)non_empty_text · is_object · has_field · numeric_equals · length_bounded · keyword_present · required_fields · equals_expected — décider si un candidat satisfait un critère
Agrégateurs (7)collect_array · concat_text · join_lines · sum_values · majority_value · first_result · max_by_score_field — recombiner des morceaux en un tout
Générateurs (2)echo_generator · const_generator — produire des candidats (triviaux en Mode A ; remplacés par le SLM en Mode C)
Juges (9)length_band · keyword_overlap · groundedness · consistency · j_non_empty · j_is_object · j_keyword · j_length · j_equals_expected — noter des candidats pour le consensus

On remarque le déséquilibre assumé : peu de générateurs (deux), beaucoup de vérificateurs, transformateurs et juges. C'est une conséquence directe du pari S1 : en Mode A, la « génération » est triviale ; toute l'intelligence est dans la sélection et la transformation. En Mode C (self-host), ce sont les générateurs et les juges qui deviennent des appels au SLM, tandis que les vérificateurs restent déterministes.

2.3 — Le même nom, deux réalités (Mode A ↔ Mode C)

Voici le mécanisme qui fait toute la souplesse d'EFE, et il mérite qu'on s'y arrête. La couche SDK contient un Resolver (détaillé dans la Partie 5–6) dont le rôle est de transformer un nom d'agent en un objet concret. Or ce nom est interprété différemment selon le mode d'exécution.

En Mode A (keyless, déterministe)

le nom est une clé dans la flotte. "uppercase" résout vers la struct Uppercase ci-dessus. Tout est local, gratuit, instantané, reproductible. C'est le mode de la démo, du développement, de l'intégration continue — et l'ancre reproductible que la provenance peut rejouer (ADR-007).

En Mode C (self-host, SLM local)

le même nom devient une instruction envoyée à un petit modèle de langage local. "uppercase" devient, en substance, un prompt qui demande au modèle d'effectuer la tâche. La topologie qui orchestre les agents ne change pas d'une seule ligne.

L'intérêt est considérable. On peut prototyper et tester une topologie entièrement en Mode A — c'est gratuit et déterministe, donc idéal en CI —, puis basculer la même topologie en Mode C pour la faire tourner sur un vrai SLM souverain, sans réécrire la logique de coordination. Le découplage nom → réalité est ce qui rend cette bascule possible.

Un point reste invariant à travers les deux modes, et c'est volontaire : le vérificateur de T1 demeure toujours déterministe, tiré de la flotte, même quand les générateurs sont des appels au SLM. La raison tient au pari S1 : si l'on confiait la vérification au même type de modèle (biaisé) qui a généré les candidats, on retomberait dans le piège des erreurs corrélées — l'essaim validerait ses propres erreurs. En gardant une ancre déterministe et objective pour juger, on conserve un point de vérité externe aux biais des générateurs. C'est l'ADR-SWARM-002.

§3 T1 · Generate-Verify — générer en masse, sélectionner finement

T1 est l'incarnation la plus directe du pari S1, et le pattern qui a gagné le gate Lot S2 sur les tâches vérifiables. Son principe tient en une phrase : lancer beaucoup de générateurs en parallèle, puis laisser un vérificateur choisir le meilleur a posteriori.

3.1 — Le mécanisme

L'objet GenerateVerify::new(k, max_concurrency) prend deux paramètres : k, le nombre de candidats à produire (la « taille » de l'essaim sur cette tâche), et max_concurrency, le nombre maximum de générateurs autorisés à tourner simultanément. À l'exécution, il lance les K générateurs comme autant de tâches asynchrones, collectées dans un JoinSet, et borne leur parallélisme avec un Semaphore : on peut demander K = 200 candidats tout en n'en exécutant que 8 à la fois, pour ne pas saturer la machine. Chaque générateur reçoit un numéro de variant distinct, ce qui le pousse à produire une variation différente.

Une fois les candidats produits, le vérificateur entre en scène. Il note chaque candidat (score) et indique lesquels « passent » (passes). La sélection finale suit une règle à deux niveaux, soigneusement choisie : on retient le candidat passant de meilleur score ; s'il n'y a aucun passant, on retient par défaut le candidat de meilleur score (un repli gracieux plutôt qu'un échec) ; et s'il n'y a aucun candidat du tout, on renvoie None. Le résultat, GvResult, porte le candidat sélectionné et le meilleur score observé.

Figure 1 — T1 : K générateurs en parallèle (bornés par un sémaphore) ; le vérificateur note tout le monde et retient le meilleur passant — ici c₂, même s'il est minoritaire.

3.2 — Pourquoi ça bat le vote — l'argument complet

Reprenons l'argument du §1.1, en l'appliquant concrètement à T1. Supposons quatre générateurs sur une tâche d'extraction. Trois d'entre eux partagent un biais et produisent la même réponse fausse ; le quatrième produit la réponse juste. Un vote majoritaire élirait l'erreur trois-contre-un. T1, lui, ne compte pas les voix : il fait passer chaque candidat sous le regard du vérificateur. Comme la réponse du quatrième générateur satisfait réellement le critère (par exemple, ses entiers extraits correspondent au texte) et que les trois autres échouent à la vérification, c'est le candidat juste, pourtant minoritaire, qui est retenu.

La clé de voûte est une asymétrie : générer est bon marché, vérifier est sûr. Produire K candidats coûte K appels, mais chacun est peu coûteux ; vérifier un candidat est une opération déterministe fiable. On dépense donc dans la quantité (générer beaucoup, pour maximiser la chance que la bonne réponse soit présente) et on s'appuie sur la qualité de la vérification (pour l'extraire à coup sûr). C'est l'inverse du réflexe « un seul agent, mais qu'il ait raison » — réflexe qui mise tout sur un coup et n'a aucun filet.

Quand T1 ne suffit pas. T1 suppose qu'il existe un vérificateur unique et fiable. Pour certaines tâches, ce n'est pas le cas : la « qualité » d'une réponse est multidimensionnelle (longueur, pertinence, ancrage, cohérence…) et aucun critère seul ne tranche. C'est précisément là qu'intervient le consensus : on remplace le vérificateur unique par un panel de juges, et l'on agrège leurs avis. Ce qui nous amène à la section suivante.

§4 T-Consensus — un panel de juges sur le substrat

Quand aucun vérificateur unique ne suffit, on convoque un panel. Plusieurs juges notent les candidats selon des critères différents, et l'on agrège leurs avis. T-Consensus orchestre cela sur le substrat, et — point important — il le fait en respectant le keystone de la Partie 3.

4.1 — Le déroulé sur le substrat

L'exécution se déroule en deux phases qui exploitent directement le Blackboard et le bus. Phase de génération : un générateur produit K candidats (en parallèle, bornés par un sémaphore, comme en T1), et chacun est écrit au Blackboard sous /cand/<i> — c'est la vérité. Phase de jugement : J juges s'exécutent en parallèle (bornés, par défaut, à max_concurrency = 8), chacun évalue tous les candidats, et écrit son ballot (un score par candidat) au Blackboard sous /ballot/<j>, tout en publiant une notification légère sur le bus. Enfin, l'agrégateur collecte les ballots et calcule un gagnant.

Ici se joue le respect du keystone. L'agrégateur pourrait être tenté de lire les ballots depuis le bus, au fil de leur publication. Ce serait une erreur : le bus peut perdre des notifications, et l'agrégateur déciderait alors sur un ensemble incomplet de ballots. Au lieu de cela, il réconcilie depuis le snapshot du Blackboard : il lit /ballot/*, donc tous les ballots réellement écrits. Le subscribe_prefix("ballot.") sur le bus ne sert qu'à le réveiller (« de nouveaux ballots sont arrivés ») ; la décision, elle, est prise sur la vérité exhaustive. Conséquence : même si le bus perd la moitié de ses notifications, le verdict reste juste.

Figure 2 — Le consensus écrit candidats et ballots dans la vérité (Blackboard) ; l'agrégateur réconcilie depuis le snapshot, jamais depuis le seul bus. La perte d'indice n'altère pas le verdict.

4.2 — Les juges réels

Un juge implémente assess(task, candidates) → Vec<f64> : il attribue un score à chaque candidat. Le code en fournit plusieurs, chacun capturant une dimension de « qualité » distincte. Leur diversité est le point : c'est en combinant des regards complémentaires qu'on dépasse ce qu'un vérificateur unique pourrait juger.

JugeDimension qu'il mesure
VerifierJudgeenveloppe n'importe quel Verifier déterministe pour en faire un juge — le pont entre l'ancre objective de T1 et le panel.
LengthBandJudgela proximité d'un candidat à une longueur cible (ni trop court, ni trop long).
KeywordOverlapJudgele recouvrement de mots-clés entre la tâche et le candidat — une mesure grossière de pertinence.
GroundednessJudgel'ancrage du candidat dans un champ source fourni — une défense directe contre l'hallucination.
ConsistencyJudgela cohérence interne du candidat et son accord avec les autres.

L'agrégateur, lui, ne voit jamais les juges : il ne reçoit que des Ballot{ judge, scores }. Cette indirection est précieuse — on peut ajouter, retirer ou remplacer des juges sans toucher à la logique d'agrégation, et réciproquement changer de méthode d'agrégation (Vote → Borda → Condorcet) sans toucher aux juges.

4.3 — L'escalade coût-consciente

Convoquer un panel de juges a un coût (chaque juge fait, en Mode C, autant d'appels au SLM qu'il y a de candidats). Or ce coût est parfois inutile : si les candidats sont manifestement d'accord, un simple vote suffit à trancher. D'où la politique AggregatorPolicy::Escalating. On tente d'abord un vote gratuit ; si la confiance qu'il dégage dépasse un seuil configurable (with_escalation(seuil, escalate_to)), on s'arrête là — coût = K générateurs, zéro juge. Sinon, on escalade vers la méthode plus fine (Borda ou Condorcet) en payant les juges. La confiance devient ainsi un levier de coût : on ne dépense l'effort de jugement que lorsque l'essaim hésite réellement. Trois tests verrouillent ce comportement (le vote est choisi quand les candidats s'accordent ; les juges sont sautés quand le vote est confiant, exécutés quand il est incertain).

§5 Borda, chiffré de bout en bout

Cette section est le cœur arithmétique du document. On y explique précisément comment l'agrégateur de Borda transforme des scores de juges en un gagnant et une confiance — d'abord l'algorithme, puis un exemple entièrement calculé, repris du test du code lui-même.

5.1 — Pourquoi Borda, et pas le vote

Le vote majoritaire ne regarde que le premier choix de chaque juge : il jette toute l'information sur la manière dont les juges classent les autres candidats. Borda, lui, exploite le classement complet. Un candidat que tous les juges placent deuxième (jamais premier) est sans doute un meilleur compromis qu'un candidat placé premier par la moitié et dernier par l'autre — et c'est exactement ce genre de signal que Borda capte et que le vote ignore. C'est pour cela que Borda peut « battre le vote » quand les juges apportent un signal ordinal indépendant.

5.2 — L'algorithme exact

1. ranks = scores_to_ranks(scores)   // rang 0 = meilleur ; ex-æquo → rang MOYEN (fractionnaire)
2. points_i = Σ_juges ( (K−1) − rang_i )      // K = nombre de candidats
3. gagnant = argmax(points)                   // tiebreak : # 1ʳᵉˢ places, puis plus petit index
4. confiance = marge(points) / ( J × (K−1) )  // marge = 1ᵉʳ − 2ᵉ des totaux ; J = nb de juges

Décortiquons chaque ligne. Ligne 1 : on convertit les scores bruts d'un juge en rangs, où 0 désigne le meilleur. Le point délicat — et c'est le plus piégeux du consensus — est le traitement des ex-æquo : deux candidats à score égal reçoivent le rang moyen de leur groupe (par exemple, deux candidats se disputant les positions 0 et 1 reçoivent tous deux le rang 0,5). Sans cette moyenne, l'ordre d'arrivée des ex-æquo introduirait un biais arbitraire. Conséquence remarquable : un juge « neutre » qui donnerait le même score à tous attribue à chacun le rang moyen (K−1)/2 — donc le même nombre de points à tout le monde — et ne modifie donc pas le classement. La neutralité est mathématiquement neutre.

Ligne 2 : on convertit les rangs en points. Le meilleur (rang 0) reçoit K−1 points, le suivant K−2, et ainsi de suite jusqu'à 0 pour le dernier. On somme ces points sur tous les juges. Ligne 3 : le gagnant est celui de plus haut total ; en cas d'égalité, on départage par le nombre de premières places, puis par le plus petit index (un choix déterministe pour ne jamais dépendre du hasard). Ligne 4 : la confiance normalise la marge (l'écart entre le premier et le deuxième total) par le maximum théorique possible (J × (K−1), ce qu'obtiendrait un candidat classé premier par tous les juges face à un dernier classé dernier par tous). Une confiance proche de 1 signale un gagnant net ; proche de 0, un quasi-ex-æquo.

5.3 — L'exemple, calculé (K = 3 candidats A, B, C · J = 2 juges)

Prenons l'exemple exact du test textbook_borda_winner. Deux juges notent trois candidats. Le juge 1 préfère A, puis B, puis C ; le juge 2 préfère A, puis C, puis B. Voici leurs scores bruts.

Étape 4 — gagnant et confiance. Le total maximum est 4, atteint par A : A gagne (selected_index = 0). Pour la confiance, la marge entre le premier total (4) et le deuxième (1) vaut 3 ; le plafond théorique est J × (K−1) = 2 × 2 = 4 ; la confiance est donc 3 / 4 = 0,75. La leçon de l'exemple. Ici A était unanimement premier, donc Borda le sépare nettement (confiance élevée, 0,75). Mais l'intérêt de Borda se révèle dans les cas moins évidents : si la bonne réponse avait été classée 2ᵉ par tous les juges plutôt que 1ᵉ par la moitié, le vote majoritaire aurait pu la rater, tandis que Borda — en cumulant ses bonnes positions sur tous les juges — l'aurait fait remonter. Borda récompense la solidité ordinale, pas la simple popularité.

5.4 — Les deux alternatives d'agrégation

Borda n'est pas seul. Le code propose trois agrégateurs, chacun avec son domaine de pertinence.

MajorityVote — le plancher de référence. Il prend simplement la valeur de candidat la plus fréquente. Le code le qualifie explicitement de plancher : il est construit « pour être mesuré, pas pour être vendu ». Il sert d'étalon contre lequel comparer les méthodes plus fines, et il échoue — par construction — sur les erreurs corrélées.

Borda — le signal ordinal. Décrit ci-dessus. Pertinent quand les juges apportent un classement fiable et qu'on veut récompenser les bons compromis.

Condorcet — les duels, avec repli Copeland. Plutôt que de sommer des points, Condorcet organise des duels deux à deux : un candidat qui bat tous les autres en confrontation directe (le « gagnant de Condorcet ») est élu. Mais ces duels peuvent former un cycle (A bat B, B bat C, C bat A — le paradoxe de Condorcet). Dans ce cas, le code bascule sur la méthode de Copeland (le bilan de victoires : nombre de duels gagnés + un demi-point par nul), qui est Condorcet-consistante, et il signale cycle_detected pour que l'appelant sache qu'un cycle a eu lieu. Condorcet est pertinent quand l'ordre des préférences est plus fiable que l'intensité des scores.

Tous renvoient le même type, AggOutcome, qui porte le candidat sélectionné, son index, le vecteur de scores, la confiance, le nom de la méthode et le drapeau cycle_detected. L'appelant est donc indifférent à la méthode employée — il lit toujours la même structure.

§6 T2 Pipeline & T3 Hiérarchique — dompter une tâche dure

T1 et le consensus supposent que la tâche tient dans ce que le code appelle l'« enveloppe de capacité » : la difficulté qu'un petit modèle peut gérer en un coup. T2 et T3 répondent à la question inverse — que faire d'une tâche trop dure pour cette enveloppe ? La réponse commune : la découper en morceaux qui, eux, rentrent dans l'enveloppe.

6.1 — T2 · Pipeline streaming

Le pipeline enchaîne des étapes (Stage) : normaliser, puis découper en phrases, puis extraire, puis collecter, par exemple. Sa particularité tient à son mode d'exécution : il tourne sur la StreamingSwarm de la Partie 3 (§4), sans barrière de couche. Chaque étape traite une entrée dès qu'elle arrive de l'étape précédente, plutôt que d'attendre que toute l'étape amont soit finie. La terminaison est détectée par quiescence (le compteur de crédits de la Partie 3). Le pipeline est l'outil de prédilection quand une tâche dure se laisse décomposer en une suite de transformations simples : on remplace un gros problème par une chaîne de petits.

6.2 — T3 · Hiérarchique (récursif)

Le pattern hiérarchique met en scène trois rôles : un Decomposer qui découpe la tâche en sous-tâches, des Solver qui les résolvent en parallèle, et un Merger qui recombine les sous-résultats. La propriété qui en fait un outil puissant est la récursivité : un Solver n'est pas forcément un agent élémentaire — ce peut être un T1 entier, un T2, ou même un autre T3. On peut donc construire des « superviseurs de superviseurs », ou un « vérifier-de-vérifier », en emboîtant les topologies. Le code fournit des adaptateurs prêts à l'emploi (GvSolver qui enveloppe un Generate-Verify en Solver, FnSolver pour un Solver ad hoc).

L'usage typique est exactement celui du pari S1 poussé d'un cran : une tâche trop dure pour être résolue — donc vérifiée — d'un coup est découpée en sous-tâches qui, elles, sont assez simples pour qu'un T1 les résolve de façon fiable. On ramène ainsi le problème difficile dans l'enveloppe où les garanties de T1 s'appliquent, puis on recombine.

Figure 3 — T2 (étapes chaînées sur le substrat, terminaison par quiescence) et T3 (décompose → résout en ∥ → fusionne, récursif). T3 s'appuie sur un T2 mono-étage pour exécuter ses Solver en parallèle.

§7 Synthèse — choisir sa topologie

Les quatre topologies ne sont pas concurrentes : elles répondent à des formes de problème différentes, et se composent. Le tableau suivant résume quand employer chacune, et sur quel levier agir.

SituationTopologieLevier principal
tâche vérifiable, un vérificateur fiable existeT1K (taille de l'essaim) + max_concurrency
pas de vérificateur unique sûr ; qualité multidimensionnelleConsensusles J juges + la méthode (Vote → Borda → Condorcet) + le seuil d'escalade
tâche = suite de transformationsT2la chaîne d'étapes Stage
tâche trop dure pour un coup uniqueT3la stratégie de découpe + la récursion (Solver = T1/T2/T3)

Par-delà leurs différences, les quatre patterns partagent une seule philosophie, celle du pari S1 : générer en masse, sélectionner finement. T1 génère K candidats et en sélectionne un par vérification ; le consensus génère puis sélectionne par un panel ; T2 et T3 génèrent des décompositions et recomposent. Dans tous les cas, on ne mise jamais tout sur un coup unique, et l'on s'appuie sur une étape de jugement objective pour extraire la qualité.

Enfin, un fil conducteur économique : la confiance calculée par les agrégateurs (et le seuil d'escalade) transforme la sélection en levier de coût. On ne paie l'effort coûteux — convoquer les juges, escalader vers une méthode fine, voire monter en mode Network — que lorsque l'essaim hésite. Quand les candidats s'accordent, un vote gratuit tranche ; quand ils divergent, on investit dans le jugement. C'est cette élasticité qui rend l'approche soutenable à grande échelle.
