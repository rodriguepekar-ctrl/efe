§1  Le modèle de calcul

Un agent est une fonction async pure, sans état, à signature minimale. La diversité ne vient pas d'un état interne mais d'un paramètre variant: usize. La complexité vit dans la composition (topologie), jamais dans l'agent.

// 5 traits — toute la « surface agent » du système
pub trait Generator { async fn generate(&self, task:&Value, variant:usize) -> Value; }
pub trait Verifier  { fn score(&self, task:&Value, cand:&Value) -> f64; }   // ∈ [0,1]
pub trait Stage     { async fn process(&self, input:&Value) -> Vec<Value>; } // 1→0..N
pub trait Decomposer{ async fn decompose(&self, task:&Value) -> Vec<Value>; }
pub trait Merger    { async fn merge(&self, task:&Value, parts:Vec<Value>) -> Value; }

Conséquences formelles de ce modèle :

PropriétéImplication
Sans état (structs immuables, Arc<dyn Trait>)partageables entre tâches sans verrou ; thread-safe par construction
Déterministe (pas d'I/O, pas de hasard caché)même entrée → même sortie ⇒ reproductible (Mode A) ; testable exhaustivement
Petit (médiane 3–8 LoC, ≤ 2 champs)auditable d'un coup d'œil ; surface de bug minuscule
Composable (un Solver peut être un T1/T2/T3)récursion arbitraire (« superviseur de superviseurs »)

La flotte standard enregistre 43 agents (34 catalogue + 9 juges), tous conformes à ce modèle. Le « coût » d'un run est linéaire dans le nombre d'invocations (cf. §11).

§2  Structures de données des deux substrats

Le passage d'information repose sur deux structures complémentaires. Les deux utilisent DashMap (table concurrente shard-lockée) pour éviter un verrou global.

Blackboard — état partagé versionné (vérité)

pub struct BlackboardValue {
  pub value:   serde_json::Value,
  pub version: u64,        // monotone / pointeur
  pub written_by: AgentId,
  pub written_at: SystemTime,
}
pub struct Blackboard {
  fields:  DashMap<String, BlackboardValue>, // shardé
  recent:  Mutex<VecDeque<Write>>,  // ring 8192
  writes_total: AtomicU64,
  total_bytes:  AtomicU64,        // cap global
  sink:    RwLock<Option<Arc<dyn WriteSink>>>,
  metrics: RwLock<Option<Arc<SubstrateMetrics>>>,
}

TopicRouter — pub/sub partitionné (indice)

pub struct TopicRouter {
  topics: DashMap<String,
            broadcast::Sender<SwarmEvent>>,
  capacity: usize,        // borné / canal
  published_total: Arc<AtomicU64>,
  dropped_total:   Arc<AtomicU64>,  // drops comptés
  event_sink: RwLock<Option<Arc<dyn EventSink>>>,
}
pub struct SwarmEvent {
  swarm_id, published_by:AgentId,
  topic:String, payload:Value, published_at,
}
Choix-clé : DashMap, pas Mutex<HashMap>. Les écritures concurrentes sur des pointeurs différents ne se bloquent pas (verrou par shard, granularité µs). À K agents écrivant /cand/0..K en parallèle, la contention est quasi nulle — c'est ce qui rend l'essaim scalable sans coordinateur central.

§3  Le chemin d'écriture (write path)

Chaque write(pointer, value, agent_id) traverse une séquence déterministe et bornée. C'est le point où la circulation d'information rencontre les garde-fous et la provenance.

Figure 1 — Le write path. La comptabilité d'octets (cap global + caps par namespace) borne la mémoire ; les trois exutoires (sink/metrics/ring) sont la couture où l'information devient preuve et télémétrie.

Le rejet (SizeLimitExceeded) est compté (note_rejection) : l'essaim ne peut pas saturer l'hôte — garde-fou G8, l'opposé d'un fork bomb d'agents.

§4  CAS & sémantique de version

Au-delà de l'écriture inconditionnelle, le Blackboard offre un compare-and-swap versionné (write_if) — la primitive des patterns de consensus distribué (réservation, claim, accord).

pub fn write_if(&self, ptr:&str, expected_version:u64, value:Value, who:AgentId)
    -> Result<u64, BlackboardError> {
  let entry = self.fields.entry(ptr.into());      // ← prend le verrou de SHARD
  entry.and_modify(|actual| {
    if actual.version == expected_version {          // comparaison…
      *actual = BlackboardValue{ version: expected_version+1, .. }; // …et swap, sous le MÊME verrou
    }
  });
  // le verrou de shard est tenu pendant tout le compare+swap ⇒ atomicité
}
Garantie d'atomicité (correctif d'audit B-CAS). Le guard du shard est tenu pour toute la séquence compare+swap. Deux écrivains concurrents sur le même pointeur sérialisent ; le perdant voit une version inattendue et réessaie. Aucune mise à jour perdue — invariant prouvé par le test swarm_cas_invariant (N writers concurrents, somme exacte).

Pourquoi la version, pas juste la valeur ?

La version monotone par pointeur est l'horloge logique locale du substrat. Elle permet : (1) la détection de conflit (CAS), (2) le rejeu déterministe (ADR-SWARM-007 : la provenance dépend des versions, pas de l'horloge murale), (3) la réconciliation (l'agrégateur lit la dernière version de chaque /ballot/j).

§5  Le bus par topic — fan-out O(abonnés)

Un bus broadcast global livre chaque événement à tous les agents → O(N²) à N agents (goulot mesuré « F1 »). Le TopicRouter partitionne en un canal broadcast par topic.

Figure 2 — Partitionnement du bus. subscribe(topic) = un canal ; subscribe_prefix("ballot.") fusionne plusieurs topics via des forwarders tokio::spawn dans un seul mpsc. La capacité bornée fait du backpressure ; les drops sont comptés (jamais silencieux).

§6  Le modèle de concurrence

Le pipeline streaming (T2, et T3 via T2) câble chaque étage comme un agent asynchrone : une boucle qui consomme un topic, acquiert un permis (sémaphore), spawn le handler, et libère le permis à la fin. C'est le cœur de l'exécution parallèle bornée.

// streaming.rs — la boucle d'un agent asynchrone (simplifiée)
let sem = Arc::new(Semaphore::new(max_concurrency.max(1)));
tokio::spawn(async move {
  let mut set = JoinSet::new();
  while let Some(ev) = sub.recv().await {            // ← consomme le topic
    let permit = sem.clone().acquire_owned().await?;     // ← BORNE la concurrence
    let (ctx, h) = (ctx.clone(), handler.clone());
    set.spawn(async move {
      h(ctx.clone(), ev).await;                       // process() → emit()/write()
      ctx.tracker.on_done();                            // ← crédit de quiescence
      drop(permit);
    });
    while set.try_join_next().is_some() {}          // récolte (borne le JoinSet)
  }
  while set.join_next().await.is_some() {}            // draine à la fermeture
});

Backpressure

Le sémaphore plafonne les handlers en vol par étage. Un SLM lent ne fait pas exploser la mémoire : les events s'accumulent dans le canal borné, et recv() bloque quand il n'y a plus de permis.

Crédit sûr

on_done() est appelé après que le handler ait émis ses sorties — le crédit de quiescence ne peut pas devenir nul prématurément (sinon on terminerait avant la fin d'une chaîne d'étages).

§7  Terminaison par quiescence à crédit

Comment savoir qu'un essaim a fini, sans coordinateur ni barrière globale ? Par un bilan de crédit : produit vs consommé. Quand tout ce qui a été émis a été traité et que les sources sont taries, l'essaim est quiescent.

pub struct QuiescenceTracker {
  produced: AtomicU64,  consumed: AtomicU64,
  in_flight:AtomicI64,  sources_done:AtomicBool,  notify:Notify,
}
// on_emit(n): produced += n ; in_flight += n
// on_done():  consumed += 1 ; in_flight -= 1 ; si in_flight==0 && sources_done ⇒ notify
Figure 3 — Terminaison sans barrière. L'astuce d'arrêt : les agents ne tiennent qu'un Weak<TopicRouter> ; drop de l'unique Arc fort ferme tous les topics → recv() renvoie None → chaque boucle d'agent sort proprement et rend son AgentReport.

Un timeout borne l'attente (garde-fou anti-blocage). Le rapport final expose quiesced, produced, consumed, elapsed et le détail par agent — observabilité native.

§8  Sharding déterministe du work-queue

Pour distribuer N items sur R workers sans contention ni coordinateur, EFE utilise une propriété déterministe : l'item i est possédé par shard_owner(i) = i mod R. Tous les workers calculent le même propriétaire — aucun verrou de répartition.

pub fn shard_owner(item:u64, workers:usize) -> usize { (item % workers as u64) as usize }
pub fn shard_topic(base:&str, worker:usize) -> String { format!("{base}.shard.{worker}") }
// la notif d'un item est routée vers le topic du shard de son propriétaire
// ⇒ chaque worker s'abonne à SON shard ; zéro chevauchement, zéro vol
Compose avec le bus (WS1). Le sharding réutilise le TopicRouter : la notification d'un item part vers {base}.shard.{owner}, et le worker propriétaire est le seul abonné. On obtient un work-stealing inversé (ownership statique déterministe) — idéal pour la reproductibilité (même partition à chaque run) tout en gardant le parallélisme.

Testé par work_queue_sharding : R workers, N items, chaque item traité exactement une fois, partition stable.

§9  Le math du vote (rank · Borda · Condorcet)

L'agrégation est déterministe et tolérante aux égalités (EPS = 1e-9). Trois primitives partagées :

PrimitiveDéfinitionUsage
scores_to_ranks(s)scores → rangs (0 = meilleur) ; ex-æquo partagent le rang minbase de Borda & Condorcet
prefers(s,i,j)s[i] > s[j] + EPSduels Condorcet
margin(s)écart 1er − 2ndconfiance (normalisée)

Borda — comptage de rangs

pour chaque juge b : points[i] += (K−1) − rang_b[i]   //  gagnant = argmax points
confidence = margin(points) / (|juges| × (K−1))   ∈ [0,1]

Tie-break déterministe en cascade : (1) somme Borda, (2) nombre de premières places, (3) index le plus petit. Aucune dépendance à l'ordre d'arrivée des ballots → reproductible (les ballots sont réconciliés depuis le Blackboard, pas depuis le bus).

Condorcet — vainqueur par duels

Comparaisons par paires (prefers) ; un cycle est détecté et signalé (cycle_detected) → repli Borda. C'est le « consensus craque le non-vérifiable si juges » d'ADR-SWARM-004 : avec assez de juges indépendants, un vainqueur robuste émerge même sans oracle.

Pourquoi le vote sépare l'indice de la vérité. Le bus réveille l'agrégateur (latence basse) mais peut perdre des ballots (canal borné) ; or un vote incomplet est faux. La réconciliation finale lit /ballot/0..J depuis le Blackboard (vérité exhaustive) → le vote est complet par construction. C'est le keystone WS1 appliqué à la décision.

§10  Le seam forensique (task-local, par-appel)

Relier l'appel LLM brut (modèle, prompt) au contexte d'essaim (agent, tenant) sans réécrire les agents : un task-local par appel d'agent. Concurrence-safe même à K générateurs parallèles.

tokio::task_local! { static PENDING: Arc<Mutex<Vec<PendingLlmCall>>>; }

// 1) le Meter enveloppe l'appel d'agent dans un scope (pose un puits par-appel)
// 2) le backend pousse une PendingLlmCall à chaque complete() — no-op hors scope
// 3) le Meter draine le puits, assemble un LlmProvenanceRecord (+ contexte essaim),
//    et LIE l'AgentCallRecord au premier ProvenanceId
Correction sous re-tentative. Le Retrier (mode réseau) exécute chaque tentative dans un puits imbriqué et ne ré-émet qu'un record final (avec retry_count) — le lien pointe vers l'issue retenue, jamais vers une tentative échouée. Un puits par appel d'agent (task-local scopé) ⇒ pas de course même à K générateurs concurrents.

Résultat : chaque pas de l'essaim — chaque écriture, chaque appel SLM — est forensiquement lié. La circulation d'information EST la preuve (cf. le rapport « moat »).

État

Le cœur d'exécution — modèle d'agent, double substrat, concurrence bornée, quiescence, sharding, vote, seam forensique — est livré, durci (WS1/WS3/WS5) et testé. Il alimente les 3 modes et le produit. Les garanties techniques sont model-independent : elles tiennent pour tout backend, prouvées à l'échelle par 50 runs Mode A déterministes + 3 modèles SLM réels (100 % verify/traced/tamper, verdict GO).

Profondeurs techniques suivantes (non bloquantes) : (1) subscribe_prefix à abonnement dynamique (topics créés après l'abonnement) ; (2) métriques de diversité des candidats pour piloter K dynamiquement ; (3) Condorcet étendu (Schulze) ; (4) work-queue à vol de travail (au-delà du sharding statique) pour les charges déséquilibrées.
