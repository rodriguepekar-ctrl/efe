§1  Le modèle de calcul : qu'est-ce qu'un agent ?

Intuition

Dans la plupart des frameworks d'agents, un « agent » est un objet lourd : il a une mémoire, un état conversationnel, des outils, parfois une boucle de raisonnement. EFE prend le parti inverse. Ici, un agent est une fonction — au sens mathématique : on lui donne une entrée, il rend une sortie, et il ne garde rien entre deux appels. C'est délibérément bête et minuscule. L'intelligence du système ne vient pas de la sophistication d'un agent, mais de la manière dont on en câble beaucoup ensemble (la topologie) et de la circulation de l'information entre eux.

La mécanique : cinq traits, c'est tout

Toute la « surface agent » du système tient en cinq traits (un trait en Rust est un contrat d'interface : « tout type qui implémente ce trait sait faire telle opération »). Chaque agent concret est un type qui implémente l'un d'eux :

// Les 5 contrats — rien d'autre n'est un « agent » dans EFE
pub trait Generator  { async fn generate(&self, task:&Value, variant:usize) -> Value; }
pub trait Verifier   { fn score(&self, task:&Value, cand:&Value) -> f64; }    // note ∈ [0,1]
pub trait Stage      { async fn process(&self, input:&Value) -> Vec<Value>; } // 1 entrée → 0..N sorties
pub trait Decomposer { async fn decompose(&self, task:&Value) -> Vec<Value>; } // tâche → sous-tâches
pub trait Merger     { async fn merge(&self, task:&Value, parts:Vec<Value>) -> Value; } // N → 1

Lisons-les comme des rôles humains dans une équipe : le Generator propose une idée (et le paramètre variant lui dit « propose ta 3ᵉ variante » pour obtenir de la diversité) ; le Verifier note une proposition entre 0 et 1 ; le Stage transforme une donnée et peut en produire plusieurs (un filtre rend 0 ou 1 sortie, un « fan-out » en rend plusieurs) ; le Decomposer découpe un gros problème en petits ; le Merger recolle les morceaux. Toute la flotte standard — 43 agents — n'est qu'une collection de ces cinq formes.

Le pourquoi : quatre conséquences qu'on obtient gratuitement

Ce choix radical de minimalisme n'est pas esthétique : il achète directement quatre propriétés difficiles à obtenir autrement.

Propriété du modèleCe que ça nous donne, concrètement
Sans état — l'agent est un struct immuable, partagé via Arc<dyn Trait> (un pointeur compté en références, lisible par plusieurs threads). On peut le faire tourner en parallèle sur autant de tâches qu'on veut sans aucun verrou : rien à protéger, puisqu'il n'y a rien à modifier. La sûreté concurrente est garantie par construction, pas par discipline.
Déterministe — pas d'entrée/sortie cachée, pas de hasard non maîtrisé (la diversité passe par variant, explicite). Même entrée ⇒ même sortie. Donc le run est reproductible (Mode A) et testable exhaustivement. C'est la base de la re-preuve déterministe (ADR-SWARM-007).
Petit — médiane de 3 à 8 lignes, au plus 2 champs de configuration. Un agent s'audite d'un coup d'œil. Sa surface de bug est minuscule. Un humain (ou un régulateur) peut lire et comprendre chaque brique du système.
Composable — un agent « solveur » peut être lui-même une topologie entière (T1, T2 ou T3). On construit des comportements arbitrairement riches par emboîtement (« superviseur de superviseurs ») sans jamais alourdir un agent individuel.
Exemple concret — l'agent le plus simple du dépôt. Le stage Uppercase met un texte en majuscules. Le voici en entier : 
pub struct Uppercase;                                  // 0 champ : aucune config
impl Stage for Uppercase {
  async fn process(&self, x:&Value) -> Vec<Value> {
    vec![json!({ "text": text_of(x).to_uppercase() })]  // 1 ligne utile
  }
}
C'est tout. Pas de mémoire, pas de réseau, pas de clé. Et pourtant, branché dans un pipeline derrière un normalize_whitespace et un filter_nonempty, il participe à un comportement utile.

La flotte standard enregistre exactement 43 agents (34 du catalogue Mode A + 9 juges) — un test l'assure (assert_eq!(fleet.len(), 43)). Le « coût » d'un run est simplement le nombre d'invocations d'agents, que la gouvernance de budget plafonne (cf. §11).

§2  Les deux substrats : où l'information vit

Intuition

Si les agents ne gardent rien, où est l'information du run ? Dans le substrat — l'espace partagé où un agent dépose son résultat pour qu'un autre le reprenne. EFE utilise deux substrats complémentaires, et c'est le point le plus important à comprendre. Imaginez une salle de réunion : il y a un tableau blanc au mur (tout le monde y écrit, ça reste affiché, c'est la référence) et il y a les gens qui se parlent (rapide, mais on peut rater une phrase si on est distrait). EFE a exactement ces deux canaux : le Blackboard (le tableau — la vérité durable) et le TopicRouter (la parole — l'indice éphémère).

La mécanique : deux structures bâties sur DashMap

Les deux substrats reposent sur une même brique : DashMap. Une HashMap classique protégée par un seul verrou deviendrait un goulot — chaque écriture bloquerait toutes les autres. DashMap découpe la table en plusieurs shards (tranches), chacun avec son propre petit verrou. Deux agents qui écrivent à des endroits différents tombent (presque toujours) sur des shards différents et ne se gênent donc pas. C'est ce qui rend l'essaim parallèle sans coordinateur central.

Blackboard — l'état partagé versionné (la vérité)

pub struct BlackboardValue {
  pub value:      Value,       // la donnée (JSON)
  pub version:    u64,         // compteur ↑ par pointeur
  pub written_by: AgentId,     // qui (provenance)
  pub written_at: SystemTime,
}
pub struct Blackboard {
  fields:  DashMap<String, BlackboardValue>,
  recent:  Mutex<VecDeque<Write>>, // ring 8192
  total_bytes:  AtomicU64,         // cap global
  sink:    … // → provenance (chaque write)
  metrics: … // → Prometheus
}

TopicRouter — la diffusion partitionnée (l'indice)

pub struct TopicRouter {
  topics: DashMap<String,
            broadcast::Sender<SwarmEvent>>,
  capacity: usize,              // borne / canal
  published_total: AtomicU64,
  dropped_total:   AtomicU64,    // drops COMPTÉS
}
pub struct SwarmEvent {       // un « message »
  swarm_id, published_by:AgentId,
  topic:String, payload:Value,
  published_at:SystemTime,
}

Côté Blackboard, notez le champ version : chaque pointeur a son propre compteur qui s'incrémente à chaque écriture. C'est une horloge logique locale — on verra au §4 qu'elle est la clé du compare-and-swap et du rejeu déterministe. Côté TopicRouter, notez broadcast::Sender : c'est un canal de diffusion (un message envoyé est reçu par tous les abonnés de ce canal), mais il y a un canal par topic — d'où le mot « partitionné ».

Le pourquoi : deux substrats parce qu'aucun seul ne suffit

Pourquoi se compliquer avec deux mécanismes ? Parce qu'ils ont des défauts opposés, et qu'en les combinant chacun couvre le défaut de l'autre.

  • Le bus seul (TopicRouter) est rapide mais peut perdre des messages : son canal a une capacité bornée, et si un abonné est lent, des messages sont droppés (comptés, mais perdus). Acceptable pour un « signal », inacceptable pour un vote — un vote incomplet est faux.
  • Le tableau seul (Blackboard) ne perd rien, mais pour savoir « y a-t-il du nouveau ? » il faudrait scruter en boucle (polling) — lent et gourmand.

La combinaison — c'est le keystone WS1 de l'architecture — donne le meilleur des deux : le bus réveille le consommateur instantanément (« un ballot est arrivé ! »), et le tableau lui garantit l'exhaustivité au moment de conclure (« relis les J ballots sur le tableau, ils y sont tous »). On résume ce contrat par : « le bus est l'indice, le Blackboard est la vérité ».

À retenir. Quand un juge a fini de noter, il fait les deux : bb.write("/ballot/3", …) (dépose sur le tableau, durable) et router.publish("ballot.3", …) (crie « j'ai fini », rapide). L'agrégateur est réveillé par le cri, mais compte les votes en relisant le tableau. Aucun vote perdu, latence minimale.

§3  Le chemin d'écriture, octet par octet

Intuition

Une écriture sur le Blackboard n'est pas un simple « range ça dans la case ». C'est le moment où la circulation d'information rencontre les garde-fous (on ne saturera pas la mémoire) et la provenance (cette écriture sera tracée). Comprendre ce chemin, c'est comprendre comment l'essaim reste borné et auditable même quand des dizaines d'agents écrivent simultanément.

La mécanique : sept étapes déterministes

Chaque appel write(pointer, value, agent_id) traverse la séquence suivante. Elle est déterministe (toujours le même ordre) et bornée (aucune étape n'est illimitée).

Figure 1 — Les sept étapes du write path, de la validation au triple exutoire.
  1. Validation du pointeur. Le « pointeur » est un chemin de type /cand/3. On vérifie qu'il est bien formé (pas de caractères interdits) — une première barrière contre les entrées malveillantes.
  2. Mesure de taille. On calcule combien d'octets pèse la nouvelle valeur, et combien pesait l'ancienne (si le pointeur existait). La différence, c'est l'impact mémoire net de cette écriture.
  3. Cap global. On vérifie que total_bytes − ancien + nouveau ≤ plafond. Si l'écriture ferait déborder le budget mémoire total du Blackboard, on la refuse (SizeLimitExceeded), et on incrémente un compteur de rejets. L'essaim ne peut pas faire exploser la RAM de l'hôte.
  4. Cap par namespace. En plus du plafond global, on peut donner des sous-budgets par préfixe (ex. /cand/* a droit à 4 Mo, /ctrl/* à 64 Ko). Le cap le plus spécifique (préfixe le plus long) s'applique. Ça empêche un seul namespace bavard d'affamer les autres.
  5. Incrément de version. La nouvelle version est l'ancienne + 1. C'est l'horloge logique du §4.
  6. Insertion. On range la BlackboardValue dans le shard DashMap correspondant. C'est la seule étape qui prend un verrou — et seulement le verrou de ce shard, en microsecondes.
  7. Triple exutoire (le plus important). Après l'insertion, l'écriture est notifiée à trois destinataires optionnels : (a) le write-sink → c'est là que naît la provenance (chaque écriture devient un maillon de la chaîne cryptographique) ; (b) les metrics → un compteur Prometheus s'incrémente, l'écriture devient observable ; (c) le ring de rejeu → les 8192 dernières écritures sont conservées pour le replay et le débogage.
Le détail qui compte : le rejet est silencieux pour l'agent, bruyant pour la télémétrie. Quand une écriture est refusée pour cause de cap, l'agent reçoit une erreur typée (SizeLimitExceeded) — il peut dégrader proprement — et un compteur global est incrémenté (note_rejection). On ne perd jamais l'information « il y a eu de la pression mémoire » ; elle remonte en métriques. C'est l'opposé d'un fork bomb d'agents qui plante l'hôte sans prévenir.

§4  Le compare-and-swap (CAS) & les versions

Intuition

L'écriture du §3 est inconditionnelle : « écris, quoi qu'il y avait avant ». Mais parfois on veut écrire seulement si personne ne m'a doublé. Exemple : deux agents veulent « réserver » la même ressource. On ne veut pas qu'ils l'obtiennent tous les deux. C'est le rôle du compare-and-swap (CAS, « compare-et-échange ») : « écris cette valeur, mais uniquement si la version actuelle est exactement celle que j'ai lue ; sinon, dis-moi que j'ai été doublé ». C'est la primitive de base de tous les protocoles d'accord (réservation, claim, consensus distribué).

La mécanique : tout le travail sous un seul verrou

pub fn write_if(&self, ptr:&str, expected:u64, value:Value, who:AgentId)
    -> Result<u64, BlackboardError> {
  let entry = self.fields.entry(ptr.into());     // ① prend le verrou du SHARD
  entry.and_modify(|actual| {
    if actual.version == expected {                 // ② COMPARE (sous le verrou)
      *actual = BlackboardValue{ version: expected+1, .. }; // ③ SWAP (même verrou)
    }
  });                                                // ④ relâche le verrou
}

La subtilité tient en un mot : atomicité. Les étapes ② (comparer) et ③ (échanger) se déroulent pendant que le verrou du shard est tenu. Aucun autre agent ne peut s'intercaler entre la comparaison et l'échange. C'est exactement ce qu'on attend d'un CAS : la séquence « lire-la-version, vérifier, écrire » est indivisible.

Le pourquoi : un correctif d'audit qui change tout

Une implémentation naïve ferait : « lis la version (verrou pris puis relâché), compare en dehors, puis réécris (verrou repris) ». Entre les deux prises de verrou, un autre agent peut écrire → mise à jour perdue. Le code ci-dessus tient le verrou du début à la fin du compare+swap (correctif d'audit noté B-CAS). Deux écrivains concurrents sur le même pointeur sont donc forcément sérialisés : le premier passe, le second voit une version inattendue et réessaie. Jamais de mise à jour perdue — et c'est prouvé par le test swarm_cas_invariant (N writers concurrents incrémentent un compteur ; la somme finale est exacte).

Pourquoi des versions, et pas juste des valeurs ?

La version monotone par pointeur n'est pas un gadget : c'est une horloge logique locale qui rend trois choses possibles.

  • Détection de conflit (le CAS qu'on vient de voir).
  • Rejeu déterministe : la provenance d'un run dépend des versions, pas de l'horloge murale. Deux exécutions qui produisent le même ensemble d'écritures dans le même ordre logique donnent le même provenance_root, même si les timestamps diffèrent (ADR-SWARM-007).
  • Réconciliation : au moment d'agréger, on lit la dernière version de chaque /ballot/j — sans ambiguïté sur « quelle écriture est la bonne ».
Exemple — une réservation de fournisseur. Deux sous-agents évaluent le même lot et veulent le marquer « attribué ». Tous deux lisent la version v=7. Le premier appelle write_if(ptr, 7, …) → succès, la version passe à 8. Le second appelle aussi write_if(ptr, 7, …) → la version vaut maintenant 8 ≠ 7 → refus. Le second sait qu'il a été doublé et abandonne proprement. Aucun double-attribution, aucun verrou applicatif à gérer.

§5  Le bus partitionné : éviter l'explosion O(N²)

Intuition

Quand beaucoup d'agents s'envoient des messages, le comment on diffuse devient critique. La façon naïve — un grand mégaphone où chacun crie et où tout le monde écoute tout — ne tient pas à l'échelle : avec N agents qui parlent et N qui écoutent, on a de l'ordre de N² livraisons, dont la plupart inutiles (un agent reçoit des messages qui ne le concernent pas et doit les filtrer). Ce goulot a été mesuré dans EFE sous le nom « F1 ». La solution : ne pas avoir un mégaphone, mais un canal par sujet (« topic »). On ne reçoit que les messages du/des sujets auxquels on s'est abonné.

Figure 2 — Le partitionnement du bus transforme un fan-out quadratique en fan-out proportionnel au nombre d'abonnés réellement concernés.

La mécanique : un canal de diffusion par topic, créé à la volée

Le TopicRouter tient une DashMap<topic, broadcast::Sender>. Quand on publish un événement, on récupère (ou on crée à la volée) le canal du topic concerné et on y diffuse — seulement aux abonnés de ce canal. Deux opérations d'abonnement existent :

  • subscribe("ballot.3") : je veux exactement ce topic → je reçois un récepteur sur ce canal.
  • subscribe_prefix("ballot.") : je veux tous les topics qui commencent par ballot. (donc tous les juges). Le routeur lance alors un petit forwarder (tokio::spawn) par topic correspondant, qui reverse les messages dans un unique canal mpsc que je consomme. C'est exactement ce que fait l'agrégateur du consensus pour écouter tous les ballots d'un coup.

Le pourquoi : la capacité bornée est une feature, pas un défaut

Chaque canal a une capacité finie. Si un producteur va plus vite que le consommateur, le canal se remplit, puis droppe les plus anciens — et incrémente dropped_total. On pourrait croire que perdre des messages est mauvais ; en réalité c'est le mécanisme de backpressure qui empêche un emballement mémoire. Et c'est précisément pour ça qu'on a deux substrats (§2) : le bus a le droit de perdre un indice parce que la vérité est sur le tableau. Les drops sont comptés (jamais silencieux) → on les voit en métriques, on peut alerter, mais la correction du vote n'en dépend jamais.

En résumé. Le bus optimise la latence et la scalabilité du signal ; il accepte de perdre des indices sous pression, ce qui le rend robuste. La correction métier (compter tous les votes, ne rien rater) est déléguée au Blackboard. Séparer ces deux responsabilités est ce qui permet à l'essaim de monter en charge sans devenir ni lent ni faux.

§6  La concurrence bornée : parallélisme sans déni de service

Intuition

« En parallèle » est facile à dire, dangereux à faire naïvement. Si on lance K générateurs d'un coup et que chacun appelle un SLM qui prend 3 secondes, lancer 10 000 tâches simultanées ferait s'effondrer l'hôte (mémoire, descripteurs, contention). On veut donc du parallélisme borné : « jusqu'à P agents en vol à la fois, pas plus ; les suivants attendent leur tour ». L'outil pour ça est le sémaphore : un distributeur de P jetons. Pour s'exécuter, une tâche doit prendre un jeton ; quand elle finit, elle le rend. S'il n'y a plus de jeton, on attend qu'un se libère.

La mécanique : la boucle d'un agent asynchrone (pipeline)

Voici le cœur de l'exécution en flux (T2, et T3 qui s'appuie dessus). Chaque étage du pipeline est un agent qui tourne dans cette boucle :

let sem = Arc::new(Semaphore::new(max_concurrency.max(1)));   // P jetons
tokio::spawn(async move {
  let mut set = JoinSet::new();                         // suit les tâches filles
  while let Some(ev) = sub.recv().await {              // ① un message arrive sur mon topic
    let permit = sem.clone().acquire_owned().await?;       // ② prends un jeton (ou attends)
    let (ctx, h) = (ctx.clone(), handler.clone());
    set.spawn(async move {                            // ③ traite EN PARALLÈLE
      h(ctx.clone(), ev).await;                         //    process() → emit()/write()
      ctx.tracker.on_done();                            // ④ crédit de quiescence (§7)
      drop(permit);                                  // ⑤ rends le jeton
    });
    while set.try_join_next().is_some() {}            // ⑥ récolte les finies (borne le JoinSet)
  }
  while set.join_next().await.is_some() {}              // ⑦ draine à la fermeture du topic
});

Déroulons-la en mots. ① L'agent attend un message sur son topic d'entrée. ② Avant de le traiter, il prend un jeton — si les P jetons sont déjà pris, cette ligne bloque jusqu'à ce qu'un se libère (c'est la borne). ③ Il lance le traitement dans une tâche fille (set.spawn) : on n'attend pas qu'il finisse pour aller chercher le message suivant — c'est ça, le parallélisme. ④ À la fin du traitement, il signale « j'ai fini un » au compteur de quiescence (§7). ⑤ Il rend son jeton. ⑥ Il ramasse au passage les tâches déjà terminées (pour ne pas accumuler des poignées mortes). ⑦ Quand le topic se ferme (fin du run), il draine les dernières tâches en cours et rend son rapport.

Le pourquoi : deux subtilités qui évitent des bugs réels

Backpressure naturelle

Si un SLM est lent, les P jetons restent pris, la ligne ② bloque, et l'agent arrête de consommer son topic. Les messages s'accumulent alors dans le canal borné du bus (qui finira par dropper, §5) plutôt que dans une file mémoire illimitée. La pression se propage proprement de l'aval vers l'amont, sans explosion mémoire.

Crédit « sûr » (l'ordre compte)

on_done() est appelé après que le handler ait émis ses sorties (étape ④, à l'intérieur de la tâche). Si on créditait avant l'émission, le compteur pourrait atteindre zéro alors qu'une chaîne d'étages n'est pas finie → on terminerait l'essaim trop tôt. L'ordre « émets puis crédite » garantit qu'on ne déclare jamais la fin prématurément.

Le même schéma (JoinSet + Semaphore pour les générateurs ; tokio::spawn + Semaphore pour les juges) gouverne tous les sites parallèles du système. Il n'y a pas de pool de threads caché : la concurrence est explicite, lisible, et bornée partout. Un test (async_agent_concurrency_is_bounded) vérifie que la borne P est bien respectée sous charge.

§7  La terminaison : savoir qu'un essaim a fini

Intuition

Question piège : dans un système où des agents émettent des messages qui déclenchent d'autres agents qui émettent encore d'autres messages, comment sait-on que c'est fini ? Il n'y a pas de chef qui dit « stop ». La réponse d'EFE est élégante : on tient un bilan comptable. Tant que tout ce qui a été émis n'a pas été traité, il reste du travail. Quand « émis = traité » et qu'aucune nouvelle source ne va injecter de travail, l'essaim est quiescent — silencieux, donc terminé.

La mécanique : trois compteurs et une notification

pub struct QuiescenceTracker {
  produced:  AtomicU64,   // total de messages émis
  consumed:  AtomicU64,   // total de messages traités
  in_flight: AtomicI64,   // = produced − consumed (en vol)
  sources_done: AtomicBool, // plus de nouvelle injection ?
  notify: Notify,         // réveille celui qui attend la fin
}
// on_emit(n)  : produced += n ; in_flight += n
// on_done()   : consumed += 1 ; in_flight -= 1 ;
//               si in_flight == 0 && sources_done ⇒ notify (quiescent !)

Chaque émission appelle on_emit (le compteur monte) ; chaque traitement terminé appelle on_done (il descend). Le « en vol » (in_flight) est la différence. Quand il retombe à zéro et que les sources sont taries, on déclenche la notification.

Figure 3 — De la quiescence détectée à l'arrêt propre, via l'astuce du pointeur faible.

Le pourquoi : arrêter les agents sans leur dire « arrête »

Une fois la quiescence détectée, il faut terminer les boucles d'agents (souvenez-vous, chacune est un while let Some(ev) = sub.recv().await qui tourne tant qu'il arrive des messages). L'astuce est jolie : les agents ne tiennent qu'un pointeur faible (Weak<TopicRouter>) vers le routeur, pas un pointeur fort. Quand le coordinateur fait drop(self.router) — il lâche l'unique pointeur fort — le routeur est détruit, tous ses canaux se ferment, et chaque recv() renvoie None. Les boucles sortent d'elles-mêmes, proprement, et rendent leur AgentReport. Pas de message « poison », pas de flag à scruter : la fermeture des canaux est le signal d'arrêt.

Et si ça ne se termine jamais ? Un timeout enveloppe l'attente de quiescence. Si l'essaim n'a pas convergé dans le délai imparti, on arrête quand même et on le signale (quiesced = false dans le rapport). C'est un garde-fou anti-blocage : un agent boucleur ne peut pas figer le système indéfiniment. Le rapport final expose quiesced, produced, consumed, elapsed et le détail par agent — toute la matière pour diagnostiquer.

§8  Le sharding déterministe : répartir sans chef

Intuition

Quand on a N tâches (items) à distribuer sur R ouvriers (workers), la façon classique est une file partagée où chacun pioche — mais une file partagée, c'est un verrou contendu, donc un goulot. EFE évite complètement la file : il décide à l'avance, par une formule, quel ouvrier possède quel item. Comme tous les ouvriers calculent la même formule, ils sont d'accord sans se parler. C'est le sharding déterministe.

La mécanique : une formule, deux topics

pub fn shard_owner(item:u64, workers:usize) -> usize {
  (item % workers as u64) as usize          // l'item i appartient à l'ouvrier i mod R
}
pub fn shard_topic(base:&str, worker:usize) -> String {
  format!("{base}.shard.{worker}")                // chaque ouvrier écoute SON topic
}

L'item i est possédé par l'ouvrier i mod R. Pour notifier qu'un item est prêt, on publie sur le topic du shard de son propriétaire ({base}.shard.{owner}), et seul cet ouvrier y est abonné. Résultat : chaque item est traité exactement une fois, par un seul ouvrier, sans qu'aucun n'ait eu à verrouiller une file commune ni à « voler » du travail à un autre.

Le pourquoi : reproductibilité + zéro contention

Ce choix réutilise le bus du §5 (le sharding « compose avec WS1 ») et offre deux bénéfices. D'abord, aucune contention de répartition : pas de file partagée, donc pas de verrou chaud. Ensuite, et c'est plus subtil, la partition est déterministe : pour les mêmes N et R, l'item 17 ira toujours à l'ouvrier 17 mod R. Donc deux exécutions du même run produisent la même affectation — ce qui sert directement la reproductibilité (et donc la re-preuve déterministe). On appelle parfois ça du « work-stealing inversé » : au lieu de voler dynamiquement, l'ownership est statique et prévisible.

Le compromis assumé. Le sharding statique est idéal quand la charge est équilibrée (chaque item coûte à peu près pareil). Si la charge est très déséquilibrée (un item 100× plus lourd), un ouvrier peut traîner pendant que d'autres sont oisifs — c'est le prix du déterminisme. Le vol de travail dynamique (work-stealing) est noté comme évolution possible (§12) pour ces cas. Pour les essaims de nano-agents, où les items sont homogènes, le déterminisme l'emporte. Test : work_queue_sharding (R ouvriers, N items, couverture exacte, partition stable).

§9  Le math du vote : transformer des scores en décision

Intuition

À la fin d'un consensus, on a K candidats et J juges, et chaque juge a donné une note à chaque candidat — soit une matrice J×K de scores. Comment en tirer un gagnant, de façon juste et déterministe ? On ne peut pas juste faire la moyenne des notes : un juge sévère qui note tout le monde bas écraserait la voix d'un juge généreux. La théorie du vote a résolu ce problème il y a deux siècles (Borda, Condorcet). EFE en implémente deux méthodes, robustes aux égalités et totalement reproductibles.

La mécanique : trois primitives partagées (rank.rs)

Tout repose sur le passage des scores (continus) aux rangs (positions), avec une tolérance EPS = 1e-9 pour traiter les quasi-égalités comme des égalités (sinon le bruit flottant créerait de faux départages).

PrimitiveCe qu'elle calculeSert à
scores_to_ranks(s)convertit des scores en rangs (0 = meilleur) ; les ex-æquo partagent le rang minimum du groupebase de Borda & Condorcet
prefers(s, i, j)vrai si s[i] > s[j] + EPS (i est strictement préféré à j)duels de Condorcet

Borda — le comptage de rangs

L'idée de Borda : chaque juge classe les candidats, et un candidat marque d'autant plus de points qu'il est bien classé. Avec K candidats, être 1er (rang 0) rapporte K−1 points, 2e (rang 1) rapporte K−2, …, dernier rapporte 0. On additionne sur tous les juges.

pour chaque juge b : points[i] += (K − 1) − rang_b[i] // gagnant = argmax points
confiance = margin(points) / (|juges| × (K − 1)) // normalisée ∈ [0,1]

La normalisation de la confiance est importante : on divise la marge par le maximum théorique (tous les juges unanimes pour un seul candidat), ce qui ramène la confiance entre 0 et 1, comparable d'un run à l'autre. Une confiance proche de 0 signifie « match serré, pas de vrai gagnant » — c'est elle qui déclenche l'escalade humaine (human-in-the-loop) quand elle passe sous un seuil.

Exemple chiffré. 4 candidats ["hello", "hi", "hello world", "h"], 2 juges. 
juge 0 (length_band)   scores [0.998, 0.002, 0.5, 0.0001] → rangs [0,2,1,3] → points [3,1,2,0]
juge 1 (keyword_overlap) scores [1.0, 0.5, 0.75, 0.0]     → rangs [0,2,1,3] → points [3,1,2,0]
─────────────────────────────────────────────────────────────────────────────────
Borda total = [6, 2, 4, 0]   →   gagnant = index 0 ("hello")
confiance = margin([6,2,4,0]) / (2 × 3) = (6 − 4) / 6 ≈ 0,33
Le gagnant est « hello », avec une confiance modérée (0,33) — un humain pourrait vouloir confirmer.

Le départage déterministe (le diable est dans les détails)

Que faire si deux candidats ont le même total Borda ? On départage en cascade, par des critères déterministes : (1) la somme Borda, puis (2) le nombre de premières places, puis (3) le plus petit index. Comme aucun de ces critères ne dépend de l'ordre d'arrivée des ballots, le résultat est identique à chaque run. C'est crucial : les ballots sont réconciliés depuis le Blackboard (la vérité, §2), pas depuis le bus dont l'ordre est non-déterministe. Vote complet et reproductible.

Condorcet — le vainqueur par duels

L'alternative de Condorcet : un candidat est vainqueur s'il bat tous les autres en duel (préféré par une majorité de juges dans chaque face-à-face, via prefers). C'est plus robuste quand les juges sont indépendants. Mais Condorcet a un piège célèbre : le cycle (A bat B, B bat C, C bat A — pas de vainqueur). EFE le détecte (cycle_detected) et se replie alors sur Borda. C'est la traduction technique d'ADR-SWARM-004 : « le consensus craque le non-vérifiable si on a des juges » — avec assez de juges indépendants, un vainqueur robuste émerge même sans oracle de vérité.

Pourquoi le vote relit le tableau (rappel du keystone). Un vote doit être complet pour être juste. Le bus peut perdre un ballot sous pression (§5) ; s'y fier rendrait le vote faux. La réconciliation finale lit /ballot/0…J depuis le Blackboard — exhaustif par construction. C'est le keystone « indice/vérité » appliqué au moment le plus sensible : la décision.

§10  Le seam forensique : relier chaque appel à sa preuve

Intuition

Quand un agent Mode C appelle un vrai modèle (SLM local ou frontière), on veut capter une fiche forensique : quel modèle, quels paramètres, quel seed, le hash du prompt et de la réponse, la latence. Problème : le backend qui fait l'appel ne connaît pas le contexte d'essaim (quel agent, quel tenant), et la couche qui connaît ce contexte (le Meter) ne voit pas l'appel LLM brut. Comment les relier sans réécrire tous les agents pour qu'ils trimballent ce contexte ? Avec un canal invisible : le task-local.

La mécanique : un puits par appel d'agent

Un task-local est une variable attachée à une tâche async (et à ses sous-tâches), invisible ailleurs — un peu comme une variable « locale au fil d'exécution ». Le mécanisme tient en trois temps :

tokio::task_local! { static PENDING: Arc<Mutex<Vec<PendingLlmCall>>>; }

// ① le Meter enveloppe l'appel d'agent dans un scope : il pose un « puits » task-local
// ② à chaque complete(), le backend POUSSE une PendingLlmCall dans le puits courant
//    (no-op s'il n'y a pas de scope — ex. Mode A keyless : rien à capter)
// ③ l'appel fini, le Meter DRAINE le puits, assemble un LlmProvenanceRecord (+ contexte
//    essaim : agent, tenant, swarm) et LIE l'AgentCallRecord au premier ProvenanceId

Le backend pousse « à l'aveugle » dans le puits courant ; le Meter, qui a posé ce puits juste avant l'appel, sait à quel agent il appartient. La jointure se fait sans que ni l'un ni l'autre n'ait eu besoin de connaître l'autre. C'est ça, un seam (une couture) : un point de raccord propre entre deux couches qui s'ignorent.

Le pourquoi : concurrence-safe et correct sous re-tentative

Deux propriétés rendent ce seam robuste là où une solution naïve casserait.

  • Un puits par appel d'agent. Comme le puits est task-local (scopé à la tâche de cet appel précis), K générateurs en parallèle ont chacun leur propre puits. Aucune collision, aucune course — même à fort parallélisme. Une variable globale partagée, elle, mélangerait les appels concurrents.
  • Correct sous re-tentative. En mode réseau, le Retrier peut ré-essayer un appel qui a échoué. Il exécute chaque tentative dans un puits imbriqué et ne ré-émet vers le puits parent qu'un seul record final — celui de l'issue retenue, avec son retry_count. Le lien forensique pointe donc vers la bonne tentative (celle qui a produit la sortie utilisée), jamais vers une tentative avortée. Sans ce soin, le pont N17 lierait l'agent à un appel fantôme.
La conséquence profonde. Chaque pas de l'essaim — chaque écriture au tableau, chaque appel de modèle — est forensiquement lié à la chaîne de provenance. La circulation d'information n'accompagne pas la preuve : elle est la preuve. C'est ce qui permet, plus tard, de re-prouver hors-ligne « quel nano-agent a produit quoi, avec quel modèle, et pourquoi tel gagnant » (voir le rapport dédié au moat).

Les quatre invariants durs (ce qui ne peut JAMAIS arriver)

Au-delà des coûts, EFE garantit des propriétés absolues, prouvées par des tests dédiés. Un invariant, c'est une promesse que le système tient en toute circonstance, y compris sous concurrence adverse.

I13 — le budget n'est jamais dépassé.
Chaque appel est facturé par ajout atomique puis revert si ça dépasse le plafond. Testé à 8 threads × 1000 charges : la dépense finale est toujours ≤ plafond. Le P&L est protégé par construction.
CAS — aucune mise à jour perdue.
Sur un même pointeur, le verrou de shard est tenu pendant tout compare+swap. Deux écrivains sérialisent ; le perdant réessaie. Prouvé par swarm_cas_invariant (somme exacte de N writers).
Complétude — tous les votes comptés.
L'agrégateur lit les ballots depuis le Blackboard (vérité), pas le bus. Un drop de bus ne peut pas rendre un vote incomplet. La décision est correcte indépendamment de la pression réseau.
Egress = 0 — aucun réseau caché.
Le cœur (SDK) n'a aucune dépendance réseau/TLS — asserté en CI (keyless_guardrails). Le self-host « shell-out » curl vers 127.0.0.1. Air-gappable par construction.
Pourquoi ces invariants comptent pour la confiance. Un système d'agents qui « marche en général » ne suffit pas en environnement régulé. Ce qui rassure un acheteur, c'est ce qui ne peut jamais arriver : pas de dépassement de budget, pas de perte de vote, pas de fuite réseau, pas de donnée écrasée. Ces invariants sont la traduction technique de la promesse « souverain, gouverné, vérifiable ».
