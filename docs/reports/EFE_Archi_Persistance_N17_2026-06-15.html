Architecture · avant code · fermeture du gap §17 « persistance N17 »

Persister N17

Forensique par-appel durable & verify_bridge offline — le moat conversationnel qui survit à la fin du run.
EFE prouve déjà « quel agent a dit quoi, à partir de quoi » — et même, en Mode C, « quel modèle a produit cette sortie, avec quel prompt, quelle graine » : c'est le pont N17, un LlmProvenanceRecord forensique par appel LLM, lié à l'enregistrement d'essaim par un llm_provenance_id. Mais ce pont a aujourd'hui une faille temporelle : les records d'essaim sont persistés (et verify/:id les re-prouve), tandis que les forensiques N17 s'évaporent à la fin du run — la passerelle les jette en persistant. Conséquence chirurgicale : le llm_provenance_id de chaque agent Mode C devient un pointeur pendant dès la dernière ligne du run, et verify/:id ne lance jamais verify_bridge. Ce document est l'architecture qui ferme la faille : persister la forensique N17 durablement et de façon tamper-evidente (scellée comme la chaîne d'essaim), et rendre verify_bridge re-jouable hors ligne — par un tiers, des jours plus tard, sans process vivant, sans provider, sans réseau. Le seam existe déjà : le trait LlmResolver a été conçu pour « un store réel derrière ».
aujourd'hui : N17 jeté à la persistance → pointeur pendant demain : forensique durable + scellée (n17_root) verify_bridge rejoué OFFLINE (tiers, sans réseau) format de record GELÉ · Mode A : no-op total

§0 Plan & statut du document

Architecture avant code, le genre du projet. Trois exigences : ne composer que des primitives vérifiées (chaque citation porte son fichier et sa ligne), chiffrer chaque coût, et spécifier le harnais jusqu'aux critères. Le statut diffère des familles itérative/adaptative : il n'y a ici aucun prior défavorable à respecter, ni même un arbitrage de valeur. Persister la forensique N17 et la re-vérifier hors ligne est un renforcement du moat — la capacité d'audit la plus probante du projet, aujourd'hui amputée de sa moitié durable. Le « gate » n'est donc pas un GO/NO-GO de valeur mais une preuve de correction (round-trip sans perte, falsification toujours détectée) doublée d'une mesure de coût (octets par record, latence de re-preuve). La discipline, elle, est identique : aucun code avant l'ordre ; le jour du build, le harnais et ses verdicts AVEC le code ; format de record d'essaim gelé (parité ADR-014/015) ; Mode A invisible (aucun appel LLM, donc rien à persister).

AAnnexe — schémas, signatures, glossaire

La thèse en quatre phrases. ① La forensique N17 (un LlmProvenanceRecord par appel LLM) doit être persistée avec les records d'essaim — elle l'est déjà serde, il suffit d'arrêter de la jeter. ② Elle doit être scellée en chaîne HMAC propre (n17_root), car un store forensique qu'on peut éditer en silence ne vaut rien pour l'audit — le projet ne demande jamais de croire un store, il le re-prouve. ③ verify/:id doit alors lancer verify_bridge contre cette forensique persistée — le lien llm_provenance_id cesse d'être pendant. ④ Et le tout doit se rejouer hors ligne : un tiers, muni des seuls records exportés + la clé tenant, re-prouve la chaîne d'essaim, la chaîne N17, et le pont — sans process, sans provider, sans réseau.

§1 Le problème — la faille temporelle du pont

Le pont N17 est l'une des plus belles pièces du moat : il relie deux granularités de provenance en une seule lignée. Mais il a une faille qui ne se voit qu'en suivant la vie d'un run après sa fin — et c'est exactement là que l'audit, lui, commence.

1.1 — Ce que le pont N17 établit (à l'instant du run)

Pour chaque appel d'un agent Mode C (un modèle de langage local), le backend pousse une forensique par-appel — moteur, modèle, température, graine, hash du prompt, hash de la réponse, latence, re-tentatives (n17.rs : 33-46) — qu'un collecteur assemble en un LlmProvenanceRecord complet en y ajoutant le contexte d'essaim (tenant, swarm, agent, rôle ; n17.rs : 92-177). Le mécanisme est élégant et sans couplage : un task-local par appel d'agent (n17.rs : 48-67) relie le backend, qui ignore l'essaim, au Meter, qui ignore l'appel LLM brut. L'AgentCallRecord d'essaim porte alors un llm_provenance_id qui pointe vers ce record N17 : « une seule lignée, deux granularités ». À l'instant du run, verify_bridge (bridge.rs : 220-238) classe chaque lien — cohérent, lacune, pendant, incohérence d'isolation — et le résumé N17 part dans la réponse HTTP.

1.2 — Ce qui se brise dès que le run se termine

Suivons la persistance, pas à pas, au fichier et à la ligne. La passerelle persiste un run via StoredRun::from_outcome (store.rs : 36-45) : elle copie outcome.records() — les AgentCallRecord — plus la racine, la sortie, la topologie. Elle ne copie pas outcome.llm_records : la forensique N17 est tout simplement jetée. Le schéma Postgres le confirme (store_pg.rs : 20-25) : la table swarm_runs a une colonne records, pas de colonne N17. Et verify/:id (verify.rs : 19-45) ne lance que verify_swarm (chaîne + contenu + DAG, ligne 30) — jamais verify_bridge.

La conséquence, énoncée crûment. Chaque AgentCallRecord Mode C persisté porte un llm_provenance_id — mais le record N17 qu'il désigne n'existe plus nulle part de durable. Le lien est un pointeur pendant dès la dernière ligne du run. Un auditeur qui interroge verify/:id trois jours plus tard apprend que la chaîne d'essaim est intacte — mais rien sur « ce verdict Mode C est-il bien sorti d'un appel réel à tel modèle, avec tel prompt, telle graine ? ». Le moat conversationnel a, aujourd'hui, une moitié qui ne survit pas à la nuit.

1.3 — Pourquoi ce n'est pas un détail d'implémentation

La valeur probante d'EFE — celle qui distingue un essaim auditable d'une boîte noire — repose sur une phrase, répétée dans la doc de verify/:id : « l'endpoint ne demande pas de croire le store ; il re-prouve ». Cette phrase est tenue pour la chaîne d'essaim. Elle est fausse, aujourd'hui, pour la forensique LLM : non seulement on ne la re-prouve pas, on ne la conserve même pas. Or c'est précisément la forensique LLM qui répond aux questions d'un régulateur sur un système agentique : quel modèle a pris cette décision ? avec quelle instruction ? la sortie vient-elle vraiment de là ? Le gap §17 « persistance N17 » n'est donc pas cosmétique : c'est la moitié manquante de la promesse centrale du produit, sur la dimension (le LLM) où elle compte le plus.

§3 La thèse — re-prouver, pas croire le store

Le réflexe serait : « il suffit de stocker les records N17 quelque part ». C'est nécessaire, pas suffisant. Le projet a une doctrine sur ce qu'est une preuve durable, et la persistance N17 doit s'y plier entièrement — sinon elle livre un faux sentiment de sécurité.

3.1 — Un store forensique non scellé ne vaut rien pour l'audit

La chaîne d'essaim est tamper-evidente : ses AgentCallRecord sont scellés en chaîne HMAC, et verify_swarm détecte toute mutation (sortie substituée, lecture forgée, réordre). Si l'on persistait la forensique N17 en simple JSONB non scellé, on créerait une asymétrie absurde : un attaquant (ou un bug) pourrait réécrire le hash du prompt, changer le modèle déclaré, ou modifier la graine d'un record N17 sans qu'aucune re-preuve ne le voie — alors même que la sortie d'essaim, elle, reste scellée. La forensique LLM deviendrait le maillon faible exact de la chaîne probante. La doctrine est sans ambiguïté (doc de verify/:id) : « on ne demande pas de croire le store ; on re-prouve ». La persistance N17 doit donc être scellée au même titre que la chaîne d'essaim.

3.2 — Deux chaînes, un seul lien sécurisé

L'architecture en une image. Deux chaînes HMAC parallèles, scellées avec la même clé tenant (HKDF, server-side), au même instant : la chaîne d'essaim (existante, provenance_root) et une chaîne N17 neuve (n17_root). Le LIEN entre les deux — le llm_provenance_id — est commis dans le payload scellé du record d'essaim (il y est déjà : le format n'a pas besoin de changer). La CIBLE du lien — le contenu forensique — est scellée dans la chaîne N17. verify_bridge vérifie que le lien résout (même tenant, même swarm) ; les deux chaînes garantissent que ni le lien ni sa cible n'ont bougé. Le lien est sellé ici, sa cible est scellée là, et le pont les recoud — tamper-evident de bout en bout, hors ligne.

Ce choix — une chaîne N17 parallèle plutôt qu'une fusion dans la chaîne d'essaim — découle directement du gel du format : l'AgentCallRecord ne porte que l'id du record N17, pas son hash de contenu. Y ajouter le hash de contenu changerait le format gelé (et invaliderait les runs déjà persistés). Une chaîne N17 séparée évite cela : elle scelle le contenu de son côté, le record d'essaim garde son id, et le pont relie les deux à la vérification. Zéro churn sur le format validé, parité exacte avec la discipline d'ADR-014 (appariement déterministe) et d'ADR-015 (messagerie).

3.3 — Le prior est favorable, le genre du gate est donc différent

Contrairement à l'itératif (NO-GO mesuré) ou à la messagerie (CONDITIONNEL σ*), persister N17 n'a pas de contre-partie de valeur : il n'y a pas de « quand ne pas le faire ». C'est un renforcement pur du moat, à prior favorable comme l'arrêt adaptatif (ADR-014). Le gate (§8) n'est donc pas un arbitrage GO/NO-GO de valeur, mais une preuve de correction (le round-trip persiste→relit→re-prouve sans la moindre perte, et la falsification est toujours attrapée et localisée) doublée d'une mesure de coût (octets par record, latence de re-preuve avec N17). Le projet reste honnête sur le genre : ici, le harnais ne demande pas « est-ce que ça vaut le coût » mais « est-ce que c'est correct, tamper-evident, et combien ça coûte ».

§4 Architecture A — la forensique durable & scellée

Trois gestes : arrêter de jeter, sceller, étendre le schéma. ~150 lignes côté store + ~80 côté provenance (le scellement N17). Aucune primitive cryptographique nouvelle — on réutilise la machinerie de chaîne HMAC et la clé HKDF par tenant.

4.1 — Le scellement N17 (efe-swarm-provenance)

// efe-swarm-provenance : sceller la forensique en chaîne HMAC propre (clé tenant).
// Réutilise canon::canonical_bytes (hash de contenu déterministe) + chain_hmac (ADR-007).
pub struct SealedN17 {
    pub leaf_hashes: Vec<[u8; 32]>,           // sha256 canonique de CHAQUE record (ordre stable)
    pub n17_root: Option<[u8; 32]>,           // HMAC replié sur les feuilles ordonnées (clé tenant)
}
// NB (impl) : le sceau ne porte PAS les records (ils vivent dans RunOutcome.llm_records /
// StoredRun.llm_records) ; il porte les FEUILLES, qu'on persiste (StoredRun.n17_leaves) pour
// pouvoir LOCALISER un record muté à la re-preuve — d'où le param sealed_leaves ci-dessous.

/// Scelle un ensemble de records N17 : ordre canonique (par provenance_id — déterministe),
/// hash de contenu par record, chaîne HMAC → n17_root. Même clé que la chaîne d'essaim.
pub fn seal_n17(records: &[LlmProvenanceRecord], key: &[u8]) -> SealedN17;

/// Re-prouve la chaîne N17 depuis les records persistés + les FEUILLES scellées + la clé :
/// recompute chaque feuille et la compare à la feuille scellée (→ localise un record muté),
/// puis rejoue le HMAC et compare à n17_root (→ détecte une forge). Le param sealed_leaves est
/// ce qui distingue « localiser une mutation » de « détecter une forge de racine ».
pub fn verify_n17_chain(records: &[LlmProvenanceRecord], sealed_leaves: &[[u8;32]],
                        n17_root: Option<[u8;32]>, key: &[u8])
    -> N17ChainVerdict;  // { intact, records, root, first_break: Option<ProvenanceId>, reason }

L'ordre de scellement est canonique (tri par provenance_id) — pas l'ordre d'assemblage, qui dépend de l'ordonnancement concurrent des K agents. C'est la même leçon qu'ADR-007 : on ne scelle jamais sur une coordonnée non déterministe. Honnêteté à dire d'emblée : un record N17 porte des champs intrinsèquement per-run (recorded_at, trace_id v4 — n17.rs : 115, 169), si bien que n17_root est, comme provenance_root, une empreinte par-run ; ce qui est invariant et re-prouvable, c'est que les records persistés recomposent exactement le n17_root stocké — la tamper-evidence, pas une racine universelle.

4.2 — Le store, qui cesse de jeter (efe-swarm-gateway)

// store.rs — StoredRun gagne la forensique + sa racine.
pub struct StoredRun {
    pub records: Vec<AgentCallRecord>,        // (inchangé) la chaîne d'essaim
    pub llm_records: Vec<LlmProvenanceRecord>, // NEUF : la forensique N17 (serde JSONB)
    pub n17_root: Option<String>,              // NEUF : la racine de la chaîne N17 (hex)
    pub root, output, topology, created_at,    // (inchangés)
}
impl StoredRun {
    fn from_outcome(tenant, outcome) -> Self {
        let sealed = seal_n17(&outcome.llm_records, &tenant_key);  // ← on ne jette plus
        Self { records: outcome.records().to_vec(),
                llm_records: outcome.llm_records.clone(),           // ← on GARDE
                n17_root: sealed.n17_root.map(hex32), … }
    }
}

Côté Postgres (store_pg.rs), deux colonnes write-once de plus — llm_records JSONB et n17_root TEXT — sous le même ON CONFLICT DO NOTHING que les records d'essaim : la forensique est immuable par construction au niveau du store, et tamper-evidente par la chaîne N17 au niveau de la preuve (ceinture et bretelles, comme pour l'essaim). Le store en mémoire reçoit les mêmes champs. Compatibilité ascendante : un run persisté avant cette évolution a llm_records vide et n17_root nul — la re-preuve N17 le traite comme « 0 forensique » (un run Mode A le serait aussi), sans rien casser.

4.3 — Le coût, chiffré a priori

Un LlmProvenanceRecord sérialisé est de l'ordre de 1 à 2 Ko JSON (hashs en hex, params, métadonnées). Un run Mode C typique fait quelques appels LLM (K générateurs + J juges) : quelques Ko par run, du même ordre que les AgentCallRecord déjà persistés. Le scellement N17 est un hash SHA-256 par record + un repli HMAC — négligeable (microsecondes) devant la latence d'un seul appel LLM (secondes). La re-preuve ajoute un verify_n17_chain + un verify_bridge, tous deux O(records), purs CPU — le harnais §8 chiffrera la latence exacte, mais l'ordre de grandeur est celui de verify_swarm, soit des microsecondes à dizaines de microsecondes. Le coût est dominé par le stockage (quelques Ko), pas par le calcul.

§5 Architecture B — verify_bridge offline

La forensique durable ne sert l'audit que si un tiers peut la re-vérifier sans rien d'autre que les données et la clé. C'est la partie « offline » du gap, et elle se décline en une fonction pure, un résolveur sur le store, un endpoint enrichi, et un export jumeau.

5.1 — La fonction pure : verify_run_offline

// efe-swarm-provenance — la re-preuve COMPLÈTE, pure (aucune async, aucun réseau, aucun provider).
pub struct OfflineVerdict {
    pub swarm: SwarmProvenanceReport,   // chaîne d'essaim + contenu + DAG (verify_swarm, existant)
    pub n17_chain: N17ChainVerdict,     // la chaîne N17 se recompose-t-elle ? (§4.1)
    pub bridge: BridgeReport,           // chaque Mode C résout-il en Consistent ? (verify_bridge, existant)
    pub fully_proven: bool,             // swarm.ok() && n17_chain.intact && bridge.all_mode_c_consistent()
}

/// Re-prouve TOUT depuis les seuls records persistés (essaim + N17) + la clé tenant.
/// Un tiers, des jours plus tard, sans process vivant : la définition même du moat.
pub fn verify_run_offline(
    swarm_records: &[AgentCallRecord],
    n17_records:   &[LlmProvenanceRecord],
    n17_leaves:    &[[u8; 32]],            // les feuilles scellées persistées (→ localisation)
    n17_root:      Option<[u8; 32]>,
    key:           &[u8],
) -> OfflineVerdict {
    let swarm     = verify_swarm(swarm_records, key);
    let n17_chain = verify_n17_chain(n17_records, n17_leaves, n17_root, key);
    let resolver  = MapResolver::from_records(n17_records.iter());  // le seam, déjà prévu
    let bridge    = verify_bridge(swarm_records, &resolver);
    OfflineVerdict { fully_proven: swarm.ok() && n17_chain.intact && bridge.all_mode_c_consistent(),
                     swarm, n17_chain, bridge }
}

Tout ce qu'elle appelle existe et est pur : verify_swarm (recalcule chaîne+contenu+DAG), verify_n17_chain (§4.1, neuf), MapResolver::from_records (bridge.rs : 83 — pré- charge le résolveur depuis de vrais records N17), verify_bridge (bridge.rs : 220). C'est l'assemblage des trois preuves en une, sans aucune dépendance vivante.

5.2 — L'endpoint enrichi & l'export jumeau

GET /v1/swarm/verify/:id charge désormais aussi les records N17 du store, appelle verify_run_offline, et ajoute au VerifyResponse les champs du pont : bridge_consistent, n17_records, mode_c_consistent / _unlinked / _broken, n17_chain_intact, n17_root. Le verdict verified devient « chaîne d'essaim OK ET (zéro Mode C, ou chaîne N17 intacte ET pont entièrement cohérent) » — un run Mode A reste verified trivialement (0 forensique, 0 pont). Et l'export offline gagne un jumeau : GET /v1/swarm/runs/:id/n17, sœur de /records (records.rs : 2-3), donne à l'auditeur la seconde moitié — de sorte qu'avec les deux exports + la clé tenant, il rejoue verify_run_offline sur sa propre machine.

5.3 — Le runbook tiers : un vérificateur autonome

Pour incarner « offline » jusqu'au bout, un petit binaire/exemple verify_offline lit deux fichiers JSON (les records d'essaim exportés, les records N17 exportés) et une clé tenant, et imprime le OfflineVerdict : chaîne d'essaim, chaîne N17, pont, verdict global — sans démarrer la passerelle, sans toucher au réseau, sans contacter un provider. C'est le pendant exact de ce que la campagne propriétaire a fait pour la messagerie (rejouer sur une seconde machine), porté à l'audit forensique : la preuve voyage avec les données, pas avec le service qui les a produites.

Ce que l'offline change pour un régulateur. Aujourd'hui, prouver « ce verdict Mode C vient d'un appel réel à gemma3:12b avec ce prompt et cette graine » exige un process EFE vivant — et même lui ne le peut plus une fois le run fini. Demain, le régulateur reçoit deux fichiers et une clé, lance un binaire de quelques centaines de lignes, et obtient un verdict tamper-evident qu'il a recalculé lui-même. La confiance ne repose plus sur le service ; elle repose sur les mathématiques et la clé. C'est la définition du moat, étendue à la forensique LLM.

§6 Les invariants — famille I-PN (Persist N17)

Six invariants, la grammaire du projet : une phrase vérifiable, un gardien keyless nommé. Note de méthode : ces gardiens se testent keyless sans Ollama, en assemblant des LlmProvenanceRecord synthétiques (le collecteur sait le faire hors d'un vrai appel — n17.rs tests) ; le Mode C réel est un test ignoré-sans-modèle, comme ses pairs.

Inv.ÉnoncéGardien (keyless)
I-PN1Durabilité : chaque LlmProvenanceRecord d'un run Mode C est persisté — zéro perte entre la fin du run et la relecture ; le compte relu == le compte produit.n17_round_trips_through_the_store
I-PN2Tamper-evidence forensique : la chaîne N17 se recompose depuis les records ; toute mutation d'un champ forensique (hash de prompt, modèle, graine, sortie) casse verify_n17_chain et localise la 1ʳᵉ faute.mutated_n17_field_breaks_the_chain_and_localizes
I-PN3Pont re-vérifiable offline : verify_run_offline rejoue depuis les seuls records persistés (essaim + N17) + clé — sans process, sans provider ; chaque Mode C résout en Consistent.offline_verify_reproves_swarm_n17_and_bridge
I-PN4Plus de pointeur pendant après persistance : un llm_provenance_id d'un record Mode C persisté résout toujours vers un N17 persisté ; une forensique manquante est détectée (Missing), jamais ignorée.persisted_link_resolves_or_is_flagged_missing
I-PN5Isolation conservée à la relecture : la triple cohérence (existe · même tenant · même swarm) tient sur le store relu, pas seulement sur le collecteur en mémoire ; un N17 d'un autre tenant/swarm est TenantMismatch/SwarmMismatch.cross_tenant_n17_is_rejected_after_reload
I-PN6Format d'essaim GELÉ & Mode A no-op : la persistance N17 n'ajoute aucun champ à AgentCallRecord (store parallèle) ; un run Mode A persiste 0 forensique, et sa re-preuve reste verified trivialement (parité ADR-014/015).mode_a_persists_zero_n17_and_stays_verified

Le couple I-PN2 / I-PN3 est le cœur. Ensemble ils énoncent la version forensique de la doctrine du projet : la preuve ne se demande pas, elle se recalcule — et depuis les données seules. Le test d'I-PN2 (muter un champ N17 et exiger que la chaîne casse en localisant) est le test le plus court qui distingue un store forensique auditable d'un simple journal qu'on peut éditer en silence.

§7 Le modèle de menace — ce que le sceau attrape

Une architecture de preuve se juge à son modèle de menace explicite. Voici, sans fard, ce que la double chaîne attrape, et ce qu'elle n'attrape pas — car la deuxième colonne est aussi importante que la première.

7.1 — Ce que le sceau n'attrape PAS (et pourquoi c'est honnête de le dire)

La chaîne N17 prouve que les records forensiques n'ont pas bougé depuis le scellement. Elle ne prouve pas que la forensique était vraie au moment du scellement : si le backend avait menti (déclaré gemma3:12b en appelant autre chose), le mensonge serait scellé fidèlement. C'est la limite de toute provenance auto-déclarée — le projet l'assume déjà pour le model_hash_verified: false du record N17 (n17.rs : 124), qui dit explicitement « identité de modèle non vérifiée cryptographiquement ». La persistance N17 hérite cette honnêteté : elle rend la forensique durable et inviolable après coup, pas attestée à la source — ce dernier point (attestation matérielle du modèle) est un autre chantier, explicitement hors périmètre.

7.2 — Le lien contenu↔sortie : un renforcement possible, scopé dehors

Aujourd'hui verify_bridge vérifie qu'un lien Mode C existe et résout (même tenant, même swarm). Il ne vérifie pas que n17.output_hash égale le hash de sortie de l'AgentCallRecord — et pour cause : les deux hashent des domaines différents (le N17 hashe les octets bruts de la réponse LLM via blake3_bytes, n17.rs : 103 ; le record d'essaim hashe la valeur JSON canonique via blake3_value). Une égalité naïve ne tiendrait donc pas. Prouver « la sortie d'essaim EST littéralement ces octets LLM » exigerait d'aligner les domaines de hash (par exemple, le Meter enregistrant aussi le hash brut de la réponse sur le record d'essaim). C'est un renforcement réel et désirable, mais qui touche au format de capture — donc noté pour un lot futur, pas glissé en douce dans celui-ci. Le présent lot prouve : le lien existe, résout, et ni lui ni sa cible n'ont bougé — déjà bien au-delà de l'état actuel (où la cible n'existe pas).

§8 Le harnais — Lot N17-PERSIST

La discipline maison : le jour du build, le harnais AVEC le code, ses verdicts archivés. Le genre est ici correction + coût, pas arbitrage de valeur (§3.3) — mais la rigueur est la même, et l'artefact daté part dans scripts/swarm/ comme ses prédécesseurs.

Le harnais imprime néanmoins les coûts mesurés (octets, latences) — la notice d'exploitation : « activer la persistance N17 coûte ≈ X Ko/run et Y µs/re-preuve ».

8.2 — Le volet Mode C réel (ignoré sans Ollama)

Un test bout-en-bout, ignoré par défaut comme ses pairs Mode C : un vrai run self-host (gemma3:12b) produit de vrais LlmProvenanceRecord, on les persiste, on coupe tout (drop du collecteur, du swarm, du process simulé), et l'on re-prouve uniquement depuis le store + la clé. C'est la démonstration que la forensique d'un vrai appel LLM survit à la mort de tout ce qui l'a produite — exactement la propriété qu'un auditeur exige. Il s'inscrit dans la lignée de selfhost_iterative et selfhost_mailbox : graine épinglée pour la reproductibilité, sortie propre si le modèle est absent.

9.2 — ADR-SWARM-016, le squelette

Titre : « Persistance N17 — forensique par-appel durable, scellée, et verify_bridge rejouable hors ligne ». Contexte : gap §17 « persistance N17 » ; le pont N17 prouvé au run mais jeté à la persistance (from_outcome ignore llm_records ; verify/:id n'appelle jamais verify_bridge) → llm_provenance_id pendant. Décision : ① persister la forensique (serde, déjà prêt) ; ② la sceller en chaîne HMAC parallèle (n17_root, clé tenant) — un store forensique non scellé ne vaut rien pour l'audit ; ③ verify_run_offline = verify_swarm + verify_n17_chain + verify_bridge, pur ; ④ endpoint enrichi + export jumeau /n17 + binaire tiers ; ⑤ format de record d'essaim GELÉ (chaîne parallèle, pas de champ ajouté) ; ⑥ Mode A no-op. Hors périmètre versionné : attestation matérielle du modèle (le sceau prouve l'inviolabilité après coup, pas la véracité à la source) ; le lien contenu↔sortie par alignement des domaines de hash (renforcement futur, touche au format de capture). Verdict : Lot N17-PERSIST — GO sur correction (round-trip + falsification) + coût chiffré. Conséquences : le moat conversationnel survit à la fin du run et se re-prouve hors ligne ; 6 invariants I-PN gardés ; la promesse « on ne croit pas le store, on re-prouve » enfin tenue pour la forensique LLM.
