B0 — La readiness Mode C, avant le GPU

Trois réglages Mac-side qui décident si le GPU mesurera du vrai — ou de l'illusion.
L'audit de readiness pré-GPU a tranché : faire tourner des essaims Mode C sur GPU est à portée, mais trois défauts feraient mentir la mesure. (1) Le sentinel — un appel LLM qui échoue devient une chaîne vide, et l'agreement() par égalité exacte lit plusieurs vides comme une unanimité : sur GPU chargé (OOM, timeouts), l'essaim s'arrête au plancher en croyant à une économie, alors qu'il s'est tu. Aucun des trois n'exige le GPU pour être corrigé : ils se font sur le Mac, ils sont petits, et le seam CI est l'enabler qui rend les deux autres testables. C'est la condition pour que l'investissement GPU mesure une justesse réelle, pas une latence trompeuse.

Le geste, en une phrase

B0 ne livre aucune capacité nouvelle : il rend le chemin Mode C qui existe déjà honnête (le sentinel : ne plus confondre un échec corrélé avec un consensus), testable (le seam : faire tourner le Mode C en CI contre un backend déterministe) et calibrable (la width : que la parallélisation soit réellement à la main de l'opérateur, avec un défaut informé). Ce sont les trois pré-requis pour qu'un run Mode C sur GPU mesure quelque chose de vrai. Le harnais de mesure proprement dit — comparer cheap-parallèle vs gros modèle — est l'étape suivante (B1) ; B0 est ce qui doit être propre avant que B1 ait un sens.

L'ordre n'est pas celui de la liste. On les a nommés « width, sentinel, seam » ; on les livre dans l'ordre des dépendances : le seam (B0.3) d'abord, parce qu'il est l'unique moyen de tester le sentinel (B0.2) et le correctif oracle Mode C déjà commité ; le sentinel ensuite, prouvé par le seam ; la width (B0.1) en parallèle, indépendante des deux autres.

§1 Le contexte : ce que l'audit a tranché

L'audit de readiness Mode C a séparé deux objectifs qu'on confondait sous « mettre sur GPU ». Faire tourner des essaims Mode C sur la box GPU est GO : le chemin de run se scelle, re-prouve (R0), dégrade proprement sur panne d'endpoint, et la concurrence est bornée par construction. Mais valider la thèse — mesurer si l'essaim de petits modèles en parallèle bat le gros modèle, en coût et en justesse — est NO-GO : le harnais de bench ne sait piloter qu'un cluster gRPC, pas un endpoint d'inférence, et ne porte aucune vérité-terrain. Ce harnais-là est B1.

Entre les deux, l'audit a isolé trois défauts qui ne bloquent pas le bring-up mais qui fausseraient la mesure ou la rendraient invérifiable. Ce sont eux, B0. Leur trait commun, et la raison de les traiter avant tout achat de GPU : ils sont entièrement Mac-side — du code de SDK et de topologie, pas d'inférence — et ils sont petits. On peut, et on doit, les fermer pendant que la box GPU n'existe pas encore.

§2 B0.3 — Le seam CI Mode C l'enabler

2.1 — Le problème : le Mode C est un angle mort de la CI

Le SwarmBuilder ne sait construire un backend que d'une seule façon : build_local_backend(endpoint, model, …) (backend/mod.rs:224), qui fabrique en dur un OllamaBackend ou un OpenAiLocalBackend à partir d'une URL. Le seul mode sans backend est Keyless (Mode A, flotte déterministe). Il n'existe aucun moyen d'injecter un Arc<dyn LocalBackend> de test. Conséquence directe : toute l'intégration Mode C réelle — resolver → llm_gen → construction du prompt → ask() → parsing → consensus → sizer → scellement → verify_swarm — ne tourne jamais en CI. Seules des briques unitaires sont gardées (le gen_prompt pur, un mock Scripted dans llm.rs:235, un Flaky dans backend/mod.rs:498) — mais jamais leur composition via run_traced. Les harnais Mode C complets (modec_memory_active, replay_real…) sont tous #[ignore], gatés sur un Ollama local.

Le symptôme concret. Le correctif qu'on vient de commiter (9eb6553 : l'oracle v2 enfin actif en Mode C) porte une note d'honnêteté : « le test Mode-C end-to-end du resolver attend le seam d'injection de backend en CI ». Ce seam, c'est B0.3. Tant qu'il n'existe pas, on croit que l'oracle gate l'acceptation en Mode C — c'est tracé unitairement — mais on ne l'a jamais vu tourner bout-en-bout. Et le fix sentinel (B0.2) serait dans le même cas : invérifiable.

2.2 — Le design : un point d'injection sous feature = "test-util"

Le geste est minimal et chirurgical : ajouter un seam qui injecte un backend déjà construit, en court-circuitant build_local_backend, et le rendre atteignable depuis les tests d'intégration (dossier tests/) — donc pas via #[cfg(test)] (invisible hors du crate) mais via une feature cargo test-util, désactivée par défaut.

  1. Exposer le contrat. Sous feature = "test-util", ré-exporter pub trait LocalBackend (aujourd'hui pub(crate)) et fournir un pub struct ScriptedBackend : un backend déterministe, sans réseau, dont les réponses sont scriptées (une fonction (prompt, params) → Option<String> ou une file de réponses), où None = échec injecté (le cas qui nourrit B0.2).
  2. Le slot d'injection. Ajouter SwarmBuilder::with_local_backend(Arc<dyn LocalBackend>) (sous la même feature) qui stocke un injected_backend: Option<Arc<dyn LocalBackend>>.
  3. La résolution. Dans run_traced, la construction du backend devient : injected_backend.clone().or_else(|| build_local_backend(…)). Quand un backend est injecté, le kind est ModeC (le resolver bâtit alors LlmGen/LlmJudge par-dessus l'injecté, et — depuis 9eb6553 — garde les juges-oracles déterministes) ; le health-check est trivialement satisfait (l'injecté est sain par construction) ; le garde-fou souveraineté G2 ne s'applique pas (aucun endpoint réseau, aucun egress). Tout le reste du chemin — N17, scellement, verify_swarm — est inchangé.
backend_effectif = injected_backend ?? build_local_backend(endpoint, model, …)

2.3 — L'invariant I-SEAM : la production ne bouge pas d'un octet

Le danger d'un seam de test est qu'il devienne une porte dérobée en production. I-SEAM l'interdit par construction : le slot d'injection, le ScriptedBackend et le ré-export du trait n'existent que sous feature = "test-util", jamais dans le build par défaut. Le chemin de production — ClientMode::SelfHost → build_local_backend → Ollama/OpenAiLocal enveloppés du Breaker(Retrier(…)) — est strictement inchangé : sans la feature, injected_backend n'est même pas un champ compilé. Et même activée, la feature n'ouvre aucun egress : un ScriptedBackend ne parle à rien.

§3 B0.2 — Le sentinel : un vide n'est pas un accord

3.1 — La chaîne du défaut, maillon par maillon

Le bug est une cascade de trois maillons, tous bénins isolément, catastrophiques ensemble :

  1. L'échec devient un vide. Un appel LLM qui échoue (timeout, OOM GPU, file Ollama pleine) fait que backend.complete(…) renvoie None. Puis ask() (llm.rs:44) applique .unwrap_or_default() : None devient String::default(), c'est-à-dire la chaîne vide "". L'échec a perdu son identité : il est désormais indistinguable d'une réponse légitimement vide.
  2. Le vide compte comme accord. agreement(candidates) (selector.rs:14) mesure la fraction de paires de candidats strictement égales (candidates[i] == candidates[j]). Plusieurs "" sont tous égaux entre eux ⇒ toutes les paires « matchent » ⇒ agreement = 1.0. Un essaim qui a entièrement échoué est lu comme parfaitement unanime.
  3. La fausse unanimité gouverne trois décisions. agreement() est la primitive partagée derrière :
    • selector.rs:65 — if agreement(c) ≥ vote_threshold ⇒ on choisit Vote (on fait confiance à l'accord, on n'appelle pas les juges) ;
    • sizing.rs:105 — StopRule::Agreement ⇒ Some(agreement(c)) : le signal d'arrêt du sizer adaptatif ;
    • iterative/mod.rs:92 — 1.0 − agreement(c) : la métrique de convergence itérative.
    Donc une fausse-unanimité de vides ⇒ (a) le sélecteur croit à l'accord et n'escalade pas aux juges ; (b) le sizer s'arrête au plancher k_min ; (c) l'itératif converge faussement.

3.2 — L'invariant violé, et le principe du correctif

Le défaut tient à un glissement de sens. « Accord » devrait signifier « l'essaim a convergé sur une réponse » ; le code le lit comme « les candidats sont byte-égaux ». Or un vide est une absence de signal, pas un consensus : deux silences ne sont pas un accord, ils sont deux échecs. Le correctif réinscrit ce sens à la source, en un seul point — la primitive agreement() — d'où il rayonne, correctement, vers les trois consommateurs.

I-SENT. Un candidat absent (au sens de answer_is_present : null, chaîne vide, tableau/objet vide) ne contribue jamais à l'accord — pas même apparié avec un autre absent. Une fausse-unanimité d'échecs ne déclenche donc ni arrêt anticipé du sizer, ni Vote-sans-juges, ni convergence itérative.

Concrètement, une paire ne compte comme « identique » que si les deux candidats sont présents et égaux. answer_is_present vit dans le même crate (topology.rs:81) que agreement : la primitive peut donc le consulter sans dépendance nouvelle.

agreement = | { (i,j) : présent(cᵢ) ∧ présent(cⱼ) ∧ cᵢ = cⱼ } | / | { (i,j) : i<j } |

Le dénominateur reste l'ensemble de toutes les paires : c'est délibéré. Les vides tirent l'accord vers le bas au lieu d'être ignorés — un échec partiel n'est pas une convergence. Trois conséquences, par construction :

  • Tous-vides (l'essaim a entièrement échoué) ⇒ zéro paire identique ⇒ agreement = 0. Aucune fausse convergence : le sizer continue (monte K, retente), le sélecteur escalade aux juges, l'itératif itère. La dégradation cesse d'être invisible.
  • Accord réel sur une vraie valeur ⇒ inchangé : les présents agréants comptent exactement comme avant. Zéro régression sur le chemin sain (c'est ce que les tests existants de agreement, selector.rs:91-94, continuent d'asserter — aucun n'emploie de candidat vide).
  • Mix (p. ex. 3 réels « A » + 1 vide, k=4) ⇒ 3 paires identiques sur 6 ⇒ 0.5. Sous le seuil 0.9 : on ne s'arrête pas tant qu'une partie de l'essaim échoue. Conservateur et honnête : on ne déclare pas victoire pendant qu'un quart se tait.

L'aval est déjà honnête — le fix ferme la dernière faille

Il faut être précis sur ce que le correctif change et ne change pas. Un run tous-vides a déjà, en aval, le bon verdict : le gagnant est vide ⇒ answer_is_present(gagnant) = false ⇒ produced_acceptable = false ⇒ failed = true ⇒ il n'est pas appris (porte I-MEM3) et il est compté en échec (qui nourrit le read-back k_min ↑). Ce que le défaut sentinel ajoutait, c'était l'arrêt prématuré : le sizer déclarait k_used = k_min « par accord » — une fausse économie, un stop_reason mensonger, et la perte de toute chance d'obtenir une vraie réponse à K plus grand. Le fix supprime cette fausse convergence ; l'aval, lui, continuait déjà à compter l'échec. La combinaison est vertueuse : plus de fausse économie + l'échec compté ⇒ la mémoire d'EFE apprend même de la dégradation GPU (la famille « difficile sous charge » voit son k_min monter).

L'edge honnête. Le garde k < 2 ⇒ 1.0 (un candidat unique est « trivialement d'accord ») subsiste : un candidat unique vide renverrait 1.0 et déclencherait l'arrêt — mais le gagnant vide retombe sur produced_acceptable = false en aval, donc l'échec reste capté. Cet edge dégénéré (consensus à k=1) est noté ; on peut le durcir (renvoyer 0 si l'unique candidat est absent), mais ce n'est pas le cœur du défaut.

3.3 — Le test (rendu possible par B0.3)

Deux niveaux. Unitaire (topology, sans seam) : agreement sur des vides renvoie 0, sur un mix renvoie la fraction des présents, sur un accord réel reste inchangé. Bout-en-bout (sdk, via le seam B0.3) : un ScriptedBackend renvoyant None sur tous les appels, branché dans un consensus adaptatif, doit (a) ne pas s'arrêter prématurément en invoquant un faux « agreement », et (b) produire un run échoué (non acceptable, non appris), pas une économie propre. C'est exactement le scénario « GPU saturé » que rien ne couvre aujourd'hui.

§4 B0.1 — La width : un défaut par-protocole + le knob opérateur

4.1 — Le problème : un défaut conservateur qui affame le GPU

La largeur d'exécution — combien d'appels LLM partent réellement en parallèle — est résolue par WidthSpec::resolve(mode, backend_width) (client.rs:91). En Auto + Mode C, elle vaut backend.suggested_width().unwrap_or(2).max(1) (client.rs:102). Or le trait expose un défaut conservateur de 2 (backend/mod.rs:90), et ni OllamaBackend ni OpenAiLocalBackend ne le surchargent — tous deux héritent donc de 2. Résultat : même à k_max=24, seuls 2 appels partent de front ; les 24 candidats sont sérialisés deux par deux.

Le danger n'est pas la surcharge : la concurrence est toujours bornée par un sémaphore de largeur, côté générateurs (consensus_topology.rs:189) et juges. Le danger est l'opposé et c'est précisément ce qui tuerait la thèse : vLLM vit du continuous batching — il sert efficacement des dizaines de séquences concurrentes. À width=2, le 5090 est affamé, et « beaucoup de petits modèles en parallèle » ne se produit jamais. On paierait du GPU pour une parallélisation qui n'a pas lieu.

4.2 — La tension de conception : le SDK ne connaît pas la capacité du serveur

Deux contraintes encadrent le design. (1) La pureté du SDK (G1). Le SDK ne lit jamais l'environnement : WidthSpec::resolve est une fonction pure. Le knob opérateur EFE_SWARM_WIDTH est lu côté passerelle (le binaire) et injecté ici en WidthSpec::Fixed(w) (client.rs:79). (2) L'ignorance de la capacité. Le SDK ne peut pas connaître le --max-num-seqs du serveur vLLM cible. Un défaut « large » serait donc un pari aveugle sur une capacité inconnue.

4.3 — Le design : un défaut informé par le PROTOCOLE + le knob comme source de vérité

On ne devine pas la capacité ; on devine la famille de serveur à partir du protocole, ce qui est sûr.

  • (a) Un défaut par-backend, principié. OpenAiLocalBackend sert un endpoint /v1/chat/completions — ce qui implique un serveur de la famille batching (vLLM, TGI, llama.cpp-server). Il surcharge donc suggested_width() vers une valeur nettement plus haute (de l'ordre de 8), parce que l'OpenAI-compatible est le signe d'un serveur qui aime la concurrence. OllamaBackend, lui, reste conservateur (2) : Ollama sérialise nativement à OLLAMA_NUM_PARALLEL. Ce n'est pas un pari sur la capacité, c'est un défaut par-protocole — meilleur point de départ, jamais une garantie.
  • (b) Le knob reste la vérité. EFE_SWARM_WIDTH (passerelle) → WidthSpec::Fixed écrase tout défaut. C'est lui que l'opérateur calibre sur le --max-num-seqs réel de son vLLM. Le défaut par-backend n'est qu'un filet pour le cas « je n'ai rien réglé ».
  • (c) La documentation. La recette explicite : mesurer une valeur de width sous charge GPU réelle, la matcher au --max-num-seqs de vLLM, et l'avertissement clair que width=2 sous-alimente le GPU. C'est un réglage conscient, pas un bug — mais il doit être réglé sciemment.

I-WIDTH. La concurrence reste bornée par le sémaphore (jamais unbounded) ; le SDK reste pur (ne lit pas l'env — la passerelle injecte) ; le défaut est informé par le protocole, jamais par une capacité supposée ; le knob opérateur prime sur le défaut. Le SDK ne peut pas, à lui seul, surcharger le serveur — c'est à l'opérateur de ne pas dépasser la capacité vLLM, le breaker (G3) n'amortissant que les échecs, pas une surcharge.

4.4 — Le test

Pur, déterministe : WidthSpec::Fixed(w) (le knob opérateur) prime sur tout défaut ; OpenAiLocalBackend::suggested_width() > OllamaBackend::suggested_width() (le protocole informe) ; en Auto Mode C, la largeur suit le backend. Les tests existants de resolve (client.rs:137-146) encadrent déjà la résolution ; on ajoute l'asymétrie par-protocole.

§5 Séquence, invariants, hors-portée

5.1 — La séquence de livraison (par dépendance)

  1. B0.3 — le seam CI d'abord. C'est l'instrument : feature test-util, ScriptedBackend, with_local_backend, la résolution injected ?? build. Aucun test de comportement à lui seul — mais il rend testable tout le reste, à commencer par le correctif oracle Mode C déjà commité.
  2. B0.2 — le sentinel, prouvé par le seam. Le correctif tient en un point (agreement : un absent n'agrée jamais) ; le test unitaire est immédiat, le test bout-en-bout (backend qui échoue ⇒ pas de fausse économie) passe via B0.3.
  3. B0.1 — la width, en parallèle, indépendante. Défaut par-protocole + knob + doc + test pur.

5.2 — Les trois invariants

InvariantÉnoncé
I-SEAM

I-SENT

5.3 — Honnêtement hors-portée

  • Le transport fork-curl → client HTTP poolé. Chaque appel LLM fait un fork/exec de curl (pas de keep-alive, pas de multiplexing HTTP/2). C'est un sujet de performance à haut QPS, pas de readiness — la concurrence reste correcte et bornée. À remplacer avant un débit soutenu, pas avant le bring-up.
  • La vérification réelle de l'épingle SPKI (canal TLS). L'épingle est aujourd'hui forensique mais non vérifiée sur le canal (curl en HTTP nu). C'est de la sécurité de canal — Axe C, pas B0. Décision séparée : reverse-proxy TLS, ou « LAN de confiance » documenté.
  • Le harnais d'inférence de bench (B1). Client HTTP vLLM/Ollama + schéma de vérité-terrain + branchement de l'oracle sur les labels — c'est la mesure, l'étape suivante. B0 la rend possible (le seam teste, le sentinel n'altère pas, la width calibre) mais ne la livre pas.
  • R3 / l'attestation de calcul. Toujours non câblée en production (R2 loopback ou R4 distant seulement). Le moat « computation attestée » reste l'Axe C.

5.4 — Synthèse

B0 n'ajoute aucune fonctionnalité ; il rend le Mode C digne de la mesure. Le seam le rend testable de bout en bout — et ferme, au passage, la dette du correctif oracle. Le sentinel le rend honnête — un échec corrélé cesse de se déguiser en consensus, et la dégradation sous charge GPU devient visible et apprise. La width le rend calibrable — la parallélisation passe réellement à la main de l'opérateur, avec un défaut informé par le protocole plutôt qu'un plancher qui affame le GPU. Aucun n'exige le GPU pour être livré : tous se font sur le Mac, ils sont petits, et ils sont la condition pour que, le jour où la box 5090 arrive, ce qu'on lui demande de mesurer soit vrai.

En une phrase. B0 ne prépare pas le GPU à tourner — il tourne déjà — mais à mesurer sans mentir : un essaim qui ne confond plus le silence avec l'accord, dans un chemin qu'on peut enfin tester, à une largeur qui exploite vraiment le parallélisme. C'est le socle propre sous B1.
